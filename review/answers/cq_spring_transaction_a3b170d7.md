# Spring 声明式事务的原理与常见失效场景

## 核心结论

Spring 声明式事务通过 AOP 代理拦截方法，选择事务管理器，按传播行为开启/加入事务，再根据返回或异常决定提交回滚；绕过代理、异常规则不匹配或资源不受同一事务管理器控制都会导致“事务失效”。

## 1 分钟版

- 调用必须经过 Spring 代理，事务拦截器才会执行；同类自调用常绕过代理。
- 默认通常只对 `RuntimeException` 和 `Error` 回滚，受检异常需配置 `rollbackFor` 或手动标记。
- 异常被业务代码捕获吞掉，代理看到正常返回就会提交。
- `REQUIRED` 加入已有事务，`REQUIRES_NEW` 挂起外层并新开事务，`NESTED` 常依赖保存点，语义不能混用。

## 3 分钟版

代理从 TransactionAttributeSource 读取 `@Transactional` 元数据，通过 PlatformTransactionManager 获得事务状态，并把连接等资源绑定到当前线程。目标方法结束后，拦截器按回滚规则处理。常见问题包括对象不是 Spring Bean、方法调用未经过代理、方法可代理性受限、选错事务管理器、异步切线程、多个数据源没有分布式事务，以及数据库引擎本身不支持事务。事务边界还应避免包住远程调用和长耗时操作，否则会扩大锁时间并耗尽连接池。

## 关键细节

- 注解放在实现类的公开业务方法上通常最清晰，具体代理限制需结合 Spring 版本和代理方式。
- `readOnly` 多是优化提示，不是跨数据库统一的写入禁止保证。
- 回滚只影响同一事务资源，消息发送需用事务消息、outbox 等协调。
- `REQUIRES_NEW` 会额外占连接，嵌套过深可能耗尽连接池。

## 原理机制

代理建立“进入事务—调用目标—完成事务”的模板。事务同步管理器用 ThreadLocal 绑定资源，因此同线程传播有效，异步线程不会自动继承。传播行为决定当前有事务时是加入、挂起、保存点还是报错。

## 项目经验版

项目映射提示：可用真实订单写入说明事务边界、失败注入、回滚验证和消息一致性方案。若没有事故数据，只列验证步骤，不编造“线上零故障”或性能提升。

## 常见追问

- 问：同类方法互调为什么可能失效？答：`this` 调用没经过外层代理，事务拦截器没有机会执行。
- 问：异常捕获后还能回滚吗？答：需重新抛出符合规则的异常，或调用 `setRollbackOnly`；否则代理会按正常返回提交。
- 问：`REQUIRES_NEW` 与 `NESTED` 区别？答：前者是独立物理事务并挂起外层，后者通常在同一物理事务中用保存点。
- 问：异步方法能继承调用方事务吗？答：通常不能，因为事务资源绑定在线程上。

## 易错点

- 不要把所有失效都归因于“private 方法”。
- 不要认为声明式事务能自动覆盖数据库与消息队列。
- 不要忽略异常类型、捕获行为和实际代理调用路径。
