# 数据库成为性能瓶颈时，如何优化动态查询？

## 核心结论

先定位瓶颈，再分层优化：SQL 和索引优化优先，其次缓存和读写分离，再考虑搜索引擎、预聚合、分库分表。不要一上来就分库分表，先用 explain、慢查询和业务访问模式判断问题来源。

## 1 分钟版

我会先看慢查询、QPS、连接数、CPU、IO、锁等待，确认是 SQL 慢、数据量大、热点读、写入压力还是锁冲突。SQL 层面优化索引、避免全表扫描、减少回表和排序。读多写少可以加 Redis 缓存、本地缓存或读写分离。复杂动态查询可以把部分字段同步到 Elasticsearch。数据量持续增长时，再做分区、归档、分库分表或预聚合表。

## 3 分钟版

优化路径要从低成本到高成本。第一，分析慢 SQL，用 explain 看 type、key、rows、Extra，补合适联合索引，减少 select *，避免函数和隐式转换导致索引失效。第二，针对热点读加缓存，设计缓存 key、过期策略、击穿/穿透/雪崩防护和一致性策略。第三，动态多条件查询如果数据库难以支撑，可以引入 ES 做倒排索引和聚合。第四，报表类查询可以做离线或准实时预聚合。第五，数据量超单机能力后再考虑分库分表，同时处理路由、分页、事务和扩容问题。

## 关键细节

- 先定位，再优化，避免盲目加缓存或拆库。
- 索引优化通常是性价比最高的第一步。
- 缓存要配套一致性和异常保护。
- ES 适合搜索和复杂过滤，不适合替代强事务数据库。

## 原理机制

- B+Tree 索引降低扫描范围。
- 覆盖索引减少回表。
- 缓存把高频读从数据库转移到内存。
- 预聚合用写入或离线成本换查询速度。

## 项目经验版

项目映射要使用真实慢查询、访问模式和优化前后指标。可以订单列表作为推演：统计常用筛选组合、设计联合索引、限制深分页，再评估缓存、ES 和冷热归档；未提供执行计划和压测数据时不能声称已经获得性能收益。

## 常见追问

- 问：缓存和数据库一致性怎么保证？答：常见做法是先写库再删除缓存，配合重试、消息或 binlog 补偿；强一致要求更高成本，必须先确认业务能容忍的陈旧窗口。
- 问：深分页怎么优化？答：优先用基于稳定排序键的游标翻页，限制任意跳页；大批量导出走异步任务，避免数据库扫描并丢弃大量前置记录。
- 问：什么场景适合用 Elasticsearch？答：全文检索、多字段过滤、相关性排序和聚合更适合；强事务、实时唯一约束和主数据写入仍应留在数据库。
- 问：分库分表后跨库查询怎么办？答：尽量按访问模式选分片键并避免跨库；无法避免时用聚合服务、冗余读模型或离线数仓，同时限制分页、排序和事务范围。

## 易错点

- 不要一开始就说分库分表。
- 不要忽略 explain 和慢查询定位。
- 不要把缓存当成没有代价的万能方案。
