# AQS 的核心原理是什么？

## 核心结论

AQS 是 JUC 中构建锁和同步器的基础框架：用一个 `state` 表示同步状态，用 FIFO 双向等待队列管理竞争失败的线程，子类只需要定义获取和释放状态的规则。

## 1 分钟版

- 独占模式一次只允许一个线程成功，例如 `ReentrantLock`；共享模式允许多个线程同时成功，例如 `Semaphore`。
- 获取失败的线程封装成 Node 加入 CLH 变体队列，前驱满足条件后再被唤醒并重试 CAS。
- AQS 负责排队、阻塞、唤醒和取消；子类通过 `tryAcquire`、`tryRelease` 等模板方法定义业务语义。
- `ConditionObject` 维护独立条件队列，`signal` 只是把节点转移到同步队列，重新竞争成功后才能继续执行。

## 3 分钟版

线程调用 `acquire` 时先尝试修改 `state`；失败后入队并检查前驱节点。只有位于有效头节点之后的线程适合再次竞争，否则通过 `LockSupport.park` 挂起。释放线程更新状态后，会找到后继有效节点并 `unpark`。队列解决的是竞争秩序和通知丢失问题，CAS 解决的是状态更新原子性，两者缺一不可。取消和超时节点不会立即从所有链路消失，后续遍历会跳过或清理，因此不能把队列理解成严格无残留的普通链表。

## 关键细节

- `state` 的含义由同步器决定：可表示重入次数、许可数或倒计数。
- AQS 队列是 CLH 思想的双向链表变体，节点保存线程和等待状态。
- 公平性由获取策略决定，不是 AQS 队列天然保证。
- `park` 允许先 `unpark` 后 `park`，可避免经典的通知先于等待而丢失。

## 原理机制

主链路是“CAS 尝试获取 → 失败入队 → 判断前驱 → park → 被释放者唤醒 → 重新 CAS”。释放必须先让共享状态对后继可见，再唤醒等待线程。独占和共享模式复用相同队列，但共享获取成功后可能继续传播唤醒。

## 项目经验版

项目映射提示：排查线程大量 `WAITING (parking)` 时，可结合线程栈定位具体同步器，再看持锁线程、队列长度、等待时间和超时策略。只有真实使用过自定义同步器时才讲实现经历，不把阅读源码包装成项目成果。

## 常见追问

- 问：AQS 为什么需要队列？答：CAS 只决定一次竞争的胜负，队列负责让失败线程有序等待、阻塞和被唤醒，避免持续自旋浪费 CPU。
- 问：`signal` 后线程会立刻执行吗？答：不会，节点先从条件队列转入同步队列，还要重新获得锁。
- 问：AQS 是否保证公平？答：不保证；公平锁会检查队列前驱，非公平锁通常允许新线程先抢一次。
- 问：AQS 与 `synchronized` 的关系？答：AQS 是 Java 类库同步器框架，`synchronized` 由 JVM monitor 实现，两者不是同一套代码。

## 易错点

- 不要把 AQS 说成一把具体的锁。
- 不要说入队后只会被唤醒一次；中断、取消和伪唤醒都要求循环检查条件。
- 不要把条件队列和同步队列混为一谈。
- 复习反馈：说到 `signal` 时补一句“只完成条件队列到同步队列的转移，线程仍需重新获得锁”。
