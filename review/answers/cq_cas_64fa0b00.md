# CAS 的原理、ABA 问题与解决方案

## 核心结论

CAS 是“比较内存中的当前值与期望值，相等才原子写入新值”的硬件原子操作，适合低冲突下的无锁更新；它不能自动解决复合不变量、ABA、无限重试和多变量一致性。

## 1 分钟版

- Java 原子类通常在循环中读取旧值、计算新值、CAS 更新，失败则重试。
- 原子性来自 CPU 的比较交换指令及 JVM 封装，可见性和有序性还依赖相应内存语义。
- ABA 指值从 A 变 B 又回 A，单看值的 CAS 无法发现中间变化。
- 可用版本戳、标记位或不可复用节点解决 ABA，例如 `AtomicStampedReference`。

## 3 分钟版

CAS 的优势是竞争失败的线程不必进入内核阻塞，临界区很短且冲突低时延迟好。竞争激烈时，大量线程反复读取和 CAS 会消耗 CPU，并造成缓存行抖动，阻塞锁反而可能更合适。CAS 只能保证一次内存位置更新，若业务要求“余额与流水同时变化”或“先检查再修改多个字段”，仍需锁、事务或把状态封装成一个不可变对象整体替换。ABA 是否有害取决于语义：普通计数从 A 回 A 可能无妨，链表节点被移除、复用再放回则可能破坏结构。

## 关键细节

- CAS 包含内存地址、期望值和新值三个要素。
- 自旋必须有退出、退避或冲突控制策略。
- `LongAdder` 通过分散热点降低高并发计数竞争，但 `sum()` 不是并发更新时的原子快照。
- 版本戳需要随每次语义变更递增，不能只比较业务值。

## 原理机制

CPU 保证比较与写入不可分割；失败线程观察到新值后重新计算。JMM 层面的原子类为读写提供规定的内存效果，使更新能在并发线程间正确传播。版本化 CAS 把 `(value, version)` 作为比较条件，从而识别 A→B→A。

## 项目经验版

项目映射提示：计数器优化要用压测比较 `AtomicLong`、`LongAdder` 和分片计数，并说明是否需要实时精确值。涉及库存、余额等业务约束时，不能仅以“用了 CAS”代替幂等、持久化和事务设计。

## 常见追问

- 问：CAS 一定比锁快吗？答：不一定；高冲突或临界区较长时，自旋浪费和缓存竞争可能比阻塞切换更贵。
- 问：ABA 怎么解决？答：把版本号或标记与值一起比较，或避免对象地址/节点被快速复用。
- 问：`LongAdder` 为什么快？答：它把热点更新分散到多个 Cell，读取时汇总，以读取一致性换写吞吐。
- 问：CAS 能保证多个变量原子更新吗？答：不能，除非封装成单个不可变状态再整体 CAS，否则需要更高层同步。

## 易错点

- 不要把 CAS 说成“没有任何锁”；底层仍依赖硬件原子和内存协议。
- 不要认为一次 CAS 能保护先读后写的任意业务流程。
- 不要在无界循环中忽略退避、中断和失败上限。
