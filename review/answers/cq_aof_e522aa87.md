# Redis AOF 重写的过程

## 核心结论

AOF 重写不是压缩原日志，而是根据当前内存状态生成一份更短、能恢复同样数据的新 AOF；重写期间的新写入还要单独记录，完成后原子切换文件。

## 1 分钟版

- 达到阈值或手工触发后，Redis 创建后台重写任务，读取当时的数据视图生成最小命令集合。
- 主进程继续处理请求，新写入照常进入当前 AOF，并进入用于重写衔接的增量缓冲/机制。
- 后台文件完成后，主进程在短暂协调阶段追加增量并原子替换旧文件。
- fork、写时复制、磁盘吞吐和最终切换都可能造成延迟抖动，需要监控而非宣称完全无阻塞。

## 3 分钟版

旧版经典流程通过 fork 子进程共享内存快照，子进程遍历数据生成重写文件；父进程同时把新命令写到旧 AOF 和重写缓冲。子进程结束后父进程合并增量并 rename。Redis 7 的 multi-part AOF 引入 base/incr 文件和 manifest，具体文件组织发生变化，但核心仍是“基线 + 增量 + 原子发布”。重写只保留当前状态所需命令，例如多次覆盖同一 key 最终只需恢复最新值。

## 关键细节

- 重写与 `appendfsync` 的刷盘策略是不同概念。
- 大实例 fork 和 COW 可能增加内存峰值与延迟。
- 磁盘空间至少要容纳旧文件、新基线和增量，切换前不能提前删除旧文件。
- 重写失败应继续使用旧 AOF，不应破坏现有可恢复性。

## 原理机制

重写任务从一致数据视图建立基线，主线程记录视图之后的变更，发布时把两部分组成完整历史并原子替换元数据/文件。原子切换保证宕机时要么使用旧版本，要么使用完整新版本。

## 项目经验版

项目映射提示：容量规划记录 AOF 增长率、重写时长、fork 延迟、COW 内存和磁盘余量。回答时注明实际 Redis 大版本，不把 Redis 7 文件布局套到旧版本。

## 常见追问

- 问：重写会丢失期间的新写入吗？答：不会，主进程会记录快照之后的增量并在发布前衔接到新 AOF。
- 问：重写完全不阻塞吗？答：后台生成占大头，但 fork、协调切换和磁盘/内存竞争仍可能造成停顿。
- 问：AOF 重写等于压缩旧文件吗？答：不是，它从当前数据状态重新生成恢复命令。
- 问：Redis 7 有什么变化？答：采用多段 AOF 与 manifest 管理 base/incr 文件，需按版本理解具体流程。

## 易错点

- 不要混淆 AOF 重写、刷盘和 RDB 快照。
- 不要忽略 COW 额外内存和磁盘双份空间。
- 不要使用单一旧版本流程描述所有 Redis 版本。
