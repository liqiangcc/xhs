# 如何使用 Redis 正确实现分布式锁？

## 核心结论

Redis 单实例锁的基本正确姿势是 `SET key uniqueValue NX PX ttl` 原子加锁，Lua 脚本“比较 value 后删除”原子解锁；还必须处理租约过期、业务超时、主从切换、重试风暴和下游幂等，不能只写 SETNX。

## 1 分钟版

- value 使用每次持有者唯一 token，避免旧请求误删新持有者的锁。
- 加锁与过期必须一条命令完成，防止进程在两步之间宕机形成死锁。
- 解锁用 Lua 原子执行 `GET == token` 后 DEL，不能先 get 再 del。
- TTL 要覆盖业务时间并留裕量；若续期，必须确认仍是自己持有且设置最大持有边界。

## 3 分钟版

锁保护的是并发进入，不自动保证业务只执行一次。持有者暂停超过 TTL 后，另一个客户端可获得锁，旧持有者恢复后仍可能写入，因此关键资源需要 fencing token 或由数据库版本号拒绝过期持有者。Redis 主从异步复制场景下，主节点写锁后尚未同步就故障切换，可能出现两个客户端同时持锁；高正确性场景应评估一致性协调系统、数据库锁或 Redlock 的假设与争议。重试要有超时、随机退避和最大次数，避免惊群。

## 关键细节

- token 需全局/足够唯一，并贯穿解锁和续期。
- Lua 保证 Redis 内单次脚本原子，但不能让跨系统业务事务原子。
- 看门狗续期会延长故障持锁时间，需要进程健康与上限控制。
- 锁服务不可用时要定义 fail-open、fail-closed 或降级路径。

## 原理机制

NX 提供互斥创建，PX 提供故障租约，唯一 token 提供所有权识别，Lua 提供条件删除原子性。fencing token 再把持锁顺序传给被保护资源，由资源拒绝旧序号写入，补足租约过期后的安全边界。

## 项目经验版

项目映射提示：真实方案应说明锁粒度、TTL 估算、P99 业务时长、重试、续期、监控、故障注入和下游幂等。没有线上数据时不声称“绝对安全”。

## 常见追问

- 问：为什么不能直接 DEL？答：锁可能已过期并被别人获取，直接删除会误删新锁，必须比较 token。
- 问：业务超过 TTL 怎么办？答：受控续期或加长租约，并用 fencing/版本校验防止暂停的旧持有者继续写。
- 问：Redis 锁能保证 exactly-once 吗？答：不能，超时、重试和故障都可能重复执行，业务仍需幂等。
- 问：主从切换有什么风险？答：异步复制未完成时切主，锁记录可能丢失，导致双持有者。

## 易错点

- 不要把 SETNX 和 EXPIRE 分成两条非原子命令。
- 不要认为加锁成功后业务一定在 TTL 内完成。
- 不要忽略锁之外的数据一致性和幂等。
