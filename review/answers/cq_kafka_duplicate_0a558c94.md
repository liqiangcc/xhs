# Kafka 如何处理重复消费？

## 核心结论

Kafka 常见交付语义是至少一次：消费者处理成功前宕机、位点提交失败、超时重平衡都可能重复。正确做法是让业务写入幂等，并协调“业务结果”和 offset，而不是指望关闭重试。

## 1 分钟版

- 先提交 offset 再处理会丢消息；先处理再提交不会轻易丢，但故障窗口会重复。
- 用业务唯一键、数据库唯一约束、状态机条件更新或幂等表去重，优先让最终写天然幂等。
- 手动提交也不能消除处理成功到提交之间的窗口，只是让边界更可控。
- Kafka 事务可协调 Kafka 内的生产和 offset；写外部数据库仍需 outbox/inbox、幂等或专门事务方案。

## 3 分钟版

重复来源包括 Producer retry（需幂等生产者）、Consumer 处理后未提交、重平衡时旧实例未及时停止，以及下游超时导致调用方不知道是否成功。消费端应定义稳定 eventId 和业务 key，把去重记录与业务修改放在同一数据库事务，或用条件更新保证状态只前进一次。去重记录要设计保留期和分区，不能用易丢失的短 TTL Redis key 代替关键持久化保证。失败消息应有限重试、退避并转入死信/停车场，避免毒消息阻塞分区。

## 关键细节

- `enable.auto.commit` 只控制位点自动提交，不等于业务处理完成。
- 重平衡前应停止拉取/等待在途任务，并正确提交已完成的连续位点。
- 同一分区 offset 有序，但并行处理后不能越过未完成的低 offset 随意提交。
- exactly-once 要明确边界；Kafka EOS 不能自动覆盖任意外部系统。

## 原理机制

Consumer group 通过 committed offset 记录下一次消费位置。业务处理与 offset 存在两个独立状态，故障会落在中间窗口。幂等写或同事务 inbox 把“是否处理过”与业务结果统一，重放时得到相同结果。

## 项目经验版

项目映射提示：真实案例应给出 eventId 规则、唯一索引、位点提交方式、重平衡处理、重试/DLQ 和重复率监控。没有测量时不宣称 exactly-once。

## 常见追问

- 问：手动提交 offset 能避免重复吗？答：不能消除，只能选择提交时机；处理成功到提交成功之间仍可能故障。
- 问：Redis SETNX 可以做幂等吗？答：可用于低风险短窗口，但关键业务要考虑过期、淘汰和持久化，通常数据库唯一约束更稳。
- 问：Kafka 事务能保证数据库不重复吗？答：不能自动保证外部数据库，需要幂等、outbox/inbox 或适配的事务架构。
- 问：为什么不能先提交再处理？答：提交后进程若宕机，该消息不会再投递，造成丢失。

## 易错点

- 不要把“关闭自动提交”说成解决了重复。
- 不要将 Kafka 内部 EOS 扩大到所有下游系统。
- 不要忽略并行处理下的连续 offset 提交。
