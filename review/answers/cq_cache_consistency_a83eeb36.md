# 如何保证 MySQL 与 Redis 的缓存一致性？

## 核心结论

常见基线是 Cache Aside：读未命中查库回填，写先提交数据库再删除缓存；它提供最终一致性而非强一致，必须结合并发竞态、删除失败、过期时间、消息补偿和业务容忍窗口设计。

## 1 分钟版

- 更新数据库后删除缓存，比“更新缓存”更少维护派生值，也避免多写者覆盖顺序问题。
- 删除失败要重试，可靠方案可用本地消息/outbox、binlog CDC 或消息队列异步补删。
- 缓存设置合理 TTL 作为最终兜底，并治理热点 key 击穿。
- 对强一致读，考虑绕过缓存、版本校验或把关键写约束放回数据库，而不是承诺 Redis 与 MySQL 原子提交。

## 3 分钟版

典型竞态是：读请求未命中后读到旧库值，写请求提交并删缓存，随后旧读又把旧值回填。可通过较短过期、回填版本校验、写路径标记、串行化热点或延迟再次删除缩短窗口；“延迟双删”的延迟值必须来自真实读写耗时，仍不是严格证明。CDC 监听 binlog 能解耦业务写路径并补偿删除，但也有投递延迟、重复和乱序，需要按主键有序、幂等与监控积压。

## 关键细节

- 先删缓存再写库会扩大“读回旧值并长期回填”的窗口，通常不作为默认顺序。
- 事务未提交前删除缓存，其他读可能重新加载旧值；应与提交时机协调。
- 缓存值可携带数据版本/更新时间，拒绝旧事件覆盖新值。
- 热点重建要互斥或逻辑过期，防止大量请求同时打库。

## 原理机制

数据库是真实来源，缓存是可丢弃派生数据。写提交后发出失效事件，消费者以幂等和顺序保护删除/刷新；TTL 提供最终自愈。要更强一致，就必须增加同步协调并接受延迟与可用性成本。

## 项目经验版

项目映射提示：真实回答需给出允许陈旧时长、读写 QPS、热点分布、失败重试、CDC 延迟和对账指标。没有这些事实时只讲方案边界，不虚构一致性等级。

## 常见追问

- 问：为什么写后删除而不是更新缓存？答：缓存可能是组合派生值，删除让后续读按真实库重建，也减少并发更新覆盖顺序问题。
- 问：延迟双删能保证强一致吗？答：不能，只是用第二次删除缩小特定竞态窗口，延迟和失败仍需治理。
- 问：binlog 方案要注意什么？答：事件可能重复、延迟、乱序或积压，需要幂等、按 key 顺序、版本校验和监控。
- 问：删除缓存失败怎么办？答：持久化重试任务或可靠消息补偿，配合 TTL 和告警，不能只打印日志。

## 易错点

- 不要宣称 Cache Aside 天然强一致。
- 不要把 TTL 当成唯一一致性方案。
- 不要忽略事务提交时机和旧读回填竞态。
