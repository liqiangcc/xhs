# IO 多路复用及 select、poll、epoll 的区别

## 核心结论

IO 多路复用让一个线程等待多个文件描述符的就绪事件，再对就绪 fd 执行非阻塞读写；select、poll 每次都传入并扫描关注集合，Linux epoll 在内核维护关注表并返回就绪事件，更适合大量连接少量活跃的场景。

## 1 分钟版

- select 使用位图，受 fd 集合大小限制，调用前后还需重建集合。
- poll 使用数组，没有 select 的固定 bitmap 上限，但仍要复制和线性扫描。
- epoll 通过 create/ctl/wait 分离注册与等待，关注集合留在内核，就绪事件进入 ready list。
- 水平触发未读完会继续通知，边缘触发只在状态变化时通知，要求非阻塞并循环读到 EAGAIN。

## 3 分钟版

“就绪”不等于业务数据一定完整，也不等于读写不会出错；事件循环仍需处理短读、短写、连接关闭和背压。epoll 的优势不是所有操作绝对 O(1)，注册、回调、ready list 和高活跃率都有成本；当几乎所有连接都活跃时，扫描差距会缩小。Java NIO Selector 在不同操作系统映射到不同机制，Linux 常用 epoll，但业务层还要防止耗时任务阻塞 EventLoop。

## 关键细节

- 多路复用解决等待多个 fd，不自动把业务处理变成并行。
- LT 易使用；ET 减少重复通知但必须彻底 drain。
- 写事件不能长期无条件订阅，否则 socket 可写会导致空转。
- 一个慢连接的业务处理不应占住唯一事件循环线程。

## 原理机制

应用把关注的 fd 和事件注册给内核，阻塞等待就绪集合；内核在设备/协议状态变化时标记事件，应用醒来后分发处理。epoll 避免每轮完整传入关注集合，但用户态仍要处理返回的活跃事件。

## 项目经验版

项目映射提示：真实网络服务可说明连接数、活跃率、EventLoop 数、任务卸载、读写水位和 P99。没有基准测试时不说 epoll 在所有负载下都更快。

## 常见追问

- 问：epoll 为什么适合 C10K？答：关注集合常驻内核，只返回就绪项，连接多而活跃少时避免每轮扫描全部 fd。
- 问：ET 为什么必须非阻塞？答：一次通知后要循环读写到 EAGAIN，否则剩余数据可能没有新边沿触发，阻塞又会卡住事件循环。
- 问：IO 多路复用是同步还是异步？答：就绪等待通常属于同步非阻塞 I/O 模型，实际读写仍由应用线程执行。
- 问：epoll 是否永远 O(1)？答：不是；返回和处理就绪事件至少与活跃事件数有关，注册和内核管理也有成本。

## 易错点

- 不要把 IO 多路复用等同于多线程。
- 不要把就绪通知说成完整消息已到达。
- 不要脱离 Linux 语境把 epoll 说成跨平台统一实现。
