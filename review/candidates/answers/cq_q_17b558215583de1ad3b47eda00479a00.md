# SQL：按日期取购买数量 Top 2，先明确“恰好两行”还是“并列都保留”

## 核心结论

原始面经只保留了一个表的三个信息：`id`、日期、当天购买数量，并要求“求每天最多购买的 top2”。它没有保存 SQL 方言、列名、并列规则或并列时的二级排序。

下面候选答案明确采用一个可执行契约：以 MySQL 8.4 兼容的窗口函数语法为目标；每个日期**最多返回两行**，购买数量降序，数量相同时按唯一 `id` 升序打破并列。`purchases(id, purchase_date, purchase_count)` 是为了演示和测试而定义的等价表名/列名，不是原题原文。如果面试官想要“前两个名次且并列全部保留”，应改用 `DENSE_RANK()`，结果可能超过两行。

## 1 分钟版

我会先问清楚并列怎么处理。若要求“每天最多两条记录”，用 `ROW_NUMBER()` 最直接：

1. `PARTITION BY purchase_date`，让每天独立排名；
2. `ORDER BY purchase_count DESC, id ASC`，购买量越大排名越靠前，并用唯一 `id` 保证并列时结果确定；
3. 外层筛选 `rn <= 2`；
4. 最后再按日期和名次排序，只负责展示结果。

SQL 如下：

```sql
WITH ranked AS (
    SELECT
        id,
        purchase_date,
        purchase_count,
        ROW_NUMBER() OVER (
            PARTITION BY purchase_date
            ORDER BY purchase_count DESC, id ASC
        ) AS rn
    FROM purchases
)
SELECT id, purchase_date, purchase_count
FROM ranked
WHERE rn <= 2
ORDER BY purchase_date ASC, rn ASC;
```

MySQL 8.4 官方文档说明，`ROW_NUMBER()` 会在每个 partition 内给行编号；window 内没有 `ORDER BY` 时编号顺序不确定，所以这里必须把排名规则写进窗口定义。

## 3 分钟版

这题真正容易答错的不是窗口函数名字，而是“top2”的语义。

原始题目没有保存 tie contract，所以我不会把某一种并列规则冒充成原题要求。若面试官确认“每个日期最多两条”，我选择 `ROW_NUMBER()`。分区键是日期，排序主键是当天购买数量降序；如果只有这一列，购买数量相同的行仍是 peers，哪两条被选中没有业务确定性，因此我再增加 `id ASC` 作为候选实现的二级排序，并假设 `id` 唯一。

如果面试官说“第二名有三个人就都要返回”，那“最多两行”这个契约就不成立。此时可以把 `ROW_NUMBER()` 换成 `DENSE_RANK()`，再筛 `rank <= 2`；它保留前两个不同购买数量对应的所有行，因此一天可能返回两条以上。若语义是竞赛名次、且中间名次需要跳号，则讨论 `RANK()`。

执行顺序上，窗口排名结果不能在同一 SELECT 的 `WHERE` 里直接按别名过滤；这里先在 CTE 中产生 `rn`，再由外层查询筛 `rn <= 2`。最终 `ORDER BY purchase_date, rn` 只控制返回展示顺序，不替代窗口内部的排名规则。

## 关键细节

- **源事实**：一个表至少包含 `id`、日期、当天购买数量；目标是逐日 Top 2。
- **候选 API/数据模型**：测试表命名为 `purchases(id, purchase_date, purchase_count)`；这是等价 fixture，不是原始列名恢复结果。
- **并列策略**：本答案默认“每天最多两行”，因此使用 `ROW_NUMBER()`；若要求保留并列名次，改用 `DENSE_RANK()`。
- **确定性**：窗口排序使用 `purchase_count DESC, id ASC`。如果真实表中的 `id` 不是唯一键，应换成能形成稳定全序的唯一键组合。
- **NULL 边界**：原题没有保存空值语义。候选 fixture 把日期和购买数量定义为 `NOT NULL`；真实表若允许 NULL，需先约定 NULL 是否参与排名。
- **数据类型**：原题没有保存日期类型和购买数量类型；fixture 使用文本日期和整数仅用于可执行验证。
- **复杂度**：逻辑上需要按日期分区并按排名键排序。无可利用访问路径时，可把排序成本粗略理解为随每个分区大小增长的 `O(sum n_d log n_d)`；实际 MySQL 执行计划、临时表和排序策略应以 `EXPLAIN`/运行环境为准，不能仅凭 SQL 文本断言。
- **索引**：是否能减少扫描/排序取决于真实过滤条件、索引和优化器计划。原题没有给 schema/index，不应承诺“建某个索引就一定免排序”。

## 原理机制

窗口函数不会像普通 `GROUP BY` 那样把每天压成一行，而是保留每条输入记录并为其附加分区内排名。因此它适合“每组取前 N 条”。

候选 fixture 使用 `purchases(id INTEGER PRIMARY KEY, purchase_date DATE NOT NULL, purchase_count INTEGER NOT NULL)`；这些标识符和类型只用于可执行验证。

查询：

```sql
WITH ranked AS (
    SELECT
        id,
        purchase_date,
        purchase_count,
        ROW_NUMBER() OVER (
            PARTITION BY purchase_date
            ORDER BY purchase_count DESC, id ASC
        ) AS rn
    FROM purchases
)
SELECT id, purchase_date, purchase_count
FROM ranked
WHERE rn <= 2
ORDER BY purchase_date ASC, rn ASC;
```

不变量是：在同一个 `purchase_date` partition 中，`rn=1` 和 `rn=2` 必须对应排序键 `(purchase_count DESC, id ASC)` 的前两行；不同日期互不竞争排名。外层只保留 `rn <= 2`，所以每个日期最多两行。

可执行回归覆盖三个日期：普通不同购买量、第一名并列、三行完全同购买量。并列时断言 `id ASC` 决定保留哪两行，从而证明候选的 deterministic tie policy，而不是依赖数据库碰巧返回的物理顺序。

## 常见追问

- 问：为什么这里用 `ROW_NUMBER()` 而不是 `RANK()`？答：因为当前候选契约是“每个日期最多两行”。`ROW_NUMBER()` 对每行给唯一序号；若业务要求并列全部保留，就应换成 `DENSE_RANK()` 或按明确名次语义选择 `RANK()`。
- 问：为什么排序还要加 `id ASC`？答：只按购买数量排序时，相同购买量之间没有确定的先后；若结果只保留两行，必须增加唯一的二级排序键才能让“哪两行”可重复验证。
- 问：为什么不能直接 `WHERE ROW_NUMBER() ... <= 2`？答：MySQL 的窗口计算发生在 `WHERE/GROUP BY/HAVING` 之后；这里先在 CTE 中计算排名，再在外层按排名过滤。
- 问：如果一天第二名有三条相同购买量，怎么返回全部？答：把窗口函数改为 `DENSE_RANK()`，仍按购买量降序排名并筛 `rank <= 2`；此时每天可能超过两行，这与当前“最多两行”契约不同。
- 问：什么索引最合适？答：题目没有过滤条件、真实列类型和现有索引，不能从题干唯一推出。应基于真实 schema 和 `EXPLAIN` 验证；候选答案只要求排名语义正确，不把某个索引方案冒充源题要求。

## 易错点

- 把“Top 2 行”和“Top 2 名次并列全保留”混为一谈。
- 用 `ROW_NUMBER()` 却只按购买数量排序，导致并列时保留记录不稳定。
- 写成 `rn = 1`，实际只返回 Top 1。
- 用 `GROUP BY purchase_date` 后直接取非聚合列，既丢失行级排名语义，也可能依赖非标准/非确定行为。
- 把示例表名、列类型、NULL 规则或 MySQL 版本说成原面经已经给出的条件。
