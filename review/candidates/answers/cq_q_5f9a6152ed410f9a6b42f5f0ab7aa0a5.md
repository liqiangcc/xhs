# 手写节流（Throttle）函数

## 核心结论

节流不是“固定模板”，先要约定 leading/trailing 语义。来源只要求实现 Throttle，因此本候选明确采用：一个窗口内最多执行一次；第一调用立即执行（leading），窗口内的多次调用只保留最新的 `this` 和参数，并在窗口结束补一次（trailing）；暴露 `cancel()` 丢弃待执行 trailing。核心状态是上次真正执行时间、一个定时器和最新待执行调用。

## 1 分钟版

- 第一次调用立即执行并记录 `lastInvokeTime`。
- 后续调用计算 `remaining = wait - (now - lastInvokeTime)`；若已经跨过窗口，立即执行当前调用。
- 仍在窗口内时覆盖 `pendingThis/pendingArgs`，并且最多只挂一个 timer；因此高频输入不会创建一串定时器。
- timer 到点只执行最后一次待调用，并以实际执行时刻更新 `lastInvokeTime`。
- `cancel()` 清 timer、丢 pending，并重置时间，使下一次调用重新作为 leading 调用。

## 3 分钟版

```javascript
function throttle(fn, wait) {
  if (typeof fn !== 'function') throw new TypeError('fn must be a function');
  if (!Number.isFinite(wait) || wait < 0) throw new RangeError('wait must be non-negative');

  let lastInvokeTime = -Infinity;
  let timerId = null;
  let pendingThis;
  let pendingArgs;

  function invoke(time, receiver, args) {
    lastInvokeTime = time;
    pendingThis = pendingArgs = undefined;
    return fn.apply(receiver, args);
  }

  function trailing() {
    timerId = null;
    if (pendingArgs !== undefined) invoke(Date.now(), pendingThis, pendingArgs);
  }

  function throttled(...args) {
    const now = Date.now();
    const remaining = wait - (now - lastInvokeTime);
    if (remaining <= 0) {
      if (timerId !== null) {
        clearTimeout(timerId);
        timerId = null;
      }
      return invoke(now, this, args);
    }
    pendingThis = this;
    pendingArgs = args;
    if (timerId === null) timerId = setTimeout(trailing, remaining);
  }

  throttled.cancel = function cancel() {
    if (timerId !== null) clearTimeout(timerId);
    timerId = null;
    pendingThis = pendingArgs = undefined;
    lastInvokeTime = -Infinity;
  };
  return throttled;
}
```

这段实现可以口头概括成两个分支：如果当前调用已经获得新的执行资格，就清掉旧窗口的 timer 并立即执行；否则只更新“最后一次待执行调用”，且只在没有 timer 时安排一个 trailing。这样执行频率由真正执行时刻约束，而窗口内又不会丢失最新状态。

## 关键细节

- 节流的 leading/trailing 组合没有唯一标准答案，必须先说清契约；本实现固定为 leading + latest-trailing，而不是声称来源已经指定。
- `remaining` 基于“实际执行时间”而不是“最近输入时间”，否则连续事件可能不断把窗口向后推，行为会更像 debounce。
- 窗口内只保留最新参数，所以 `t=0` 执行 A，`t=20` 来 B，`t=60` 来 C，`wait=100` 时，约 `t=100` 补的是 C。
- 跨过窗口时若旧 trailing timer 还挂着，必须先清理，避免当前立即执行后旧 timer 又重复触发。
- `this` 通过 `apply` 保存；箭头函数若直接包住 `fn(...args)` 很容易丢调用方 receiver。
- 时间复杂度每次调用 O(1)，状态 O(1)；真实 timer 只保证“不早于延迟”而非精确时钟，后台标签页等环境还可能被浏览器限频。

## 原理机制

throttle 把连续时间切成由“真正执行”锚定的最小间隔。`lastInvokeTime` 决定当前调用是否拥有立即执行资格；timer 只是把窗口内最后一次 pending 调用延后到资格恢复时。因为任何时刻至多一个 timer，且 pending 只保存最后一次调用，所以事件频率再高也不会让执行频率超过约每 `wait` 一次。

## 项目经验版

来源没有真实项目材料，不能虚构滚动监听或埋点收益。实际使用前我会先确认业务要 leading、trailing 还是两者、组件卸载时是否 cancel、是否需要 `flush()`，并用可控 fake clock 测时间边界，而不是靠 `setTimeout` + sleep 的脆弱测试。

## 常见追问

- 问：Throttle 和 Debounce 的核心差别是什么？答：Throttle 保证高频期间按上限频率持续执行；Debounce 通常等输入安静一段时间才执行，连续输入会不断推迟。
- 问：为什么 trailing 要保留“最后一次”参数？答：这是本实现显式选择的 latest-trailing 语义，可让窗口结束时反映最新状态；若业务要首个或累计事件，应改契约。
- 问：为什么跨窗口立即执行前要清 timer？答：timer 代表旧窗口的待执行调用；当前调用已经取得新的执行资格，再让旧 timer 触发会造成额外一次执行。
- 问：组件销毁为什么要 cancel？答：否则挂起的 trailing 可能在生命周期结束后继续调用旧回调或持有参数引用。
- 问：`Date.now()` 会不会受系统时钟回拨影响？答：会；强时序场景可注入单调时钟，例如浏览器的 `performance.now()`，但要让 timer 与测试时钟使用同一时间基准。

## 易错点

- 不声明 leading/trailing 行为，导致实现和测试各自理解不同。
- 每次高频调用都新建 timer，最终出现一串延迟执行。
- timer 执行后忘记清 `timerId`，后续再也无法调度 trailing。
- 不保存最新 `this/args`，trailing 调到旧参数。
- 把最近输入时间当执行时间更新，意外把 throttle 写成 debounce。
