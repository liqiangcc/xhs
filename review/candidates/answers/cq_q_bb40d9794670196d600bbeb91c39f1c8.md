# 生产消费（1:2）程序：并发处理但顺序输出 1-100

## 核心结论

来源只保留“生产消费（1:2）程序，顺序输出 1-100”，没有解释 `1:2` 的记号，也没有给函数签名。结合该题所在的 **Go 后端**面试记录和 `producer-consumer/channel` 标签，下面采用一个明确、可执行但不冒充原题事实的契约：**1 个生产者、2 个消费者**；生产者产生 `1..100`，两个消费者并发接收任务，最终输出必须严格是 `1,2,...,100`，不丢、不重。关键点是：任务 Channel 的 FIFO 只能约束“发送/接收”的配对顺序，**不能保证两个消费者完成副作用的全局顺序**；因此要把“并发处理”和“有序输出”分开，由单一排序/提交协调器负责最终顺序。

## 1 分钟版

- 一个 producer 把 `1..100` 写入 `jobs`，写完关闭 `jobs`。
- 两个 consumer 并发从 `jobs` 取值，处理后把结果写入 `results`；它们不直接 `fmt.Println`。
- `WaitGroup` 等两个 consumer 退出后关闭 `results`，避免接收方永久等待。
- 主 goroutine 是唯一输出协调器：收到的结果可能是 `2,1,4,3...`，先放进 `pending`，只要 `next` 已到达，就连续提交 `next,next+1...`。
- 这样 worker 可以乱序完成，而最终 observable output 仍严格递增。若让两个 consumer 自己打印，即使 `jobs` 是 FIFO，也可能出现“consumer A 先取 1，consumer B 后取 2，但 B 先打印 2”。

## 3 分钟版

```go
package orderedpc

import "sync"

func OrderedProducerConsumer(n, consumerCount int) []int {
    if n <= 0 {
        return []int{}
    }
    if consumerCount <= 0 {
        panic("consumerCount must be > 0")
    }

    jobs := make(chan int)
    results := make(chan int)

    var wg sync.WaitGroup
    wg.Add(consumerCount)
    consumer := func() {
        defer wg.Done()
        for v := range jobs {
            // 这里可以做真正的并发计算；不要在 worker 中承担最终有序输出。
            results <- v
        }
    }
    for i := 0; i < consumerCount; i++ {
        go consumer()
    }

    go func() {
        for i := 1; i <= n; i++ {
            jobs <- i
        }
        close(jobs)
    }()

    go func() {
        wg.Wait()
        close(results)
    }()

    next := 1
    pending := make(map[int]struct{})
    out := make([]int, 0, n)
    for v := range results {
        pending[v] = struct{}{}
        for {
            if _, ok := pending[next]; !ok {
                break
            }
            out = append(out, next)
            delete(pending, next)
            next++
        }
    }
    return out
}
```

面试题固定 `1:2` 与 `1-100` 时调用 `OrderedProducerConsumer(100, 2)` 即可。示例返回切片是为了让顺序契约可测试；真实程序可以在协调器的 `out = append(...)` 位置调用单一 writer/打印函数。若“消费”会产生新结果，应把 `results <- v` 换成 `results <- result{seq:v, value:...}`，仍按 `seq` 提交。

## 关键细节

- **FIFO 不等于副作用有序**：Channel 可以按发送/接收规则交付值，但两个 goroutine 在收到值之后何时运行由调度决定。把 `Println` 放在消费者里，会把输出顺序交给调度器。
- **一个地方拥有输出顺序**：协调器是唯一提交者，`next` 是“下一条允许对外可见的序号”。只有 `pending[next]` 存在时才能推进。
- **关闭方向**：生产者是 `jobs` 的唯一发送方，所以由它关闭 `jobs`；`results` 有多个发送方，不能由任一 consumer 单独关闭，而应由等待全部 consumer 的 goroutine 关闭。
- **不要求两个 consumer 平均分工**：正确性契约是 100 个值恰好处理一次并按序提交；Go 调度不保证两个 worker 各处理 50 个。若业务要求配额公平，需要另外定义调度策略。
- **背压**：这里使用无缓冲 Channel，生产和消费天然互相施加背压。改成缓冲 Channel 影响吞吐/排队，不改变“worker 不直接有序输出”的核心边界。
- **空间复杂度**：最坏情况下早到结果都堆在 `pending`，额外空间 O(n)；若每个任务处理时间接近，通常窗口更小。若 n 很大，可以用有界 reorder window、按分片提交或重新设计任务顺序约束。
- **重复/丢失防线**：当前 producer 每个序号只发送一次。生产任务若来自外部重试系统，需要单独定义幂等键/去重，不能把这个内存示例外推成 exactly-once 交付保证。

## 原理机制

生产消费模型里其实有两个顺序：**任务进入队列的顺序**和**并发处理完成/副作用提交的顺序**。多消费者让第二个顺序天然可能和第一个顺序不同。要同时获得并发度和确定性输出，最常见的办法不是强迫 worker 串行，而是给任务携带序号，在末端做 reorder/commit：完成快的结果先缓存，只有连续前缀已经齐全时才推进可见顺序。

这个实现的安全性不依赖 `sleep` 或“碰巧谁先运行”。`next` 和 `pending` 只由主 goroutine 访问，不需要额外 mutex；workers 只通过 Channel 传值。`WaitGroup` 解决的是 `results` 何时可以安全关闭，而不是输出排序本身。排序不变量是：`out` 始终等于从 1 开始、当前已经完整到达的最长连续前缀。

## 项目经验版

来源没有给真实线上场景、QPS、任务耗时分布或消息中间件，因此不能虚构“线上就是这样做的”。落地时先问清“顺序”到底是全局顺序、同一 key 内顺序，还是仅要求输入有序；全局有序会形成单提交点，吞吐上限和故障恢复都要评估。若任务来自 Kafka/数据库而不是进程内 Channel，还要把分区、offset/事务、失败重试和幂等性纳入设计，不能把这个 Go 内存模型直接等价成分布式 exactly-once。

## 常见追问

- 问：`jobs` 是 FIFO，为什么不能两个消费者直接打印？答：FIFO 只约束值被发送/接收的顺序关系；消费者拿到值后可能被调度、阻塞或执行不同耗时，后拿到 2 的 goroutine 完全可能先执行打印。
- 问：为什么不加一个 mutex 让消费者打印？答：普通 mutex 只保证同一时刻一个人打印，不保证抢到锁的顺序是 1、2、3；还需要显式的 `next` 条件。把顺序状态集中到一个协调器更容易证明。
- 问：可以用 `sync.Cond` 吗？答：可以。每个 worker 在准备提交值 v 时等待 `v == next`，提交后递增 `next` 并唤醒其他 worker。但这会让已完成 worker 阻塞在提交门口；reorder coordinator 把处理和提交解耦得更清楚。
- 问：如果第 1 个任务一直很慢怎么办？答：后面的结果会积压在 `pending`，这是严格顺序的 head-of-line blocking。若不能接受，就必须放宽全局顺序，改成分 key/分片有序或定义超时跳过语义。
- 问：怎么验证不是“偶尔正确”？答：让两个 consumer 的完成顺序被故意打乱，重复运行并用 `go test -race` 检查数据竞争；每次都断言长度为 100 且第 i 个结果恰好是 `i+1`。

## 易错点

- 两个 consumer 从 FIFO Channel 取值后各自打印，误以为 Channel FIFO 会自动扩展成副作用 FIFO。
- 任意一个 consumer 退出时关闭 `results`，导致另一个 consumer 后续发送触发 `send on closed channel`。
- 用 `time.Sleep` 调节输出先后，把调度偶然性当同步协议。
- 只加 mutex 保护 `Println`，却没有“轮到哪个序号”的条件。
- 为了强行顺序让整个消费阶段退化成一个 worker，虽然正确却失去 1:2 并发模型的意义。
- 把进程内 Channel 的一次发送/接收直接说成分布式 exactly-once；失败恢复和持久化语义根本不是同一层问题。
