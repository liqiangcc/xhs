# 单线程函数限流器：超过频率阈值返回 false

## 核心结论

来源只说明“单线程调用一个函数，实现限流器，调用频率超过阈值时返回 false，否则 true”，没有规定窗口算法和时间边界。这里明确采用**滑动时间窗口的准入语义**：在任意调用时刻 `now`，只统计区间 `(now - windowMillis, now]` 内已经返回 `true` 的调用；若其中已有 `maxCalls` 次则本次返回 `false`，并且被拒绝的调用不写入窗口。单线程条件下用时间戳队列即可，不需要锁。

## 1 分钟版

- 构造参数是 `maxCalls`、`windowMillis` 和可注入时钟；本答案要求时钟返回非负、单调不减的毫秒值，这是为了让测试可重复，也避免系统时间回拨把窗口语义搞乱。
- 每次 `allow()` 先删除所有 `timestamp <= now - windowMillis` 的已放行记录，因此恰好位于左边界的调用已经过期。
- 清理后如果队列大小已经达到 `maxCalls`，返回 `false`；拒绝记录不入队，所以持续重试不会主动延长封禁时间。
- 否则把当前时间入队并返回 `true`。队列只保存当前窗口内的成功准入，长度最多是 `maxCalls`。
- 单次最坏可能清理多个旧时间戳，但每个时间戳只入队和出队一次，所以均摊时间 O(1)，额外空间 O(maxCalls)。

## 3 分钟版

```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Objects;
import java.util.function.LongSupplier;

public final class SlidingWindowRateLimiter {
    private final int maxCalls;
    private final long windowMillis;
    private final LongSupplier clock;
    private final Deque<Long> accepted = new ArrayDeque<>();
    private long lastNow = -1L;

    public SlidingWindowRateLimiter(int maxCalls, long windowMillis, LongSupplier clock) {
        if (maxCalls <= 0) throw new IllegalArgumentException("maxCalls must be > 0");
        if (windowMillis <= 0) throw new IllegalArgumentException("windowMillis must be > 0");
        this.maxCalls = maxCalls;
        this.windowMillis = windowMillis;
        this.clock = Objects.requireNonNull(clock, "clock");
    }

    public boolean allow() {
        long now = clock.getAsLong();
        if (now < 0) throw new IllegalStateException("clock must be non-negative");
        if (lastNow >= 0 && now < lastNow) {
            throw new IllegalStateException("clock must be non-decreasing");
        }
        lastNow = now;

        long cutoff = now >= windowMillis ? now - windowMillis : -1L;
        while (!accepted.isEmpty() && accepted.peekFirst() <= cutoff) {
            accepted.removeFirst();
        }
        if (accepted.size() >= maxCalls) {
            return false;
        }
        accepted.addLast(now);
        return true;
    }
}
```

例如 `maxCalls=3, windowMillis=1000`，在 `0/100/200ms` 三次调用都返回 `true`，`300ms` 返回 `false`。到 `1000ms` 时，`0ms` 恰好落在左边界并被淘汰，所以 `1000ms` 可以再次返回 `true`。如果 `999ms` 的拒绝请求也写入队列，就会改变恢复时间；本答案明确选择“只统计已放行调用”的准入契约。

## 关键细节

- **阈值到底统计什么**：来源只说“调用频率”，没有说明是所有尝试还是成功准入。本实现统计成功准入；若要对原始尝试频率限流，应在判断前记录每次尝试，行为会不同。
- **窗口边界**：本契约使用 `(now-windowMillis, now]`。因此 `now-windowMillis` 上的旧记录过期，避免一个时间戳同时属于相邻两个完整窗口边界。
- **为什么不用固定窗口计数器**：固定窗口只需一个计数器和窗口起点，但边界两侧可以出现瞬时双倍突发；滑动窗口更贴合“任意连续时间段最多 N 次”的契约，代价是保存最多 N 个时间戳。
- **为什么队列长度有界**：达到 `maxCalls` 后后续请求直接拒绝且不入队；清理只会缩短队列，所以 `accepted.size() <= maxCalls` 始终成立。
- **时钟**：示例不直接调用 `System.currentTimeMillis()`，而是注入 `LongSupplier`，这样边界测试无需 sleep。真实实现可注入单调时间源适配器；如果使用会回拨的墙上时钟，应定义回拨策略。
- **单线程边界**：来源明确是单线程，所以 `ArrayDeque` 和普通字段足够。若多个线程并发调用，清理、容量判断、入队必须作为一个原子临界区处理，不能直接把这段代码宣称为线程安全。
- **复杂度**：每个成功时间戳入队一次、最多出队一次，因此 m 次调用的队列操作总量 O(m)，均摊 O(1)；空间 O(maxCalls)。

## 原理机制

这个限流器维护一个不变量：`accepted` 中只包含当前滑动窗口内、已经成功放行的调用时间戳，并按时间非降序排列。调用开始先推进左边界，把不再属于窗口的旧时间戳移除；此时队列大小就是当前窗口已经消耗的配额。若大小等于上限，拒绝而不改变状态；否则追加 `now`，让本次调用占用一个配额。因为输入时间单调不减，队首永远是最先过期的记录，所以只需要 FIFO 队列。

固定窗口、令牌桶和漏桶都可以满足不同的“限流”目标，但状态语义不同。固定窗口强调每个离散窗口的计数；令牌桶允许按桶容量吸收突发；漏桶更接近稳定输出速率。来源没有指定这些语义，因此不能把其中任何一个说成原题唯一答案。

## 项目经验版

来源没有真实线上 QPS、租户维度或故障数据，不能虚构生产经验。实际落地前需要确认阈值维度（全局、用户、接口还是资源）、允许突发程度、拒绝是否计数、时间源、分布式一致性和失败策略。单机单线程队列算法只证明核心状态机；跨进程限流还要选择共享状态或分片策略，并单独验证延迟与一致性代价。

## 常见追问

- 问：为什么拒绝请求不入队？答：这是本答案明确选择的“成功准入消耗配额”契约。若业务要限制所有尝试频率，应把每次尝试都记录，恢复时间会被高频重试推迟。
- 问：为什么 `1000ms` 时 `0ms` 的记录要过期？答：因为窗口定义为 `(now-1000, now]`，左端开区间；边界规则必须先定义，否则测试会出现 off-by-one 争议。
- 问：固定窗口为什么可能突发翻倍？答：如果上一个窗口末尾放行 N 次、下一个窗口开头又放行 N 次，那么很短的连续区间里可能观察到接近 2N 次成功调用。
- 问：多线程还能直接用吗？答：不能。队列清理、大小判断和追加之间存在竞态；要加锁、使用原子状态机或换成并发安全设计。
- 问：如果只要求平均速率并允许短时突发呢？答：令牌桶通常更自然：按速率补充令牌、桶容量定义最大突发；这和当前“任意滑动窗口最多 N 次”不是同一个契约。

## 易错点

- 没定义“超过阈值”统计成功准入还是所有调用尝试，就直接写代码。
- 窗口左右边界不明确，导致恰好在 `windowMillis` 处多算或少算一次。
- 拒绝请求也写入成功队列，却仍声称“拒绝不消耗配额”。
- 用墙上时钟但不处理时间回拨，队列顺序和过期判断失效。
- 来源明确单线程，却反过来把无锁 `ArrayDeque` 实现宣传成并发线程安全。
