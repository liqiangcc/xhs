# Spring Boot 跟 Spring 的区别是什么？

## 核心结论

最准确的关系不是“Spring 和 Spring Boot 二选一”，而是：

```text
Spring Framework
→ 提供 IoC/DI、AOP、事务、Web、数据访问等核心编程模型和基础设施

Spring Boot
→ 建立在 Spring 生态之上
→ 用约定、Starter、自动配置和运行/运维能力降低 Spring 应用的装配成本
```

所以一句话可以概括为：**Spring Framework 主要解决“应用怎么组织和开发”，Spring Boot 主要解决“Spring 应用怎么更快地装配、启动和交付”。**

Spring Boot 并没有替代 Spring Framework。一个典型 Spring Boot 应用仍然使用 Spring 的 `ApplicationContext`、Bean、依赖注入、Spring MVC / WebFlux、事务等能力；Boot 做的是根据类路径、已有 Bean 和配置条件给出合理默认值，并把常见依赖和运行方式组织起来。

## 1 分钟版

面试可以这样回答：

- **Spring Framework 是基础框架**：核心是 IoC/DI 容器，并提供 AOP、事务、Web、数据访问等模块。
- **Spring Boot 是基于 Spring 的应用装配层**：目标是让 Spring 应用以更少的显式配置快速启动，并提供一套“开箱即用但可覆盖”的默认约定。
- **Starter** 负责把一组常用依赖以受管理的方式组合起来，减少手工寻找和拼装依赖。
- **Auto-configuration** 会根据 classpath、配置和当前 Bean 条件尝试配置 Spring 应用；它不是不可控的“魔法”，开发者可以自己定义 Bean 替换默认配置，也可以排除特定自动配置。
- **运行与生产能力**方面，Boot 支持直接运行的应用形态、常见嵌入式服务器组合，并提供外部化配置、Actuator 的健康检查/指标等能力。

因此：

```text
Spring = 核心能力和编程模型
Spring Boot = Spring + 更强的默认装配、依赖管理和应用运行体验
```

## 3 分钟版

### 1. Spring Framework 解决什么

Spring Framework 的核心是 IoC 容器和依赖注入。

对象不需要自己到处 `new` 或主动查找依赖，而是把依赖声明出来，由 Spring 容器创建 Bean、建立依赖关系并管理生命周期。这让业务对象之间的耦合更容易控制，也便于测试和替换实现。

在这个基础上，Spring Framework 还提供或整合了很多基础能力，例如：

- AOP；
- 声明式事务；
- Spring MVC / WebFlux；
- 数据访问支持；
- 事件、资源、校验等基础设施。

因此 Spring Framework 更像“应用的基础编程模型和容器”。

### 2. Spring Boot 解决什么

如果只使用 Spring Framework，很多能力都可以实现，但应用还需要自己决定和组织很多事情：

```text
选哪些依赖
→ 用哪些兼容版本
→ 配哪些 Bean
→ Web 容器怎么接
→ 配置从哪里读取
→ 应用怎么打包和启动
→ 健康检查/指标怎么接
```

Spring Boot 的目标就是降低这些重复装配成本。

它采用 opinionated defaults，也就是对常见场景给出默认选择，但当你的要求与默认值不一样时，允许你逐步替换。

### 3. Starter：解决依赖组合问题

Starter 可以理解为“场景化依赖入口”。

例如做某种数据访问或 Web 应用时，开发者通常需要一组相互配套的 Spring 和第三方依赖。Starter 把常用依赖描述组合起来，并配合 Boot 的依赖管理减少版本拼装工作。

所以 Starter 主要解决：

```text
我需要这个能力
→ 应该引哪些常见依赖
→ 由 Boot 提供一组一致、受支持的组合
```

它不是代码生成器，也不意味着引入 Starter 后所有行为都不可修改。

### 4. Auto-configuration：解决常见 Bean 装配问题

Boot 的自动配置会根据当前环境“尝试”配置应用。

典型判断条件包括：

- classpath 上是否有某个库；
- 用户是否已经定义了某个 Bean；
- 某个配置属性是否满足条件。

所以正确理解是：

```text
环境满足条件
+
用户没有提供更明确的配置
→ Boot 提供默认配置
```

如果开发者自己定义了相应 Bean，很多默认自动配置会退让；也可以显式 exclude 某类自动配置。

因此“Spring Boot 的核心就是自动配置”只说对了一部分。Boot 还包含 Starter、应用启动、外部化配置、打包和生产可观测能力等一整套应用体验。

### 5. 运行和生产能力

Boot 把“开发完成以后如何运行和观察应用”也纳入常用能力范围。

典型包括：

- 可直接启动的 Spring 应用；
- 常见 Web 场景的嵌入式服务器组合；
- 外部化配置；
- Actuator 提供的 health、metrics、auditing 等生产就绪能力。

这些能力并不意味着“用了 Boot 就自动具备完整生产治理”。安全策略、容量、告警、发布、网络和业务监控仍然需要按真实系统设计。

### 6. 两者关系收口

可以把层次理解成：

```text
你的业务代码
    ↓
Spring Boot（约定、自动配置、Starter、运行/运维体验）
    ↓
Spring Framework（IoC/DI、AOP、事务、Web 等基础能力）
    ↓
Java / 第三方库 / 容器等
```

这张图是帮助理解的逻辑层次，不代表所有 Boot 功能都只存在于一个物理“上层模块”。

## 关键细节

- **Spring Boot 不是 Spring Framework 的替代品**，它构建 Spring-based application，底层大量能力仍来自 Spring Framework。
- **Spring Framework 的核心回答是 IoC/DI 容器和基础模块；Boot 的核心价值是降低应用装配和运行成本。**
- **自动配置是 conditional 的**。不要把它描述成“扫描到什么就无条件创建什么”。
- **自动配置是 non-invasive 的**：开发者可以定义自己的配置替代默认行为，也可以排除具体自动配置。
- **Starter 主要是依赖描述和组合入口**，不是“Starter 本身把所有功能代码都实现了”。
- **约定优于配置不等于不能配置**。Boot 提供默认值，但需求偏离默认时可以显式调整。
- **嵌入式 Web 服务器是 Boot 常见能力，不等于 Spring Framework 本身没有 Web 能力**；Spring MVC / WebFlux 的编程模型属于 Spring Framework。
- **Actuator 是生产就绪能力的一部分**，能提供健康、指标等端点，但不等于完整的生产运维平台。
- 不要把“传统 Spring = 必须 XML、Spring Boot = 完全不用配置”当作本质区别。现代 Spring Framework 本身也支持 Java/注解配置；Boot 的关键是默认装配和应用体验，而不是简单“去掉 XML”。

## 原理机制

为什么 Spring Boot 能减少配置？

因为它把大量重复决策变成了条件化默认值：

```text
Starter
→ 提供常用依赖集合

classpath / Bean / property 条件
→ 决定哪些 Auto-configuration 生效

用户自定义 Bean / 配置
→ 覆盖或让默认配置退让

Spring Application
→ 组织应用启动

Externalized Configuration / Actuator 等
→ 补齐常见运行期能力
```

这里最重要的不变量是：**默认值只能在条件成立时帮你装配，显式业务意图仍然应该优先。**

这也是为什么排查 Boot 问题时不能只说“自动配置失效了”，而应该按条件链排查：

```text
依赖是否在 classpath
→ 对应自动配置是否存在
→ 条件为什么匹配/不匹配
→ 是否已经有用户 Bean
→ 属性值是什么
→ 是否被 exclude
```

Boot 的条件评估报告就是帮助观察这条链路的一种方式。

## 项目经验版

来源没有提供真实项目经历、Spring/Boot 版本或具体故障，因此不能虚构“线上项目从 Spring 迁到 Boot 后效率提升多少”。

如果在真实项目里判断是否以及如何使用 Spring Boot，我会先看边界：

- 如果项目本来就在 Spring 生态里，Boot 通常可以减少依赖和基础配置的重复装配；
- 如果默认自动配置不符合要求，就明确覆盖对应 Bean 或排除自动配置，而不是为了“保持 Boot 默认”牺牲业务约束；
- 升级时同时检查 Boot、Spring Framework 和第三方依赖的兼容矩阵，避免只升级一个版本号；
- 遇到 Bean 为什么出现/没出现的问题，优先查看自动配置条件和 conditions report，而不是靠猜；
- 生产环境仍需独立设计监控暴露、安全、容量和发布策略，Actuator 只是提供观测入口的一部分。

## 常见追问

- 问：Spring Boot 是否可以脱离 Spring Framework？  
  答：典型 Spring Boot 应用就是 Spring-based application，会使用 Spring Framework 的容器和很多基础模块。Boot 的定位不是替代 Spring，而是简化 Spring 应用的创建、配置、运行和交付。

- 问：`@SpringBootApplication` 为什么能启动很多东西？  
  答：它会把应用配置和自动配置入口组织起来。自动配置再根据 classpath、已有 Bean 和属性等条件决定哪些默认配置生效。不要把它概括成“一个注解把所有 Bean 都扫描出来”。

- 问：自动配置和手写配置冲突怎么办？  
  答：Boot 的自动配置设计为可退让。很多场景下自己定义对应 Bean 后默认配置会 back off；也可以显式 exclude 特定自动配置。具体行为应看对应条件，而不是假设所有配置都能以同一种方式覆盖。

- 问：Starter 和 auto-configuration 是一回事吗？  
  答：不是。Starter 重点解决依赖组合；auto-configuration 重点解决在条件满足时如何提供默认 Spring 配置。两者常一起工作，但职责不同。

- 问：Spring Boot 一定比 Spring Framework 快吗？  
  答：不能把“开发装配效率更高”偷换成“运行性能一定更快”。Boot 主要降低启动项目和配置基础设施的工程成本；运行性能取决于实际依赖、配置、业务逻辑、JVM 和部署环境。

- 问：Spring Boot 为什么适合微服务？  
  答：它的独立运行、配置和生产就绪能力让服务化应用更容易启动和交付，但“微服务”还涉及服务边界、通信、容错、观测、数据一致性和部署治理，不能把用了 Boot 等同于完成微服务架构。

## 易错点

- 把 Spring 和 Spring Boot 说成两个互相替代、完全独立的框架。
- 只说“Spring 配置多，Boot 配置少”，却说不清 IoC/DI、Starter、自动配置分别解决什么。
- 把 auto-configuration 说成无法覆盖的“魔法”。
- 把 Starter 当成自动配置本身，混淆依赖组合和 Bean 装配两个职责。
- 认为 Spring Framework 只能 XML 配置，而 Spring Boot 才支持注解/Java 配置。
- 把“Spring Boot 开发更省装配工作”说成“Spring Boot 运行性能一定更高”。
- 把 Actuator 等同于完整生产运维体系，或虚构项目中的监控收益。
