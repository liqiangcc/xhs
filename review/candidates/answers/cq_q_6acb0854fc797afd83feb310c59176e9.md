# 多线程循环打印 1-10：用 monitor 协调顺序

## 核心结论

当前仓库保留的原题是“算法/并发：手撕多线程循环打印 1-10（线程同步机制）？”。来源没有保存线程数量、是否必须固定某个线程打印奇数/偶数、是否要求重复多轮，也没有指定同步原语。为了给出可执行且不冒充原题约束的实现，这里采用一个明确的最小契约：`N >= 2` 个工作线程共同输出 `1..10`，每个数字恰好一次且整体严格递增；数字归属按 round-robin 分配给线程。round-robin 是本答案的实现选择，不是来源事实。

实现上用一个共享 `next` 作为唯一状态，用同一个 monitor 保护“检查轮次 → 输出 → `next++`”这一原子临界区。不轮到自己的线程在 `while` 条件中 `wait()`；当前线程完成一次输出后 `notifyAll()`，让其他线程重新竞争 monitor 并再次检查条件。这样不需要忙等，也不会把线程调度顺序误当成输出顺序。

## 1 分钟版

- 先定共享状态：`next` 表示下一个待打印数字，初始为 1。
- 对 `N` 个线程定义当前数字的 owner：`(next - 1) % N`。
- 每个线程进入同一个 `synchronized (monitor)`；如果当前 `next` 不属于自己，就在 `while` 中 `wait()`。
- 轮到自己时，在持有 monitor 的情况下输出 `next`，然后 `next++`，再 `notifyAll()`。
- `wait()` 必须放在 `while` 而不是 `if` 里，因为线程可能被错误唤醒或出现 spurious wakeup，醒来后必须重新检查条件。
- `next > max` 时也要 `notifyAll()` 后退出，避免其他线程还留在 wait set 里无法结束。

## 3 分钟版

下面把线程数参数化；题目只要求 1-10 时传 `maxValue = 10`：

```java
import java.util.function.BiConsumer;

public final class RoundRobinPrinter {
    private final Object monitor = new Object();
    private final int workerCount;
    private final int maxValue;
    private int next = 1;

    public RoundRobinPrinter(int workerCount, int maxValue) {
        if (workerCount < 2) {
            throw new IllegalArgumentException("workerCount must be >= 2");
        }
        if (maxValue < 0) {
            throw new IllegalArgumentException("maxValue must be >= 0");
        }
        this.workerCount = workerCount;
        this.maxValue = maxValue;
    }

    public void runWorker(int workerId, BiConsumer<Integer, Integer> sink)
            throws InterruptedException {
        if (workerId < 0 || workerId >= workerCount) {
            throw new IllegalArgumentException("invalid workerId");
        }

        while (true) {
            synchronized (monitor) {
                while (next <= maxValue && ownerFor(next) != workerId) {
                    monitor.wait();
                }

                if (next > maxValue) {
                    monitor.notifyAll();
                    return;
                }

                int value = next++;
                sink.accept(workerId, value);
                monitor.notifyAll();
            }
        }
    }

    private int ownerFor(int value) {
        return (value - 1) % workerCount;
    }
}
```

如果只想演示两个线程，可以创建两个 worker，`workerId` 分别是 0 和 1。按照上面的契约，线程 0 负责 1、3、5、7、9，线程 1 负责 2、4、6、8、10；但“奇偶分工”只是 `N=2` 时 round-robin 的结果，不应倒推成原题已明确要求。

## 关键细节

- **共享不变量**：在任何时刻，`next` 都是尚未输出的最小整数；只有持有同一个 monitor 的线程才能读取并推进它。
- **为什么是 `while`**：`Object.wait` 允许 spurious wakeup，而且 `notifyAll` 会同时唤醒多个等待者；醒来不代表条件成立，所以必须重新检查 owner 条件。
- **为什么用 `notifyAll`**：当有多个可能的等待线程时，`notify()` 可能唤醒一个仍不满足条件的线程。`notifyAll()` 配合条件循环更容易保持正确性；代价是会有额外唤醒和锁竞争。
- **为什么不能只靠 `volatile int next`**：`volatile` 可以解决单次读写的可见性，但“判断轮次 → 输出 → 自增”是一个复合协调协议；没有互斥和等待机制时仍可能产生竞争或忙等。
- **为什么不建议 `sleep` 控顺序**：sleep 只延迟当前线程，不建立“该谁执行”的条件协议；调度器也不保证睡眠结束后的获取顺序。
- **终止路径**：最后一个数字输出后，其他线程可能仍在 `wait()`。结束分支再次 `notifyAll()`，所有线程醒来后看到 `next > maxValue` 并退出。
- **中断**：示例把 `InterruptedException` 交给调用方处理，不吞掉中断。生产代码要根据任务取消语义决定是传播、恢复中断标记还是做清理。
- **输出顺序**：示例把 `sink.accept` 放在 monitor 内，是为了让“观测到的输出顺序”也属于同步协议。如果 sink 是很慢的 I/O，需要权衡临界区长度，但不能在没有额外顺序机制时简单移出去又声称输出仍严格有序。

## 原理机制

Java 每个对象都有关联的 monitor 和 wait set。线程只有在持有该对象 monitor 时才能调用 `wait/notify/notifyAll`。`wait()` 会把当前线程放入该对象的 wait set，并释放这个 monitor；被唤醒后线程还要重新竞争 monitor，重新获得锁后才能从 `wait()` 返回。

这里的状态机只有一个共享状态 `next`：

`等待 owner 条件 -> 获得 monitor -> 输出 next -> next++ -> 唤醒等待者 -> 下一轮`

`synchronized` 的 unlock/lock 还提供必要的 happens-before 关系，因此前一个线程在临界区内对 `next` 的更新，对随后获取同一个 monitor 的线程可见。正确性不是来自“线程大概率交替调度”，而是来自受 monitor 保护的状态转换和条件等待。

## 项目经验版

来源没有给真实项目、线上线程数、延迟或吞吐数据，因此不能虚构生产结论。真实业务如果只是要顺序消费任务，我会先判断是否真的需要多个线程共同打印/消费；很多场景用单消费者会更简单。如果确实要线程按阶段协作，可以比较 `synchronized + wait/notifyAll`、`ReentrantLock + Condition`、`Semaphore` 或更高层并发组件，并用线程 dump、延迟分布和竞争指标验证是否存在锁竞争或卡死。

## 常见追问

- 问：为什么 `if` 不行？答：线程醒来后条件可能仍不成立，且规范允许 spurious wakeup；条件等待应使用 `while` 重新检查。
- 问：为什么不用 `notify()`？答：多个线程等待不同轮次时，`notify()` 唤醒谁是不确定的，可能唤醒不该执行的线程；`notifyAll()` 让所有线程醒来后按条件筛选。
- 问：能不能用 `Lock/Condition`？答：可以。它能为不同条件建立独立等待队列，在线程数较多时减少无效唤醒，但核心仍是“共享状态 + 条件谓词 + 原子状态转换”。
- 问：能不能用 `AtomicInteger`？答：能做无锁/自旋版本，但单独的原子自增并不能自动保证线程按指定 owner 有序输出；还需要条件协调，而且自旋会消耗 CPU。
- 问：两个线程时怎么变成奇偶打印？答：设 `N=2`，owner 公式自然让 1/3/5/7/9 属于线程 0、2/4/6/8/10 属于线程 1。
- 问：复杂度是什么？答：有效输出次数是 O(maxValue)；共享数据是 O(1)。但 `notifyAll()` 可能带来额外调度和锁竞争，这属于并发运行时开销，不能只用算法大 O 忽略。

## 易错点

- 用 `if` 包住 `wait()`，醒来后不重新检查条件。
- 用 `Thread.sleep` 猜测调度顺序。
- 只给 `volatile/AtomicInteger`，却没有定义线程 owner 和等待协议。
- `next++` 或输出放到 monitor 外，破坏“检查条件与推进状态”的原子性。
- 最后一个线程退出时没有唤醒其他等待线程，导致程序无法完整结束。
- 多线程场景只调用 `notify()`，却没有证明被唤醒的一定是下一位 owner。
- 把“2 个线程奇偶交替”写成原题明确要求；当前来源只保留了多线程循环打印 1-10 和线程同步机制。
