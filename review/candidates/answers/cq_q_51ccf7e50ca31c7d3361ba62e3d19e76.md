# AQS / ReentrantLock 如何实现公平锁和非公平锁？

## 核心结论

AQS 本身提供的是“同步状态 + 等待队列 + 阻塞/唤醒”的框架，并不会自动把锁变成公平锁。以 OpenJDK 21 GA 的 `ReentrantLock` 为例，公平与非公平的关键差异在 **竞争到空闲状态时，是否允许新到线程绕过已经排队的线程直接 CAS 抢锁**：

- `NonfairSync` 在看到 state 为 0 时可以直接 CAS，不先检查队列前驱，因此允许 barging（插队）。
- `FairSync` 在 CAS 前增加队列公平性检查：初始公平尝试要求当前没有排队线程，排队后的竞争路径要求当前线程没有排队前驱，才允许把 state 从 0 改成 1。
- 两种模式都使用 AQS 的等待队列；不是“公平锁有队列、非公平锁没有队列”。
- 两种模式都支持可重入：如果当前线程已经是 owner，就增加 state/hold count，而不是把自己再次排队。
- 解锁时递减 state，降到 0 才真正释放 owner；随后由 AQS 的 release/唤醒机制推动等待线程继续竞争。

所以公平与非公平不是两套完全不同的锁，而是在同一个 AQS 排队/状态框架上采用不同的“入场策略”。

## 1 分钟版

可以把 AQS 看成一个排队大厅：

1. `state` 表示锁状态/重入次数，AQS 维护等待队列。
2. 第一次抢锁时，如果 state=0：
   - **非公平锁**：直接 CAS 0→1，成功就拿到锁，不先看前面有没有人排队。
   - **公平锁**：先看队列，只有没有应该排在自己前面的线程时才 CAS。
3. 如果锁被别人占用，获取失败后，两种模式最终都会进入 AQS 获取流程，在等待队列中阻塞并被唤醒重试。
4. 如果 owner 就是自己，则直接把 state 加 1，实现可重入。
5. unlock 把 state 减 1；只有减到 0 才清 owner，并使后继等待者有机会继续获取。

一句话：**AQS 负责“怎么排队、怎么睡、怎么醒”，`FairSync` / `NonfairSync` 决定“醒来或新到时能不能插队抢 state”。**

## 3 分钟版

`ReentrantLock` 内部的同步器继承 AQS。构造时根据 fairness 参数选择 `FairSync` 或 `NonfairSync`。AQS 的 state 在这里被用作重入计数：0 表示当前未持有，大于 0 表示 owner 的持有次数。

### 非公平路径

OpenJDK 21 GA 的 `NonfairSync.initialTryLock()` 在 state=0 时直接尝试 CAS：

```text
state == 0
    ↓
CAS(0, 1)
    ↓ success
setExclusiveOwnerThread(current)
```

它不会先问“队列里有没有比我更早到的线程”。因此可能出现：

```text
T1 持锁
T2 已经排队等待
T1 释放
T3 此时刚好到达
T3 直接 CAS 成功
T2 继续等待
```

这就是 barging。它减少了“必须先排队再被唤醒”的约束，通常有利于吞吐，但等待时间的方差可能更大。

### 公平路径

公平同步器在 state=0 时，会在 CAS 前增加队列顺序检查。OpenJDK 21 GA 中：

- `FairSync.initialTryLock()` 要求没有已排队线程后才尝试 CAS；
- `FairSync.tryAcquire()` 要求 `!hasQueuedPredecessors()` 后才尝试 CAS。

逻辑可以概括为：

```text
state == 0
    ↓
我前面是否已有等待者？
    ├─ 是 → 不直接抢，进入/继续 AQS 获取流程
    └─ 否 → CAS(0, 1)
```

因此公平锁的核心不是“强制线程调度绝对公平”，而是 **锁的获取策略不主动让后来者绕过已经排队在前面的线程**。

### 竞争失败以后

无论公平还是非公平，快速获取失败后都会落到 AQS 的 acquire 机制。AQS 负责维护 FIFO 等待队列、把获取失败的线程排队、在合适时机阻塞，并在 release 后让符合条件的等待线程重新尝试获取。

因此要分清两个层次：

```text
ReentrantLock FairSync / NonfairSync
        ↓ 定义获取策略
AQS
        ↓ 提供 state + queue + park/unpark/acquire/release 框架
JVM / OS scheduler
        ↓ 实际线程调度
```

## 关键细节

- **AQS 的 FIFO 队列不等于自动公平**：AQS 文档明确允许同步器采用 barging 策略。是否检查排队前驱，是具体同步器的策略。
- **两种锁都有队列**：非公平只是在 state 刚好可用时允许后来线程直接竞争；竞争失败后照样进入 AQS 等待路径。
- **可重入与公平性是两件事**：owner 再次 lock 时增加 state，两种模式都不会要求 owner 去队尾排队，否则就不再是可重入锁。
- **完全释放才交接**：unlock 只把重入计数减一；只有 state 变成 0 时才清除 owner 并完成一次真正 release。
- **公平不是调度公平**：公平 `ReentrantLock` 控制的是锁获取时的排队策略，不能保证 JVM/操作系统一定按严格时间顺序调度线程。
- **`tryLock()` 是重要边界**：OpenJDK `ReentrantLock` 文档明确说明，不带超时的 `tryLock()` 不遵守 fairness 设置；只要锁此刻可用，它可以成功，即使公平锁已有等待线程。
- **公平锁也不是“谁先调用 lock 谁绝对先拿到”**：公平性讨论针对已经进入同步器竞争/等待的获取策略，还受线程何时真正运行到竞争点等调度因素影响。
- **性能权衡**：OpenJDK 文档说明，在高竞争下公平锁通常可能降低总体吞吐，但可减小锁获取时间的波动，并降低长期饥饿的风险。

## 原理机制

AQS 把同步器拆成两个部分：

1. 子类通过 `tryAcquire` / `tryRelease` 定义“什么条件下可以获得/释放同步状态”；
2. AQS 负责围绕这个结果完成排队、阻塞、唤醒和重试。

`ReentrantLock` 正好利用这个分离点实现公平策略：

```text
             state 可用
                │
        ┌───────┴────────┐
        │                │
   NonfairSync       FairSync
   直接尝试 CAS       先检查队列顺序
        │                │
        └───────┬────────┘
                │ 获取失败
                ↓
          AQS 等待/重试框架
```

这也解释了为什么“公平锁和非公平锁都基于 AQS”并不矛盾：AQS 提供机制，具体同步器提供策略。

从并发语义看，非公平模式允许一个新线程在“锁刚释放、老等待者尚未重新占有”的窗口里直接 CAS；公平模式通过队列前驱检查关闭这个主动插队入口。两者并没有改变 state 的互斥语义：任意时刻仍然只有 owner 能以独占方式持有锁。

## 项目经验版

来源没有提供真实项目经历，不能虚构“线上因为公平锁解决过某事故”。工程选型时应先看业务目标：

- 如果目标是总体吞吐，临界区较短且线程饥饿风险可接受，默认非公平策略通常更合适。
- 如果更关心等待时间的可预测性、希望减少长期得不到锁的概率，可以评估公平锁，但必须通过真实压测验证吞吐代价。
- 不能只凭“公平”二字判断更安全；还要观察临界区长度、竞争强度、线程池大小、是否存在超时/SLA，以及是否混用 `tryLock()`。
- 诊断时可结合线程 dump、JFR/Profiler、锁等待时间分布和业务超时指标，确认问题究竟是锁竞争、线程调度还是临界区本身过长。

这些属于工程验证方法，不是题目来源中的既定项目事实。

## 常见追问

- 问：AQS 不是 FIFO 队列吗，为什么还能非公平？答：FIFO 是等待队列组织方式；AQS 并不要求每次 state 空闲时只能让队头抢。具体同步器可以允许新线程直接 CAS，这就是 barging。
- 问：公平锁是不是性能一定更差？答：不能说“一定”。OpenJDK 文档指出高竞争下公平锁通常可能降低总体吞吐；具体差距要用真实 workload 测。
- 问：非公平线程抢失败怎么办？答：快速路径失败后仍进入 AQS acquire 流程排队、阻塞、被唤醒后重试，不是一直在外面无序自旋。
- 问：公平锁怎么判断自己前面有没有线程？答：在 OpenJDK 21 GA 的公平获取路径中使用队列状态/`hasQueuedPredecessors()` 之类的检查，在没有应优先于当前线程的等待者时才 CAS。
- 问：可重入时也要检查公平队列吗？答：当前线程已经是 owner 时直接增加持有计数；公平性约束的是不同线程争夺空闲锁，不应阻止 owner 重入。
- 问：`tryLock()` 在公平锁上也公平吗？答：不带超时的 `tryLock()` 不遵守公平设置；OpenJDK 文档明确允许它在锁可用时直接成功。
- 问：公平锁能完全杜绝饥饿吗？答：它显著约束了锁层面的插队，但线程调度、暂停、超时/取消等因素仍然存在，不能把锁公平性扩大成整个运行时的绝对调度保证。

## 易错点

- 说“公平锁使用 AQS 队列，非公平锁不使用队列”。
- 说“AQS 天然就是公平锁实现”。
- 只记住 `hasQueuedPredecessors()`，却说不清它解决的是“阻止后来者在 state 空闲时插队”。
- 忽略 reentrant 分支，把 owner 重入也描述成重新排队。
- 把 state 从 1 减到 0 和每次 unlock 都等价起来；多次重入时只有最后一次 unlock 才真正释放。
- 把公平锁描述成 JVM/OS 线程调度的严格 FIFO 保证。
- 忘记无超时 `tryLock()` 不遵守 fairness 设置。
