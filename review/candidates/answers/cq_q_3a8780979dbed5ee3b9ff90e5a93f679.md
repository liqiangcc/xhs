# Java / JVM 内存区域怎么划分？

## 核心结论

从 JVM 规范的运行时数据区看，这道题最稳妥的回答是先按“是否线程私有”来划分：

```text
线程共享
├─ Heap（堆）
└─ Method Area（方法区）

线程私有
├─ Java Virtual Machine Stack（JVM 栈）
└─ pc Register（程序计数器）
```

这四个区域分别回答了不同问题：

- **Heap**：对象实例和数组的规范级分配区域，所有 JVM 线程共享，由自动存储管理系统（GC）回收。
- **JVM Stack**：每个线程私有，随着线程创建而创建，主要保存方法调用对应的 Frame；Frame 中包含局部变量表、操作数栈以及动态链接/返回等所需数据。
- **Method Area**：所有线程共享，保存每个类的结构信息，例如运行时常量池、字段和方法数据，以及方法/构造器代码。它是 JVM 规范里的抽象区域，不能直接把“方法区 = Metaspace”当成所有 JVM/所有版本都成立的定义。
- **pc Register**：每个线程私有。当前执行的是非 native 方法时，它表示正在执行的 JVM 指令地址；当前方法是 native 时，规范把它的值定义为未指定。

面试时不要只背“堆、栈、方法区、程序计数器”四个名词，最好同时说明 **共享范围、存什么、生命周期、典型错误边界**。

## 1 分钟版

可以这样答：

- **堆**：线程共享，JVM 启动时创建；类实例和数组从这里分配，垃圾回收主要管理这里。无法满足所需堆内存时会抛 `OutOfMemoryError`。
- **JVM 栈**：线程私有，线程创建时建立；每次方法调用创建一个栈帧，栈帧里有局部变量、操作数栈等。调用深度超过可用栈深度会 `StackOverflowError`；如果栈需要扩展但内存不足，也可能 `OutOfMemoryError`。
- **方法区**：线程共享，保存类级结构，包括运行时常量池、字段/方法信息和代码。它是规范抽象，不应简单等同于 HotSpot 的 Metaspace；无法满足方法区内存需求时会 `OutOfMemoryError`。
- **程序计数器**：线程私有，用来记录当前线程执行到哪条 JVM 指令；执行 native 方法时其值由规范定义为未指定。

一句话总结：

```text
对象/数组主要看堆；
方法执行过程看每线程 JVM 栈和 Frame；
类级元数据看方法区；
线程当前执行位置看 pc Register。
```

## 3 分钟版

### 1. Heap：对象和数组的共享分配区域

JVM 规范规定，Heap 是所有线程共享的运行时数据区。

它最核心的职责是：

```text
class instances
+
arrays
→ 从 Heap 分配
```

Heap 的存储由自动存储管理系统管理，也就是通常说的 GC。规范并没有规定必须使用哪一种垃圾回收算法，也没有要求 Heap 在物理内存中必须连续。

因此：

- “对象在堆上”是规范层面的抽象模型；
- 具体 JVM 可以做逃逸分析、标量替换等优化，但不能因此把规范模型反过来说成“对象本来就不属于堆”；
- 如果 JVM 无法提供对象/数组分配所需要的 Heap 空间，会抛 `OutOfMemoryError`。

### 2. JVM Stack：每个线程的方法执行栈

每个 JVM 线程都有自己的 JVM Stack，在线程创建时一起创建。

方法每调用一次，会创建一个新的 Frame；方法正常返回或异常退出后，这个 Frame 被销毁。

一个 Frame 里主要包括：

- 局部变量；
- 操作数栈；
- 动态链接、方法返回和异常处理所需的数据。

可以把关系理解成：

```text
Thread
  ↓ owns
JVM Stack
  ↓ contains
Frame 1
Frame 2
Frame 3
...
```

这里要特别避免一句常见但过度简化的话：

> “局部变量和对象都在栈里。”

更准确的是：局部变量表属于 Frame；如果一个局部变量保存的是对象引用，那么这个**引用值**可以在局部变量表里，但它所引用的类实例按 JVM 规范仍然从 Heap 分配。

JVM Stack 典型有两类错误边界：

- 线程所需栈深度超过实现允许的深度：`StackOverflowError`；
- 如果实现支持动态扩展栈，但无法拿到足够内存完成创建/扩展：`OutOfMemoryError`。

### 3. Method Area：共享的类级结构区域

Method Area 是 JVM 规范定义的共享运行时数据区。

它存储每个类相关的结构，例如：

- run-time constant pool；
- 字段数据；
- 方法数据；
- 方法和构造器的代码。

每个类或接口都有自己的运行时常量池，而运行时常量池是从 Method Area 分配的。

这里最容易混淆的是：

```text
JVM Specification 的 Method Area
≠ 必然等于某个 HotSpot 版本的具体内存实现
```

规范说 Method Area **逻辑上属于 Heap 的一部分**，但没有规定它的物理位置、是否连续、是否必须垃圾回收，也没有规定具体实现技术。

所以：

- 旧 HotSpot 的 PermGen 是一种历史实现；
- HotSpot 的 Metaspace 是一种具体实现术语；
- 但在回答 JVM 规范问题时，不能把“Method Area 就是 Metaspace”写成普遍定义。

如果无法满足方法区所需内存，也会抛 `OutOfMemoryError`。

### 4. pc Register：每线程当前执行位置

每个 JVM 线程都有自己的 pc Register。

对于当前正在执行的**非 native** 方法，pc Register 表示当前正在执行的 JVM 指令地址。

对于当前正在执行的 **native** 方法，JVM 规范规定 pc Register 的值是 undefined。

它之所以必须线程私有，很容易从线程执行模型理解：

```text
多个线程
→ 各自独立执行
→ 各自需要知道“我当前执行到哪”
```

因此不能让所有线程共用一个 pc。

### 5. 用一张表收口

| 区域 | 是否线程共享 | 主要内容 | 生命周期/边界 |
| --- | --- | --- | --- |
| Heap | 共享 | 对象实例、数组 | JVM 生命周期；空间不足可 `OutOfMemoryError` |
| JVM Stack | 私有 | 方法 Frame、局部变量、操作数栈等 | 随线程创建/销毁；可能 `StackOverflowError` / `OutOfMemoryError` |
| Method Area | 共享 | 类级结构、运行时常量池、字段/方法数据、代码 | JVM 生命周期；空间不足可 `OutOfMemoryError` |
| pc Register | 私有 | 当前非 native JVM 指令位置 | 随线程存在；native 方法时值未指定 |

## 关键细节

- **题目里的“栈”应优先回答 JVM Stack**，不是泛化成操作系统进程栈。
- **JVM Stack 是线程私有的，Heap 和 Method Area 是线程共享的**，这是最重要的第一层划分。
- **Frame 才是一次方法调用的执行单元**；方法调用创建 Frame，方法结束销毁 Frame。
- **局部变量表里的对象引用不等于对象本体在栈里**；类实例和数组按规范从 Heap 分配。
- **Method Area 是规范抽象**。不要把它和某个 JVM/某个版本中的 PermGen、Metaspace 机械画等号。
- **规范说 Method Area 逻辑上是 Heap 的一部分**，但不意味着它必须和对象堆使用同一块物理区域或相同管理策略。
- **运行时常量池属于每个类/接口的运行时结构，并从 Method Area 分配**。
- **pc Register 是每线程一个**；非 native 方法时记录 JVM 指令位置，native 方法时值未指定。
- **Heap 的 GC 算法不是 JVM 规范固定的**；规范要求自动存储管理，但不规定必须用 G1、CMS 或其他具体收集器。
- JVM 规范还定义了 Native Method Stacks 等运行时区域，但当前原题明确要求的是堆、JVM 栈、方法区和程序计数器，应先把这四个答完整，再把其他区域当作补充。

## 原理机制

这四个区域其实对应两种完全不同的状态：

```text
JVM 级共享状态
→ Heap
→ Method Area

线程执行状态
→ JVM Stack
→ pc Register
```

为什么 Heap / Method Area 要共享？

因为对象实例、数组和类级结构都需要被多个线程共同访问。一个类的字段/方法定义、一个对象实例，不可能因为线程不同就天然复制一份。

为什么 JVM Stack / pc Register 要线程私有？

因为每个线程都有独立的调用链和执行位置：

```text
Thread A:
  method1 -> method2 -> method3
  pc = instruction X

Thread B:
  method7 -> method8
  pc = instruction Y
```

如果栈和 pc 共享，两个线程的调用帧和执行位置就无法独立维护。

因此一个很好记忆的模型是：

```text
共享“数据和类型”
私有“执行上下文”
```

但这只是帮助理解的抽象，不要再把它扩张成未经规范支持的物理内存布局结论。

## 项目经验版

来源没有给出真实生产 OOM、JVM 参数、堆大小或 GC 日志，因此不能虚构“线上发生过某次 Metaspace OOM”。

真实排查 JVM 内存问题时，我会先把“规范区域”和“具体 JVM 实现指标”分开：

```text
先定位症状属于哪一类运行时区域
→ 再确认具体 JVM/版本
→ 再看该实现对应的监控指标、启动参数、GC 日志或错误信息
```

例如：

- 深递归导致 `StackOverflowError`，优先分析线程调用深度和栈；
- 大量对象分配导致 Heap 压力，优先分析对象存活、分配速率和 GC；
- 类加载/类卸载相关的内存问题，需要结合实际 JVM 对 Method Area 的实现方式分析。

不能看到“方法区”三个字，就不加版本边界地直接说“调 Metaspace 参数”；那是实现层结论，不是 JVM 规范本身。

## 常见追问

- 问：堆和栈最大的区别是什么？  
  答：Heap 是 JVM 线程共享的对象/数组分配区域；JVM Stack 是每线程私有的方法执行栈，里面存放 Frame。一个强调共享对象数据，一个强调线程调用执行上下文。

- 问：对象一定都物理存在堆内存里吗？  
  答：JVM 规范的抽象模型规定类实例和数组从 Heap 分配；具体实现可以做逃逸分析、标量替换等优化。面试回答应把规范模型和实现优化分开。

- 问：局部变量在栈里，那局部变量引用的对象呢？  
  答：引用值可以存放在 Frame 的局部变量表中，但它引用的类实例按规范从 Heap 分配。

- 问：方法区就是 Metaspace 吗？  
  答：不能这么绝对说。Method Area 是 JVM 规范抽象；Metaspace 是 HotSpot 的具体实现术语。不同 JVM、不同版本的实现可以不同。

- 问：方法区和堆到底是什么关系？  
  答：JVMS 说 Method Area 在逻辑上是 Heap 的一部分，但规范不规定其物理位置或管理策略，所以不能推导成“它和对象堆一定是同一块物理内存”。

- 问：JVM 栈什么时候会 StackOverflowError？  
  答：当线程计算所需要的栈深度超过实现允许的栈深度时会抛 `StackOverflowError`。如果动态栈无法创建/扩展，也可能是 `OutOfMemoryError`。

- 问：程序计数器为什么线程私有？  
  答：每个线程都需要独立记录自己的 JVM 指令执行位置。不同线程并发执行时，它们当前执行的指令本来就可能不同。

- 问：native 方法执行时 pc Register 存什么？  
  答：JVMS 对当前 native 方法时的 pc Register 值定义为 undefined，不应编造一个固定地址语义。

## 易错点

- 只背“堆、栈、方法区、程序计数器”，却说不出哪些共享、哪些私有。
- 把 JVM Stack 说成一个 JVM 全局共享的大栈。
- 把方法调用产生的 Frame 和整个线程的 JVM Stack 混为同一层级。
- 说“局部变量在栈，所以对象也在栈”，混淆引用和值对象。
- 把 “Method Area = Metaspace” 写成 JVM 规范定义。
- 把 PermGen、Metaspace 的 HotSpot 历史实现细节当成所有 JVM 通用事实。
- 说 Method Area 逻辑上属于 Heap，就进一步断言它必须和对象堆共用同一物理区域。
- 把 pc Register 说成线程共享。
- 忽略 native 方法时 pc Register 的值在规范中未定义。
- 把某个具体 GC 算法说成 Heap 的规范要求。
- 虚构生产 JVM 参数、OOM 数字或故障经历来填“项目经验”。
