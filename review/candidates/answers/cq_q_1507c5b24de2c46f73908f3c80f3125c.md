# synchronized 和 ReentrantLock 的区别

## 核心结论

两者都能提供**可重入的互斥锁**，正确使用时也都提供锁释放/获取之间的内存可见性保证；真正的差别主要在“语言内建的结构化 monitor”与“显式 Lock API 的可编程能力”：

- `synchronized` 是 Java 语言级同步机制，围绕对象 monitor 工作；进入同步块/同步方法时加锁，退出时无论正常返回还是异常退出都会自动解锁。
- `ReentrantLock` 是 `java.util.concurrent.locks.Lock` 的实现，锁和解锁由代码显式调用，通常必须使用 `lock(); try { ... } finally { unlock(); }`。
- `ReentrantLock` 提供 `tryLock()`、超时获取、`lockInterruptibly()`、可选公平策略、多个 `Condition` 以及锁状态/等待队列的监控接口；`synchronized` 不暴露这些同等级的策略控制接口。
- `synchronized` 配合 `Object.wait/notify/notifyAll` 使用 monitor 的等待机制；`ReentrantLock` 可以为同一把锁创建多个 `Condition`，把不同等待条件拆成不同条件队列。
- 不应简单说“ReentrantLock 一定比 synchronized 快”。现代 JVM 会持续优化两者；选择首先应看是否需要可中断、超时、公平、多个条件队列或非块结构加锁等语义能力。

一句话：**只需要简单、词法作用域清晰的互斥时优先 `synchronized`；需要更细的锁获取/等待策略和可观测能力时再考虑 `ReentrantLock`。**

## 1 分钟版

面试时我会从六个维度回答：

1. **形态**：`synchronized` 是语言内建 monitor；`ReentrantLock` 是显式 `Lock` 对象。
2. **释放方式**：`synchronized` 退出作用域自动释放；`ReentrantLock` 必须显式 `unlock()`，一般放在 `finally`。
3. **获取能力**：`ReentrantLock` 支持立即尝试、超时尝试、可中断等待；`synchronized` 没有对应的 API 入口。
4. **公平性**：`ReentrantLock(true)` 可请求公平策略；默认是非公平。`synchronized` 没有公平参数。
5. **条件等待**：monitor 使用 `wait/notify/notifyAll`；`ReentrantLock` 可创建多个 `Condition`，适合把不同等待条件分开。
6. **共同点**：两者都是可重入互斥机制；正确的 lock/unlock 与 monitor lock/unlock 都具有 Java 内存模型要求的同步语义。

选型不要只看“性能”。如果简单临界区就用 `synchronized`，代码更短且自动释放；只有在需要 `tryLock`、超时、响应中断、公平策略、多个条件队列或监控信息时，`ReentrantLock` 的额外能力才真正有价值。

## 3 分钟版

### 1. `synchronized`：结构化 monitor

每个 Java 对象都关联一个 monitor。进入：

```java
synchronized (lockObject) {
    // critical section
}
```

时，当前线程必须先获得该对象 monitor；退出同步块时，monitor 会自动释放。Java 语言规范明确规定：同步块即使因为异常而突然完成，也会执行对应的 unlock。

同步方法只是把这个规则隐式应用到实例对象或 `Class` 对象：

- 实例 `synchronized` 方法锁 `this`；
- `static synchronized` 方法锁对应的 `Class` 对象。

而且 monitor 是可重入的：同一个线程可以重复获得同一 monitor，每次 unlock 抵消一次 lock。

### 2. `ReentrantLock`：显式 Lock API

典型写法是：

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();
}
```

它同样可重入。当前线程已经持有锁时，再次 `lock()` 会增加 hold count；只有匹配到最后一次 `unlock()` 时才真正释放。

区别在于生命周期不再由 Java 语法自动包住，所以灵活性更强，但责任也转移给调用者。如果忘了在 `finally` 中解锁，异常路径可能把锁永久留在持有状态。

### 3. `ReentrantLock` 多出的获取策略

`Lock` / `ReentrantLock` 提供：

- `tryLock()`：锁当前不可用就立即失败，不必一直等；
- `tryLock(timeout, unit)`：最多等一段时间；
- `lockInterruptibly()`：等待锁时可以响应中断；
- `ReentrantLock(true)`：使用公平策略，在竞争下倾向于让等待更久的线程先获得锁。

这些能力适合“拿不到锁就降级”“超过 SLA 就放弃”“任务取消时要停止等待”等场景。

但公平也有边界：公平锁控制的是锁获取策略，不等于 JVM/操作系统线程调度绝对公平；而且无超时的 `tryLock()` 即使在公平锁上也允许在锁可用时直接成功。

### 4. 条件等待模型

`synchronized` 通常配合：

```java
obj.wait();
obj.notify();
obj.notifyAll();
```

使用对象 monitor 的等待机制。

`ReentrantLock` 则可以：

```java
Condition notEmpty = lock.newCondition();
Condition notFull  = lock.newCondition();
```

同一把锁可以绑定多个 `Condition`。例如有界队列中，“等待非空”和“等待非满”可以分开，不需要把两类等待者都放在同一个条件集合里。`Condition.await()` 会原子地释放关联锁并等待，返回前重新获得锁。

### 5. 内存语义

不要误以为 `ReentrantLock` 只是库代码所以没有 `synchronized` 的可见性保证。`Lock` 规范要求成功的 `lock` / `unlock` 具有与 Java monitor lock / unlock 相同的内存同步效果。

因此二者的核心互斥与可见性能力都成立，差异主要是 API 能力、结构化程度和策略可配置性，而不是“一个有内存屏障、一个没有”。

## 关键细节

- **两者都可重入**：不能把“可重入”当成 `ReentrantLock` 相对 `synchronized` 的独有优势。
- **自动释放是 `synchronized` 的重要安全性优势**：同步块正常或异常退出都会自动 unlock；显式 Lock 必须靠 `finally` 保证释放。
- **可中断要说准确**：`ReentrantLock.lock()` 本身不是“等待时一定可中断”的 API；需要 `lockInterruptibly()`，超时 `tryLock` 也会响应中断。
- **公平不是绝对 FIFO 调度**：`ReentrantLock(true)` 提供公平获取策略，但不保证操作系统/JVM 调度公平；无超时 `tryLock()` 还会绕开公平设置。
- **多个 `Condition` 是实际差异**：`Condition` 把 monitor 的 `wait/notify/notifyAll` 模型拆成独立条件对象，使一把锁可以管理多个等待条件。
- **不要把实现细节当语言契约**：`synchronized` 的语言/内存语义由 JLS 定义，JVM 内部具体如何优化 monitor 会随实现和版本变化；面试时可以讨论实现，但要与规范保证分开。
- **性能结论要基于 workload**：竞争强度、临界区长度、线程调度、JDK 版本都会影响结果，不能用“JUC 锁必然更快”作通用结论。
- **监控能力不同**：`ReentrantLock` 暴露 `getHoldCount()`、`getQueueLength()`、`hasQueuedThreads()`、`isLocked()` 等接口，便于诊断；这些结果很多是监控用途的估计值，不应拿来做同步正确性的判断。

## 原理机制

可以把两者看成两种“同步控制面”：

```text
synchronized
    ↓
Java 语法规定进入/退出 monitor
    ↓
JVM 实现 monitor 的竞争、阻塞和唤醒

ReentrantLock
    ↓
Lock API 明确表达 lock/tryLock/interrupt/timeout/condition
    ↓
OpenJDK ReentrantLock 通过 AQS 实现状态与等待队列
```

它们最终都要解决同一类问题：某个时刻谁拥有独占访问权，竞争失败的线程如何等待，释放之后谁重新竞争，以及释放前的写入如何对后续获得锁的线程可见。

最大的设计差异是：

```text
synchronized：语法替你约束生命周期
ReentrantLock：API 把生命周期和策略交给程序控制
```

这也是为什么 `ReentrantLock` 能做非块结构加锁、超时、可中断和多个条件队列，同时也更容易因为漏掉 `unlock()` 而出错。

## 项目经验版

当前来源只包含“比较 synchronized 与 ReentrantLock”的技术问题，没有真实项目经历，因此不能虚构“在线上项目里曾经因为某把锁解决过事故”。

工程上我会按需求选：

- 普通短临界区、没有特殊等待策略：优先 `synchronized`，让语法自动管理释放。
- 请求有超时预算，拿不到锁需要快速失败/降级：评估 `tryLock(timeout, unit)`。
- 任务支持取消，线程不应长期不可中断地等锁：评估 `lockInterruptibly()`。
- 同一共享状态上存在多类独立等待条件：评估 `ReentrantLock` + 多个 `Condition`。
- 真正需要公平策略：先确认业务为什么需要，再压测吞吐和等待时间分布；不要因为“公平”听起来更正确就默认开启。

上线前应观察真实的锁等待时间、竞争率、超时、线程 dump/JFR 等数据，而不是只依赖微基准或固定经验。

## 常见追问

- 问：`ReentrantLock` 为什么叫“可重入”，那 `synchronized` 不可重入吗？  
  答：两者都可重入。`ReentrantLock` 把 hold count 作为 API 可观察状态；Java monitor 也允许同一线程重复 lock 同一 monitor。

- 问：哪个性能更好？  
  答：没有跨版本、跨 workload 的固定答案。先按语义选，再用目标 JDK 和真实竞争模式测试。不要把历史 JVM 结论当成永久规律。

- 问：`ReentrantLock` 的优势是不是“可以中断”？  
  答：更准确地说，它提供 `lockInterruptibly()` 这个显式可中断获取方式；普通 `lock()` 和可中断获取要区分。

- 问：公平锁是不是严格先来先得？  
  答：它在竞争下偏向等待最久的线程，但不等于线程调度绝对公平；无超时 `tryLock()` 还明确不遵守 fairness 设置。

- 问：`Condition` 和 `wait/notify` 是什么关系？  
  答：`Condition` 把 Object monitor 的等待/通知模型抽象到 `Lock` 上，并允许一把 Lock 关联多个条件对象；等待时同样要原子释放锁，返回前重新获取。

- 问：为什么 `unlock()` 一定要放 `finally`？  
  答：因为 Lock API 不会随 Java 词法作用域自动释放。临界区抛异常时如果不执行 `unlock()`，其他线程可能一直无法获得锁。

- 问：两者的可见性一样吗？  
  答：在规范层面，`Lock` 要求成功的 lock/unlock 提供和 monitor lock/unlock 相同的内存同步效果；不能说只有 `synchronized` 才有 happens-before 保证。

## 易错点

- 说“`synchronized` 不可重入，只有 `ReentrantLock` 可重入”。
- 说“`ReentrantLock` 一定比 `synchronized` 快”。
- 把 `lock()` 和 `lockInterruptibly()` 混成同一个中断语义。
- 认为公平锁等于 JVM/OS 严格 FIFO 调度。
- 忘记公平 `ReentrantLock` 的无超时 `tryLock()` 会绕开 fairness。
- 用 `getQueueLength()` 等监控 API 的瞬时估计值参与同步正确性判断。
- 用 `ReentrantLock` 却没有 `try/finally`，让异常路径漏掉 `unlock()`。
- 把某个 HotSpot 版本的 monitor 优化策略当成 Java 语言永久保证。
