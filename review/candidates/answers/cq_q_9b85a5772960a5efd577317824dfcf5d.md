# URL 字符串解析并转换为 JSON

## 核心结论

来源明确要求：输入一段 URL 字符串，解析后转换为 JSON，并考虑不同协议、域名、路径和查询参数的特殊情况。这里采用 Node.js 22 的 WHATWG `URL` / `URLSearchParams` 作为解析器，而不是手写一个容易漏掉 IPv6、百分号编码、默认端口和特殊 scheme 的正则。

为了让“JSON 格式”可执行，本候选显式定义输出契约：只接受**绝对 URL**；输出字段为 `protocol`、`hostname`、`port`、`pathname`、`query`、`fragment`。`protocol` 去掉末尾冒号；无 hostname/port/fragment 用 `null`；查询参数按 URLSearchParams 解码，重复 key 保留为按出现顺序排列的数组；路径保留 WHATWG URL 的序列化形式，不额外 `decodeURIComponent`。这些 JSON 字段和重复参数策略是候选契约，不是来源原文已指定的 schema。

## 1 分钟版

- 不建议用一个大正则“解析所有 URL”；直接使用平台标准 WHATWG `URL`。
- `url.protocol`、`url.hostname`、`url.port`、`url.pathname` 分别拿协议、主机、端口、路径。
- 查询参数用 `url.searchParams` 遍历；同名参数可能重复，不能简单覆盖，第二次出现时转成数组。
- `Object.create(null)` 保存 query，避免 `__proto__` 之类的键污染普通对象原型。
- 默认端口可能被 WHATWG URL 规范化为空字符串，所以输出层统一转成 `null`。
- 无 base 的 `new URL(input)` 要求绝对 URL；相对路径输入在本候选中直接视为非法。

## 3 分钟版

```javascript
function parseUrlToJson(input) {
  if (typeof input !== 'string' || input.length === 0) {
    throw new TypeError('input must be a non-empty absolute URL string');
  }

  const url = new URL(input);
  const query = Object.create(null);

  for (const [key, value] of url.searchParams) {
    if (!Object.hasOwn(query, key)) {
      query[key] = value;
    } else if (Array.isArray(query[key])) {
      query[key].push(value);
    } else {
      query[key] = [query[key], value];
    }
  }

  return JSON.stringify({
    protocol: url.protocol.endsWith(':')
      ? url.protocol.slice(0, -1)
      : url.protocol,
    hostname: url.hostname || null,
    port: url.port || null,
    pathname: url.pathname,
    query,
    fragment: url.hash ? url.hash.slice(1) : null,
  });
}
```

例如：

```text
https://example.com:8443/a/b?tag=java&tag=js&empty=#top
```

会得到语义上等价于：

```json
{
  "protocol": "https",
  "hostname": "example.com",
  "port": "8443",
  "pathname": "/a/b",
  "query": {"tag": ["java", "js"], "empty": ""},
  "fragment": "top"
}
```

## 关键细节

- **协议**：WHATWG `URL.protocol` 带末尾 `:`；输出 schema 为了更简洁主动去掉冒号。`https:`、`ftp:`、自定义 scheme 都由标准解析器处理，本答案不把协议硬编码成 HTTP/HTTPS 两种。
- **域名/主机**：使用 `hostname` 而不是 `host`，因为 `host` 会把端口一起带上。没有主机的 scheme（例如某些 opaque URL）输出 `hostname: null`。
- **端口**：`url.port` 是字符串。WHATWG URL 会对 special scheme 的默认端口做规范化，因此显式写出的默认端口也可能表现为空字符串；本 schema 把空字符串统一映射为 `null`。
- **路径**：使用 `pathname` 的标准序列化值，不自行做 `%xx` 解码。路径中 `%2F` 是否应被当成分隔符属于语义层问题，不能在通用 parser 里随意解码。
- **查询参数**：`URLSearchParams` 按参数对遍历并解码 query。重复 key 不应静默丢失，本候选第一次存字符串，第二次升级成数组。
- **空值与无等号参数**：如 `?a=&b`，URLSearchParams 都可以给出空字符串值；JSON 中保留 `""`，不猜测成 `null`、布尔值或数字。
- **`+` 与百分号编码**：query 的解码规则交给 URLSearchParams；路径则不复用 query 的解码规则，因为两者编码语义不同。
- **IPv6**：不要自己按冒号切 host/port；标准 URL parser 能识别方括号包裹的 IPv6 host 与后续端口。
- **用户名/密码**：WHATWG URL 也能提供 `username/password`，但来源只要求协议、域名、路径、查询参数，本候选输出 schema 有意不包含凭据，避免把敏感信息随 JSON 扩散；若业务需要必须显式扩展 schema。
- **非法与相对输入**：本候选不传 `base`，所以 `/a?x=1` 之类相对引用会抛 `TypeError`。若需求允许相对 URL，就必须额外传入可信 base，并把该 base 纳入输入契约。

## 原理机制

URL 不是简单的 `scheme://host/path?query` 字符串切片。不同 scheme、IPv6、userinfo、默认端口、百分号编码以及 query 中的重复 key 都会让手写 split/regex 很快失去正确性。标准解析器先依据 WHATWG URL 状态机把输入规范化成结构化 URL 对象，再由 `URLSearchParams` 处理 query 参数对；我们的代码只负责把这些结构化字段映射到项目定义的 JSON schema。

这个设计还把“语法解析”和“业务解释”分开：parser 不把 `"123"` 自动转数字，也不把 `"true"` 自动转布尔，更不对路径做业务级解码。类型推断和路由语义应该由上层根据 schema 决定，否则同一个通用 URL 解析器会偷偷改变数据含义。

## 常见追问

- 问：为什么不用正则？答：URL 的语法和规范化规则包含 scheme、IPv6、userinfo、默认端口和编码等大量边界；使用平台标准 WHATWG parser 比维护“大一统正则”可靠得多。
- 问：为什么重复 query key 要数组？答：`?tag=a&tag=b` 是合法且常见的参数形式；直接写对象会让后值覆盖前值。本候选选择数组保留所有出现值，这是显式 schema 决策。
- 问：`https://example.com:443/` 的 port 为什么可能是空？答：WHATWG URL 会规范化 special scheme 的默认端口；输出层因此把空 port 映射成 `null`，表示没有需要单独传递的显式非默认端口。
- 问：为什么 pathname 不直接 `decodeURIComponent`？答：路径编码和 query 编码不是同一规则，盲目解码还可能把编码后的保留字符改变成结构分隔符；通用 parser 应保持标准 URL 的 pathname 序列化结果。
- 问：相对 URL 怎么处理？答：`new URL(relative, base)` 可以处理，但 base 会直接影响结果。本候选只接受绝对 URL；若允许相对输入，就把 base 作为显式参数和验证条件。
- 问：如何避免 `__proto__` query key 的问题？答：query 使用 `Object.create(null)`，并通过 `Object.hasOwn` 判断已有键，不让普通对象原型参与键存储。

## 易错点

- 用 `split(':')` 解析 host/port，遇到 IPv6 立即出错。
- 用一个正则宣称支持所有 URL，却没有覆盖协议差异、默认端口和编码规则。
- 把重复 query key 静默覆盖，导致信息丢失。
- 路径与 query 都无条件 `decodeURIComponent`，破坏保留字符语义或抛出编码异常。
- 把空字符串自动转成 `null`、数字或布尔值，混淆语法解析与业务类型推断。
- 未明确相对 URL 是否允许，却在不同机器上使用不同 base 得到不同结果。
- 把 username/password/token 等敏感内容默认写入 JSON 或日志。
