# HTTP 和 HTTPS 的区别

## 核心结论

HTTP 定义应用层语义；HTTPS 通常指 HTTP 运行在 TLS 提供的安全信道之上。相较裸 HTTP，正确部署并正确验证证书的 HTTPS 能为传输中的数据提供机密性、完整性与端点认证；它不是“加密后就绝对安全”，证书校验、服务端配置、终端安全和业务授权仍是边界。

## 1 分钟版

- 分层：HTTP 负责请求、响应和语义；HTTPS 在 HTTP 下增加 TLS 安全信道，HTTP 语义本身不因 TLS 而改变。
- 安全目标：TLS 握手认证服务端（客户端认证可选）、协商密码参数并建立密钥；记录层用这些参数保护后续流量。
- 结果：正确验证后可防窃听、篡改和伪造；HTTP 明文传输不提供这些 TLS 保护。
- 选择：公网登录态、敏感数据或需要防窃听和篡改的链路，应使用正确配置并完成证书验证的 HTTPS；裸 HTTP 不提供 TLS 的这些传输保护。

## 3 分钟版

先区分协议语义和传输保护：HTTP 的方法、状态码、缓存等语义由 HTTP 定义；HTTPS 是让 HTTP 通过 TLS 通道传输。TLS 1.3 的目标是提供认证、机密性和完整性：握手协议认证通信方、协商加密参数、建立共享密钥材料，记录协议使用这些参数保护后续记录。

“HTTPS 为什么安全”不能只答“用了非对称加密”。认证与密钥协商发生在握手阶段；后续应用数据由记录层按协商出的流量密钥独立保护。TLS 1.3 规定服务端总会被认证，客户端认证是可选的；客户端必须把证书链、主机名和信任策略作为验证链路的一部分，否则 HTTPS 仍可能被中间人伪装。

安全性也有范围：TLS 保护的是通信端点之间的传输，不替业务判断登录态是否被盗、接口是否越权、服务器是否已被攻陷，也不完全隐藏流量长度。TLS 1.3 的 0-RTT 是版本特性，RFC 明确它以某些安全属性为代价，不能对有副作用请求随意启用。

## 关键细节

- TLS 1.3：握手认证、协商密码模式和参数、建立共享密钥；记录层用流量密钥保护每条记录。
- 安全属性：TLS 1.3 指出建立后的数据仅对端点可见，攻击者修改会被检测；它不隐藏数据长度，记录可使用 padding 降低部分流量分析风险。
- 认证边界：服务端认证是 TLS 1.3 的常规属性，客户端认证可选；“有证书”不等于客户端已经正确校验证书与目标主机。
- 版本边界：本文的握手和 0-RTT 细节专指 TLS 1.3（RFC 8446）；不要拿它逐报文套用到 TLS 1.2 或非 TLS 的 HTTPS 部署。

## 原理机制

HTTPS 的流程是“HTTP 请求/响应 → TLS 安全信道”。连接建立时，握手确定对端身份、密码参数和共享密钥材料；建立后，记录层把应用数据分成记录并用流量密钥保护。于是攻击者即使控制网络，也不能在不被发现的前提下读取或修改已建立通道中的内容；但这依赖客户端实际完成认证与信任判断。

## 项目经验版

项目映射提示：用真实配置和抓包/监控说明 TLS 版本、证书链和续期、主机名校验、是否启用 mTLS、握手失败率及连接复用情况。没有这些事实时，不要编造“开启 HTTPS 后性能下降多少”或“完全防住了某次攻击”。

## 常见追问

- 问：HTTPS 是不是只在 HTTP 上加了一个证书？答：证书参与身份认证；完整 TLS 还包含握手协商、密钥建立和记录层流量保护。
- 问：为什么握手后还要用对称流量密钥？答：TLS 握手建立共享密钥材料，再由记录层用流量密钥保护连续应用数据；具体算法与密钥派生由协商版本决定。
- 问：HTTPS 能防 SQL 注入或越权吗？答：不能。TLS 保护传输通道，不替代输入校验、认证、授权和服务端安全控制。
- 问：TLS 1.3 的 0-RTT 能给所有请求加速吗？答：不能无条件使用；RFC 8446 明确它以某些安全属性为代价，需按重放风险和请求语义评估。

## 易错点

- 不要把 HTTP 与 HTTPS 说成两个不同的业务语义协议；HTTP 语义仍在，差别是 TLS 保护的传输通道。
- 不要只说“非对称加密所以安全”；认证、密钥协商和记录保护各有职责。
- 不要把 HTTPS 说成可解决终端被控、证书错误、业务越权或所有流量分析问题。
- 不要把 TLS 1.3 的 0-RTT、认证和密码套件结论无边界地套到其他 TLS 版本。
