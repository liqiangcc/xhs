# 数据库 B+ 树的高度和入度（扇出）怎么计算？

## 核心结论

仓库原题只保留了“数据库 B+ 树的高度和入度计算?”，没有给页大小、键大小、指针大小、叶子记录大小、节点头/槽目录开销、装载率，也没有说明“高度”是按边数还是按层数、“入度”是指孩子数（fanout）还是教材里的阶。因此这题不能直接报一个固定数字，正确做法是**先把存储模型写清，再代公式**。

用一个常见的简化模型说明：内部节点可用空间为 `U` 字节，保存 `f` 个孩子指针和 `f-1` 个分隔键；键大小为 `K`，孩子指针大小为 `C`。则

`f*C + (f-1)*K <= U`

所以最大扇出

`f_max = floor((U + K) / (C + K))`。

若叶子每条索引记录平均占 `E` 字节，则简化叶容量 `L = floor(U_leaf / E)`。如果把根算第 1 层、叶子算第 `H` 层，并假设节点都接近满载，则高度 `H` 能容纳的记录数上界约为

`L * f_max^(H-1)`，

因此容纳 `N` 条记录所需的最小满载高度是满足 `L * f_max^(H-1) >= N` 的最小整数 `H`，即

`H = 1 + ceil(log_{f_max}(N / L))`（当 `N > L`；否则 `H=1`）。

## 1 分钟版

先别背“B+ 树一般三层”。面试时先问清四件事：页多大、内部键/指针多大、叶子一条索引记录多大、树高按层还是按边。

内部节点若有 `f` 个孩子，通常对应 `f-1` 个分隔键，所以不是简单的 `pageSize/(key+pointer)`：要解 `f*C + (f-1)*K <= U`。得到 `f_max` 后，再算叶子一页能放多少条 `L`。满载近似下，一层叶子放 `L` 条，两层放 `f_max*L`，三层放 `f_max²*L`，逐层乘 fanout，直到覆盖 `N`。

真实数据库还要扣节点头、slot directory、记录头、变长字段等开销，并考虑实际装载率，所以公式给的是**模型结果/容量估算**，不是从“16KB 页”就能推出的真实固定树高。

## 3 分钟版

### 1. 先定义“入度”

数据库语境里更常用“fanout/扇出”：一个内部节点最多指向多少个孩子。若一个节点有 `f` 个孩子指针，则典型搜索树布局中有 `f-1` 个分隔键。设扣掉页头等元数据后可用于这些条目的空间是 `U`：

`f*C + (f-1)*K <= U`

整理后：

`f*(C+K) <= U+K`

所以：

`f_max = floor((U+K)/(C+K))`。

若实现实际保存的是“每个槽一个 key+child-pointer”、有前缀压缩、变长键或额外 record header，就必须换成真实布局重新算，不能机械套这一个式子。

### 2. 再算叶子容量

叶子与内部节点存的东西通常不同。设叶子可用空间 `U_leaf`，每条叶记录平均 `E` 字节，则最简单估算为：

`L = floor(U_leaf/E)`。

`E` 到底是“键+RID”、还是“完整聚簇记录”、是否包含记录头/变长字段目录，都由具体存储引擎和索引类型决定。

### 3. 最后算高度

本文约定根为第 1 层，叶子为第 `H` 层。满载容量上界：

- `H=1`：根本身就是叶子，约 `L` 条；
- `H=2`：根指向最多 `f_max` 个叶页，约 `f_max*L` 条；
- `H=3`：约 `f_max²*L` 条；
- 一般地：`L*f_max^(H-1)`。

所以对 `N>L`：

`H = 1 + ceil(log_{f_max}(N/L))`。

如果题目问“从根到叶经过几条边”，答案是 `H-1`；这就是为什么必须先确认高度定义。

### 4. 满载高度不是最坏高度

上面的式子使用最大 fanout，算的是接近满载时的容量/最小高度。若要求 B+ 树理论最坏高度，必须再给最小占用规则：非根内部节点最少孩子数、叶子最少记录数、根的特殊下界。只有这些参数明确后，才能用最小 fanout/最小叶容量反推最大高度。

## 关键细节

- **页大小 ≠ 可用空间**：页头、槽目录、记录头等都会占空间；先从物理页大小扣掉固定/变动开销得到 `U`。
- **内部节点和叶子分开算**：内部节点主要决定 fanout，叶子记录大小决定每页数据量。
- **主键/二级索引可能不同**：叶记录载荷不同，`E` 不同，最终高度也可能不同；不能只看 key 长度。
- **变长键/压缩**：这时 `K` 更适合看成平均或上界条目尺寸，结果是估算范围，不是精确常数。
- **装载率**：实际树不会保证每页满载；做容量规划时可用有效 fanout `f_eff ≈ occupancy * f_max` 做敏感性估算，但 occupancy 必须来自题设、文档或实测，不能拍一个 70% 当事实。
- **根节点特殊**：理论最坏高度推导时根的最小孩子数通常与普通内部节点不同，不能统一套同一个最小占用下界。
- **高度定义**：本文 `H` 是层数；若教材用边数定义 height，要减 1。

## 原理机制

下面给一个只负责“简化模型计算”的 Java helper，参数全部显式传入，避免把某个数据库实现细节硬编码成 B+ 树定义：

```java
public final class BPlusTreeSizing {
    private BPlusTreeSizing() {}

    public static int maxFanout(long usableInternalBytes, long keyBytes, long childPointerBytes) {
        requirePositive(usableInternalBytes, "usableInternalBytes");
        requirePositive(keyBytes, "keyBytes");
        requirePositive(childPointerBytes, "childPointerBytes");
        long fanout = (usableInternalBytes + keyBytes) / (keyBytes + childPointerBytes);
        if (fanout < 2 || fanout > Integer.MAX_VALUE) {
            throw new IllegalArgumentException("fanout outside supported range");
        }
        return (int) fanout;
    }

    public static int leafCapacity(long usableLeafBytes, long leafEntryBytes) {
        requirePositive(usableLeafBytes, "usableLeafBytes");
        requirePositive(leafEntryBytes, "leafEntryBytes");
        long capacity = usableLeafBytes / leafEntryBytes;
        if (capacity < 1 || capacity > Integer.MAX_VALUE) {
            throw new IllegalArgumentException("leaf capacity outside supported range");
        }
        return (int) capacity;
    }

    public static int minimumFullLevels(long records, int fanout, int leafCapacity) {
        if (records < 0) throw new IllegalArgumentException("records must be non-negative");
        if (fanout < 2) throw new IllegalArgumentException("fanout must be at least 2");
        if (leafCapacity < 1) throw new IllegalArgumentException("leafCapacity must be positive");
        if (records <= leafCapacity) return 1;
        long capacity = leafCapacity;
        int levels = 1;
        while (capacity < records) {
            if (capacity > Long.MAX_VALUE / fanout) return levels + 1;
            capacity *= fanout;
            levels++;
        }
        return levels;
    }

    private static void requirePositive(long value, String name) {
        if (value <= 0) throw new IllegalArgumentException(name + " must be positive");
    }
}
```

仓库测试不会只复述这三个函数，而会用逐个枚举 `f` 验证 fanout 不等式的最大解，并用 `BigInteger` 的 `L*f^(H-1)` 直接容量公式交叉验证高度。

## MySQL/InnoDB 例子应该怎么说

MySQL 8.4 官方文档说明 InnoDB 表/二级索引由页组成并排列成 B-tree 索引结构；`innodb_page_size` 默认是 16KB，同时支持 4KB、8KB、16KB、32KB、64KB。这个事实只能告诉你“页是容量计算的起点”，**不能单独推出 fanout**。还需要知道索引页实际可用空间、记录格式、键与指针/记录载荷等。因而面试中若有人直接用 `16KB / keySize` 得出“入度”，应继续追问其节点布局假设。

## 项目经验版

仓库来源没有真实表结构、索引 DDL、页转储或生产树高数据，因此不编造“线上某张表三层 B+ 树”的经历。真实排查/容量估算时，我会先固定存储引擎版本和 page size，再从索引定义与真实记录格式估算条目尺寸，最后用数据库提供的索引统计、页分析工具或可复现实验校验，而不是只靠纸面公式。

## 常见追问

- 问：为什么内部节点是 `f` 个指针、`f-1` 个 key？答：这是本文采用的经典分隔键模型：相邻孩子范围之间需要一个分隔键；若具体实现布局不同，就用实际条目结构重写不等式。
- 问：为什么不能直接 `16KB/(key+pointer)`？答：因为页有元数据开销，而且 `f` 个孩子通常只对应 `f-1` 个分隔键；真实实现还可能有 slot/record header、压缩和变长字段。
- 问：一千万条数据树高怎么算？答：先得到 `f` 和叶容量 `L`，再找最小 `H` 使 `L*f^(H-1) >= 10,000,000`；没有 `f/L` 就没有唯一数值答案。
- 问：三层树能存多少？答：在本文“根为第 1 层”的定义下，上界约 `L*f²`；如果对方把高度定义成边数，要先统一口径。
- 问：怎么估算最坏高度？答：用最小而不是最大 fanout/叶容量，并单独处理根的最小孩子数；这些最小占用规则必须由 B+ 树定义或具体实现给出。
- 问：为什么二级索引和聚簇索引高度可能不同？答：叶子保存的载荷不同会改变 `E`，内部键宽也可能不同，于是 `L` 和 `f` 都可能变化。

## 易错点

- 没给任何尺寸参数就直接背“3 层”或“4 层”。
- 把物理 page size 当成 100% 可放键/指针的 `U`。
- 内部节点和叶子使用同一个 entry size。
- 混淆“最大 fanout 算出的满载最小高度”和“最小占用下界算出的理论最大高度”。
- 混淆层数与边数两种 height 定义。
- 把某个 MySQL/InnoDB 版本的 page size 或记录布局冒充成所有数据库 B+ 树的定义。
