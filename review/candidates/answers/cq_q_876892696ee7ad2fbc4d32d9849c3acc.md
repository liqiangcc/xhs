# 如何设计一个支持敏感数据存储和传输安全的加解密平台？

## 核心结论

我会把它设计成“**数据分级 + 版本化密码策略 + KMS/HSM 密钥控制面 + 数据面加解密 + 全链路 TLS + 审计/轮换/灾备**”，而不是做一个“所有系统把明文发给中央服务，再用固定算法加一下”的接口。

先确定三个边界：

1. **哪些数据必须加密、谁允许解密**：身份证号、银行卡号、密钥材料、普通业务字段的等级不同；还要明确是否需要等值查询、排序、模糊搜索、脱敏展示。
2. **传输安全和存储安全分开设计**：新 TLS 协议基线使用 TLS 1.3；TLS 终止后，数据库/对象存储里的敏感数据仍要独立做静态保护。
3. **密钥和数据分离**：业务库保存密文与 `key_id/key_version/profile` 等元数据，不保存长期主密钥。数据密钥 DEK 用于实际数据加密，上层 KEK/主密钥留在受控 KMS/HSM 边界，通过 envelope encryption 管理。

数据面默认采用经批准的**认证加密**配置，而不是自创算法；密码套件做成版本化 profile，例如 `profile=v3` 绑定算法、模式、nonce/IV、tag、AAD 和密钥类型。国内商用密码要求存在时，SM2/SM4 等也通过受控 profile 接入，并以目标系统当前合规/测评要求决定具体组合，而不是在业务代码里散落 `if 国密 then ...`。

一句话：**平台真正要统一的是密钥生命周期、授权、密码策略版本、明文边界和可恢复性，而不是只统一一个 encrypt/decrypt API。**

## 1 分钟版

我会按五层回答：

1. **数据与策略层**：先做数据分级和使用场景分类，明确字段是否只需保密、是否要防篡改、是否支持查询，以及需要国际算法还是商用密码 profile。
2. **密钥控制面**：KMS/HSM 管理 KEK/主密钥、密钥版本、授权、轮换、吊销和审计；业务只拿 `key_id`，不能把主密钥写配置文件或日志。
3. **存储数据面**：采用 envelope encryption。每个对象/批次/租户按策略生成或获取 DEK，用 AEAD 加密，库里保存 `ciphertext + key_id + key_version + profile + nonce/tag`；轮换时新写用新版本，旧数据后台迁移。
4. **传输数据面**：外部和服务间都建立 TLS 1.3 保护；若需要服务身份鉴别可采用双向认证。加解密网关只是一个可选集中策略点，网关后的链路仍不能默认可信。
5. **运维闭环**：监控 KMS/HSM 可用性、加解密错误、旧密钥版本占比、轮换 backlog、TLS/证书故障和审计完整性；KMS 故障、密钥吊销、迁移中断时按数据等级定义 fail-closed 或受控降级，绝不自动回退明文。

## 3 分钟版

### 1. 先定威胁模型和数据契约

先问：

```text
data_class          = P0/P1/P2...
decrypt_principals  = 哪些服务/角色能解密
query_requirement   = 只读 / 等值查询 / 排序 / 模糊搜索
retention           = 保存多久
transport_boundary  = 外部、跨机房、服务间
crypto_profile      = 国际标准 / 商用密码 / 其他监管配置
availability_target = 加解密和 KMS 的 SLO
```

这一步很重要，因为“加密身份证号”和“需要对手机号做等值检索”不是同一个契约。不能先选算法，再逼所有业务适配。

### 2. 控制面：KMS/HSM + Policy

控制面维护：

```text
key_id
key_version
key_purpose
tenant/domain
algorithm_profile
state: pre-active / active / disabled / revoked / retired
allowed_callers
created_at / rotation metadata
```

业务服务不持有长期 KEK/主密钥。典型 envelope encryption 路径是：

```text
            KMS / HSM boundary
                │  wrap / unwrap
                ▼
             DEK (data key)
                │
                ▼
plaintext -> AEAD encrypt -> ciphertext envelope
```

密文 envelope 至少要有版本信息：

```json
{
  "format_version": 3,
  "profile": "storage-aead-v3",
  "key_id": "customer-pii",
  "key_version": 17,
  "nonce": "...",
  "ciphertext": "...",
  "tag": "..."
}
```

如果业务需要把 tenant、字段名、记录主键等上下文绑定到密文，可把稳定上下文作为 AAD，使密文不能被无声搬到另一个语义位置；具体 AAD 内容必须保持可重建，否则会把自己锁死。

### 3. 存储路径：认证加密，不自己发明密码协议

敏感字段/对象默认使用经批准的 authenticated encryption profile，例如部署环境允许的 GCM 类 AEAD 配置。profile 必须统一约束：

- 算法与模式；
- nonce/IV 生成与唯一性策略；
- tag 长度；
- AAD 规则；
- DEK 类型与层级；
- 最大单次数据量；
- 密文 envelope 格式；
- 允许的解密旧版本范围。

算法参数不能写死成“永远正确”。NIST 的 GCM 指南正在修订，所以平台要通过 profile/version 让参数可以演进，而不是把密码细节散到几百个业务服务里。

### 4. 查询和脱敏：不要把三个问题混在一起

**加密**解决机密性/完整性，**脱敏**解决展示暴露，**可搜索性**是另外一个数据访问问题。

例如手机号：

- 页面只显示 `138****1234`：这是展示脱敏；
- 数据库落盘保护：这是加密；
- 还要按完整手机号等值查：需要额外设计受控索引/token，而不能因为“要查询”就把原字段明文留一份。

如果提出 deterministic encryption、tokenization、FPE 或 searchable encryption，必须重新确认泄露面、查询能力和合规要求；不能把它们当普通 AEAD 的无成本替代。

### 5. 传输路径：TLS 1.3 + 身份与授权

当前 TLS 1.3 规范是 RFC 9846；新 TLS 协议设计应以 TLS 1.3 为基线。

链路可以是：

```text
client
  -- TLS 1.3 -->
API / crypto gateway
  -- TLS 1.3 + service identity -->
business service / storage adapter
```

TLS 只保护链路。若网关解密后把明文经未保护内部网络发送，系统仍有明文暴露边界。因此要明确：

- TLS 在哪里终止；
- 哪个进程允许看到明文；
- 服务身份如何认证；
- 哪个 caller 可用哪个 `key_id` 解密哪个数据域；
- 明文是否会进入 MQ、日志、trace、dump 或缓存。

### 6. 加解密网关 vs SDK/Sidecar

**中央 crypto gateway**：

优点：
- 统一鉴权、策略、审计和算法迁移；
- 业务接入成本低；
- 能隐藏 KMS/HSM 细节。

代价：
- 成为高价值攻击面和容量瓶颈；
- 明文可能集中经过网关；
- 网络调用增加时延和故障面。

**SDK/sidecar**：

优点：
- 数据路径短，明文不必经过中央网关；
- 容量随业务实例水平扩展。

代价：
- 版本治理、策略一致性和密钥权限更难管理；
- SDK bug 的爆炸半径可能很大。

我的默认做法是：**策略与密钥控制面集中，数据面可根据数据等级选择 gateway/sidecar/SDK**，而不是强制所有数据都经过一个中心进程。

### 7. 商用密码 / 国密 profile

来源明确提到“国密算法”。平台应把它设计成 policy profile，例如：

```text
profile = cn-commercial-crypto-<version>
```

该 profile 决定允许的算法、证书/密钥类型、组件和测评要求。GB/T 39786-2021覆盖网络和通信安全、应用和数据安全等密码应用要求；SM2/SM4国家标准定义相应算法基础/原语。

这里不能把“支持 SM2/SM4”直接等同于“系统已合规”。真正上线前仍要根据目标系统等级、监管范围和当前密码应用安全性评估要求冻结具体 profile，并使用合规实现/设备。

### 8. 轮换与迁移

正常轮换不要停机全量改库：

```text
T0: key v17 active
T1: create/activate v18
T2: new writes -> v18
T3: reads accept v17 + v18
T4: background re-encrypt v17 -> v18
T5: reconciliation proves old-version population reaches policy threshold
T6: retire/disable v17
```

这样密文自带 `key_version`，迁移可恢复、可统计。

紧急泄露时不同：可能要立即 disable/revoke 某版本并触发高优先级 re-encryption。是否允许旧数据继续解密必须按事件响应策略决定，不能和普通轮换混为一谈。

### 9. 故障与灾备

关键故障至少包括：

- KMS/HSM 不可用；
- key disabled/revoked；
- crypto gateway 过载；
- ciphertext/profile 元数据损坏；
- 轮换跑到一半；
- TLS 证书/握手失败；
- KMS 主区故障或灾备切换；
- 业务误用错误 `key_id/tenant`。

原则：

- 高敏感写入默认 **fail closed**，不能 KMS 不通就写明文；
- 是否允许短期缓存已解包 DEK 是安全与可用性权衡，必须限定内存边界、TTL、权限和数据等级，不能默认无限缓存；
- 灾备必须同时恢复“密文数据 + 可用的正确密钥版本/元数据”；只备份数据库、不验证密钥恢复，等于不可恢复；
- 后台 re-encryption 必须幂等、可断点续跑，旧/新 envelope 都可识别。

### 10. 容量与观测

不要声称“一台 HSM/KMS 能扛多少”。用实测公式：

```text
required_crypto_workers
  = ceil(target_encrypt_decrypt_ops / measured_safe_ops_per_worker)

required_kms_capacity
  = ceil(target_unwrap_or_key_ops / measured_safe_key_ops_per_unit)
```

并且区分：

- 业务 encrypt/decrypt OPS；
- KMS unwrap/sign/key-management OPS；
- key cache hit ratio；
- payload size；
- gateway/SDK CPU 成本；
- P50/P99/P999 latency；
- TLS handshake 与连接复用；
- HSM/KMS throttling；
- 轮换迁移吞吐。

监控至少包括：加/解密成功率和延迟、授权拒绝、KMS/HSM 饱和度、key-version 使用分布、旧版本 backlog、轮换失败、TLS/证书失败、审计事件缺口和明文泄露检测告警。日志和 trace 只能记录 `request_id/key_id/version/result` 等必要元数据，禁止记录原始明文和密钥材料。

## 关键细节

- **当前 TLS 1.3 规范要看 RFC 9846**：它已经取代 RFC 8446；新协议使用 TLS 时应要求 TLS 1.3。
- **TLS 不等于静态加密**：链路安全和数据库/对象存储密文是两层不同控制。
- **KMS 不是一个“存 key 的 Map”**：授权、状态、版本、轮换、吊销、恢复和审计都是控制面。
- **主密钥与数据密钥分层**：业务数据不应直接绑定一个不可轮换的全局主密钥。
- **密文格式必须版本化**：没有 `profile/key_version`，后续算法迁移和密钥轮换会非常痛苦。
- **认证加密优先**：只做 confidentiality 而不检测密文篡改，会留下完整性空洞。
- **nonce/IV 是协议的一部分**：不能让每个业务随意生成、复用或截断。
- **AAD 要稳定可重建**：它适合绑定上下文，但不能绑定未来无法恢复的临时字段。
- **脱敏不是加密替代品**：展示掩码不能证明数据库泄露后数据仍受保护。
- **可查询性不是免费功能**：等值/范围/模糊查询会改变泄露模型和索引设计。
- **加解密网关也是攻击面**：集中治理换来集中风险，必须限权、限流、隔离和审计。
- **轮换与吊销不同**：正常轮换允许迁移窗口；泄露后的吊销可能要求立即阻止旧 key 使用。
- **灾备必须验证密钥恢复**：只有密文没有密钥，数据同样不可用。
- **不要自动回退明文**：密码依赖故障时的“临时兼容”往往会变成永久安全洞。

## 原理机制

这个平台可以抽象成两个状态机。

**数据状态机：**

```text
plaintext
   ↓ encrypt(profile, key_version, context)
ciphertext-envelope(vN)
   ↓ rotate/re-encrypt
ciphertext-envelope(vN+1)
```

**密钥状态机：**

```text
created -> active -> rotating -> retired
                   \-> disabled/revoked
```

正确性依赖几个不变量：

1. 业务数据能从 envelope 唯一确定解密所需的 profile 和 key version；
2. caller 只有在身份、数据域、用途都满足策略时才能调用对应 key；
3. 长期上层密钥不离开受控 KMS/HSM 边界；
4. 新 profile 上线不会让旧密文瞬间不可读，旧 profile 退出前有可验证迁移；
5. 任何密码组件故障都不会悄悄把保护级别降成明文；
6. 传输链路和存储链路分别有保护，不能依赖其中一层替代另一层；
7. 审计能够回答“谁、何时、以哪个 key/version、对哪个数据域做了什么密码操作”，但审计本身不记录秘密。

只要这些不变量成立，算法、KMS供应商、gateway/SDK形态可以演进；如果不成立，即使算法本身很强，也可能因为密钥泄露、明文边界或轮换失败而失去系统级安全性。

## 项目经验版

来源没有给真实系统的 QPS、敏感字段数量、数据量、KMS/HSM 品牌、监管等级、轮换周期或故障数据，所以不能虚构“线上就是每 90 天轮换”“我们有几台 HSM”。

真实落地时，我会先做一份 crypto inventory：

- 哪些表/字段/对象属于哪个 data class；
- 哪些服务现在能看到明文；
- 哪些链路仍低于目标 TLS profile；
- 哪些数据需要等值/范围/模糊查询；
- 当前密钥放在哪里、谁能取；
- 密文是否有版本字段；
- 轮换一次要重加密多少数据；
- KMS/HSM/Gateway 的实测吞吐和 P99；
- 灾备站是否真的能恢复 key + metadata；
- 日志、trace、MQ、缓存里是否有敏感明文副本。

上线采用分阶段迁移：

```text
inventory
 -> shadow encrypt / decrypt verification
 -> small-tenant canary
 -> dual-read old/new envelope
 -> new writes switch profile
 -> background re-encryption
 -> reconciliation
 -> retire old profile
```

回滚应回到“仍受支持的前一版密文 profile”，而不是回滚到明文。

## 常见追问

- 问：为什么不能直接用数据库 TDE 就结束？
  答：TDE 主要保护数据库存储介质层，不能替代字段级授权、业务服务看到明文的边界、跨系统传输和细粒度密钥生命周期。是否需要字段级加密取决于威胁模型，TDE 可以是其中一层而不是全部。

- 问：DEK 和 KEK 为什么要分层？
  答：分层让大量数据加密操作与长期上层密钥隔离，业务密文只绑定可轮换的数据密钥/包装信息；上层密钥留在更严格的 KMS/HSM 权限边界，轮换和权限控制更集中。

- 问：加密后还要按手机号查询怎么办？
  答：先确认只需等值还是还要范围/模糊查询。通常需要额外的受控 token/index 设计；它会泄露不同程度的相等性或模式信息，必须单独评审，不能把明文索引偷偷保留下来。

- 问：为什么网关后还要 TLS？
  答：TLS 在终止点之后不再自动保护明文。若内部链路仍跨进程/主机/网络，应该继续建立服务身份和传输保护，不能把“内网”当成密码边界。

- 问：KMS 挂了是不是整个系统都不可用？
  答：取决于数据等级和数据面设计。高敏感写入应优先 fail closed；可用性可通过高可用 KMS/HSM、合理的短期数据密钥缓存和连接复用提高，但不能以无限缓存密钥或回退明文换可用性。

- 问：密钥轮换时是不是要一次性全库重加密？
  答：不必。密文带 `key_version/profile` 后，可以新写切新版本、读路径兼容旧版本、后台渐进 re-encrypt，最后对账并退出旧版本；紧急吊销才需要更激进的策略。

- 问：支持 SM2/SM4 就等于国密合规了吗？
  答：不等于。算法只是基础。GB/T 39786-2021还覆盖通信、应用和数据等密码应用要求，最终还要按目标系统当前监管和测评 profile 确认算法组合、组件、密钥管理和实施要求。

- 问：怎么防止开发把明文打进日志？
  答：平台 API 默认只记录 request/key/profile/result 元数据，日志 SDK 做字段分类和拦截，trace/MQ/cache 同样纳入敏感数据 inventory；测试和上线门禁要有 secret/PII 泄露扫描与采样核查。

- 问：怎么证明平台真的安全可用？
  答：除了密码算法本身的合规实现，还要做权限越权测试、nonce/profile错误测试、篡改密文测试、KMS/HSM故障、证书失败、网关过载、轮换中断、灾备恢复和旧版本对账，并用目标负载证明加解密与密钥操作的 P99/SLO。

## 易错点

- 只说“HTTPS + AES”就认为存储和传输都解决了。
- 把已经被 RFC 9846 取代的 RFC 8446 当作当前 TLS 1.3 规范。
- 把主密钥直接配置在业务服务、环境变量、数据库或日志里。
- 自己拼“加密 + hash/MAC”协议，却没有版本化、nonce、tag 和错误处理规范。
- 只做保密不做完整性保护，却称为“安全密文存储”。
- 每个业务自己决定 nonce/IV、算法、key 格式，导致不可统一迁移。
- 认为“数据脱敏”可以替代数据库静态加密。
- 为了支持查询偷偷保留一份明文索引。
- 认为“网关解密后是内网”就可以明文传输。
- KMS/HSM 故障时自动降级为明文写入。
- 正常 key rotation 和安全事件后的 key revocation 使用同一策略。
- 只备份密文数据库，不演练密钥和 key metadata 恢复。
- 把“支持 SM2/SM4”直接写成“所有中国业务都已经合规”。
- 用某个厂商 benchmark 或虚构生产节点数证明密码平台容量。
