# == 和 equals 的区别

## 核心结论

`==` 是 Java 运算符：用于基本类型时比较数值/布尔值，用于引用时比较两个引用是否指向同一对象；`equals` 是实例方法，比较规则由运行时类实现，`Object.equals` 默认与引用相同，但值对象可重写为逻辑相等。选哪个取决于要比较“同一对象”还是“业务值是否相等”。

## 1 分钟版

- 基本类型：用 `==` 比较值；没有对基本类型直接调用实例 `equals` 的语法。
- 引用：`a == b` 检查是否同一对象或同为 `null`；内容相同的两个对象也可能为 `false`。
- `equals`：`Object` 默认实现相当于引用相等；如 `String` 等类可重写为按内容比较。
- 空值：`a.equals(b)` 在 `a` 为 `null` 时抛异常；已知常量可写成 `"x".equals(a)`，或使用 `Objects.equals(a,b)`。

## 3 分钟版

JLS 将 `==` 分成数值、布尔和引用相等运算。基本类型的 `==` 按相应值比较；引用 `==` 为 true 的条件是两个操作数都为 `null`，或都指向同一个对象/数组。它不调用对象的 `equals`，所以不能用它泛化判断两个独立值对象的业务内容相等。

`equals` 是动态分派的方法调用。`Object.equals` 的默认契约是最具区分性的等价关系，默认实现与 `==` 相同；子类可重写并必须满足自反、对称、传递、一致以及对 `null` 返回 false 的契约。因而回答时应先说实际类型：`String` 的 `equals` 按字符序列，而没有重写的普通对象仍是引用比较。

选择规则很简单：判断是否同一个实例、做单例/哨兵引用判断时用 `==`；判断领域值是否相等时调用语义正确的 `equals`。若对象作为哈希集合或映射的键使用，重写 `equals` 时还必须重写 `hashCode`；`Object` 的契约要求相等对象具有相同哈希码。

## 关键细节

- 浮点 `NaN` 是反例：JLS 指出任何 `NaN == NaN` 都是 false；不要把 `==` 简化为所有“数值相等”直觉。
- 包装类型比较要先区分是否发生自动拆箱；比较业务值应优先使用 `equals`/`Objects.equals`，不要依赖引用相同。
- `equals` 不是天然“内容比较”：若类没有重写，它继承 `Object.equals`，语义仍是引用相等。
- 需要双向比较未知可空对象时用 `Objects.equals(a,b)`；不要靠捕获空指针异常处理相等性。

## 原理机制

`==` 在表达式求值时按操作数类型选择数值、布尔或引用相等规则；引用规则只关心同一引用。`equals` 是虚方法调用，先由接收者实际类决定实现，再执行该类定义的等价关系。值对象通过重写把“相同业务字段”映射为 true；若类声明相等对象，`hashCode` 也必须遵守相同哈希码契约。

## 项目经验版

项目映射提示：用真实领域对象说明哪些字段定义身份、哪些字段不参与相等性，给出 `equals/hashCode` 的测试用例和 HashMap/HashSet 行为。没有这些事实时，不要编造某次缓存命中或去重事故。

## 常见追问

- 问：两个 `new String("x")` 用 `==` 与 `equals` 的结果？答：通常不是同一对象所以 `==` 为 false；String 重写了 equals，字符相同则为 true。
- 问：为什么重写 equals 必须重写 hashCode？答：`Object` 契约要求两个相等对象返回相同 hashCode；因此重写值相等规则时必须同步重写 hashCode。
- 问：`null == null` 和 `null.equals(x)`？答：前者为 true；后者没有接收者可调用，会抛 NullPointerException。
- 问：`Double.NaN == Double.NaN` 为什么不是 true？答：JLS 为浮点 NaN 定义了特殊相等规则，任何 `==` 比较 NaN 均为 false。

## 易错点

- 不要把 `==` 一律说成比较地址；基本类型走数值/布尔相等规则。
- 不要把 `equals` 一律说成内容比较；它取决于运行时类是否及如何重写。
- 不要用 `==` 判断两个包装类型的业务值，相同引用只是实现和上下文结果，不是值语义。
- 不要重写 equals 后遗漏 hashCode，或破坏对称/传递契约。
