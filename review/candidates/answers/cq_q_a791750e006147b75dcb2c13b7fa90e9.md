# 两个上亿 URL 文件如何找出重复 URL？

## 核心结论

原始面试笔记只保留了“两个包含上亿 URL（最长 64 byte）的文件中找出重复 URL”。它没有保存内存大小、文件具体字节数、URL 是否已规范化、是否要求保留重复次数，也没有要求必须使用布隆过滤器或哈希切分。一个可扩展且结果精确的方案是：使用同一个确定性哈希把两个文件分别切成相同编号的磁盘分区，使相同 URL 必然进入同一对分区；随后逐对分区做**原始 URL 的精确相等比较**求交集。哈希只负责路由，不直接决定“相等”，因此哈希碰撞不会产生错误结果。

## 1 分钟版

- 先确认“重复”的语义。这里采用最小假设：每行一条 URL，按原始字节/字符串精确相等判断，最终输出两个文件之间的去重交集；如果题目要求 URL 规范化或重复次数，契约要另外定义。
- 若数据能够放入内存，最简单的是把较小文件放进精确 `HashSet`，扫描另一个文件求交集。
- 若内存放不下，选同一个稳定哈希 `h(url)` 和同一个分区数 `K`，把文件 A、B 都按 `h(url) mod K` 写入 `A_i`、`B_i`。相同 URL 的哈希值相同，所以一定进入同一个编号的分区。
- 对每个 `i`，把较小的 `A_i`/`B_i` 放入精确集合，再扫描另一侧并做字符串相等判断；输出使用集合去重。某个桶仍过大时继续增加 `K`、递归再分区，或对该桶做外排序归并。
- 布隆过滤器可以作为可选的前置筛选来减少明显不可能命中的项，但它有假阳性，因此不能单独作为“两个文件存在相同 URL”的最终精确判定。

## 3 分钟版

先把来源事实和设计假设分开。来源明确的是：有两个文件、URL 数量达到上亿级、单条 URL 最长 64 byte、目标是找出重复 URL。来源没有给机器内存和磁盘预算，所以不能直接声称“全部放内存”或固定切成多少桶；`K` 应根据实际文件字节数、可用内存和哈希集合开销测量后选择。来源也没有说明同一 URL 在单个文件中出现多次时是否要输出多次，下面把目标定义为“两个文件的唯一交集”。

可扩展方案分两阶段。

第一阶段是外部分区。对两个文件使用完全相同的确定性哈希函数和分区数 `K`：

```text
bucket = h(url) mod K
A 中的 URL -> A_bucket
B 中的 URL -> B_bucket
```

核心不变量是：如果 `u` 在 A 和 B 中完全相同，则两边计算出的 `h(u)` 必然相同，因此 `u` 必然同时落到 `A_i` 与 `B_i`。所以后续只需要比较同编号的分区，不需要做全文件两两比较。哈希函数发生碰撞只会让不同 URL 落到同一个桶，不会让它们被判成相同，因为第二阶段仍然比较完整 URL。

第二阶段逐桶精确求交。对于每一对 `(A_i, B_i)`，优先把字节更小的一侧读入精确哈希集合，扫描另一侧；只有 `set.contains(fullUrl)` 成立时才输出。为了让同一 URL 在文件内部重复出现时不重复输出，可以让最终结果也是集合，或在桶内命中后记录已输出状态。如果某个分区因数据倾斜仍超过内存，不要改变正确性契约，可以对该分区再次使用另一个盐/更多位递归切分，或者对这两个桶进行外排序后用双指针归并求交。

这个方案的关键是“哈希负责定位，完整值负责确认”。因此不需要依赖“哈希无碰撞”这种不现实假设。磁盘 I/O 大致是一次顺序读输入并写分区，再顺序读各分区；实际临时空间、打开文件数、缓冲区大小和分区数需要按机器资源测量。64 byte 的上界可以用于容量估算，但文件还可能包含换行、编码以及哈希集合对象/索引开销，不能简单用 `数量 × 64` 当作真实内存占用。

如果面试官继续问布隆过滤器，可以把它定位为优化而不是正确性基础。例如先对 A 建布隆过滤器，扫描 B 时把“确定不存在”的 URL 丢掉，只把“可能存在”的候选送入后续精确集合/分区比较。这样可以减少部分写盘或查找，但“可能存在”不能直接输出，因为假阳性会把并不存在于 A 的 URL 留下来。最终仍需要精确比较或权威集合确认。

## 关键细节

- **相等语义**：这里按完整 URL 字符串精确相等。大小写、默认端口、尾斜杠、百分号编码、查询参数顺序是否规范化都不是原始来源事实；若业务要求语义等价，应先定义 canonicalization，再把规范化结果作为比较键。
- **分区数 K**：不是题目给定常量。目标是让单个桶在最坏/高分位情况下能被当前内存处理，并为哈希集合额外开销留余量；遇到倾斜要继续切分，而不是假设均匀分布。
- **哈希碰撞**：只影响哪些不同 URL 共处一个桶，不影响最终精确相等判断。不要把 64 位哈希值本身当成 URL 身份。
- **文件内重复**：如果只求集合交集，桶内集合和最终输出都去重；如果题目要求多重集交集，需要改成计数映射并输出 `min(countA, countB)` 次。
- **异常与恢复**：分区文件最好写入临时目录并记录批次/分区元数据；失败重跑时清理或使用新的批次目录，避免把旧分区混入新结果。
- **并行化**：不同桶可以独立处理，但并发度受磁盘吞吐和内存约束；不能为了 CPU 并行把多个大桶同时装入内存导致抖动。

## 原理机制

把完整数据集拆成分区，本质上是在利用等价元素具有相同路由结果这个不变量。设路由函数 `p(u)=h(u) mod K`。对于任意完全相同的 URL `u`，A 中的 `u` 与 B 中的 `u` 都满足相同的 `p(u)`，因此全局交集可以拆成各编号桶交集的并集：

```text
A ∩ B = union_i (A_i ∩ B_i)
```

这里每个 `A_i ∩ B_i` 使用完整字符串相等判断，所以即使存在 `x != y` 但 `p(x)=p(y)`，也只会增加同桶比较量，不改变结果。这个性质使方案能够在内存不足时通过磁盘顺序分区把一个全局问题拆成多个可控的小问题。

## 项目经验版

来源没有真实机器配置、文件大小、URL 分布或线上指标，因此不虚构生产数据。实际落地时我会先采样测量：总字节数、URL 长度分布、重复率、哈希桶大小分布、可用内存和磁盘顺序吞吐；据此选择 `K` 和单任务并发度。正式跑批前用已知交集的小样本验证“同 URL 同桶、碰撞不误报、文件内重复不重复输出、倾斜桶可再次切分”，再对全量任务记录每桶记录数/字节数、最大桶、处理耗时、临时磁盘峰值和最终交集计数，便于发现数据倾斜或漏分区。

## 常见追问

- 问：为什么不能只保存 URL 的哈希值然后比较？答：有限位数哈希存在碰撞可能。哈希值适合路由和加速，最终精确结果应比较完整 URL，或者使用能证明满足题目错误概率要求的显式概率契约；原题没有给这种概率容忍度。
- 问：如果一个桶还是放不进内存怎么办？答：对该桶递归再分区，或对两个桶外排序后归并求交；正确性不依赖“第一次分桶一定均匀”。
- 问：布隆过滤器能直接找出重复 URL 吗？答：不能作为精确最终判定。它可以快速判定“肯定不在集合中”，但“可能在”包含假阳性，仍需完整值确认。
- 问：为什么最长 64 byte 有用？答：它提供单条原始 URL 的大小上界，能辅助估算输入和分区规模；但哈希表、字符串对象、换行和实现元数据都会增加实际内存，所以仍要实测。
- 问：两个文件各自有重复 URL 怎么办？答：若目标是唯一交集，集合化后每个 URL 只输出一次；若要求出现次数，则维护计数并明确多重集语义。

## 易错点

- 把规范化后的题目括号中的“布隆过滤器/哈希切分”误当成原始笔记明确要求的方法。
- 只比较哈希值，不比较完整 URL，把碰撞变成错误答案。
- 固定写死分区数，却不检查最大桶和数据倾斜。
- 忽略文件内重复，导致相同 URL 被重复输出。
- 把布隆过滤器“可能存在”当成“确定存在”。
- 用 `URL 数量 × 64 byte` 直接声称内存一定够，忽略字符串/哈希集合和运行时开销。
