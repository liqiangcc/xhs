# 协程与线程的区别及适用场景

## 核心结论

在 Kotlin/JVM 语境中，协程是可挂起、可恢复的并发计算，最终仍运行在操作系统管理的线程上；线程则是操作系统调度的执行资源。协程在等待可挂起操作时可释放承载线程，让同一线程运行别的协程，因此适合大量可挂起 I/O 任务；它不等于更快的 CPU，也不替代线程、调度器、取消和背压设计。

## 1 分钟版

- 承载层：JVM 上协程仍由 OS 线程运行；dispatcher 决定协程使用哪些线程或线程池。
- 等待方式：协程可 suspend 而不阻塞线程；线程阻塞时该线程不能继续执行别的任务。
- 生命周期：普通 Kotlin 父子 Job 层级用 scope 组织成树，父协程等待子协程完成，父取消或失败会递归影响子协程；监督作用域另有失败隔离边界。
- 选型：大量网络、数据库等可挂起等待可考虑协程；CPU 密集型仍受可用 CPU 和承载线程限制，不能把“协程多”误答成“并行核数更多”。

## 3 分钟版

先限定实现：协程不是跨语言统一的“用户线程”结论。这里按 Kotlin 官方文档回答 Kotlin/JVM：协程是可 suspend 的计算，可并发执行；在 JVM 与 Kotlin/Native 上，并发代码包括协程仍运行在 OS 管理的线程上。dispatcher 决定协程使用的线程/线程池，协程可在一个线程 suspend、在同一线程让其他协程运行，也可能按 dispatcher 在另一线程恢复。

与线程统一按三个维度比较。第一，调度资源：线程是 OS 调度资源；协程依赖线程承载，不能脱离线程执行。第二，等待语义：只有实际执行到可挂起操作时，协程才让承载线程运行其他协程；外层标记为 `suspend` 不会自动改变所调 API 的行为。第三，生命周期：线程的创建、等待、取消需由应用明确管理；普通 Kotlin 父子 Job 层级借 scope 与结构化并发形成父子任务树，父任务等待子任务完成，父任务失败或取消会递归取消子任务。`supervisorScope` 则包含 `SupervisorJob`：子协程失败不影响同 scope 的其他子协程；若 block 本身以异常结束，才取消 scope 与其子协程。

选型先看工作是否真的可挂起。大量网络请求、异步数据库调用或其他提供 suspend/非阻塞接口的等待型任务，可在等待时让承载线程运行其他协程；阻塞调用不会因为外层有协程而自动变成挂起。CPU 密集任务可用协程组织并发，但实际并行度仍由 dispatcher 配置、承载线程和可用 CPU 决定；协程不会凭空增加并行硬件资源。反例是把每个阻塞 I/O 都写进协程并承诺“不会阻塞线程”，这与实际调用是否可挂起相矛盾。

## 关键细节

- Kotlin 文档定义 coroutine 为可 suspend 的计算；其可与其他协程并发，也可能并行运行。
- 在 JVM 上，协程运行在线程上；dispatcher 控制协程使用的线程或线程池，协程不总绑定到一个固定线程。
- `CoroutineScope` 管理协程生命周期；普通父子 Job 层级下父协程等待子协程，父失败或取消会递归取消子协程；`supervisorScope` 的子失败隔离规则不同。
- `runBlocking` 在新协程中原地运行 block 并阻塞当前线程直到完成；官方将它定位为把常规阻塞代码桥接到挂起风格库的工具，并提示在挂起函数中调用它会冗余地阻塞线程。

## 原理机制

典型路径是：`scope 启动协程 → dispatcher 分派到承载线程 → 执行到可挂起操作 → 协程 suspend，线程可运行其他协程 → 条件满足后 dispatcher 恢复协程 → 普通 scope 等待、完成或传播取消`。保证的核心是挂起可让线程复用、scope 可管理子任务生命周期；监督作用域把子失败隔离为不同规则。成本与边界是承载线程仍有限，实际并行由 dispatcher 与线程资源决定。故“高并发优势”来自等待期间复用线程与结构化生命周期，而不是绕开 OS 调度。

## 项目经验版

项目映射提示：写清 JVM/Kotlin 版本、dispatcher 配置、调用的是 suspend/非阻塞还是阻塞客户端、并发请求量、线程池指标、取消超时、背压和压测数据。没有这些事实时，不要虚构“协程改造后线程数或 QPS 的提升”。

## 常见追问

- 问：协程是不是不需要线程？答：不是。在 Kotlin/JVM 上它仍运行在 OS 线程上；协程解决的是等待期间如何组织与复用线程，而非取消线程这一资源层。
- 问：`suspend` 是否自动把阻塞调用变成非阻塞？答：不是。它允许挂起与恢复；底层调用是否阻塞仍取决于所用 API 和 dispatcher。
- 问：为什么要用 structured concurrency？答：普通 scope 把父子任务的完成、失败和取消联系起来；若允许子任务独立失败，使用 `supervisorScope`，并处理其失败报告。
- 问：协程适合 CPU 密集计算吗？答：可用它组织任务，但并行度仍受 CPU 和承载线程限制；不能以“协程数量大”推导 CPU 吞吐必然提升。

## 易错点

- 不要把 Kotlin 协程当作脱离 OS 线程的执行实体，或把其他语言的实现细节直接外推过来。
- 不要把 suspend 与非阻塞划等号；只有实际可挂起操作才会让线程复用。
- 不要忽略 scope、取消和 dispatcher，只谈“轻量”；普通 Job 的失败传播与 `supervisorScope` 的子失败隔离不是同一规则。
- 不要将 I/O 等待型优势外推为 CPU 密集任务的无条件性能优势。
