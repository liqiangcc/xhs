# 和大于等于目标值的最短连续子数组

## 核心结论

这题能不能直接用滑动窗口，关键不在“连续子数组”四个字，而在**窗口和是否具有单调性**。两份原始面经只保留“和大于等于目标值的最短连续子数组”，没有给元素正负、`target` 范围或返回约定；其中一条结构化标题带了“滑动窗口”，但原始笔记没有这个提示，因此不能把“所有输入都能滑窗”当成来源事实。下面给一个明确的可执行参考契约：`target > 0`，数组元素都为正整数，返回和至少为 `target` 的最短非空连续子数组长度；不存在时返回 0。这个契约下可以 O(n) 滑窗；若允许负数，普通滑窗不再成立，应改用前缀和 + 单调队列等方案。

## 1 分钟版

- 先确认输入约束：只有在窗口右扩时和不下降、左缩时和不增加，滑动窗口才有单调性；正数或非负数满足这个条件。
- 维护窗口 `[left, right]` 和 `sum`，右指针每次加入一个元素。
- 当 `sum >= target` 时，当前窗口已经可行；先更新最短长度，再不断右移 `left`，直到窗口重新不满足条件。
- 因为每个元素最多被右指针加入一次、被左指针移出一次，所以时间 O(n)，除几个变量外空间 O(1)。
- 若数组允许负数，缩左端可能反而让和变大，普通滑窗失去正确性；此时应切换到前缀和 + 单调队列，并重新定义边界契约。

## 3 分钟版

先把缺失条件说清楚。这里采用参考契约：`target > 0`；`nums` 非 `null`，允许空数组；每个元素必须 `> 0`；答案是满足 `sum >= target` 的最短非空连续子数组长度，没有解返回 0。为了避免大量正整数累加时 `int` 回绕，窗口和使用 `long`。

```java
public final class MinSubarrayLen {
    public static int minLengthAtLeast(int target, int[] nums) {
        if (target <= 0) {
            throw new IllegalArgumentException("target must be positive");
        }
        if (nums == null) {
            throw new IllegalArgumentException("nums must not be null");
        }

        int left = 0;
        int best = Integer.MAX_VALUE;
        long sum = 0L;

        for (int right = 0; right < nums.length; right++) {
            int value = nums[right];
            if (value <= 0) {
                throw new IllegalArgumentException("all elements must be positive");
            }
            sum += value;

            while (sum >= target) {
                best = Math.min(best, right - left + 1);
                sum -= nums[left++];
            }
        }

        return best == Integer.MAX_VALUE ? 0 : best;
    }
}
```

为什么 `while` 收缩是安全的？在正数契约下，固定 `right` 时，把 `left` 右移只会让窗口和严格下降。因此只要当前窗口仍满足 `sum >= target`，继续缩左端就一定是在寻找“同一个右端下更短的可行窗口”；一旦低于目标，再缩只会更小，没有必要。右端继续前进后再重复这个过程，就覆盖了每个右端对应的最短可行窗口。

例如 `target=7, nums=[2,3,1,2,4,3]`：右端扩到 `4` 后窗口和达到 12，连续收缩得到 `[4,3]`，长度 2；后续不可能得到长度 1，因为没有单个元素达到 7，所以答案是 2。

## 关键细节

- **来源边界**：两份原始笔记都没有保存“元素一定为正”或具体 API；“滑动窗口”只出现在结构化标题中。本答案把正数条件明确标成参考契约，而不是原题事实。
- **为什么正数重要**：右扩只增大 `sum`、左缩只减小 `sum`，这给了双指针单调前进的正确性基础。允许负数后，这个性质会消失。
- **更新时机**：求“最短”要在 `sum >= target` 时边更新边收缩，不能只在刚达到条件时更新一次。
- **无解**：使用 `Integer.MAX_VALUE` 作为内部哨兵，最终转换为 0；“0 表示无解”是参考契约选择，不是来源明确要求。
- **空数组**：循环不进入，返回 0；`null` 则 fail-fast 抛异常，避免和空数组混为一谈。
- **溢出**：窗口和使用 `long`，避免多个正 `int` 累加时先发生 32 位整数回绕。
- **零元素**：非负数组其实仍可使用普通滑窗，但本参考实现选择严格正数并对 0 报错，让实现契约与证明保持简单；若题目允许 0，可以放宽检查为 `value < 0`。
- **复杂度**：虽然代码有嵌套 `while`，但 `left/right` 都只单调向右，每个元素最多进出窗口一次，所以总时间 O(n)，不是 O(n²)。

## 原理机制

设窗口状态为 `(left, right, sum)`。正数契约给出两个单调关系：右移 `right` 加入新元素时 `sum` 增大；右移 `left` 移除旧元素时 `sum` 减小。算法在每个 `right` 上维持这样一个过程：先扩张到当前窗口，再在可行时尽可能收缩左边界。收缩结束后，要么没有可行窗口，要么刚刚记录过以该 `right` 结尾的最短可行窗口。

两个指针都不会回退，所以总移动次数至多线性级别。这个证明依赖“移除左端不会让和变大”；如果数组含负数，例如窗口左端是 `-5`，移除它会让窗口和增加，算法就可能跳过更短解，因此必须换方法。

允许负数时，一个常见 O(n) 变体是构造前缀和 `prefix[i]`，把问题转成寻找最小 `j-i` 使 `prefix[j]-prefix[i] >= target`；再用单调队列维护可能成为最优左端的前缀下标。这里不展开第二份完整实现，因为原始来源没有保存负数约束，但面试时应明确指出这不是同一个滑窗证明。

## 项目经验版

来源没有真实项目背景，不能虚构线上使用经历。项目映射时，这类“最短满足阈值的连续区间”可以对应流量窗口、连续批次容量或时间序列阈值扫描，但必须先确认数据是否具备单调性。真正决定能否用双指针的不是业务名词，而是“加入/移除元素后约束如何变化”；如果数据可为负、可回撤或权重会动态修改，就应重新选算法并用边界样例验证。

## 常见追问

- 问：为什么这个滑窗不是 O(n²)？答：内层 `while` 的总次数受 `left` 单调前进限制；整个执行过程中 `left` 最多从 0 走到 n，所以两个指针总移动 O(n)。
- 问：数组里有 0 还能用吗？答：可以，非负数仍保持窗口和单调不减/不增；当前代码只是为了明确参考契约而拒绝 0，放宽为非负时修改输入检查即可。
- 问：数组里有负数为什么不行？答：移除负数会让窗口和变大，当前“可行就持续收缩、不可行就等右端扩张”的单调推理被破坏，可能漏解。
- 问：如果允许负数怎么办？答：可用前缀和 + 单调队列，把目标改写成 `prefix[j]-prefix[i] >= target`，在线维护最有希望的左端下标，典型复杂度 O(n)。
- 问：为什么用 `long sum`？答：元素是 `int` 时，多项累加可能超出 32 位范围；使用 `long` 避免窗口判断因为整数回绕而失真。

## 易错点

- 没确认元素符号就直接套普通滑动窗口。
- 求最短时只更新一次，没有在 `sum >= target` 的循环里持续收缩左端。
- 看到双层循环就误判为 O(n²)，没有按指针总移动次数做摊还分析。
- 用 `int sum` 处理大值数组，窗口和回绕后导致错误比较。
- 把“0 表示无解”“正数数组”“`target > 0`”这些参考实现选择说成原题已经给出的条件。
- 负数场景仍强行复用同一滑窗不变量，而没有切换到前缀和等正确模型。
