# SQL：计算购买量排名前 25% 的用户

## 核心结论

来源要求在订单或行为表中找出“购买量排名在前 25% 的用户”，并明确提示可使用 `PERCENT_RANK()` 或 `NTILE(4)`；但没有给真实表结构，也没有定义“购买量”是订单数、件数还是金额。这里采用一个最小可执行契约：`purchase_events(user_id, quantity)` 每行是一条购买记录，`quantity` 是本次购买件数；先按用户汇总 `SUM(quantity)`，再按汇总购买量降序计算 `PERCENT_RANK()`，取 `pct_rank <= 0.25` 的用户。

## 1 分钟版

- 第一步先把明细表聚合到“每个用户一行”，否则窗口函数排的是订单/行为记录，不是用户。
- 这里把购买量定义为 `SUM(quantity)`；如果真实题目定义为购买次数或金额，只替换聚合指标，排名框架不变。
- 对用户购买量降序做 `PERCENT_RANK()`，排名越靠前值越接近 0。
- 过滤 `pct_rank <= 0.25` 得到处于前 25% 排名区间的用户；并列用户共享相同 rank，因此可能返回超过严格 25% 的人数。
- 如果业务要求把用户机械切成四个大小尽量接近的桶，可以改用 `NTILE(4)` 并取第 1 桶，但它可能把并列购买量拆到不同桶。

## 3 分钟版

```sql
WITH user_purchase AS (
    SELECT
        user_id,
        SUM(quantity) AS purchase_qty
    FROM purchase_events
    GROUP BY user_id
),
ranked AS (
    SELECT
        user_id,
        purchase_qty,
        PERCENT_RANK() OVER (
            ORDER BY purchase_qty DESC
        ) AS pct_rank
    FROM user_purchase
)
SELECT
    user_id,
    purchase_qty
FROM ranked
WHERE pct_rank <= 0.25;
```

例如 8 个用户的购买量依次为 100、90、80、70、60、50、40、30，`PERCENT_RANK()` 的前两名分别是 0 和约 0.143，第三名约 0.286，因此结果是前两名。若前两名同为 100，它们会共享 rank 1 和 `pct_rank = 0`，都进入结果；这正体现了 percentile-rank 方案对并列的语义。

## 关键细节

- **先聚合再排名**：题目要的是用户排名。若直接在明细上开窗口，一个下单多次的用户会出现多行，结果粒度错误。
- **购买量定义**：来源只说“购买量”。本候选显式选择 `SUM(quantity)`；若一行就是一次购买且没有数量列，可以改用 `COUNT(*)`。
- **排序方向**：购买量越大排名越靠前，所以窗口使用 `ORDER BY purchase_qty DESC`。
- **`PERCENT_RANK` 语义**：通常基于 `(rank - 1) / (rows - 1)`，相同排序值共享 rank；因此阈值方案保留并列关系，但人数不保证恰好占 25%。
- **`NTILE(4)` 语义**：把排序后的行尽量均匀分成 4 桶，取 `bucket = 1`。它更接近“取四分之一行数”，但当人数不能被 4 整除时桶大小不同，而且并列值可能跨桶。
- **小样本**：只有 1 个用户时 `PERCENT_RANK()` 为 0，该用户会被选中；这比强行要求至少四人才有“前 25%”更符合排名函数本身的定义。
- **排序输出**：来源没有要求最终展示顺序；如需按购买量降序展示，应在最外层显式 `ORDER BY purchase_qty DESC`。

## 原理机制

这道题有两个不同层次的粒度转换。第一层通过 `GROUP BY user_id` 把明细购买记录收缩成用户级指标；第二层窗口函数在“用户集合”上计算相对排名，但不会再次改变行数。最后 `WHERE pct_rank <= 0.25` 才把排名结果裁剪为目标集合。

`PERCENT_RANK` 和 `NTILE(4)` 不是完全等价的写法：前者表达“相对 rank 落在前 25% 区间”，天然保留并列 rank；后者表达“排序后分成四个近似等大的行桶”。选择哪个取决于业务到底重视并列公平还是严格控制选中人数。

## 项目经验版

来源没有真实订单 schema、购买量口径、数据规模、数据库方言或生产指标，不能虚构。实际落地时应先确认统计周期、取消/退款是否扣除、用户 ID 是否稳定、购买量是件数/次数/金额，以及并列边界如何处理，再根据目标数据库支持的窗口函数和执行计划决定实现。

## 常见追问

- 问：为什么不能直接 `NTILE(4)`？答：可以，题目也提示了它；但它按行数分桶，可能拆开并列值。若业务要求“相同购买量必须同档”，`PERCENT_RANK`/`RANK` 类方案更自然。
- 问：为什么不是 `ROW_NUMBER()`？答：`ROW_NUMBER()` 会给每行唯一序号，即使购买量相同也强行分先后；除非业务明确需要精确截取固定人数，否则会破坏并列语义。
- 问：如果购买量指订单数怎么办？答：把 `SUM(quantity)` 改成 `COUNT(*)` 或对有效订单 ID 做相应计数，后续排名逻辑不变。
- 问：如果要严格返回恰好 25% 的用户数？答：需要先定义人数取整方式和并列打破规则，再用 `ROW_NUMBER()`/`NTILE` 或计算 cutoff；不能同时保证“恰好 25%”和“所有并列都不拆分”。
- 问：为什么要用 CTE？答：主要是把“用户级聚合”和“排名”两个步骤分开，便于表达粒度；也可以写成嵌套子查询。

## 易错点

- 在订单明细上直接排名，得到的是记录排名而不是用户排名。
- 忘记降序，结果选出购买量最低的 25%。
- 把 `PERCENT_RANK <= 0.25` 说成“永远恰好返回 25% 的用户”。
- 用 `NTILE(4)` 时忽略并列值可能被分到不同桶。
- 来源没定义购买量口径，却默认成金额、订单数或件数并把它写成原题事实。
