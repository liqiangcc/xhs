# 算法：双线程交替打印奇偶数

## 核心结论

来源只保留“算法：双线程交替打印奇偶数”，没有规定数字范围、由奇数线程还是偶数线程先打印、使用哪种同步原语、异常/中断策略。下面采用一个最小可执行契约：给定非负 `maxInclusive`，两个线程共同按严格递增顺序打印 `0..maxInclusive`；偶数线程只打印偶数，奇数线程只打印奇数，因此偶数线程先打印 `0`。实现用一个共享计数器 + `synchronized` 监视器；每个线程在“轮到自己”之前用 `while` 等待，打印后递增计数器并 `notifyAll()`。如果题目要求从 `1` 开始，只需把初始计数改为 `1`，核心同步不变量不变。

## 1 分钟版

- 共享状态只有 `next`：它表示下一次应该打印的数字；`next` 的奇偶性决定当前拥有打印资格的线程。
- 两个线程都在同一个 monitor 上同步，先在 `while (next <= max && parity 不匹配)` 中 `wait()`，不能用 `if`，因为线程被唤醒后必须重新检查条件。
- 获得资格后在锁内记录/打印当前 `next`，再 `next++`，最后 `notifyAll()` 唤醒另一方重新竞争并检查条件。
- 结束时也要 `notifyAll()`：否则一个线程打印最后一个数字后退出，另一线程可能还睡在 `wait()` 里，程序无法结束。
- `next` 的读取、判断、打印、递增都在同一临界区里完成，保证不会重复、跳号或由错误线程打印。

## 3 分钟版

```java
static final class AlternatingPrinter {
    private final Object monitor = new Object();
    private final int maxInclusive;
    private int next = 0;

    AlternatingPrinter(int maxInclusive) {
        if (maxInclusive < 0) {
            throw new IllegalArgumentException("maxInclusive must be >= 0");
        }
        this.maxInclusive = maxInclusive;
    }

    void printEven() throws InterruptedException {
        printParity(0);
    }

    void printOdd() throws InterruptedException {
        printParity(1);
    }

    private void printParity(int parity) throws InterruptedException {
        while (true) {
            synchronized (monitor) {
                while (next <= maxInclusive && (next & 1) != parity) {
                    monitor.wait();
                }

                if (next > maxInclusive) {
                    monitor.notifyAll();
                    return;
                }

                System.out.println(next);
                next++;
                monitor.notifyAll();
            }
        }
    }
}
```

启动两个线程分别调用 `printEven()` 和 `printOdd()` 即可。线程的启动顺序不影响结果：即使 odd 线程先获得锁，它看到 `next == 0` 与自己的 parity 不匹配，就会等待；even 线程打印 `0` 后将 `next` 改成 `1` 并通知，资格自然交给 odd 线程。

## 关键细节

- **条件必须用 `while` 重检**：`wait()` 允许虚假唤醒，而且 `notifyAll()` 只表示“状态可能变化了”，不保证被唤醒线程此刻一定满足业务条件。把条件写成 `if` 会破坏 guard invariant。
- **打印与状态推进要原子地放在同一锁内**：如果先释放锁再打印，另一个线程可能已经推进并输出下一项，导致观察到乱序；如果递增不受同一锁保护，则可能重复或丢数字。
- **终止通知不能漏**：例如 `maxInclusive=4`，even 打印 `4` 后 `next=5`。odd 若正等待，需要一次通知才能醒来看到终止条件并退出。
- **`notifyAll()` 比 `notify()` 更稳健**：这里只有两个参与者时 `notify()` 也可能工作，但 `notifyAll()` 让所有等待者醒来后自行用 guard 判断资格，减少将来扩展/额外等待者时唤醒错误对象造成的风险。
- **中断语义**：示例把 `InterruptedException` 向上传递，不吞掉中断。如果业务要求一个线程中断时另一个线程也尽快退出，需要再定义共享取消状态并在 finally/退出路径通知等待者。
- **输出目标**：真实代码不一定应在锁内做慢 I/O。面试演示可直接打印；工程实现可把“记录下一个合法值”与真正的慢输出解耦，但如果要求全局输出顺序，就必须为下游排序/串行化建立同等强度的顺序保证。
- **从 1 开始**：把 `next` 初始值改成 `1` 后，odd 线程先有资格；同步协议本身无需重写。

## 原理机制

核心不变量是：在任意时刻，`next` 是唯一的“下一项”，只有满足 `(next & 1) == parity` 的线程可以消费它。monitor 把“检查资格 → 消费当前值 → 推进 `next`”包成一个互斥状态转换。这样状态 `k` 只能转换成 `k+1`，不能同时被两个线程消费，也不可能跳到 `k+2`。

`wait()` 做两件事：原子地释放 monitor 并把线程放入等待集合；被唤醒后，它必须重新获得同一个 monitor 才能继续。因此另一个线程可以在等待期间进入临界区、推进 `next`，然后 `notifyAll()`。条件循环不是附属写法，而是把“通知”与“获得业务资格”解耦：通知只提示重新检查，真正决定谁能打印的是共享状态本身。

对 `N = maxInclusive + 1` 个数字，状态转换发生 `N` 次，时间复杂度是 `O(N)`；除输出之外共享状态是常数级 `O(1)`。线程调度和上下文切换带来常数开销，因此这种写法主要用于同步机制演示，不适合拿两个线程做一个本可单线程顺序完成的纯打印任务来追求性能。

## 项目经验版

来源没有真实生产场景，不能虚构“线上用 wait/notify 做过奇偶打印”。工程里如果目标是两个 worker 按条件交接任务，我会优先把协议写成明确状态机，定义所有正常、取消和异常退出路径，再选择 `Condition`、`Semaphore`、阻塞队列或更高层并发原语。`wait/notify` 适合面试中证明 monitor/条件等待机制，但真实系统通常应优先选更容易约束和观测的高层抽象。

## 常见追问

- 问：为什么必须用 `while`，不能用 `if`？答：线程可能虚假唤醒，也可能被通知后发现资格已经被别的线程改变；只有重新检查 guard 才能保证不变量。
- 问：odd 线程先启动会不会先打印 `1`？答：不会。共享 `next` 初始为 `0`，odd 即使先拿锁也会因 parity 不匹配进入等待；决定顺序的是状态，不是线程启动先后。
- 问：为什么最后还要 `notifyAll()`？答：一个线程可能在另一个线程完成最后一次状态推进时仍等待；没有终止通知，它看不到 `next > max`，进程可能挂住。
- 问：能不能用两个 `Semaphore`？答：可以。even semaphore 初始 1、odd 初始 0，每打印一个数就 release 对方；这种“令牌交接”更直接，但仍要认真处理结束和中断，避免最后一个 release/退出协议不对称。
- 问：能不能用 `ReentrantLock + Condition`？答：可以，而且可以为奇偶线程分别建立 Condition，精确 signal 对方；guard 仍然必须用 while 重检，核心状态机没有变化。
- 问：`volatile int next` 能不能替代 synchronized？答：不能单独替代。volatile 只保证可见性和部分有序性，不能把“检查 parity + 输出 + next++”组合成互斥的原子状态转换，也不提供条件等待协议。
- 问：为什么说这不是性能优化？答：打印本来可以单线程顺序完成；强制两线程交替会增加锁、调度和上下文切换，题目价值在验证并发协议而不是提高吞吐。

## 易错点

- 用 `if` 包 `wait()`，没有处理虚假唤醒或唤醒后条件再次失效。
- 只在正常打印后通知，却忘了最后一次推进后的终止通知，导致另一线程永久等待。
- 把启动顺序当成同步协议，靠 `Thread.sleep()` 猜调度时机。
- 在锁外同时读取/递增共享计数器，产生重复、跳号或错误线程消费。
- 吞掉 `InterruptedException` 后继续运行，使调用方无法可靠取消线程。
- 只给“奇偶判断”而没有明确共享状态、等待条件和退出条件。
