# 如何不停服地将 16 张分表迁移到 64 张？

## 核心结论

不要把“不停服迁移”理解成一次性把 16 张表改成 64 张表。更稳妥的做法是把迁移拆成**可重放的全量搬迁 + 持续增量 CDC + 分批路由切换 + 双向可回滚窗口 + 持续对账**。真正的难点不是 copy 数据，而是定义旧表和新表谁是事实源、如何保证全量与增量没有缝、切换时如何阻止旧路由继续写，以及回滚时旧侧是否仍然保持最新。

## 1 分钟版

- 先把分片规则版本化：`route_v1` 指向 16 表，`route_v2` 指向 64 表；按用户/哈希桶小批量切换，不能一次全量改路由。
- 先建立增量捕获基线，再做全量回填。全量按主键范围/固定桶分页，CDC 从一致性快照对应的 binlog/GTID 位点继续追，目标写入必须幂等。
- 切换一个桶前先让该桶的增量追平，再用路由 epoch/短暂写栅栏阻止旧写者越过切换点，然后把写主权切到新表；读先影子校验，再灰度放量。
- 回滚不是“把开关拨回去”这么简单。新表成为主写后，旧表若没有反向 CDC 或受控双写，就已经变旧，不能安全直接回切。
- 全程看 CDC lag、回填速度、源库负载、对账差异、双写/补偿队列和新旧读结果差异；超过阈值就暂停当前批次，而不是继续扩大。

## 3 分钟版

先澄清真实规模：16 张表总数据量、峰值读写 QPS、单行平均大小、最大可接受迁移时长、允许的一致性窗口、binlog 保留期、可接受的单桶切换抖动和回滚窗口。容量可以先用公式估算：`理想回填时间 ≈ 总有效字节 / 安全回填带宽`。例如仅做演算，若总量 4 TiB、在不伤线上 SLO 的前提下只能给迁移 200 MiB/s，理想下限约 5.8 小时；生产计划还要给 CDC、校验、重试和高峰降速留余量，不能把 5.8 小时当承诺。

数据流我会设计成一个显式状态机。先创建 64 张目标表并保证 schema/index 与当前写路径兼容，冻结不受控 DDL；启动 CDC 并取得一致性快照对应的 binlog/GTID 水位 `T0`。随后按稳定主键范围或虚拟桶做全量扫描，每一行按照 `route_v2` 写入目标表，使用主键/业务版本做幂等 upsert。全量期间产生的新写继续进入旧表，由 CDC 按提交顺序补到新表；回填事件和流式事件可能相遇，因此目标端必须以主键和版本/位点避免旧快照覆盖新修改。

当某个迁移桶全量完成、CDC 追到切换水位并且对账通过后，进入切流。先对该桶开启影子读比较；再短暂阻止旧 epoch 的新写进入，等待在途事务与 CDC 追平，原子提升路由版本，把该桶的新写主权交给 64 表侧。旧版本客户端或缓存的旧路由必须带 epoch/version，被服务端拒绝或重新解析，否则“已经切到新表”后仍可能出现迟到旧写。读流量可以在新侧预热缓存后从 1%/5%/20%/100% 灰度。

如果业务要求可快速回滚，切到新主写后的窗口内必须让旧侧继续收到新变更，例如新→旧反向 CDC；或者在非常短的切换阶段采用受控双写并把部分失败落入可靠补偿队列。应用双写本身不是原子事务，不能把“两个写请求都发了”当成一致性证明。回滚前还要先确认旧侧追平到当前水位，再切路由。稳定超过回滚窗口后才能停止反向同步、归档旧表并最终下线。

验收不能只比行数。至少做分桶行数、主键范围/哈希校验、关键金额或状态等业务不变量、随机全行抽样，并对切换桶持续比较新旧读结果。上线按桶分批推进，故障注入 CDC 重启/重复事件、回填中断、目标库超时、切换瞬间实例重启和路由缓存过期；要求恢复后不丢写、不发生旧值覆盖新值，并且能停在任一阶段继续或回滚。

## 关键细节

- **全量与增量必须同一个时间轴。** Debezium 的 MySQL 连接器会在一致性快照时记录 binlog 位置，快照完成后从该位置继续流式捕获；自己实现时也必须保存等价的快照水位，不能“先 copy 几小时再开 binlog”。
- **回填要可重入。** 用主键范围或稳定虚拟桶做 checkpoint，失败后从已完成 chunk 继续；避免 `LIMIT offset,n` 在大表上随 offset 变大而退化，也避免单个超大事务长时间占用 undo/锁/IO。
- **目标写入要抗乱序和重复。** CDC 框架重启可能重放已发事件；目标侧以稳定主键和提交版本/源位点判断新旧，重复事件得到同样结果。
- **路由需要版本而不只是配置开关。** 请求在入口解析 `route_epoch`，写入前再次校验主权；长事务、异步任务、缓存路由和延迟消息都要考虑旧 epoch。
- **DDL 也要纳入迁移控制。** MySQL 8.4 的部分 InnoDB DDL 可以并发 DML，但并非所有操作都是 instant/online；迁移期最好冻结非必要 DDL，必要变更先验证 `ALGORITHM`/`LOCK` 能力并让新旧 schema 保持兼容。
- **binlog 保留期是硬边界。** 迁移或 CDC 停机时间若超过可用日志窗口，旧水位可能无法继续，只能重新建立快照/基线；因此保留期必须覆盖最坏迁移暂停与恢复时间。

## 原理机制

这类迁移本质上是在两个存储拓扑之间转移“写主权”。全量回填解决 `T0` 之前的历史状态，CDC 解决 `T0` 之后的提交变化；幂等键与提交顺序把重复/乱序收敛成确定状态；路由 epoch/fencing 定义某一时刻到底哪一侧有资格接受新写；对账则独立证明目标状态与事实源一致。

一个可操作的桶状态可以是：

`OLD_PRIMARY → SNAPSHOT_COPYING → CDC_CATCHING_UP → SHADOW_READ → CUTOVER_FENCED → NEW_PRIMARY_WITH_ROLLBACK_SYNC → NEW_PRIMARY → RETIRED`

只有满足当前状态的退出条件才进入下一步。这样进程崩溃后读取状态与 checkpoint 就能继续，不需要依赖“这次脚本大概执行到哪了”的人工记忆。

16→64 以后还要考虑下一次扩容。若业务现在直接写 `hash(key) % 64`，下一次扩容仍会搬大量数据；可以把逻辑虚拟桶与物理表解耦，例如先固定较多逻辑桶，再维护 `bucket → physical shard/table` 映射，后续只迁移需要重平衡的桶。代价是多一层路由元数据与配置一致性治理。

## 项目经验版

项目映射提示：回答真实经历时补齐你实际的**总数据量/单表大小、峰值 QPS、分片键、旧新路由算法、事实源选择、CDC 工具、最大 lag、单批桶数、对账规则、回滚窗口、压测结果和最终迁移时长**。重点说清你个人做的取舍，例如为什么选择“旧主写 + CDC”而不是长时间应用双写、怎样定义切换水位、怎样证明旧路由已经被 fencing。

如果没有真实项目数据，可以只用演算说明容量方法，例如“4 TiB、200 MiB/s 的理论回填下限约 5.8 小时”，并明确它只是容量示例，不要写成“我线上就是 4 TiB、6 小时完成”。

## 常见追问

- 问：为什么不直接把应用改成同时写 16 表和 64 表？答：应用双写存在“旧成功新失败/新成功旧失败”的部分提交窗口，必须额外有事务外盒、补偿队列或 CDC 对账。长时间双写会把迁移问题变成持续的分布式一致性问题，所以更常把一侧保持为明确事实源。
- 问：全量复制时还有写入，怎么保证不漏？答：先建立一致性快照和对应 binlog/GTID 水位，再做全量；快照之后的提交由 CDC 补齐。关键是全量与增量共享一个确定的时间边界。
- 问：切到新表后发现错误，为什么不能直接切回旧表？答：因为切换后的新写可能只存在新侧。要想回滚，旧侧必须通过反向 CDC/受控双写追到当前水位，并在回切前再次 fencing。
- 问：如何证明迁移正确？答：CDC lag 归零只是必要条件，不是充分条件；还要做分桶计数、校验和/哈希、业务不变量、随机全行抽样和影子读差异，最终以业务状态而不是“脚本成功退出”验收。
- 问：Canal 和 Debezium 选哪个？答：两者都可作为 binlog CDC 工具，面试重点不是品牌，而是能否保存可靠位点、正确处理 schema/重启/重复事件、提供可观测 lag，并让目标写入幂等；具体选型按现有中间件生态和运维能力决定。

## 易错点

- 不要先跑完全量再启动增量捕获，否则全量窗口内的在线变更可能没有可恢复的统一水位。
- 不要认为双写天然强一致；跨两个存储的两个独立提交一定要设计部分失败和补偿。
- 不要只看“行数相等”就切流，必须校验内容和业务不变量。
- 不要声称路由切回就等于回滚；旧侧是否持续收到新写决定了它能不能成为事实源。
- 不要把 MySQL “online DDL”理解成所有 DDL 都完全无锁；不同操作的算法、锁级别和失败条件不同。
- 不要把容量示例写成真实生产指标，也不要在没有真实 SLO/流量数据时宣称已经验证迁移时长。
