# SQL：找出连续三天上升 / 下降的记录

## 核心结论

来源只保留“SQL 题：波峰波谷，连续三天”，结构化题目进一步写成“查询波峰波谷，找出连续三天上升/下降的记录”，但没有真实表名、字段名和返回粒度。这里采用一个最小可执行契约：`daily_metric(dt, metric)` 每个自然日最多一行；“连续三天”指三个相邻自然日；严格上升是 `v1 < v2 < v3`，严格下降是 `v1 > v2 > v3`；结果返回每一个满足条件的三日滑动窗口及趋势。用 `LAG` 取前两天的日期和值，再同时检查日期连续性和值的单调性。

## 1 分钟版

- 先按日期排序，用 `LAG(..., 1/2)` 取前一天、前两天的值和日期。
- 只看“相邻三行”还不够：数据可能缺天，所以必须额外验证 `d2 -> d1 -> d0` 都相差 1 个自然日。
- 严格上升条件是 `v2 < v1 AND v1 < v0`；严格下降反过来；相等不算上升或下降。
- 一个连续四天都上升的序列会产生两个合格三日窗口，这是“每个三日窗口”的结果语义；若题目要合并成整段趋势，需要再做 gaps-and-islands。
- “波峰/波谷”如果被面试官定义成“中间一天比左右两天都高/低”，那是另一套局部极值条件，不能和“连续三天单调上升/下降”混为一谈。

## 3 分钟版

假设表结构如下：

```sql
daily_metric(
    dt     DATE PRIMARY KEY,
    metric NUMERIC NOT NULL
)
```

返回每一个连续三天严格上升或严格下降的窗口：

```sql
WITH ordered AS (
    SELECT
        dt,
        metric,
        LAG(dt, 1) OVER (ORDER BY dt) AS prev_dt,
        LAG(metric, 1) OVER (ORDER BY dt) AS prev_metric,
        LAG(dt, 2) OVER (ORDER BY dt) AS prev2_dt,
        LAG(metric, 2) OVER (ORDER BY dt) AS prev2_metric
    FROM daily_metric
),
qualified AS (
    SELECT
        prev2_dt AS start_date,
        prev_dt AS middle_date,
        dt AS end_date,
        CASE
            WHEN prev2_metric < prev_metric
             AND prev_metric < metric THEN 'up'
            WHEN prev2_metric > prev_metric
             AND prev_metric > metric THEN 'down'
        END AS trend
    FROM ordered
    WHERE julianday(prev_dt) - julianday(prev2_dt) = 1
      AND julianday(dt) - julianday(prev_dt) = 1
      AND (
            (prev2_metric < prev_metric AND prev_metric < metric)
         OR (prev2_metric > prev_metric AND prev_metric > metric)
      )
)
SELECT start_date, middle_date, end_date, trend
FROM qualified
ORDER BY end_date;
```

上面用 `julianday` 是为了给仓库里的 SQLite fixture 一个可执行版本。Hive / Spark SQL / MySQL / PostgreSQL 的日期差函数不同，真实面试时应把“相差 1 天”的表达替换成目标方言，例如 `datediff` 或日期加减；窗口函数的核心思路不变。

## 关键细节

- **先定义结果粒度**：这里一行代表一个“三日窗口”，不是一整段趋势。`2026-01-01` 到 `2026-01-04` 四天持续上涨会返回 `01-01~01-03` 和 `01-02~01-04` 两行。
- **日期连续性不能省**：若数据只有 1 日、2 日、4 日，三行在窗口排序上相邻，但不是连续三个自然日，不能判为“三天连续”。
- **相等值的语义**：本答案采用严格上升/下降，`10,10,11` 不命中。若业务把“不下降/不上升”也算趋势，需要改成 `<=` / `>=`，这必须由题目定义。
- **一日多行**：本契约假设每天一行。真实表如果一天多条记录，应先按业务口径聚合到日粒度，再做窗口判断，否则“前两行”不等于“前两天”。
- **NULL**：示例把 `metric` 定义为 `NOT NULL`。若真实数据允许 NULL，要先定义缺失值是否打断趋势；通常应把它视为断点，而不是用默认值填充。
- **方言差异**：`LAG` 很通用，但日期函数不统一；回答时应明确目标引擎，不能把 SQLite 的 `julianday` 写成 Hive/Spark 的固定语法。
- **性能**：主要成本来自按日期排序的窗口计算；大表若按实体（如用户、商品）分别判断，应写 `PARTITION BY entity_id ORDER BY dt`，并结合真实引擎的分区/排序策略验证执行计划。

## 原理机制

`LAG` 把“当前行需要比较前两天”转成同一行上的六个字段：当前日期和值、前一天日期和值、前两天日期和值。之后判断分两层：先证明三条记录在时间轴上真的相邻，再判断三个值是否严格单调。这样避免了自连接三次带来的可读性问题，也避免把“排序后的相邻记录”误当成“自然日连续”。

如果题目其实要“波峰 / 波谷”作为局部极值，则三天窗口中间值才是判断对象：峰值是 `prev_metric > prev2_metric AND prev_metric > metric`，谷值反过来。那与连续三天单调上升/下降是不同问题，应该先向面试官确认。

## 项目经验版

来源没有给真实业务表、数据量、引擎版本或生产指标，不能虚构项目经历。实际落地时我会先确认日粒度、重复记录、缺失日、NULL、是否按实体分组以及 SQL 方言，再用一组包含缺天、相等值、四天连续趋势和趋势反转的 fixture 验证结果；大数据引擎上再看排序/Shuffle 的实际执行计划和数据分布。

## 常见追问

- 问：为什么不能只比较连续三行？答：因为连续三行可能跨过缺失日期；题目说“三天”时必须同时验证日期差。
- 问：四天连续上涨返回几条？答：按本答案的“三日滑动窗口”契约返回两条；若要返回整段上涨区间，需要改成趋势分段 / gaps-and-islands。
- 问：相等算上涨吗？答：本答案按“严格上升/下降”处理，所以不算；如果面试官定义为非递减/非递增，再改比较符。
- 问：如果每个用户都要分别找趋势？答：所有 `LAG` 加 `PARTITION BY user_id`，并把最终结果带上 `user_id`；日期连续性仍要逐用户检查。
- 问：波峰波谷怎么写？答：如果指局部极值，则比较中间一天和左右两天：中间值同时大于左右是峰，同时小于是谷；这与三天单调趋势不是同一条件。
- 问：Hive/Spark SQL 能直接运行这段吗？答：窗口函数思路可以，`julianday` 是 SQLite fixture 的日期表达；应换成目标引擎的 `datediff` / 日期运算语法。

## 易错点

- 把排序后的相邻三行直接当成连续三个自然日。
- 没定义严格还是非严格趋势，遇到相等值时结果不确定。
- 一天多行时不先聚合到日粒度就直接 `LAG`。
- 四天趋势产生两个三日窗口，却误判为重复数据。
- 把“局部峰谷”和“连续三天单调上涨/下跌”写成同一个条件。
- 不说明 SQL 方言，直接把某个引擎的日期函数冒充成通用 SQL。
