# 如何使用 Redis 正确实现分布式锁？

## 核心结论

先把 Redis 锁当作**有有效期的互斥租约**，而不是“拿到一次就永久拥有资源”。当前 Redis 单实例正确模式是用一条 `SET key token NX PX ttl` 获取锁，`token` 对每次持锁请求唯一；释放时 Redis 8.4+ 可用 `DELEX key IFEQ token`，更早版本用 Lua 原子执行“值仍等于 token 才删除”。真正决定方案是否可靠的是：TTL 内能否完成工作、超时后旧持有者会不会继续写、故障切换是否破坏互斥，以及高竞争下怎样限时重试。

## 1 分钟版

- **获取**：`SET lock:key unique-token NX PX ttl`，把“仅不存在时写入”和“设置过期时间”放在同一条命令里。
- **释放**：只能删除自己仍持有的锁；Redis 8.4+ 用 `DELEX ... IFEQ token`，旧版本用 compare-and-delete Lua，不能直接 `DEL`。
- **超时边界**：TTL 是锁的有效窗口。业务超过 TTL 后，新客户端可能已拿到锁，所以不能假设旧客户端恢复后仍有写权限；长任务要受控续期，并考虑 fencing token。
- **故障与竞争**：Redis 主从复制是异步的，简单“主挂了切副本”可能出现双持有者；竞争失败应设置获取超时并随机退避，避免所有客户端同步重试。

## 3 分钟版

先定义锁的业务不变量：同一资源在锁的有效窗口内最多允许一个持有者进入临界区；拿不到锁是等待、快速失败还是降级；最长业务时长和可接受的故障风险分别是多少。锁 key 应对应真正需要互斥的资源粒度，value 则是本次请求唯一 token，而不是用户 ID 这类会被不同持锁周期复用的值。

单实例获取使用：

```text
SET resource-lock <unique-token> NX PX <ttl-ms>
```

`NX` 保证 key 不存在时才写入，`PX` 同时设置租约到期时间。释放必须验证所有权：Redis 8.4 引入 `DELEX key IFEQ <token>`；旧版本可在 Redis 内用 Lua 一次完成 `GET == token` 后 `DEL`。这样可以避免客户端 A 停顿到 TTL 过期、客户端 B 已重新加锁后，A 恢复并误删 B 的锁。

TTL 不是正确性的装饰，而是安全边界。Redis 官方文档明确把 lock validity time 定义为客户端可以完成工作的时间窗口；若工作可能接近 TTL，可以只在“锁仍存在且 token 仍匹配”时续期，而且续期次数应有上限。即便如此，旧客户端也可能在暂停后恢复，因此高正确性资源要把 fencing token 传给被保护资源，由资源拒绝比已见序号更旧的写入，而不是仅靠“进程还活着”推断锁仍有效。

高可用要单独讨论。Redis 官方文档指出，主从复制是异步的：客户端 A 在主节点成功写锁后，若主节点在复制前宕机并把副本提升为主，客户端 B 可以再次获得同一资源的锁。因此“单主 + 副本自动切换”并不保持严格互斥。若业务允许极少数故障窗口出现双持有者，可以明确接受该风险；若不允许，就必须选择与所需安全属性匹配的方案，而不能把普通 failover 当成互斥证明。Redlock 通过多个相互独立的 Redis master、过半成功、获取耗时小于有效期等条件提高容错，但它同样有时钟漂移、TTL、重启和 fencing 等前提，使用前要按业务一致性要求审查这些假设。

竞争控制也要设计。获取失败不能无限紧循环，应该有总超时、最大重试次数和随机退避；Redlock 文档也建议失败后随机等待以减少多个客户端同步竞争。监控至少记录获取成功率、等待时长、锁持有时长、续期次数、超时释放、token 不匹配释放、获取失败和 Redis failover；上线前做“持锁进程暂停超过 TTL、主节点故障、网络分区、重复重试”故障注入，确认业务不会因锁状态变化产生不可接受的旧写。

## 关键细节

- Redis 当前 `SET` 支持 `NX` 与 `PX` 组合，一条命令即可完成条件写入和设置过期时间；不要拆成 `SETNX` 再 `EXPIRE`。
- token 必须区分不同客户端和不同锁请求，否则旧请求可能错误释放后来的锁。
- Redis 8.4+ 的 `DELEX ... IFEQ` 可做条件删除；更早版本使用官方文档给出的 compare-and-delete Lua。
- Redis Lua 脚本在服务端原子执行，但这种原子性只覆盖 Redis 内脚本效果，不等于外部数据库或远程服务事务也被原子化。
- 主从复制的 failover 不能自动证明互斥安全；Redis 官方文档给出了“锁未复制，副本晋升，第二客户端再次加锁”的竞态。
- 锁续期必须验证 token，且要限制最大续期/重获取次数；否则可能牺牲活性。
- 高一致性场景要考虑 fencing token，因为“客户端进程仍存活”不能证明租约仍有效。

## 原理机制

这个方案由四个边界组成：`NX` 负责“同一时刻只有不存在的锁能被创建”，TTL 负责“持有者失联后锁最终可重新获得”，唯一 token 负责“识别当前所有者”，条件删除负责“只允许当前所有者释放”。它们组合后解决的是 Redis 锁记录自身的互斥和生命周期。

但租约一旦过期，旧持有者与新持有者可能在真实世界里同时继续执行。fencing token 的作用是把“持锁次序”传到真正的受保护资源：资源记住已接受的最大序号，拒绝更旧序号的请求。这样安全判断不再依赖旧客户端是否恰好及时停止。

## 项目经验版

项目映射时应替换为真实数据：锁保护的资源是什么、key 粒度为何这样选、P99/P999 临界区时长是多少、TTL 如何据此确定、是否续期、竞争失败策略、Redis 拓扑、故障切换容忍度、受保护资源是否支持 fencing，以及故障注入结果。没有真实压测和事故数据时，不声称“绝对不会重复执行”或“Redis 锁保证 exactly-once”。

## 常见追问

- **为什么不能 `GET` 后再 `DEL`？** 因为两条命令之间锁可能过期并被别人获得；需要 Redis 8.4+ 的条件删除，或旧版本 Lua 在 Redis 内原子比较并删除。
- **业务执行超过 TTL 怎么办？** 可以在 token 仍匹配时受控续期，但续期不能无限；对于不能接受旧持有者恢复后写入的资源，还要用 fencing token 拒绝旧请求。
- **Redis 主从切换后锁还安全吗？** 不能直接这么保证。异步复制可能让锁在主节点宕机前没有同步到副本，副本晋升后第二客户端再次获得锁。
- **Redlock 是否意味着绝对安全？** 不是。它依赖多个独立 master、过半成功、获取耗时小于有效期以及有限时钟漂移等假设；Redis 当前文档也要求关注 fencing、TTL 和时钟问题。
- **高竞争下为什么要随机退避？** 多个客户端若同时固定间隔重试，容易持续同步碰撞；随机延迟可以降低同时争抢同一资源的概率。

## 易错点

- 不要把 `SETNX` 与设置过期时间拆成两个非原子步骤。
- 不要用可跨持锁周期复用的固定 value，也不要无条件 `DEL`。
- 不要把 TTL 当成“业务一定能在此时间内完成”的保证。
- 不要把 Redis 脚本原子性外推成跨数据库、消息或远程服务的事务原子性。
- 不要把普通主从 failover、Redlock 或续期机制描述成无条件的绝对互斥。
