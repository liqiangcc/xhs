# 交易链路中如何划分同步与异步边界？

## 核心结论

同步与异步的边界不应该按“这个模块重不重要”来划，而应该按**用户此刻需要得到什么承诺、这个承诺依赖哪些不可缺少的业务事实**来划。能决定当前响应是否合法的最小事实集合留在同步主链路；通知、画像、统计、搜索索引等允许延迟、可重试、可补偿的派生副作用放到异步链路。异步化通常能缩短调用方等待路径、削峰并隔离慢下游，但不会凭空减少总工作量，还会引入最终一致性、重复/乱序、积压、重试和补偿成本。

## 1 分钟版

我会先定义“响应语义”，再决定同步边界，而不是先选 MQ。

- 如果接口要返回“订单已经成功成立”，那所有决定这个承诺是否成立、且失败后不能简单补偿的关键事实必须在返回前得到确定结果；如果业务允许返回“已受理/处理中”，就可以把更多后续步骤异步化。
- 同步链路尽量只保留最小业务闭环，例如必要校验、订单事实提交以及题目具体业务所要求的关键资源确认；短信、Push、积分、推荐特征、统计报表等通常更适合异步，但最终要由真实业务约束决定。
- 本地事务提交和发消息是典型双写问题，不能靠“先写库再发一次 MQ”假设永不失败；可采用 transactional outbox/CDC 一类模式，把业务事实与待发布事件先落到同一事务边界，再异步发布。
- 消费端按至少一次重放来设计更稳妥：有业务幂等键/事件 ID，明确顺序要求，有限重试、DLQ/隔离队列和对账修复。
- 异步化的收益看主链路 P99、数据库事务持有时间和下游隔离；代价看事件发布延迟、队列积压、重试率、重复处理和业务状态收敛时间。

## 3 分钟版

### 1. 先定义用户承诺，再画同步主链路

题目没有给真实交易流程、QPS 和 SLO，所以我不会直接说“支付一定同步、库存一定异步”。先问四个问题：

1. 接口成功到底表示“请求已接收”“订单已创建”还是“交易最终完成”？
2. 哪些约束一旦失败，就不能继续给出这个成功语义？
3. 哪些步骤失败后可以重试、补偿或允许短时间延迟？
4. 峰值 QPS、主链路 P99 目标、可接受异步延迟和最大积压时间是多少？

然后只把决定当前承诺的最小事实放进同步路径。例如一个允许“下单成功、后续处理继续”的模型可以抽象成：

`请求 -> 参数/权限校验 -> 关键业务约束 -> 提交订单事实 + outbox -> 返回已受理/已创建`

后续：

`outbox relay/CDC -> 消息系统 -> 多个消费者 -> 通知/积分/画像/统计/搜索等派生状态`

如果题目的业务语义要求资金确认、库存最终占用等必须完成后才能宣称“交易成功”，这些步骤就不能仅因为“慢”而移出响应前的关键路径；相反，如果产品允许明确展示“处理中”，则可以把跨服务长流程改成状态机/Saga，让最终状态稍后收敛。

### 2. 解决“数据库已提交，但消息没发出去”的双写裂缝

最危险的写法是：

`更新数据库 -> 提交 -> 调用 MQ send()`

如果数据库已经提交，而进程在发送消息前崩溃，下游永远不知道这次变化；反过来，如果先发消息再提交数据库，也可能出现消息已经被消费但本地事务回滚。

一个常见做法是 transactional outbox：在**同一个本地数据库事务**里写业务事实和 outbox 事件，事务提交后由 relay 或 CDC 把事件发布到消息系统。这样要么业务事实和待发布事件一起存在，要么一起回滚。它没有消灭重复投递，所以消费者仍必须幂等。

### 3. 把异步链路按“可重放”设计

异步消费者不能假设一条消息只来一次，也不能把“MQ 支持幂等 producer”误写成“整个业务端到端绝对 exactly-once”。我会给事件定义：

- `event_id`：识别同一事件；
- `aggregate_id/order_id`：需要按订单维持顺序时用于同一分区/有序键；
- `event_type` 和 `version`：做演进和兼容；
- 业务幂等键：例如 `(order_id, action_type, business_version)`，由目标存储的唯一约束或原子状态迁移兜底。

处理流程是：消费 -> 校验当前业务版本/状态 -> 幂等执行 -> 成功后确认消费位置。临时失败做指数退避和次数上限；持续失败进入 DLQ/隔离队列并告警；最终通过重放或对账让状态收敛。若同一订单事件存在顺序依赖，必须把顺序要求显式化，不能让并行消费随机覆盖新状态。

### 4. 异步化为什么可能改善体验和写性能

对用户体验，主要收益是**缩短响应前的串行关键路径**。假设同步链路原来依次等待核心提交、通知、积分和统计，改造后只等待核心提交，用户看到的响应时间大致从“所有同步步骤的串行/关键路径耗时”缩到“核心步骤耗时 + 入队/事件持久化开销”。但异步任务的最终完成时间未必更短，只是用户不再等待它们。

对写性能，收益来自三点：

- 主事务更短，减少数据库连接、锁和事务资源长时间占用；
- 消息队列吸收突发流量，下游按自己的处理能力消费；
- 慢下游失败不会把每个上游请求都同步拖住。

但它不是“上 MQ 就提高 TPS”。如果瓶颈本来就在核心数据库写入，或者 outbox/消息系统本身成为新瓶颈，收益可能很小；最终要用压测和排队数据验证。

### 5. 容量要看积压，而不是只看生产 QPS

设事件到达速率为 `λ`，正常消费能力为 `μ`。稳定运行至少需要长期 `μ > λ`。如果故障期间已经积压 `B` 条，希望在 `T` 秒内追平，同时线上仍以 `λ` 进入，那么恢复阶段消费能力至少要满足近似：

`μ_recovery > λ + B / T`

因此容量规划要同时看生产峰值、消费者吞吐、单条处理耗时、分区并行度、消息保留期以及最大可接受 backlog age。只说“MQ 能削峰”而没有积压清空预算，设计是不闭环的。

### 6. 故障与降级

- **消息系统或 relay 暂时不可用**：如果 outbox 已随业务事务持久化，主业务可按既定响应语义继续，事件发布延迟上升；必须监控 outbox age，恢复后补发。
- **消费者不可用**：消息积压，非关键派生状态变旧；核心订单事实不应因此被回滚。恢复时按容量预算追平。
- **重复消息**：幂等键/唯一约束/状态版本防止重复扣减或重复发奖。
- **乱序消息**：按 aggregate key 保序，或在消费端以版本号拒绝旧事件覆盖新状态。
- **跨服务业务步骤失败**：如果步骤之间存在业务补偿关系，用明确状态机或 Saga 设计补偿；不能用本地数据库事务假装覆盖多个独立服务。
- **毒消息**：有限重试后隔离，避免一条坏消息永久阻塞整个分区，同时保留人工/自动修复入口。

### 7. 观测与上线

我会把以下指标作为上线门槛：同步接口成功率/P99、核心事务耗时、outbox 未发布数量和最老事件年龄、消息端到端延迟、consumer lag/backlog age、重试/DLQ 数量、幂等冲突数、业务对账差异，以及各业务状态从“处理中”到终态的 P95/P99 收敛时间。

上线先灰度一类低风险副作用，验证消息丢失/重复/乱序和回放能力，再逐步迁移更多步骤。回滚时保留同步旧路径或停止新事件消费，不应靠直接删队列来“恢复”。

## 关键细节

- **同步边界是业务语义边界，不是组件边界**：同一个“支付”在不同产品语义下可能必须同步确认，也可能允许先返回处理中。
- **事件事实与派生状态分开**：订单主状态是权威事实；通知、报表、画像等是派生结果，允许按各自 SLO 延迟。
- **outbox 解决的是双写原子性，不是端到端 exactly-once**：relay 仍可能重复发布，消费者仍要幂等。
- **幂等不能只靠 event_id 内存去重**：需要持久化去重、唯一键或业务状态机，否则消费者重启后仍可能重复产生副作用。
- **顺序只在需要的粒度保证**：通常是同一订单/聚合内，而不是为了“全局有序”牺牲所有并行度。
- **超时不是失败终态**：同步调用超时后要查询权威状态；异步任务超时要进入重试/补偿/对账，而不是直接把用户状态改成成功。
- **背压必须可观测**：既看 consumer lag，也看最老消息年龄和预计清空时间；数量相同的积压在不同处理时延下风险不同。
- **延迟承诺必须对用户可见**：如果业务选择最终一致，就要有“处理中/失败/已完成”等明确状态，而不是异步后仍返回虚假的最终成功。

## 原理机制

同步调用把多个服务放在同一条**时延和故障传播链**上：上游必须等待下游，任何一个慢调用都会占用上游线程/连接/事务资源，并可能通过重试放大压力。异步消息在生产者和消费者之间加入可持久化缓冲，生产者只需要完成当前承诺所需的事实，消费者按自身速度处理，因此能实现时间解耦和削峰。

但解耦的代价是失去了“同一次调用栈里立即知道所有步骤结果”的简单模型。系统必须额外建立三类机制：

1. **可靠发布**：业务事实与事件之间不能出现双写裂缝，outbox/CDC 是一种典型方案；
2. **可靠消费**：面对重投、重启和部分失败，用幂等、版本、顺序键和可重放设计收敛；
3. **业务收敛**：跨服务步骤用状态机、补偿、对账把中间状态推进到终态，而不是要求所有服务共享一个本地事务。

因此异步化不是把一致性问题删除，而是把“同步原子完成”改成“有状态、可观测、可重放地最终收敛”。

## 常见追问

- 问：支付和扣库存到底要不要同步？答：不能只看组件名称，要看接口成功语义。如果返回“交易最终成功”必须依赖它们的确定结果，就应在承诺前完成；如果产品允许“订单已受理/处理中”，则可以通过状态机和补偿把后续步骤异步化。
- 问：为什么不能数据库提交后直接发 MQ？答：数据库提交成功后进程可能在发消息前崩溃，形成永久漏事件；outbox 把业务事实和待发布事件放进同一本地事务，再由 relay/CDC 重试发布。
- 问：消费者已经做了 MQ exactly-once，还需要幂等吗？答：仍需要。消息系统的 exactly-once 通常有明确范围，消费者写外部数据库、调用第三方接口等副作用仍要定义自己的原子性和幂等边界。
- 问：异步化一定能提高写 TPS 吗？答：不一定。它能缩短主事务和隔离慢下游，但如果核心数据库写就是瓶颈，或者消息系统/outbox 成为新瓶颈，TPS 提升可能有限，必须压测验证。
- 问：队列积压怎么判断严重程度？答：同时看 backlog 数量、最老消息年龄、线上到达速率和恢复消费能力，并计算在目标时间内是否能追平，而不是只看“堆了多少条”。

## 易错点

- 把“核心业务”全部同步、把“非核心业务”全部异步，忽略真正决定边界的是用户承诺和补偿能力。
- 说“引入 MQ 就保证最终一致”，却没有可靠发布、幂等、顺序、重试、DLQ 和对账闭环。
- 把 producer 幂等或 Kafka 事务无限外推为跨数据库、第三方接口的端到端 exactly-once。
- 只讲异步降低响应时间，不说明总工作量没减少、最终完成时间和数据新鲜度可能变差。
- 返回“成功”后再异步执行一个不可补偿、可能失败的关键步骤，导致接口语义与真实状态冲突。
- 只设计正常吞吐，不计算故障积压后的追平能力，也没有 backlog age 告警。
