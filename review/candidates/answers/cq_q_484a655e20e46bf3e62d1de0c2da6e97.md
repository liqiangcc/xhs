# RocketMQ 消费模式有几种？

## 核心结论

如果这里的“消费模式”指 RocketMQ 经典的 **MessageModel**，答案是 **两种：集群消费（Clustering）和广播消费（Broadcasting）**。

- **集群消费**：同一个 Consumer Group 内的多个 Consumer **共同分担**订阅消息；对这个消费组来说，一条消息由组内某一个 Consumer 处理。适合业务处理、异步解耦和横向扩容。
- **广播消费**：同一个 Consumer Group 内的 **每一个 Consumer 都会收到并消费全量消息**。适合每个实例都必须看到同一事件的场景，例如某些配置刷新或本地状态同步。

面试时最好马上补一句：**Push/Pull、PushConsumer/SimpleConsumer/PullConsumer，以及并发/顺序消费，是另外的分类维度，不要和“集群/广播”混成四五种消费模式。**

## 1 分钟版

可以这样答：

1. RocketMQ 经典 MessageModel 有两种：**CLUSTERING** 和 **BROADCASTING**。
2. **集群模式**下，同一个消费组内的消费者分摊消息，组内做负载均衡；因此增加 Consumer 可以提升消费组的并行处理能力，但最终并行度还受队列/负载分配策略等约束。
3. **广播模式**下，组内每个 Consumer 都消费完整消息流，所以增加 Consumer 不是“分担一份工作”，而是增加一份完整消费。
4. 4.x Java PushConsumer 默认是集群模式，可以通过 `MessageModel.CLUSTERING` / `MessageModel.BROADCASTING` 配置。
5. 如果面试官接着问 Push/Pull 或顺序/并发，要说明它们分别是**获取消息方式/消费者类型**和**消费处理方式**，不是第三种、第四种集群/广播模式。

一句话记忆：

```text
集群：一组人分一份活
广播：组内每个人都做一遍
```

## 3 分钟版

### 1. 集群消费：Consumer Group 内分摊消息

集群消费的核心目标是**让一个消费组作为一个逻辑订阅者，并通过多个 Consumer 实例共同处理消息**。

可以把它理解成：

```text
Topic
  ↓
Consumer Group A
  ├─ Consumer A1
  ├─ Consumer A2
  └─ Consumer A3

一份订阅消息流
→ 在 A1/A2/A3 之间分配
→ 每条消息由组内一个 Consumer 负责处理
```

因此它有几个重要特征：

- 同组 Consumer 的消费逻辑和订阅配置应保持一致；
- 组内需要做负载均衡/重平衡，把消息或队列分给不同 Consumer；
- 增加 Consumer 的目的通常是提高这个消费组的并行消费能力；
- 如果 Consumer 数量继续增加但没有更多可分配工作，并行度不会无限增长。

这是业务消费最常见的模式，例如订单事件、扣库存、异步通知等“一条业务消息在一个逻辑消费组里处理一次”的场景。

### 2. 广播消费：组内每个 Consumer 都拿全量消息

广播消费不是让组内实例分摊，而是：

```text
Topic
  ↓
Consumer Group B
  ├─ Consumer B1 ← 全量
  ├─ Consumer B2 ← 全量
  └─ Consumer B3 ← 全量
```

也就是说，对该消费组里的每一个 Consumer 来说，都要看到完整的订阅消息。

因此：

- 加一个 Consumer，会多出一个完整消费者，而不是把原有工作切得更细；
- 更适合“每个实例都必须收到”的语义；
- 不能把广播模式当成提升同一份业务消费吞吐的横向扩容手段。

### 3. 为什么 Consumer Group 是理解这两种模式的关键？

“集群还是广播”的区别，真正比较的是 **同一个 Consumer Group 内多个 Consumer 如何处理同一份订阅消息**。

集群模式：

```text
一份组级订阅
→ 组内分工
→ 负载均衡
```

广播模式：

```text
一份组级订阅
→ 复制到组内每个 Consumer
→ 每个实例都处理
```

因此同一个 Topic 被不同 Consumer Group 订阅时，本来就可以分别形成独立的逻辑订阅；不要把“多个 Consumer Group 都收到消息”和“一个 Consumer Group 内配置广播模式”混为同一个层级。

### 4. 不要把另外两个维度混进来

RocketMQ 文档里还会看到：

```text
Push / Pull
PushConsumer / SimpleConsumer / PullConsumer
并发消费 / 顺序消费
```

它们回答的问题不同：

| 维度 | 回答的问题 |
| --- | --- |
| Clustering / Broadcasting | 同一个消费组内，消息是分摊还是每个 Consumer 都拿全量？ |
| Push/Pull、Consumer 类型 | 客户端以什么 API/机制获得消息？ |
| 并发/顺序消费 | Consumer 拿到消息后以什么并发与顺序约束处理？ |

所以面试题“RocketMQ 有几种消费模式”如果没有进一步限定，优先回答 **集群 + 广播**，然后主动说明存在其他分类维度。

### 5. 版本边界

RocketMQ 4.x 的 PushConsumer 文档直接使用 `MessageModel.CLUSTERING` 和 `MessageModel.BROADCASTING`，并说明 PushConsumer 默认采用集群模式。

RocketMQ 后续版本的消费者 API 和负载均衡模型有所演进，当前文档会区分 PushConsumer、SimpleConsumer、PullConsumer 等消费者类型；但官方文档仍然讨论 cluster consumption 和 broadcast consumption。回答时最好把“经典 MessageModel 的两种模式”和“新版本消费者类型”分开，不把旧 API 名称当成所有版本的唯一接口。

## 关键细节

- **集群消费的共享范围是 Consumer Group 内部。** 不同 Consumer Group 对同一 Topic 可以各自形成独立订阅。
- **集群模式强调负载分担。** 一条消息在一个消费组内由一个 Consumer 处理，而不是组内每个 Consumer 都执行一遍。
- **广播模式强调实例级全量。** 组内每一个 Consumer 都处理全量订阅消息。
- **扩容语义不同。** 集群模式增加 Consumer 是为了分担；广播模式增加 Consumer 会增加一份完整处理。
- **4.x PushConsumer 默认是 Clustering。** 这是版本/API 相关事实，回答时不要扩张成所有客户端、所有未来版本都必须如此。
- **Push/Pull 不是集群/广播的同一维度。** 前者讨论消费者如何取得消息；后者讨论组内消息分配语义。
- **并发/顺序也不是同一维度。** `MessageListenerConcurrently` 与顺序消费解决的是消费执行顺序问题。
- **重平衡是集群消费的重要机制。** Consumer 加入、退出时，组内工作需要重新分配；具体分配粒度和策略要结合客户端类型与版本。
- **不要承诺 exactly-once。** 集群模式下故障、重试、重平衡仍可能带来重复处理，业务消费要保持幂等。

## 原理机制

两种消费模式本质上是在定义“**一份消息对一个 Consumer Group 内多个 Consumer 的交付基数**”。

集群消费：

```text
消息 M
→ Consumer Group
→ 选择/分配给组内一个 Consumer
→ 该组获得一次逻辑处理
```

所以它天然需要负载均衡：系统必须决定哪些消息或队列由哪个 Consumer 负责。Consumer 数量变化时还需要重新分配，这就是重平衡相关机制的来源。

广播消费：

```text
消息 M
→ Consumer Group
→ 复制交付语义
→ B1、B2、B3 都处理 M
```

这里的目标不是把压力均匀切开，而是让每个实例都观察到消息，所以“增加消费者 = 增加消费能力”这个集群模式直觉不能直接套用。

因此选模式时先问业务语义：

```text
这条消息在一个逻辑消费组里只需要处理一次？
→ 集群

还是这个组内每个运行实例都必须看到？
→ 广播
```

## 项目经验版

来源没有提供真实 RocketMQ 项目规模、积压量、Consumer 数量或故障记录，所以不能编造线上案例。

项目落地时可以按下面的映射检查：

```text
先确认业务交付语义
→ 是“一个逻辑订阅处理一次”还是“每实例都要处理”
→ 再选 Clustering / Broadcasting
→ 再确定 Consumer 类型与拉取/回调模型
→ 再确定并发度、顺序、重试和幂等策略
→ 最后用消费延迟、积压量、重平衡频率验证
```

例如，如果是订单事件触发库存服务，一个库存 Consumer Group 通常需要组内分摊处理，更接近集群语义；如果是每个网关实例都必须刷新一份本地配置，则要先评估是否需要广播式全量交付。这里是架构映射方法，不是对某个真实项目的经历陈述。

## 常见追问

- 问：集群消费是不是一条消息全局只消费一次？  
  答：不是。“一次”的范围是某一个 Consumer Group。不同 Consumer Group 可以分别订阅并各自消费同一 Topic 的消息。

- 问：广播模式为什么不能靠加 Consumer 提高一份业务的处理吞吐？  
  答：因为新增 Consumer 会再消费一份全量消息，而不是和已有 Consumer 分摊同一份消息。

- 问：Push 和 Pull 是不是另外两种消费模式？  
  答：这是另一种分类维度，描述客户端如何取得消息或使用什么消费者 API。经典 MessageModel 的两种模式仍是 Clustering 和 Broadcasting。

- 问：并发消费和顺序消费跟集群/广播是什么关系？  
  答：并发/顺序描述拿到消息后的处理方式；集群/广播描述组内消息如何分配。两个维度可以分别讨论。

- 问：集群模式为什么会有重平衡？  
  答：因为多个 Consumer 要共同分担工作。实例加入、退出或分配状态变化时，需要重新决定工作归属。

- 问：集群模式加 Consumer 一定能线性提升吞吐吗？  
  答：不一定。可分配消息/队列数量、单条处理耗时、下游瓶颈、客户端负载均衡方式都会限制扩容收益。

- 问：4.x PushConsumer 默认什么模式？  
  答：官方 4.x PushConsumer 文档说明默认是集群模式；回答时要带上 4.x/该 API 的版本边界。

## 易错点

- 把 Clustering、Broadcasting、Push、Pull 混在一起说成“四种消费模式”。
- 把“不同 Consumer Group 都能收到同一 Topic”误解成“同一组内广播”。
- 说集群模式“一条消息全局只有一个消费者会收到”，漏掉 Consumer Group 边界。
- 说广播模式可以通过扩容来分担同一份消费压力。
- 把“PushConsumer 默认集群模式”的 4.x API 行为写成所有 RocketMQ 版本的永恒定义。
- 把并发消费/顺序消费当成 Clustering/Broadcasting 的同义词。
- 只背两个名词，却说不清 Consumer Group、负载分配和每实例全量交付的区别。
- 把消息系统的至少一次交付直接说成业务 exactly-once，忽略重试和幂等。
