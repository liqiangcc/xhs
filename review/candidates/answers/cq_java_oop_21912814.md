# 如何理解 Java 的封装、继承与多态？

## 核心结论

封装解决“对象内部哪些细节可以被外部依赖”，继承解决“一个类如何在父类型基础上获得并扩展行为”，多态解决“调用方只依赖一个抽象时，运行时如何由实际对象选择具体实现”。三者不是三个孤立语法点：好的设计用封装守住不变量，用继承/接口表达稳定的类型关系，再通过实例方法重写和动态分派实现可替换行为。

## 1 分钟版

- **封装**不等于“字段都写成 `private` 再生成 getter/setter”。Java 的访问控制能阻止外部依赖不必要的实现细节；工程上还应把状态修改收口到有业务语义的方法里，让对象自己维护合法状态。
- **继承**让子类获得父类可继承的成员，并可重写实例方法。Java 类只有一个直接父类，但一个类可以实现多个接口；继承适合表达真正稳定的 subtype/is-a 关系，而不是单纯为了复用几行代码。
- **多态**最典型的是“父类型/接口引用指向不同实际对象，调用可重写的实例方法时执行实际运行时类型的实现”。JLS 25 明确规定，virtual/interface 调用会从目标对象的实际运行时类开始做动态方法查找。
- **重载不是这种运行时多态**：重载候选在编译期根据方法名、参数类型等完成选择；`static` 方法也不参与实例方法的动态重写，它属于 hiding。
- 选型上，如果两个类型不能长期满足“子类在父类型出现的地方仍符合调用方预期”，就不要因为复用代码强行继承；优先把可变策略抽成接口并用组合注入。

## 3 分钟版

先按四个维度讲：**目的、Java 语言机制、运行时表现、设计边界**。

### 1. 封装：控制可见性，更重要的是控制状态变化

JLS 25 的 Access Control 说明得很直接：Java 提供访问控制，是为了避免包或类的使用者依赖不必要的实现细节。`public`、`protected`、package access、`private` 决定成员在哪些位置可访问。

但“封装好”不能只看修饰符。比如 `Account` 把 `balance` 设为 `private`，却提供一个允许随意写负数的 `setBalance()`，语法上隐藏了字段，业务不变量仍然没有被保护。更好的接口是 `deposit()`、`withdraw()`，由对象内部校验金额、余额和状态。这样调用方依赖的是稳定语义，而不是对象内部存储结构。

所以封装的价值是：缩小可依赖表面、集中校验和状态迁移、让内部实现能在不破坏公开契约的前提下演进。

### 2. 继承：获得父类型能力，但同时承担父类型契约

Java 类继承是单继承：除 `Object` 外，一个类有一个直接父类。子类会继承满足可访问性等条件的方法，并可以重写可重写的实例方法。重写有明确的签名、返回类型和访问权限约束；`final` 方法不能被重写。

继承真正的设计成本是**耦合到父类型契约**。如果 `Square extends Rectangle` 以后让调用方原本对宽高可独立修改的假设失效，哪怕代码能编译，这个继承关系在业务语义上也很可疑。反过来，“支付方式都能执行 pay，但实现不同”更适合由 `PaymentMethod` 接口定义能力，各实现独立完成行为。

因此“优先组合”不是因为继承语法有问题，而是组合通常只依赖一个更小、更明确的协作接口，替换实现时影响面更小；只有类型关系和行为契约都稳定时，继承才值得承担更强耦合。

### 3. 多态：编译期先确定可调用的方法，运行时再定位重写实现

例如：

```java
interface PaymentMethod {
    Receipt pay(Order order);
}

final class CardPayment implements PaymentMethod {
    public Receipt pay(Order order) { /* ... */ }
}

final class WalletPayment implements PaymentMethod {
    public Receipt pay(Order order) { /* ... */ }
}

PaymentMethod method = chooseMethod();
Receipt receipt = method.pay(order);
```

编译器先确认 `PaymentMethod` 上存在可适用的 `pay(Order)`。运行时，如果这是普通 virtual/interface 实例调用，JLS 25 会从目标对象的实际运行时类开始动态查找重写后的方法，所以 `method` 虽然静态类型是 `PaymentMethod`，实际执行可以是 `CardPayment.pay` 或 `WalletPayment.pay`。

这里要特别区分三件事：

1. **重写 overriding**：子类/实现类重新定义可重写的实例方法，运行时可以动态分派。
2. **重载 overloading**：同名但参数列表不同；“选哪个签名”主要在编译期完成，不是运行时根据对象实际类型再挑一个重载。
3. **隐藏 hiding**：`static` 方法不存在实例方法那种 overriding；JLS 对 static invocation 明确说不需要目标引用，也不允许 overriding。字段访问同样不要当成实例方法动态分派。

这也是多态最实用的价值：Controller/Application 不需要 `if (type == ...)` 了解每个实现细节，只依赖稳定接口；新增实现时，变化可以局部化在新的实现和装配位置。

## 关键细节

- `private` 只是封装工具，不是封装本身；真正的封装要让外部只能通过稳定、合法的操作改变状态。
- Java 类是单继承，但接口可以让一个类同时承担多个抽象能力；“类继承”和“接口实现”都能参与类型多态，但耦合强度不同。
- 实例方法 overriding 和 `static` method hiding 必须区分；把“父类引用调用 static 会动态分派”作为多态示例是错误的。
- 重载与重写也必须区分：重载解决同名不同参数的编译期方法选择，重写才是典型运行时多态的基础。
- `final` 类不能被继承，`final` 实例方法不能被重写；`private` 方法不是子类可重写的父类实例方法。
- 多态不等于“所有成员都根据实际对象动态变化”。最需要记住的是可重写实例方法的 virtual/interface 动态查找边界。
- 继承既复用行为，也暴露父子类生命周期和契约耦合；如果只是复用实现而不存在稳定 subtype 关系，应优先考虑组合、委托或独立工具对象。
- 接口不是“完全没有实现”：现代 Java 接口可以有 `default`、`static`、`private` 方法；回答时不要沿用“接口只能声明抽象方法”的旧说法。

## 原理机制

可以把一次多态调用拆成两个阶段。

第一阶段是**编译期解析**：编译器根据调用表达式的静态类型、方法名、参数数量/类型、可访问性等规则确定一个可调用的方法声明。重载主要在这个阶段决议，所以变量的静态类型可能直接影响选中的重载签名。

第二阶段是**运行时方法定位**：如果调用模式是 virtual 或 interface，并且目标方法允许 overriding，JLS 25 要求从目标对象的实际运行时类开始查找覆盖实现；找到后才建立调用栈帧并执行。`static` 调用没有目标对象，`private` 方法也不会进入普通 overriding 动态查找，因此不能把它们和实例方法多态混在一起。

封装和多态在架构上正好互补：封装让每个实现把内部状态、算法和依赖隐藏在稳定契约后面；多态让上层只面向这个契约编排。继承如果使用得当，可以复用共同契约和默认行为；使用不当，则会把本应隔离的实现细节沿父类层次扩散。

## 项目经验版

项目中可以用真实的“策略切换”场景来讲，例如支付、通知、序列化、风控规则或数据源适配。先说明上层真正需要的稳定能力是什么，再定义小接口；不同实现封装自己的依赖和状态，由工厂或依赖注入完成装配，上层只调用接口。

如果历史代码是一个很深的抽象父类，要评估子类是否真的共享同一业务契约，还是只因为复用工具方法被迫继承。后者可以把公共能力下沉成组合对象，再通过回归测试验证替换前后行为一致。没有真实项目数据时，不虚构“减少了多少代码”或“性能提升多少”。

## 常见追问

- 问：封装是不是把成员变量都设为 `private`？答：不是。`private` 只限制访问范围；如果仍暴露无约束 setter，调用方照样可以破坏对象状态。封装的目标是让外部依赖稳定语义，并由对象内部维护不变量。
- 问：`static` 方法能不能被重写并产生运行时多态？答：不能按实例方法 overriding 理解。JLS 25 将同签名的 class/static method 关系定义为 hiding；static invocation 不需要目标对象，也不走普通实例方法动态查找。
- 问：重载算多态吗？答：广义教材有时会把它称为“编译期多态”，但 Java 运行时多态面试通常指 overriding + virtual/interface dispatch；重载的目标签名主要在编译期确定。
- 问：父类引用指向子类对象，访问字段会跟着子类变化吗？答：不要把字段当成方法动态分派。多态核心边界是可重写实例方法；字段、static 方法和重载遵循不同规则。
- 问：为什么常说组合优于继承？答：组合只要求持有方依赖协作对象的公开接口，通常更容易替换和测试；继承同时绑定父类型契约和可继承实现。没有稳定 subtype 关系时，为复用代码强行继承更容易产生脆弱耦合。
- 问：接口和抽象类怎么选？答：先看是否需要表达“能力契约”还是共享受保护状态/模板实现。跨多个不相关类型共享能力通常用接口；确实存在稳定类层次并需要共享实现时再考虑抽象类，同时控制继承深度和扩展点。

## 易错点

- 把“private + getter/setter”机械等同于完整封装。
- 为了复用代码就建立继承，而没有验证 subtype 契约是否成立。
- 把重载、重写、隐藏三个概念混为一谈。
- 认为字段或 `static` 方法会像可重写实例方法一样按实际对象动态分派。
- 沿用“接口只能有抽象方法”的过时结论，忽略 default/static/private interface methods。
- 把“多态减少 if”说成目的本身；真正价值是让调用方依赖稳定抽象，把实现变化隔离到边界后。
