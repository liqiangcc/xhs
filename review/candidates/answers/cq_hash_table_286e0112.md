# 哈希表如何处理 Hash 冲突？

## 核心结论

哈希表先把 key 的 hash 映射到候选桶/槽位，再比较真实 key 确认命中；不同 key 落到同一候选位置就是 Hash 冲突。常见处理可以分成两类思路：分离链接让同一桶保留多个 entry，开放寻址则按实现定义的探测序列继续寻找候选槽位。冲突并不破坏正确性，关键是“定位后继续按 key 判等”以及删除、扩容都保持各自策略的不变量；冲突越集中，需要检查的候选通常越多，但具体平均/最坏复杂度和扩容阈值必须按实现与输入分布判断，不能从抽象模型直接外推。

## 1 分钟版

- 定位只给候选位置：例如 `index = f(hash(key), capacity)`；hash 相同不代表 key 相同，最终仍要按实现的 key 相等语义确认。
- 分离链接：一个桶可关联多个 entry；插入/查询沿桶内结构寻找相等 key，删除移除对应 entry。OpenJDK 21 `HashMap` 是一个具体例子，但还包含树桶等实现细节，不能把它的阈值当通用规则。
- 开放寻址：冲突后沿探测序列继续检查槽位。删除必须保持“后续碰撞 key 仍可继续被查到”的探测不变量；经典 tombstone/dummy 方案会把已删除槽与“从未使用的空槽”区分开。
- CPython 当前 `dict` 是一个具体的开放寻址例子：索引槽有 `EMPTY`、`DUMMY` 等状态；源码明确 `DUMMY` 不能直接恢复成 `EMPTY`，否则碰撞时的探测序列会被错误截断。
- 容量和占用策略影响时间/空间折中。OpenJDK 21 `HashMap` 明确定义 load factor 并在超过阈值后 rehash；其他实现可以使用不同指标和阈值。

## 3 分钟版

先把哈希表拆成四个参与者：hash/定位函数、候选存储结构、冲突后的继续查找规则、扩容/重建规则。查询状态机是 `计算 hash → 得到初始候选 → 比较 key → 命中或继续冲突路径 → 到达实现定义的“不存在”终止条件`。因此正确性不依赖“hash 永不冲突”，而依赖冲突路径最终仍按 key 的相等关系区分不同映射。

分离链接的抽象状态是 `bucket[index] -> 多个 entry`。插入时在桶内找相等 key：找到则更新，否则加入新的 entry；查询和删除沿同一桶内结构工作。OpenJDK 21 `HashMap` 是这一类思路的具体实现：它使用桶数组，冲突桶可为普通节点链或在条件满足时转为树节点，并把 capacity、load factor 与 rehash 作为明确的时间/空间权衡。这里引用它是为了说明一种真实实现，不是宣称所有链接哈希表都有 0.75、8、64 等参数。

开放寻址的核心不是“所有 entry 必须物理放在一个简单数组”这一表述，而是冲突后通过探测序列继续检查候选槽位，并让“空、占用、删除”等状态参与终止判断。CPython 当前 `dict` 的 `dk_indices` 就记录 `DKIX_EMPTY`、有效索引和 `DKIX_DUMMY`；源码说明已删除的 Dummy 不能直接变回 Unused/Empty，否则碰撞情况下的 probe sequence 无法知道这里曾经占用过，查找可能过早结束。它证明了 tombstone/dummy 方案的删除语义，但不意味着所有开放寻址实现都必须采用 tombstone；采用 backward-shift 等其他删除算法时，应验证它自己的探测不变量。

扩容/重建也属于策略的一部分。我们的可执行模型在容量变化后把所有存活 entry 按新容量重新定位，并验证映射仍可查到；OpenJDK 21 `HashMap` 文档也把超过 `loadFactor × capacity` 后重建内部结构称为 rehash。不要因此推断“所有实现都必须逐项重新调用用户 hashCode”或采用相同阈值；真实实现可能缓存 hash、采用增量迁移或利用容量结构优化搬迁。

冲突的性能边界要用“候选检查工作量”表达得更稳妥：模型里三个落入同一桶的 key，查到第三个需要检查三个候选，说明冲突集中会增加局部工作；OpenJDK 文档也明确指出大量相同 `hashCode()` 会拖慢哈希表。至于某个具体实现是否平均 O(1)、何时退化为线性或对数、如何抵抗恶意输入，需要结合它的冲突结构、hash 分布、可排序性和扩容策略单独证明。

## 关键细节

- 本题先讲抽象冲突机制，再用 OpenJDK 21 `HashMap` 与当前 CPython `dict` 作为两个具体实现证据；不要把任何一个实现的阈值、探测公式或数据布局当成所有哈希表的统一规范。
- key 判等与 hash 必须满足具体语言/实现的契约。抽象层只要求“hash 用于缩小候选范围，最终命中仍需按 key 相等语义确认”，不要凭一个 hash 值直接认定同一 key。
- tombstone/dummy 是开放寻址的一种删除方案，不是唯一方案；不可直接置空的结论只适用于“空槽代表探测可终止”的这类探测状态机。
- 装载因子是常见的容量控制输入，但定义、阈值和是否暴露给用户都依赖实现。OpenJDK 21 `HashMap` 有显式 load factor；不能把它的 0.75 外推给 CPython 或其他哈希表。
- 并发语义不属于“哈希冲突算法”自动提供的保证。OpenJDK 21 `HashMap` 明确不同步；其他实现必须单独查线程安全/并发访问契约。

## 原理机制

以 key `k` 为例，状态流是 `h=hash(k) → i=定位(h, capacity) → 检查候选 entry`。采用链接思路时，状态进入 `bucket[i]` 的桶内结构并逐个或按树结构比较 key；采用开放寻址时，状态进入实现定义的 probe sequence，并根据 `EMPTY/ACTIVE/DELETED` 等槽位状态决定命中、继续还是终止。

插入的状态变化是“更新相等 key”或“建立新映射”；删除必须维持后续查询可达性；扩容/重建必须让所有存活映射在新结构下仍可被同一查询规则找到。模型测试验证了碰撞 key 可分别检索、第三个同桶 key 需要三个候选检查、Dummy/tombstone 不会截断后续查询，以及容量改变后的重建仍保持所有映射。真实实现的资源成本则包括桶/索引容量、链接节点或删除标记、缓存局部性，以及扩容/重建期间的额外工作和临时空间。

版本/实现边界也属于机制的一部分：OpenJDK 21 `HashMap` 的链接/树桶和 load factor 只说明这一版本的 Java 实现；当前 CPython `dict` 的 `EMPTY/DUMMY` 与探测逻辑只说明该实现。面试中如果追问某个语言库，应从抽象机制切换到该版本源码，而不是继续用通用术语猜实现细节。

## 项目经验版

项目映射时记录具体容器/版本、key 类型与判等契约、峰值元素数、占用率、碰撞分布、是否存在不可信 key、扩容次数与 p99 查询/写入延迟。若是自研表，至少构造“无冲突、同初始桶、删除后继续探测、扩容后全量可达”四类测试；若使用标准库，优先依赖该版本官方文档/源码，不用抽象模型替代真实实现证据。没有实测数据时，不声称某一策略“必然更快”。

## 常见追问

- 问：为什么 hash 相同还要比较 key？答：hash 是定位/筛选值，不同 key 可以产生相同候选位置；不比较 key 会把碰撞误判成同一映射。
- 问：开放寻址删除为什么经常需要 tombstone？答：在“真正空槽表示查找可终止”的探测方案里，直接把中间槽清空会截断后续碰撞 key 的搜索；CPython `dict` 的 `DUMMY` 就维护这个不变量。但其他删除算法可以通过移动元素等方式维护可达性，所以 tombstone 不是开放寻址的唯一删除方案。
- 问：为什么扩容后通常要重建定位关系？答：候选位置依赖容量/表结构；容量变化后必须确保每个存活 key 在新查询规则下仍可达。具体实现可以重新插入、拆分桶或做其他等价迁移。
- 问：链接法和开放寻址怎么选？答：比较目标实现的内存布局、缓存局部性、删除语义、冲突分布、扩容成本和并发要求；不要只凭“平均 O(1)”做选择。
- 问：碰撞一定退化为 O(n) 吗？答：不能一概而论。链、树、探测和可排序性会给出不同边界；应针对具体实现和输入分布分析。抽象模型只证明冲突会增加候选检查，不替具体库承诺复杂度。

## 易错点

- 不要说“好的 hash 就不会冲突”；有限候选空间下冲突是正常状态，设计要定义碰撞后的完整流程。
- 不要把 Java `HashMap` 的树化阈值、CPython `dict` 的 Dummy 状态或任何单一实现细节说成哈希表通用标准。
- 不要把“开放寻址删除必须 tombstone”说成无条件真理；正确说法是删除必须保持探测可达性，tombstone/dummy 是一种常见实现。
- 不要把 load factor 阈值、平均复杂度、并发语义从一个实现外推到另一个实现。
- 不要只报“很快”而省略冲突候选数、扩容/重建工作量和不可信输入边界。
