# 连续切分字符串判断斐波那契数列：先枚举前两项，后续只能被唯一确定

## 核心结论

仓库原始面经 `note_desc/67d6d9fd000000001d026e12.txt` 保留下来的题目是：给定一个只包含 `1-9` 的字符串，把整个字符串连续切分成 **3 个以上的数字**，判断这些数字是否可以构成斐波那契数列，最后返回布尔值。

原始记录没有给出最大字符串长度，也没有规定整数位宽或溢出策略。下面的候选实现因此选择 `BigInteger` 表示每一项，避免把 `int`/`long` 上限冒充原题约束；同时把 `null` 和出现 `0`/非数字字符视为候选 API 的非法输入并 fail-fast。因为源输入只允许 `1-9`，不存在前导零歧义。

关键剪枝是：只需要枚举前两个数字的切分位置。一旦前两项 `a,b` 确定，第三项必须等于 `a+b`，第四项必须等于 `b+(a+b)`，后续每一项都被唯一确定。于是每组前两项都可以从当前位置向后做确定性匹配；只要某个和的十进制文本不是当前位置的前缀，该组切分立即失败。

## 1 分钟版

设字符串长度为 `L`。我枚举第一刀和第二刀，得到前两项 `a`、`b`，然后从第二刀之后开始循环：

1. 计算 `sum = a + b`；
2. 把 `sum` 转成十进制字符串；
3. 检查剩余输入是否正好以这个字符串开头；
4. 匹配成功就把位置向后推进，并令 `a=b,b=sum`；否则这组前两项直接失败。

如果位置最终恰好走到字符串末尾，而且至少得到 3 项，就返回 `true`。整个过程中没有跳字符，也没有剩余字符，所以“必须是连着的”和“切完整个字符串”同时被满足。

例如 `11235813`：前两项取 `1,1` 后，后续被依次强制为 `2,3,5,8,13`，刚好消费完整个字符串，因此返回 `true`。

## 3 分钟版

这题表面像通用回溯，但斐波那契递推给了更强的约束：真正需要搜索的只有前两项。

对于任意候选切分：

- `digits[0:firstEnd]` 是第一项；
- `digits[firstEnd:secondEnd]` 是第二项；
- 从 `secondEnd` 开始，下一段不能再自由选择，它必须是前两项之和的十进制表示。

因此状态不变量是：在任意一次循环开始时，`a,b` 就是已经确认的最后两项，`index` 指向尚未消费输入的第一个字符；若剩余输入不以 `a+b` 开头，这条路径不可能通过换一个“第三项长度”补救，因为合法第三项的值和十进制长度都已经由加法唯一确定。

只要匹配成功，就把这一整段和消费掉，再滑动最近两项。最终 `index == digits.length()` 表示所有字符都被连续使用；而循环至少成功一次就意味着总项数至少为 3。

这里使用任意精度整数是为了响应“源材料没有保存位宽上限”这个边界。它不是说原题明确要求大整数，而是避免候选答案为了方便擅自添加 `32-bit` 或 `64-bit` 限制。

## 关键细节

- 源材料明确输入字符来自 `1-9`，所以候选实现不需要处理 `0` 开头数字的多种语义；出现 `0` 或其他字符被视为 API 域外输入。
- “3 个以上”意味着仅有前两项不够；必须至少成功匹配一次 `a+b`。
- 每一段都必须来自原字符串的连续前缀，且最终必须消费到末尾；不能跳过字符，也不能只匹配一个前缀后忽略剩余。
- `BigInteger` 是候选实现的数值策略，用于避免未声明的整数溢出；它会引入随数字位数增长的内存和算术成本。
- 搜索层面有 `O(L^2)` 组前两刀；每组后续只做确定性向前匹配。若暂时忽略大整数每位运算成本，可粗略看成 `O(L^3)` 字符工作；把任意精度加法和十进制转换的位成本计入后，保守上界会更高。原题没有要求特定复杂度，因此不应把某个更强复杂度当作源约束。
- 如果需要生产接口，可以把非法字符、空串、最大长度、资源限制等单独定义成正式契约；这些都不应反写成原面经原文。

## 原理机制

```java
import java.math.BigInteger;
import java.util.Objects;

public final class FibonacciString {
    private FibonacciString() {}

    public static boolean canSplitIntoFibonacci(String digits) {
        Objects.requireNonNull(digits, "digits");
        for (int i = 0; i < digits.length(); i++) {
            char ch = digits.charAt(i);
            if (ch < '1' || ch > '9') {
                throw new IllegalArgumentException("expected digits 1-9 only");
            }
        }
        if (digits.length() < 3) return false;

        int length = digits.length();
        for (int firstEnd = 1; firstEnd <= length - 2; firstEnd++) {
            BigInteger first = new BigInteger(digits.substring(0, firstEnd));
            for (int secondEnd = firstEnd + 1; secondEnd <= length - 1; secondEnd++) {
                BigInteger second = new BigInteger(digits.substring(firstEnd, secondEnd));
                if (matchesForcedSuffix(digits, secondEnd, first, second)) {
                    return true;
                }
            }
        }
        return false;
    }

    private static boolean matchesForcedSuffix(
        String digits,
        int index,
        BigInteger first,
        BigInteger second
    ) {
        int terms = 2;
        while (index < digits.length()) {
            BigInteger sum = first.add(second);
            String expected = sum.toString();
            if (!digits.startsWith(expected, index)) return false;
            index += expected.length();
            first = second;
            second = sum;
            terms++;
        }
        return terms >= 3;
    }
}
```

正确性可以分成“充分”和“完备”两部分：

- **充分性**：算法返回 `true` 时，前两段来自连续切分；之后每一段都逐字匹配前两项之和，并且最终正好消费到末尾，所以得到至少 3 个连续数字且每个 `a[i]=a[i-1]+a[i-2]`。
- **完备性**：如果存在任意合法切分，它一定有确定的第一刀和第二刀。外层枚举会访问到这对切分；从第三项开始，合法值被递推唯一确定，所以 `matchesForcedSuffix` 会逐项匹配并最终到达末尾。因此不会漏掉合法答案。

仓库测试会用一个结构不同的递归分割 oracle：它枚举所有切分，而不是复用“先定前两项再强制匹配”的实现；固定样例覆盖单/多位数、完整消费、失败剩余和超 `long` 数值，并对 5000 个只含 `1-9` 的短随机字符串做差分验证。

## 项目经验版

这是算法题，源记录没有提供生产项目场景，不应虚构线上使用经历。可迁移的思路是：当状态转移在拿到少量初始条件后变成唯一确定时，应把“通用搜索”收窄成“只枚举真正自由的决策点 + 对确定后缀做线性验证”，这样更容易证明完备性，也更容易做差分测试。

## 常见追问

- 问：为什么不需要对第三项、第四项继续回溯？答：因为斐波那契递推把下一项唯一确定成前两项之和；若对应十进制文本不匹配当前位置，这条路径已经不可能合法。
- 问：为什么用 `BigInteger`？答：源记录没有保存最大长度和整数位宽，用任意精度可以避免候选答案自行添加 `int`/`long` 上限；这是实现选择，不是源题明示条件。
- 问：如何保证所有字符都被使用？答：每次只从当前 `index` 消费下一项的完整十进制文本，并且只有 `index` 恰好到达字符串末尾才成功。
- 问：输入只有 `1-9` 有什么影响？答：没有 `0`，所以不存在 `01` 是否允许之类的前导零分支；但某次斐波那契和如果包含 `0`，它自然无法匹配源字符串。
- 问：复杂度为什么不是简单的 O(L²)？答：虽然只枚举 O(L²) 对前两项，但每一对还要向后匹配；而这里又选择了任意精度算术，所以字符扫描、加法和十进制转换都需要计成本，不能把常数位宽假设偷偷带进结论。

## 易错点

- 只判断某个前缀能形成斐波那契序列，却没有要求消费完整个字符串。
- 允许跳字符或重新从后面找下一项，违反“必须是连着的”。
- 前两项确定后仍盲目枚举第三项长度，扩大搜索且掩盖递推的唯一性。
- 用 `int`/`long` 后直接溢出，却没有声明位宽边界。
- 把候选 API 的空串/非法字符处理方式写成原题明确条件。
