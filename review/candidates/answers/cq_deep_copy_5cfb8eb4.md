# Java 浅拷贝与深拷贝的区别

## 核心结论

浅拷贝只复制对象的第一层状态：基本类型复制值，引用字段复制的仍是同一个引用，所以原对象和副本可能共享可变子对象；深拷贝则按业务要求继续复制可变对象图，使副本中的可变状态与原图隔离。真正的难点不是“再 new 一次”，而是明确哪些节点要复制、哪些不可变对象可以共享，以及怎样在有环和共享子节点的复杂对象图中保持拓扑关系。

## 1 分钟版

- Java 的 `Object.clone()` 语义是字段逐个复制，字段内容本身不会继续被克隆，因此默认是浅拷贝；类若直接使用这套机制还要满足 `Cloneable` 约定。
- 浅拷贝对嵌套可变对象最危险：两个顶层对象不同，但例如 `address`、`items` 中的元素仍可能是同一实例，一边修改会被另一边观察到。
- 深拷贝不是 Java 提供的统一关键字或接口。常见做法是显式 copy constructor/factory/mapper，递归复制需要隔离的可变节点；不可变值对象通常可以安全共享。
- 对带环或共享子节点的对象图，不能无脑递归。应按对象身份维护“原节点 → 副本节点”表，既避免无限递归，也避免把原来共享的一个节点错误复制成多个节点。
- 序列化能够遍历可序列化对象图，因此有时可用于复制，但它要求类型满足序列化契约，还有性能、兼容性和反序列化安全边界；业务代码通常应优先选择语义明确、可控的显式复制。

## 3 分钟版

先统一比较维度：**顶层对象是否新建、嵌套可变对象是否共享、对象图拓扑是否保留、复制成本和适用边界是什么**。

浅拷贝会产生一个新的顶层对象，但引用字段仍指向原来的子对象。Oracle JDK 25 对 `Object.clone()` 的实现要求非常明确：创建同类的新实例，然后像赋值一样把各字段内容复制过去，字段指向的对象本身不会继续克隆，所以它是 shallow copy。`ArrayList.clone()` 也明确说明只是浅拷贝，元素本身不会被复制。对“对象里套 List，List 里再放可变 DTO”这种结构，只复制最外层对象或最外层集合，远远不等于深拷贝。

深拷贝要从“隔离哪些可变状态”出发，而不是追求把整个世界全部复制一遍。基本类型直接复制值；`String`、不可变 value object 等没有可观察内部变更的对象通常可共享；业务上需要独立演化的可变实体、集合和数组则要创建新节点并继续复制其可变内容。File、Socket、线程、连接池句柄等外部资源不是普通内存状态，复制一个字段或重新构造一个对象都不代表复制了相同的外部资源语义，因此通常应该显式禁止、重建或重新绑定，而不是把它们当作“深拷贝成功”。

复杂对象图还要处理两个问题：**环**和**共享关系**。例如 A 引用 B，B 又引用 A；或者 A 的两个字段都指向同一个 C。如果递归时每遇到引用就直接 new，一个环会无限递归，同一个 C 也可能被错误复制成两个不同对象。JDK 25 的 `IdentityHashMap` 文档把 deep-copying 直接列为“保持对象图拓扑”的典型用途，并要求维护按引用身份判断的 node table。做法是第一次处理节点时先创建副本并登记映射，再递归填充字段；后续再次遇到同一原对象时直接复用已登记的副本。

实现方式上，显式 copy constructor、静态 factory 或 mapper 最容易表达“哪些字段共享、哪些字段复制、哪些字段禁止复制”，也最适合领域对象演进。`clone()` 可以作为局部机制，但 `Cloneable` 只是标记接口，`Object.clone()` 本身还是 `protected`，并不会自动获得深拷贝语义。Java 对象序列化会传递地遍历对象引用并重建对象图，所以在所有相关类型可序列化时可以形成一种复制路径；但 Java 25 官方文档同时明确警告不可信数据反序列化存在安全风险，因此它不应被当成无条件、低成本的通用 deep-copy 工具。

最后要看并发边界。深拷贝只能保证“复制完成后两个对象图按设计隔离”，并不天然保证复制瞬间得到一致快照。如果源对象正在被其他线程同时修改，仍然需要锁、不可变快照、版本校验或其他并发协议来定义你到底复制了哪个时刻的状态。

## 关键细节

- `Object.clone()` 是字段级复制；引用字段的目标对象不会自动继续 clone，所以“调用了 clone”不能推出“已经深拷贝”。
- `Cloneable` 是标记接口，本身没有 `clone()` 方法；不实现它而直接走 `Object.clone()` 会得到 `CloneNotSupportedException`。类若采用该机制，通常还要自行公开并约束复制语义。
- 对引用数组或集合，只创建新的容器通常仍是浅拷贝。Oracle JDK 25 明确写明 `ArrayList.clone()` 不复制元素。
- 深拷贝应按**对象身份**跟踪已处理节点，而不是按 `equals()`。两个值相等但本来是不同实例的节点，不能因为 `equals()` 相同就合并。
- 环检测和共享拓扑其实是同一个问题：先登记原对象到副本的映射，再递归填充；重复遇到原对象时复用既有副本。
- 不可变对象可共享是优化，也是更准确的语义：深拷贝的目标是隔离可变状态，不是机械地让每一个引用地址都不同。
- 序列化复制有类型契约、性能和兼容性成本；反序列化不可信数据还有明确的安全风险。
- 深拷贝不等于并发快照。源图在复制过程中被并发修改时，仍可能得到跨时刻的混合状态。

## 原理机制

可以把复制看成一个对象图转换问题。原对象是根节点，引用字段是边。浅拷贝只复制根节点的字段值，因此边仍然指向原图中的节点；深拷贝则对需要隔离的可变节点建立一张新图，并把新图中的边重新指向对应副本。

一个可靠的递归过程通常是：收到原节点 → 如果它是 `null` 或约定可共享的不可变对象，直接返回 → 如果 identity map 已有该原节点，返回已有副本 → 否则先创建“空壳”副本并登记映射 → 再逐个复制字段、集合元素或数组元素。之所以要“先登记、后递归”，正是为了在 A→B→A 的环上第二次看到 A 时能够立即返回已创建的 A'，同时也能让两个字段原本共同引用 C 时，在副本里仍共同引用同一个 C'。

成本上，浅拷贝通常只与当前对象的一层字段或容器大小相关；完整深拷贝的时间和额外内存至少与实际复制到的新对象图规模相关。对象图很大、共享很多或只需要局部隔离时，复制整个图可能比设计不可变对象、copy-on-write、持久化数据结构或只复制变更分支更浪费，因此“是否深拷贝”本身也是架构取舍。

## 项目经验版

项目映射时只使用真实场景：例如配置快照、规则树、订单草稿或缓存 DTO。说明为什么原对象不能共享可变状态、对象图里有哪些集合/嵌套节点、哪些字段是不可变值可直接复用、是否存在环或共享子节点、并发下如何拿到一致源快照，以及复制前后的性能和内存如何验证。

如果真实场景只是“防止调用方修改一个列表”，应先判断是否用不可变视图、不可变对象或受控更新 API 就够了，而不是默认做整棵对象图深拷贝。没有真实压测数据时，不声称某种复制方式“性能最好”。

## 常见追问

- 问：`Object.clone()` 是深拷贝吗？答：不是。JDK 25 规范说明它按字段内容做复制，字段引用的对象本身不会继续克隆，因此默认是浅拷贝；要深拷贝必须由具体类型继续复制需要隔离的可变子对象。
- 问：为什么深拷贝要用 `IdentityHashMap` 而不是普通 `HashMap`？答：对象图复制关心的是“是不是同一个原对象”，不是“两个对象是否 equals”。身份映射既能处理环，也能保留共享子节点关系。
- 问：二维对象数组 `clone()` 后算深拷贝吗？答：不算。外层数组可以变成新数组，但内层数组或对象元素仍是原引用；多维数组的 clone 本质上只复制一层。
- 问：用 Java 序列化做深拷贝有什么边界？答：它会遍历可序列化对象图，但要求相关对象满足序列化契约，有 CPU/内存、版本兼容和自定义序列化行为成本，而且不可信数据反序列化有安全风险。
- 问：所有引用字段都必须复制才叫深拷贝吗？答：不必机械处理。不可变对象共享通常没有可观察的可变别名问题；关键是副本需要独立演化的可变状态不能仍与原图共享。
- 问：做了深拷贝就一定线程安全吗？答：不是。深拷贝解决的是复制后的别名隔离；如果复制期间源对象被并发写，仍要额外机制保证快照一致性。

## 易错点

- 把“顶层对象地址不同”当成深拷贝，而没有检查嵌套可变对象是否仍共享。
- 认为实现 `Cloneable` 就自动拥有公开的 `clone()` 或自动递归复制能力。
- 用 `equals()` 作为对象图去重依据，导致原本不同但值相等的节点被错误合并。
- 递归复制时不先登记节点，遇到环就无限递归。
- 把不可变集合、只读视图、容器复制和元素深拷贝混为一谈。
- 把序列化复制说成无条件通用方案，忽略类型契约、性能、兼容性和反序列化安全边界。
- 忽略复制期间的并发修改，把“深拷贝”误认为自动提供一致快照。
