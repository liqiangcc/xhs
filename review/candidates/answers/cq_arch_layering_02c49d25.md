# 复杂系统为什么需要分层设计？

## 核心结论

复杂系统通常需要分层，不是因为“层数越多越好”，而是用职责边界和受控依赖把变化隔离：接口/展示、业务规则和基础设施各自演进时，影响面可控、代码更容易定位和测试。代价是跨层映射、调用和抽象成本；简单、稳定的 CRUD 不应为了形式强拆多层。

## 1 分钟版

- 分层先按变化原因分职责：入口适配协议，应用层组织用例，业务/领域层放业务规则，基础设施层实现数据库、消息和第三方适配。
- 层之间只走约定的依赖方向和接口，避免 Controller 直连持久化或业务规则散落在适配层。
- 好处是封装、替换与测试边界更清晰；代价是 DTO/对象转换、调用链和模块数增加。
- 是否分层看业务复杂度、变化频率、协作规模和可替换性；小而稳定的服务可从清晰模块开始，复杂度出现再演进。

## 3 分钟版

分层的目标是管理复杂度，不是画一张固定四层图。Microsoft 的分层架构说明把系统按责任或关注点拆开，并通过限制哪些层可以通信来获得封装：某层替换时，主要影响与它协作的层。对后端而言，可把 HTTP/RPC、鉴权和参数适配留在入口；应用层编排一次用例与事务边界；领域层保存业务规则；基础设施层实现仓储、消息、缓存和外部 SDK。层名可变，但“谁拥有规则、谁依赖谁”必须可检查。

依赖方向是关键。传统横向分层常是 UI → 业务层 → 数据访问层；Microsoft 同时指出这会让业务逻辑在编译期依赖具体数据访问实现，测试业务逻辑可能需要测试数据库。若基础设施替换频繁或业务规则重，可把接口放在业务核心、由基础设施实现，依赖反转使核心不直接依赖具体实现。这里不是说所有项目都必须上 Clean Architecture，而是按变化点选择边界。

分层带来的收益是局部性：数据库或第三方协议变化先收敛在基础设施适配，入口协议变化先收敛在接口层，业务规则可以在不启动 Web 容器或真实数据库的情况下被测试。代价是更多模块、接口、映射和调用；若每层只透传数据、跨层随意调用，便只剩复杂度而没有隔离。因此要用依赖检查、模块所有权和测试边界验证分层，而不是只按包名分目录。

## 关键细节

- “分层”与“微服务”不是同一维度：前者组织一个应用内的职责与依赖，后者处理部署和服务边界；一个单体也可以分层。
- 传统层次的典型依赖是上层调用下层；采用依赖反转时，核心定义接口，基础设施提供实现，依赖方向改变但运行期仍需完成装配。
- 分层的粒度按变化和协作边界决定；不能从“复杂”直接推导出固定的层数或包结构。
- 需要为跨层数据转换、调试链路和抽象泄漏预留成本，否则会出现“层很多但规则仍在 Controller/SQL 中”的假分层。

## 原理机制

没有分层时，入口协议、业务规则和存储/外部调用可以互相直接依赖；任一变化会沿调用点扩散。分层把代码按职责归属，配合只允许的依赖边，令变化先落在拥有该职责的模块：基础设施实现替换不应迫使业务规则重写，业务规则可通过接口替身测试。代价是一次请求需跨越更多边界并做数据映射，且接口设计错误会把基础设施细节泄漏回核心。因此收益取决于边界是否稳定、依赖是否被真正约束，而非层数本身。

## 项目经验版

项目映射提示：选择一个真实用例，画出入口、应用编排、业务规则、持久化/外部适配及编译期依赖；给出一次真实变化（如支付渠道或存储替换）原先影响的模块、采用何种边界、如何用测试和依赖检查验证。没有这些事实时，不要虚构“重构后效率提升百分比”。

## 常见追问

- 问：分层是否等于微服务？答：不是。分层约束应用内部职责与依赖；微服务约束部署和服务边界，两者可以组合，也可以独立采用。
- 问：为什么不让业务层直接依赖数据库实现？答：传统分层会造成这种编译期依赖；当替换性和独立测试很重要时，可由业务核心定义接口、基础设施实现它，避免核心依赖具体存储。
- 问：何时不应继续拆层？答：当服务简单稳定、层只做透传而没有独立变化点或测试边界时，新增层主要增加映射与调用成本，应保留清晰模块并按复杂度演进。
- 问：如何判断分层已经失效？答：检查是否出现入口直连持久化、基础设施细节进入业务规则、跨层任意调用或每层仅透传；这些现象说明依赖约束没有落地。

## 易错点

- 不要把“分层”回答成固定的 Controller/Service/DAO 名称列表；核心是职责和依赖约束。
- 不要把 Clean、六边形、洋葱和传统 N-tier 说成完全相同；它们对依赖方向的约束不同。
- 不要承诺分层必然提升性能；它主要换取可维护性和替换/测试边界，同时引入映射和调用成本。
- 不要因项目复杂就机械加层；没有稳定边界的层会制造抽象泄漏和穿透调用。
