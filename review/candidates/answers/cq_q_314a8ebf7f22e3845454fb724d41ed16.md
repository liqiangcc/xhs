# 算法：实现一个函数防抖的 TypeScript 版本

## 核心结论

仓库题源明确要求“实现一个函数防抖的 TypeScript 版本”，现有 source-first boundary audit 还记录了题源参考实现暴露过 `immediate` 选项；但题源没有把公开类型签名、浏览器/Node 定时器句柄类型、`cancel/flush`、异常策略，以及 `immediate` 是否必须支持定义成正式合同。

这个候选因此把缺失部分显式收口为一个可验证 API：`waitMs` 必须是有限非负毫秒数；默认采用 trailing-only 防抖——连续调用只保留最后一次调用的 `this` 与参数，并在安静满 `waitMs` 后执行一次；`immediate=true` 时采用 leading-only——安静窗口内第一次立即执行，后续调用只重置安静窗口且不追加尾调用。候选不提供 `cancel/flush`，也不承诺同步返回被包装函数的返回值。

## 1 分钟版

防抖的核心不是“延迟一下”，而是让一串高频调用共享一个可替换的定时器。

默认 trailing 模式下，每次调用先清掉旧定时器，再为当前这次调用新建定时器。只要后续调用在 `waitMs` 内继续到来，旧定时器就不断被取消，因此真正能走到回调的只会是最后一次调用；它捕获的 `this` 和参数也就是最后一次调用的上下文。

`immediate=true` 时，`timer` 为空表示当前不在冷却窗口，第一次调用立即执行；同时仍设置一个定时器作为冷却窗口。窗口内后续调用会重置这个定时器，但不会再次执行。直到连续 `waitMs` 没有新调用、定时器触发并把状态清空，下一次调用才重新具备立即执行资格。

单次 wrapper 调用只做常数次判断、`clearTimeout`/`setTimeout` 和引用保存，候选层面的时间/额外状态都是 `O(1)`；任一时刻只保留一个有效 timer。

## 3 分钟版

我会先把语义讲清楚再写代码，因为“防抖”常见的分歧恰好在 leading/trailing 行为。

这里默认 trailing-only。闭包里保存一个 `timer`。调用 wrapper 时，如果已经有 timer，先 `clearTimeout(timer)`；随后针对本次 `this` 和 `args` 建一个新 timer。timer 真正触发时先把 `timer` 置回 `undefined`，再执行 `fn.apply(receiver, args)`。这两个动作分别完成“安静窗口结束”和“把最后一次调用交给原函数”。

如果打开 `immediate`，wrapper 进入时先计算 `callNow = timer === undefined`。首次调用满足条件，所以先建立冷却 timer，再立即调用原函数；窗口内下一次调用因为 timer 仍存在，不会立即调用，只会清掉旧 timer 并重新开始等待。这里刻意不做 trailing 补调用，因此语义是 leading-only，而不是 lodash 一类可能支持的 leading+trailing 组合。

TypeScript 部分用显式 `this` 参数与泛型参数元组表达 receiver 和实参类型；timer 用 `ReturnType<typeof setTimeout>`，避免把句柄硬编码成浏览器的 `number` 或某个 Node 专属类型。候选把负数、`NaN`、无穷 wait 直接拒绝为 `RangeError`，这是实现侧 API 选择，不冒充原题要求。

验证分两层：先用 `tsc --strict --noEmit --target ES2020 --lib ES2020,DOM` 做类型/语法编译；再用同控制流的 JavaScript runtime mirror 配合完全确定性的 fake clock，覆盖 trailing 单次、burst 只执行最后一次、leading 冷却、多个实例互不污染、0ms 延迟以及非法 wait。当前结果为：

```text
PASS fixed=6 fake_clock=deterministic trailing=last-call leading=immediate-no-trailing this-and-args=preserved
```

## 关键细节

- **题源边界**：TypeScript、防抖目标以及 source audit 记录的 `immediate` 参考选项来自仓库来源；具体函数签名、timer 句柄表示、异常行为、`cancel/flush` 与返回值语义属于候选选择。
- **trailing 不变量**：每次 wrapper 返回时，最多只有一个仍有效的 timer；新调用先取消旧 timer，因此连续 burst 中只有最后一次闭包有机会执行。
- **leading 不变量**：`timer === undefined` 同时表示“当前不在冷却窗口”；窗口内任一新调用都会延后窗口结束时间，但不会再次触发 `fn`。
- **`this` 与参数**：不能用箭头函数直接充当 returned wrapper，否则会丢失调用方动态 `this`；这里用普通 `function` 接住 receiver，再由 timer 闭包执行 `fn.apply(receiver, args)`。
- **timer 类型**：`ReturnType<typeof setTimeout>` 让类型跟当前 TypeScript lib 中的 `setTimeout` 声明走，不把环境差异写死进业务 API。
- **0ms**：候选仍经过 timer，不把 trailing 模式退化成同步调用；fake clock 的 `advance(0)` 用例验证这一点。
- **异常输入**：负数、`NaN`、正负无穷直接抛 `RangeError`，便于让候选 API 的边界可测试；这不是原题保存下来的要求。
- **不支持的能力**：没有 `cancel()`、`flush()`、max-wait，也没有 leading+trailing 同时开启的组合；若面试官要求这些能力，应先扩展合同再修改状态机。

## 原理机制

TypeScript 候选实现：

```typescript
export function debounce<TThis, TArgs extends unknown[]>(
  fn: (this: TThis, ...args: TArgs) => void,
  waitMs: number,
  immediate = false,
): (this: TThis, ...args: TArgs) => void {
  if (!Number.isFinite(waitMs) || waitMs < 0) {
    throw new RangeError('waitMs must be a finite non-negative number');
  }

  let timer: ReturnType<typeof setTimeout> | undefined;

  return function (this: TThis, ...args: TArgs): void {
    const callNow = immediate && timer === undefined;
    if (timer !== undefined) clearTimeout(timer);

    const receiver = this;
    timer = setTimeout(() => {
      timer = undefined;
      if (!immediate) fn.apply(receiver, args);
    }, waitMs);

    if (callNow) fn.apply(receiver, args);
  };
}
```

仓库当前 formal code gate 只直接解析 Java/SQL/JavaScript/Go 代码块，因此验证资产另外保留了与上面控制流一致、只去掉 TypeScript 类型标注的 JavaScript runtime mirror；这不是第二套算法，而是为了让现有执行门禁可以跑确定性 fake-clock 回归：

```js
function debounce(fn, waitMs, immediate = false) {
  if (!Number.isFinite(waitMs) || waitMs < 0) {
    throw new RangeError('waitMs must be a finite non-negative number');
  }

  let timer;
  return function (...args) {
    const callNow = immediate && timer === undefined;
    if (timer !== undefined) clearTimeout(timer);

    const receiver = this;
    timer = setTimeout(() => {
      timer = undefined;
      if (!immediate) fn.apply(receiver, args);
    }, waitMs);

    if (callNow) fn.apply(receiver, args);
  };
}
```

状态可以压缩成两种：

- `idle`：`timer === undefined`。trailing 模式等待下一次调用建立 timer；leading 模式下一次调用可以立即执行。
- `waiting`：timer 存在。新调用会取消旧 timer 并建立新的 waiting 窗口；timer 成功触发后恢复 `idle`。

因此 burst 是否结束，不需要计数器，只由“最后一次调用之后是否完整经过 `waitMs`”决定。

## 项目经验版

这是手写函数题，仓库来源没有用户个人项目材料，所以不虚构生产经历。工程里真正落地时，我会先确认需要的是 trailing 搜索框输入、leading 防重复点击，还是 leading+trailing/maxWait 等更复杂语义；不同交互目标不能只靠一个模糊的“防抖”名称替代合同。

如果用于组件生命周期，还要明确卸载时是否需要取消未触发 timer；如果原函数有返回值或 Promise，也要单独定义 wrapper 的返回值语义。本候选没有把这些扩展偷偷塞进最小实现。

## 常见追问

- 问：为什么 trailing 模式最终一定拿到最后一次调用的参数？答：每次新调用都会取消前一个 timer，并为本次 `receiver/args` 创建新闭包；只有最后一个没有再被后续调用取消的 timer 能触发。
- 问：`immediate=true` 为什么要在 timer 到期时把 `timer` 清空，即使不执行尾调用？答：timer 同时承担冷却窗口状态；不清空就永远无法回到 `idle`，后续调用也就永远失去 leading 执行资格。
- 问：为什么 returned wrapper 不能直接写成箭头函数？答：这个实现需要保留调用方传入的动态 `this`；普通 `function` 能接收调用点 receiver，再通过 `apply` 传给原函数。
- 问：连续触发时为什么不是每隔 `waitMs` 执行一次？答：那更接近节流；这里每次调用都会把等待窗口从头开始，所以 burst 未停止就不会产生 trailing 执行。
- 问：如果要求既第一次立即执行，又在 burst 结束时再执行最后一次怎么办？答：那是 leading+trailing 的另一份状态机合同，需要额外记录本窗口是否发生过后续调用，并定义单次调用窗口是否尾触发；本候选明确没有实现它。

## 易错点

- 只 `setTimeout` 不 `clearTimeout`，结果变成“延迟执行每一次调用”而不是防抖。
- timer 触发后忘记清空句柄，导致 leading 模式永远无法重新进入首调用状态。
- returned wrapper 使用箭头函数导致动态 `this` 丢失。
- trailing burst 使用了第一次调用的参数，而不是最后一次调用的参数。
- 把 `immediate` 说成“原题强制要求”，或把 `cancel/flush/maxWait` 等常见库能力误写成仓库题源事实。
- 为了追求通用性而同时混入 leading+trailing、返回值缓存和异步取消，反而没有先把最小语义验证清楚。
