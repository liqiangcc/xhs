# Java 并发手撕：把彼此独立的 A、B、C 从串行改为并行

## 核心结论

原始美团面经明确给出：`A`、`B`、`C` 三个方法原来串行执行，每个约 10 秒，三者**没有相互依赖**，目标是缩短整体耗时。最直接的改法是把三个任务同时提交给有足够并行度的执行器，再等待三者全部结束。

用 `CompletableFuture` 时，可以为每个 `Runnable` 调用 `runAsync(task, executor)`，最后用 `CompletableFuture.allOf(a,b,c)` 汇合。JDK 21 文档明确说明，带 `Executor` 的 `runAsync` 在指定执行器中运行任务，而 `allOf` 在所有给定 future 完成后完成；若任一子任务异常，组合 future 也会异常完成。

如果三项都接近 10 秒、执行器至少能同时运行 3 项，并且它们没有争用同一个串行资源，那么关键路径会从大约 `10+10+10≈30s` 降到大约 `max(10,10,10)≈10s` 加调度开销。这个“约 10 秒”是并行条件成立时的性能模型，不是无条件 SLA。

## 1 分钟版

```text
ExecutorService pool = Executors.newFixedThreadPool(3);
try {
    CompletableFuture<Void> fa = CompletableFuture.runAsync(this::a, pool);
    CompletableFuture<Void> fb = CompletableFuture.runAsync(this::b, pool);
    CompletableFuture<Void> fc = CompletableFuture.runAsync(this::c, pool);

    CompletableFuture.allOf(fa, fb, fc).join();
} finally {
    pool.shutdown();
}
```

- 三个任务独立，所以可以同时启动；真正能否并行还取决于执行器线程数和下游资源。
- `allOf(...).join()` 是汇合点，保证后续逻辑只在三个任务都结束后继续。
- 不显式传 `Executor` 时，异步方法通常使用 `ForkJoinPool.commonPool()`；业务代码若需要隔离、限流和可观测性，通常应显式选择执行器。
- 任一任务失败时不能吞掉异常；要按业务语义决定整体失败、降级还是补偿。
- 线程池属于资源，谁创建谁负责生命周期；长期服务更常复用受控线程池，而不是每次请求新建 3 个线程。

## 3 分钟版

串行版本的依赖图是人为写成：

```text
A -> B -> C
```

但题目已经告诉我们三者没有数据依赖，真实依赖图应该是：

```text
      A
start B -> join -> continue
      C
```

所以优化重点不是某个锁，而是**去掉假的先后关系**。`CompletableFuture.runAsync` 把三项独立工作提交给执行器，`allOf` 建立唯一必要的同步点。

这里显式传 `Executor` 有两个原因。第一，JDK 文档说明不带执行器的异步方法使用默认异步执行设施，`CompletableFuture` 的常见默认是 `ForkJoinPool.commonPool()`；面试题虽然可以简写，但生产代码最好让并发资源边界可控。第二，“三个 10 秒任务约 10 秒结束”需要至少三个任务能同时获得执行资源；如果线程池只有一个工作线程，代码形式虽然是 Future，实际仍会串行。

异常也属于依赖语义。`allOf` 会等所有给定 future 完成；只要其中一个异常完成，组合 future 也异常完成。是否还要主动取消其他任务、是否允许部分结果、是否需要超时，要由真实业务决定，不能仅凭这个题干臆造。

仓库验证不靠 `sleep(10s)`。测试让三个任务启动后都先在一个 latch 上等待；主线程只有确认三个任务都已经进入后才释放 latch。如果实现实际串行，就不可能在释放前观察到三个任务同时进入。测试还验证：组合 future 等待全部正常任务、一个子任务异常会让组合 future 异常完成、调用者可以关闭自己拥有的执行器。

## 关键细节

- “无相互依赖”是并行化前提；如果 B 需要 A 的结果，就应表达成 `thenApply/thenCompose` 等依赖链，而不是强行并发。
- 三个任务各 10 秒只能推出理论关键路径约为最大单项耗时；CPU、数据库连接池、远程接口限流等共享瓶颈可能让实际耗时更高。
- `CompletableFuture.allOf` 本身不合并各子任务的返回值；若 A/B/C 有结果，要分别保留 future 并在汇合后读取。
- `join()` 抛 `CompletionException`；若调用链要求 checked exception，可使用 `get()` 并处理 `ExecutionException/InterruptedException`。
- 对 I/O 型任务也不能无限放大线程数；执行器容量应与并发预算、下游容量、队列和超时策略一起设计。
- 不要把 `CountDownLatch` 和 `CompletableFuture` 机械叠加。这个题只需要“提交独立任务 + 等全部完成”，`allOf` 已经能表达汇合；Latch 更适合需要显式计数门闩的场景。
- 若线程池由应用容器统一管理，业务方法不应随意 `shutdown()`；示例中的关闭只适用于示例自己创建并拥有的池。

## 原理机制

并行化成立的核心是不变量：在进入最终汇合点前，A/B/C 之间没有必须保持的 happens-before 业务依赖；汇合后，调用方要求三者都已完成。

三个 `runAsync` 各自产生一个 completion stage。执行器可以把三项工作分派给不同工作线程。`allOf` 不负责“让任务并行”，它只把三个完成事件组合成一个完成事件；真正的并行度来自执行器。这样把“调度”和“依赖关系”拆开后，代码能明确表达：

1. 哪些任务可以并发；
2. 由哪个执行资源执行；
3. 在哪里等待全部任务；
4. 异常沿哪条 completion 链传播。

## Java 复习实现

```java
import java.util.Objects;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;

public final class ParallelIndependentTasks {
    private ParallelIndependentTasks() {}

    public static CompletableFuture<Void> runThree(
            Executor executor,
            Runnable a,
            Runnable b,
            Runnable c) {
        Objects.requireNonNull(executor, "executor");
        Objects.requireNonNull(a, "a");
        Objects.requireNonNull(b, "b");
        Objects.requireNonNull(c, "c");

        CompletableFuture<Void> fa = CompletableFuture.runAsync(a, executor);
        CompletableFuture<Void> fb = CompletableFuture.runAsync(b, executor);
        CompletableFuture<Void> fc = CompletableFuture.runAsync(c, executor);
        return CompletableFuture.allOf(fa, fb, fc);
    }
}
```

调用方如果拥有线程池，可以这样管理生命周期：

```text
ExecutorService pool = Executors.newFixedThreadPool(3);
try {
    ParallelIndependentTasks.runThree(pool, this::a, this::b, this::c).join();
} finally {
    pool.shutdown();
}
```

## 项目经验版

这道题不需要虚构“线上从 30 秒优化到 10 秒”的经历。更可靠的表达是：先用依赖图证明 A/B/C 可并行，再说明执行器容量、下游资源、异常和超时会决定真实收益；最后用并发启动测试或 tracing 时间线证明它们确实重叠执行。

## 常见追问

- 问：为什么不用 `CountDownLatch`？答：可以用，但 `CompletableFuture.allOf` 已直接表达“三个异步任务全部完成后继续”；Latch 更偏底层计数同步，Future 还能自然承载异常和后续阶段。
- 问：用了 `CompletableFuture` 就一定从 30 秒降到 10 秒吗？答：不一定。还需要至少 3 个可用执行线程，并且 A/B/C 不被同一个连接池、锁、CPU 或限流器再次串行化。
- 问：为什么显式传线程池？答：这样并发度、隔离、队列和生命周期是可控的，不必把业务负载隐式塞进公共池。
- 问：其中一个任务失败怎么办？答：`allOf` 会异常完成；是否整体失败、允许部分结果、重试或补偿要按业务语义决定，不能自动吞异常。
- 问：A/B/C 有返回值怎么拿？答：分别保存三个 `CompletableFuture<T>`，用 `allOf` 等待后再从各自 future 取值；`allOf` 的返回值本身是 `Void`。

## 易错点

- 题目说无依赖，却仍然 `fa.join(); fb.join(); fc.join();` 后才提交下一个任务，实际上没有并行。
- 线程池只有一个线程，却误以为 Future API 自动等于并行执行。
- 每个请求都创建新线程池且不关闭，造成线程资源泄漏。
- 使用公共池执行长时间阻塞任务，却没有评估对其他公共任务的影响。
- 只考虑成功路径，异常被 `join()` 包装后没人处理。
- 把理论关键路径“约 10 秒”写成确定 SLA，忽略调度和共享资源争用。
