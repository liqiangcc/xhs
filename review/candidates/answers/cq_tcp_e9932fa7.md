# TCP 和 UDP 的区别

## 核心结论

TCP 是面向连接、可靠的字节流传输：用序号、确认、校验和与重传处理丢失和错误，并维护连接状态。UDP 是基于 IP 的数据报协议，提供最小协议机制，协议本身不保证交付、去重或有序。选型首先看应用需要谁提供交付/顺序/拥塞等语义：需要 TCP 的就用 TCP；能接受数据报语义或愿意在上层定义这些语义时才选 UDP，不能只用“UDP 更快”做决定。

## 1 分钟版

- 传输对象：TCP 暴露连续字节流；UDP 发送独立数据报，UDP 头只有源端口、目的端口、长度和校验和。
- 可靠性与顺序：TCP 的每个数据字节有序号，ACK 是累计确认，丢失可重传；RFC 768 明确 UDP 不保证交付和重复保护。
- 状态与资源：TCP 为每条连接维护 TCB、发送/接收序号、窗口和重传队列；UDP 提供最小机制，不定义这套可靠流状态。
- 选择：需要可靠有序字节流选 TCP；应用按报文处理并能自己处理丢失、重复、乱序与拥塞时，才评估 UDP。

## 3 分钟版

先用同一维度比较，而不是背“连接/不连接”的标签。TCP 的对象是连接上的字节流。RFC 9293 规定每个发送字节有序号，接收端可累计确认；可靠性由序号检测丢失、校验和检测错误、重传进行修复。连接生命周期有 LISTEN、SYN-SENT、SYN-RECEIVED、ESTABLISHED、FIN-WAIT、CLOSE-WAIT、TIME-WAIT 等状态，状态转移由用户调用、SYN/ACK/FIN/RST 段和超时驱动。

UDP 的对象是数据报。RFC 768 将它定义为在 IP 上以最小协议机制发送消息的 transaction-oriented 协议，并明确 delivery 与 duplicate protection 不受保证。它的固定头部只有端口、长度和校验和；所以“有校验和”不等于“可靠传输”——校验用于检测，不会为应用补发、排序或去重。

资源和时延的来源也要说清。TCP 维护传输控制块（TCB）、发送/接收缓冲指针、序号变量、窗口与重传队列；它还要求拥塞控制，但具体算法由 companion documents 规定，不能把某一个算法说成所有 TCP 的唯一实现。UDP 的最小头部和无连接可靠状态并不自动带来更低端到端延迟：丢包、重排、拥塞处理和应用自己的重传策略仍由系统与上层协议决定。

选型按语义而非端口号。应用若要求传输层直接提供可靠有序字节流，应选 TCP；若应用要使用 UDP 数据报语义，则需明确自己如何处理丢失、重复、乱序与需要的确认/重传/拥塞行为。RFC 9293 与 RFC 768 分别定义两组协议语义，但不提供“UDP 必然低延迟”或某个业务类别必用某协议的通用结论。反例是把业务消息直接放进 UDP 后假设“网络会送达”：RFC 768 不提供该保证。

## 关键细节

- TCP 的 ACK 值表示接收端期待的下一个序号；累计 ACK X 表示 X 之前的字节均已收到，不是“恰好收到一个包”。
- TCP 序号空间是 32 位、按模 2^32 运算；SYN 占用一个序号，首个数据字节从 ISN+1 开始。
- UDP 数据报长度字段包含 8 字节 UDP 头和数据；RFC 768 规定传输的全零校验和值表示发送方未生成校验和，其他网络协议版本的规则要按其自身规范核验。
- TCP 与 UDP 都以端口和 IP 地址参与复用/分用；“UDP 无连接”不等于没有源/目的地址和端口。

## 原理机制

TCP 的发送状态可概括为 `字节分配序号 → 进入未确认区 → 对端累计 ACK 推进 SND.UNA → 未确认丢失/错误时重传`；接收端以 RCV.NXT 和接收窗口决定可接收序号范围。连接状态机让双方对建立、数据传输和终止阶段有共同状态，代价是 TCB、缓冲、重传和拥塞控制相关资源。

UDP 的路径是 `应用给定数据报和目的端口/地址 → UDP 加端口、长度、校验和 → IP 发送`。UDP 协议不增加交付、排序或重复保护状态；若产品需要这些性质，必须在上层明确其状态、超时与资源规则。

## 项目经验版

项目映射提示：补充真实业务的消息大小、可接受丢失/乱序率、是否需要字节流或消息边界、连接数、网络环境、上层确认/重传设计、拥塞与安全方案、压测的 p95/p99 和丢包实验。没有这些事实时，不要把“某业务用 UDP 降了多少延迟”写成个人经历。

## 常见追问

- 问：TCP 有校验和和 ACK，为什么仍要重传？答：校验和用于发现错误，ACK 与序号让发送方知道哪些字节已确认；丢失或未确认的数据仍要通过重传修复。
- 问：UDP 有校验和，为什么不可靠？答：RFC 768 的可靠性缺口在交付与重复保护；校验和只能检测特定损坏，协议不负责确认、重传、排序或去重。
- 问：TCP 一定慢、UDP 一定快吗？答：不是 RFC 9293 或 RFC 768 给出的协议保证。两者定义的传输语义不同，实际时延与吞吐须按具体实现和网络环境测量。
- 问：UDP 能否实现可靠传输？答：应用可以在上层定义序号、确认、重传、排序与拥塞规则；这意味着自行承担 UDP 协议未提供的语义与状态复杂度，不能只换 socket 类型。

## 易错点

- 不要把 TCP 的“可靠”说成永不超时、永不失败或保证业务消息恰好一次。
- 不要把 UDP 的“无连接”说成没有端口、没有校验或不能双向通信。
- 不要把 UDP 的头部更小直接等同于所有工作负载下端到端更快。
- 不要把三次握手、四次挥手、TIME_WAIT 的完整机制塞进本题；它们是相邻的独立深挖题，这里只说明 TCP 的连接状态成本与边界。
