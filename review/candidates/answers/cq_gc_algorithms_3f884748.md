# JVM 常见垃圾回收算法

## 核心结论

回答 JVM 垃圾回收时，先把**基础回收算法**和**具体收集器**分开。标记-清除、复制/疏散、标记-整理描述的是“识别存活对象后怎样回收空间”的基础机制；分代描述的是怎样按对象生命周期组织回收范围；并行、并发描述的是 GC 工作怎样和应用线程配合。Serial、Parallel、G1、ZGC 则是 HotSpot 的具体收集器，它们会组合这些机制，不能简单等同于某一种教材算法。

- **标记-清除**：保留存活对象原位置，释放不可达对象占用的空间；不需要搬迁存活对象，但可能留下碎片。
- **复制/疏散**：把存活对象搬到目标空间或目标区域，再整体复用源空间；空闲空间更连续，但需要搬迁存活对象并准备目标空间。
- **标记-整理**：标记后移动并压紧存活对象，获得连续空闲空间；以搬迁和引用更新成本换取碎片控制。
- **分代**：利用“多数对象较短命、少数对象长期存活”的经验规律，把回收重点放到更可能产生大量垃圾的区域；具体代结构和搬迁策略由收集器决定。

在当前 Oracle JDK 25 HotSpot 文档中，主要支持 Serial、Parallel、G1、ZGC。G1 在 server-class 机器上是默认选择，Serial 在其他默认配置下使用；但收集器选择仍应以实际停顿、吞吐、live set、分配速率、CPU 和堆规模为依据。

## 1 分钟版

1. 先区分“算法”和“收集器”：标记-清除、复制/疏散、标记-整理是基础机制；Serial、Parallel、G1、ZGC 是具体实现。
2. 标记-清除不移动存活对象，优点是少搬迁，缺点是可能碎片化；复制/疏散移动存活对象并整体复用源区域，空间连续但有搬迁和目标空间成本；标记-整理把存活对象压紧，解决碎片但会增加移动和引用更新工作。
3. 分代不是第四种回收算法，而是组织策略；它让 JVM 优先回收更可能包含大量短命对象的区域。
4. 当前 JDK 25 中，Parallel 偏吞吐，G1 追求较高吞吐下的可控停顿，ZGC 面向更低延迟；Serial 适合较小或单处理器场景。这里说的是收集器定位，不是“某个收集器只使用某一种基础算法”。
5. 真正选型时看 p99/p999 停顿、吞吐、live set、分配速率、堆大小、CPU 和内存余量，再用 GC 日志验证，不要背“低延迟必选 X、吞吐必选 Y”的绝对结论。

## 3 分钟版

基础算法可以用三个坐标比较：**是否搬迁存活对象、回收后空闲空间是否连续、回收成本更接近扫描量还是存活量**。

标记-清除保留存活对象原位置，把不可达对象占用的空间归还给分配器。它避免了搬迁成本，但回收后可能出现不连续空洞；如果分配器或对象大小分布需要较大的连续空间，碎片会成为问题。复制/疏散把存活对象搬到目标区域，源区域随后整体复用，容易得到连续空闲空间；代价通常和需要搬迁的 live set 有关，并要求目标区域有足够容量。标记-整理也移动存活对象，但目标是把它们压紧，以得到连续可分配空间，因此会增加搬迁和引用更新工作。

分代是更高一层的组织策略。Oracle JDK 25 的调优文档仍以 generational scavenging 和 aging 解释 HotSpot 的重要技术，但**代的物理布局不能跨收集器生搬硬套**。文档在 Serial collector 的示例里讨论 Eden 和两个 Survivor 空间，同时明确提醒其他收集器可能采用不同细节；G1 则把堆划分为 region，并动态把 region 扮演为 Eden、Survivor、Old 等角色。也就是说，“年轻代常通过搬迁少量存活对象来快速回收大量短命对象”是有用的思路，但不能进一步推导成“所有收集器都固定有同样的 Eden/Survivor 比例”。

具体收集器会组合多种机制。Oracle JDK 25 将当前 HotSpot 收集器列为 Serial、Parallel、G1 和 ZGC：Serial 用单线程执行 GC；Parallel 也属于分代收集器，但使用多线程提高吞吐；G1 是 mostly concurrent、面向可控停顿和高吞吐的收集器；ZGC 面向低延迟。G1 尤其说明了为什么不能把“收集器 = 一种算法”：它按 region 管理堆，在 stop-the-world collection pause 中疏散选定 collection set 的存活对象，同时又有并发标记等阶段。

选择时不要从算法名字直接跳到结论。先明确目标：最大可接受停顿是多少、吞吐目标是多少、live set 多大、每秒分配多少、堆多大、CPU 有多少、还能给 GC 留多少额外内存。Oracle 的 JDK 25 Ergonomics 也把最大停顿目标和吞吐目标作为相互制约的行为目标：为了缩短暂停，GC 可能更频繁，从而损失吞吐；为了吞吐而扩大堆或减少回收频率，又可能增大 footprint 或某些暂停。因此最终必须用生产相似负载和 GC 日志验证。

## 关键细节

- **不要把教材算法和收集器一一对应。** G1 同时有分代、region、并发标记、stop-the-world 疏散等机制；用“G1 就是复制算法”会丢掉关键边界。
- **Eden/Survivor 需要带收集器上下文。** JDK 25 文档里的 Eden + 两个 Survivor 是 Serial collector 章节中的典型说明；G1 的年轻代由动态数量的 region 构成，不能把固定布局套过去。
- **碎片和“总空闲不足”不是一回事。** 总空闲量存在，但空闲块过于离散时，仍可能影响需要较大连续空间的分配；整理或疏散用搬迁换取更连续的可用空间。
- **复制的额外空间不是“固定浪费一半堆”。** 这是把某些教材模型误当成所有 JVM 实现。真实收集器的 region、survivor、reserve 和 evacuation 设计不同。
- **默认收集器有环境边界。** Oracle JDK 25 Ergonomics 说明 server-class 机器默认选 G1，其他情况默认 Serial；不要把“JDK 25 永远默认 G1”说成无条件事实。
- **当前版本要看当前文档。** CMS 已不是当前 JDK 25 的受支持收集器列表成员；面试提到 CMS 可以作为历史机制比较，但不要把它和当前 Serial/Parallel/G1/ZGC 并列成“当前四大收集器”。
- **观测先于调参。** G1 调优文档建议先使用默认配置，并从 GC 日志观察实际 collection 类型和阶段；例如可从 `-Xlog:gc*=debug` 开始，再按问题收窄日志，而不是先堆一组旧版本参数。

## 原理机制

从抽象层看，一次 tracing GC 可以理解为：从一组根出发确定哪些对象仍然可达 → 对不可达对象占用的空间进行回收 → 必要时移动存活对象并修正引用 → 恢复可分配空间。不同算法主要是在最后两步做不同权衡。

如果不移动存活对象，回收器需要维护空闲空间，碎片控制会成为分配器要解决的问题；如果进行复制/疏散，回收成本会更多地落在 live set 的搬迁和引用更新上，但源区域可快速整体复用；如果进行整理，则通过把存活对象压紧换取连续空间。分代再利用对象寿命分布，把更高频的回收集中在更可能“垃圾多、存活少”的区域，从而降低每轮需要处理的存活对象数量。

G1 展示了这些抽象如何被组合：堆由多个 region 组成，young collection 会选择一组 region 作为 collection set，暂停应用线程后把存活对象疏散到其他 region；全局可达性信息又通过并发标记等阶段维护。这样既能回收空间，也能围绕 pause-time goal 调整每次 collection set 的规模。具体并发协议、remembered set 和 barrier 实现属于收集器内部机制，不应从“复制算法”三个字直接推出来。

## 项目经验版

项目映射时只使用真实数据。可以拿一段脱敏 GC 日志和真实 JDK/collector 配置，按“业务目标 → 观测证据 → 假设 → 调整 → 回归”讲：例如先说明真实 p99 停顿和吞吐目标，再看 allocation rate、live set、young/old region 变化、pause phase 和 Full GC 原因，最后说明调整后在相同负载下的对比结果。

如果没有真实项目证据，应明确说这是**方法论或假设性演练**，不要编造“线上从 300 ms 降到 50 ms”之类数字。一个安全的演练可以是：假设 G1 在高峰期出现连续长暂停，先用 GC 日志区分是 evacuation failure、humongous object、young collection 过长还是系统调度问题，再决定是应用侧减少长寿命/大对象、调整堆空间，还是只在有证据时修改 GC 参数。Oracle 的 G1 调优文档也强调先诊断具体瓶颈，而不是把所有停顿都归因于“算法选错”。

## 常见追问

- 问：为什么年轻代常见复制/疏散思路？答：如果年轻区域里大多数对象很快死亡，只搬迁少量存活对象后即可整体复用源区域，成本更接近存活量；但具体布局和比例由收集器决定。
- 问：标记-整理和复制有什么区别？答：二者都会移动存活对象并获得更连续的空间；复制/疏散通常把存活对象移到目标区域后整体复用源区域，整理则强调把存活对象压紧。真实收集器可能组合二者思想。
- 问：分代是不是独立 GC 算法？答：更准确是组织策略。它决定“优先收哪些区域/年龄层”，具体空间回收仍要靠清除、疏散、整理等机制。
- 问：G1 是复制算法还是标记-整理算法？答：都不能这样单标签化。G1 有并发标记，也会在 collection pause 中疏散存活对象，region 设计让它组合多种机制。
- 问：Parallel、G1、ZGC 怎么选？答：Oracle JDK 25 把 Parallel 定位为吞吐导向，G1 是 mostly concurrent 且兼顾较高吞吐和可控停顿，ZGC 面向更低延迟；但这只是起点，最终要用真实 workload 的停顿、吞吐、live set、堆和 CPU 数据验证。
- 问：为什么不能看到 Full GC 就直接换收集器？答：Full GC 可能由堆占用、并发标记来不及完成、疏散失败、大对象或显式 GC 等多种原因触发。先定位原因，再决定是应用、容量还是收集器参数问题。

## 易错点

- 把 Serial、Parallel、G1、ZGC 当成四种“基础 GC 算法”。
- 把 G1 简化为“复制算法”或“标记-整理算法”，忽略它的并发标记、region 和疏散组合。
- 把 Serial 示例中的 Eden/两个 Survivor 当成所有 HotSpot 收集器的固定物理布局。
- 说复制算法一定浪费一半堆，或说标记-整理一定比清除快。
- 把 `Minor GC`、`Major GC`、`Full GC` 当成跨收集器、跨版本完全一致的术语。
- 不确认 JDK 版本就继续把 CMS 当作当前默认/主流可选收集器。
- 只背收集器标签，不看 pause、throughput、live set、allocation rate、heap、CPU 和日志证据。
