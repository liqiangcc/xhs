# JVM 常见垃圾回收算法

## 核心结论

先区分“算法”和“收集器实现”。基础算法可按是否移动存活对象比较：标记-清除先找出不可达对象再释放，简单但会留下碎片；复制把存活对象搬到另一块空间，分配连续但要预留目标空间；标记-整理在标记后把存活对象压紧，消除碎片但移动成本更高。分代是把这些算法按对象年龄组合的策略，并发/并行是执行方式，不是独立的回收算法。

## 1 分钟版

- 可达性：对象从 GC Roots 不可达时可回收；回收算法的共同前提是先识别存活对象。
- 标记-清除：不移动存活对象，释放不可达对象；优点是直接，代价是空闲空间可能碎片化。
- 复制：把存活对象复制到目标区域，原区域整体清空；适合存活对象少的区域，但需要目标空间并复制存活对象。
- 标记-整理：标记后移动并压紧存活对象，释放连续空间；避免碎片，但移动和更新引用会增加停顿工作。
- 分代：基于多数对象短命的假设，年轻代频繁回收、存活对象晋升；具体收集器再决定并行、并发和区域化实现。

## 3 分钟版

回答时先给比较坐标：标记-清除、复制、标记-整理解决的都是“识别不可达对象后如何回收空间”，差别在存活对象是否移动、空闲空间是否连续、额外空间和停顿工作量。不要把 CMS、G1、ZGC 直接等同于其中某一个算法；它们会组合标记、复制/整理、并发和分区等机制，且可用性与默认行为依赖 JDK 版本。

标记-清除保留存活对象原位置并回收其余空间，容易出现许多不连续空洞；需要连续空闲空间的分配会受碎片影响。复制算法把一批存活对象搬迁，源区域可整体复用，天然得到连续空闲区；代价与存活对象量相关，也需要有足够的目标空间。标记-整理同样移动存活对象，但目标是把它们压到一侧以得到连续空闲空间；它以搬迁/引用更新工作换取碎片控制。

分代策略的依据是弱分代假设：大多数对象存活时间短。JDK 21 HotSpot 文档说明，年轻代通常由 Eden 和两个 Survivor 空间组成，存活对象在 Survivor 间复制，达到年龄或空间条件后进入老年代。年轻代满时通常只收年轻代，成本近似取决于被收集的存活对象；老年代回收涉及更多对象，往往持续更久。这里的 young/minor、old/major、full 等日志术语仍要按具体收集器和 JDK 版本核对。

选择不应只说“低延迟选某收集器”。先看 p99/p999 停顿目标、吞吐、堆大小、分配速率、live set、CPU 核数和可接受内存余量，再用 GC 日志验证。大年轻代可能提高吞吐，却增加 footprint、停顿和内存可用延迟；小年轻代可以缩短年轻代停顿，但可能降低吞吐。

## 关键细节

- 碎片不是内存总量不足：总空闲足够但没有连续块时，连续分配仍可能失败；清除与整理/复制的取舍就在这里。
- 复制的“额外空间”不是固定一半堆：具体收集器的区域、Survivor 设计和晋升策略不同，回答时不要套一个通用比例。
- 分代假设是经验规律，不是每个业务都满足；长寿命对象多、晋升过快或分配过快时，分代收益会下降。
- 在 JDK 21 HotSpot 可用 `-Xlog:gc*` 观测暂停时间、回收前后堆占用、晋升和分配速率；较早 JDK 应使用其版本对应的 GC 日志参数。不要只根据一次 Full GC 就断言算法不适合。

## 原理机制

状态链是：从 GC Roots 标记可达对象 → 对不可达对象的空间执行清除，或把存活对象复制/整理到新位置 → 恢复可分配空间。标记-清除不移动存活对象并回收不可达对象，空闲空间如何记录依实现而异；复制和整理还改变存活对象位置，具体收集器需要处理搬迁后的引用关系，本题不展开并发协议。分代把这条链优先应用到年轻代：大量短命对象死亡时，只复制少量存活对象，减少每次需要处理的 live set；存活对象再逐步进入老年代。

## 项目经验版

项目映射提示：结合真实 JDK 版本、collector、堆配置和一段脱敏 GC 日志，说明停顿目标、分配率、晋升、live set 与调优前后结果。只阅读文档时应说“算法层面的推导”，不能编造 GC 次数、停顿毫秒或线上故障。

## 常见追问

- 问：为什么年轻代常用复制思路？答：弱分代假设下年轻代通常只有少量对象存活，复制少量存活对象后可整体复用原区域，成本更接近存活量而非整个堆。
- 问：标记-整理和复制有什么区别？答：二者都移动存活对象并获得连续空间；复制通常有显式目标区域，整理则把存活对象向一侧压紧，具体实现的空间和暂停代价不同。
- 问：分代是不是一种独立 GC 算法？答：更准确是组织策略：按对象年龄划分回收范围，再在各代组合清除、复制、整理和并发/并行机制。
- 问：GC 停顿只由算法决定吗？答：不是。live set、堆大小、分配率、CPU、引用处理和具体收集器阶段都会影响暂停与吞吐，必须看日志和版本。

## 易错点

- 不要把“Minor GC、Major GC、Full GC”当作跨收集器、跨 JDK 版本完全一致的术语。
- 不要把 CMS、G1、ZGC 直接贴成“标记-清除/复制/整理”之一；应先说明它们是具体实现且存在版本边界。
- 不要说复制算法固定浪费一半堆，或说标记-整理一定比清除快；两者都依赖 live set、区域设计和停顿目标。
- 不要把 GC 算法选择与 OOM 根因混为一谈；内存泄漏、live set 过大和分配突刺需要分别诊断。
