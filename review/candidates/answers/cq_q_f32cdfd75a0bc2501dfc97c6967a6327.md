# RabbitMQ 如何保证消息不丢失？

## 核心结论

“消息不丢”不能靠单个开关保证，要把链路拆成三个故障边界：**生产者 → RabbitMQ、RabbitMQ 内部存储/复制、RabbitMQ → 消费者业务处理**。生产端用 publisher confirms 确认 broker 接受，并在需要时用 `mandatory` 检测未路由消息；broker 侧按可靠性目标选择 durable queue + 持久消息，关键数据优先考虑 quorum queue 并把 confirm 作为复制完成的反馈；消费端关闭自动确认，业务成功后再 manual ack，失败时按策略 nack/reject、重试或死信。网络故障后的重发和消费端 redelivery 都可能产生重复，因此最终业务效果还必须做幂等/去重。可靠链路通常追求的是“不丢 + 可接受重复”，而不是把 RabbitMQ 的单个机制误说成端到端 exactly-once。

## 1 分钟版

可以按三个位置回答：

1. **生产者到 broker**：开启 publisher confirms。只有收到 confirm，生产者才把消息视为被 RabbitMQ 接受；连接断开时，对未确认消息重发。若业务还要求确认消息至少路由到某个队列，AMQP 0-9-1 发布时配合 `mandatory` 并处理 `basic.return`。
2. **broker 内部**：需要重启后保留消息时使用 durable queue，并按队列/协议语义发布持久消息。关键业务若需要节点故障下更强的数据安全，使用 quorum queue；其 confirm 与 quorum 复制完成相关。
3. **broker 到消费者**：使用 manual ack，只有业务处理成功后才 ack。失败可以 nack/reject 后 requeue，或进入受控重试/死信流程；连接或 channel 在未 ack 时断开，消息可以被重新投递。
4. **端到端兜底**：生产重发和消费 redelivery 都可能带来重复，所以消费逻辑必须幂等，常用业务唯一键/消息 ID 做去重。

因此完整答案不是“持久化 + ack”六个字，而是把每一段的“成功判定、失败恢复、重复副作用”都定义清楚。

## 3 分钟版

先画一条链路：

`Producer -> Exchange/Route -> Queue/Replica -> Consumer -> Business side effect`

### 1. Producer -> RabbitMQ

生产者把数据写进 TCP socket，并不能证明 broker 已经可靠接收。Publisher confirms 用来确认发布结果；连接或 channel 故障后，对**没有收到 confirm** 的消息重新发布。

这里还有一个容易混淆的边界：confirm 和“是否路由到期望队列”不是同一件事。若发布必须至少命中某个队列，需要使用 `mandatory` 等路由失败反馈并处理 `basic.return`，不能只看 confirm。

### 2. RabbitMQ 内部

如果要求 broker 重启后消息仍在，队列与消息的耐久语义必须匹配：durable queue 保存队列元数据，持久消息才能按相应队列语义在恢复后保留。

如果还要抵抗单节点故障，仅“落单机磁盘”不够。Quorum queue 通过副本共识提高数据安全；RabbitMQ 对 quorum queue 的 publisher confirm 会在消息被 quorum 接受后返回。它仍有明确前提：没有 confirm 的消息不能当作已安全保存；永久失去多数副本也超出其保证边界。

### 3. RabbitMQ -> Consumer

消费端不要在业务动作真正完成前确认。采用 manual ack：

- 业务成功并完成期望的副作用后 `ack`；
- 临时失败可以 `nack/reject + requeue`，但必须限制重试，避免 poison message 无限循环；
- 不可处理的消息按策略 reject/nack 且不 requeue，必要时进入 DLX/停车场队列并告警；
- 未 ack 的 delivery 遇到连接/channel 关闭，会发生重新投递。

Ack 的语义只是“消费者告诉 RabbitMQ：这一 delivery 已按应用定义处理完成”，它不自动替你保证数据库事务、第三方接口和 RabbitMQ ack 之间的原子性。

### 4. 为什么还要幂等

生产端可能出现“broker 已接收并发出 confirm，但 confirm 在网络中丢失”，生产者恢复后会重发；消费端在“业务已成功，但 ack 还没到 broker”时宕机，也会再次收到同一消息。

所以可靠恢复天然可能把“丢失风险”转换成“重复风险”。业务侧应按订单号、请求号或稳定 message ID 做幂等/去重，并让重复消费不会重复扣款、重复发奖或重复创建资源。

## 关键细节

- **Publisher confirm 和 consumer ack 相互独立**：前者回答 producer→broker，后者回答 broker→consumer；收到 publisher confirm 不代表消费者已执行成功。
- **Durable queue 不等于所有消息都持久**：队列元数据可恢复和消息是否按持久语义恢复是两个维度。
- **Confirm 不能替代路由失败检测**：业务要求“必须进某个队列”时，需要显式处理 unroutable 发布，例如 `mandatory + basic.return`。
- **Manual ack 的时机由业务成功边界决定**：如果数据库还没提交就 ack，消费者随后崩溃，broker 不会因为业务回滚而自动把消息找回来。
- **先业务后 ack 也不是 exactly-once**：如果数据库已经提交但 ack 丢失，会 redelivery，因此需要幂等。
- **重试要有上限和隔离**：无限 requeue 可能形成热循环并拖垮正常流量；应有 retry/backoff/parking/DLX 与告警策略。
- **死信不是“绝不丢”的充分条件**：DLX 解决的是失败消息的后续路由/隔离；死信链路本身也必须按目标可靠性配置和监控。
- **Quorum queue 的保证有前提**：关键是 confirm + quorum 复制及多数副本可恢复，不能把“使用 quorum queue”简化成无条件零丢失。
- **监控属于可靠性闭环**：需要观察 confirm timeout/nack、unroutable return、consumer redelivery、unacked、retry/DLX 堆积和队列副本健康，而不是只配置机制不观测。

## 原理机制

这类问题本质上是在分布式系统里定义“谁在什么时刻拥有这条消息的责任”。

生产者发出消息后，如果没有 broker 的确认，就存在一个不确定区间：消息可能根本没到，也可能 broker 已收但确认丢了。因此恢复策略只能选择重试；为了不丢，就必须接受潜在重复。

Broker 收到消息后，需要把“已接受”绑定到合适的持久化/复制完成点。普通 durable/persistent 语义解决重启恢复的一部分问题；quorum queue 则把关键确认点提升到多数副本接受。确认点越强，通常会付出更多写入延迟、IO 或复制成本。

消费者收到消息后也有同样的不确定区间：业务副作用与 ack 是两个动作。若先 ack 再做业务，业务失败会造成逻辑丢失；若先做业务再 ack，ack 丢失会造成重复。因此可靠消费的经典组合是“业务成功后 ack + 业务幂等”，把不可避免的分布式不确定性从“可能丢”转换成“可能重做但结果不变”。

## 项目经验版

来源没有提供真实项目经历、RabbitMQ 版本、队列类型、集群规模、吞吐、SLA 或故障数据，不能虚构。真实落地时我会先把可靠性契约写清楚：

- 哪些消息允许丢、哪些必须至少一次送达；
- producer 何时可以删除本地待发送记录；
- unroutable 是否视为业务失败；
- 使用 classic 还是 quorum queue，允许承受多少节点故障；
- consumer 的业务成功点是什么，是否能用数据库唯一约束、状态机或幂等表吸收重复；
- poison message 的最大重试次数、退避和停车场策略；
- 如何通过指标和故障演练验证“断网、broker 重启、节点故障、consumer 在业务成功后 ack 前崩溃”等场景。

只有这些故障注入能够被恢复流程正确覆盖，才算真正验证了“消息不丢”的工程闭环。

## 常见追问

- 问：消息设置 persistent，队列设置 durable，是不是就绝对不丢？
  答：不是。它们解决 broker 重启恢复的一部分问题；生产者还需要 confirm 知道消息是否到达可靠接受点，消费者还需要正确 ack，节点级故障还要结合队列复制语义。

- 问：publisher confirm 和事务 channel 怎么选？
  答：可靠发布需要确认机制；RabbitMQ 官方文档把 confirms 作为高吞吐场景的核心机制。工程上通常异步/批量处理 confirms，而不是每条消息同步阻塞等待。

- 问：收到 confirm，是否说明消费者消费成功？
  答：不说明。Publisher confirm 只覆盖 publisher 与 broker/队列接受这一侧，consumer ack 是另一套独立机制。

- 问：消费者什么时候 ack？
  答：在应用定义的业务成功边界之后。如果业务需要提交数据库事务，就至少等该事务成功；否则可能出现 broker 已删除 delivery、业务却失败的逻辑丢失。

- 问：如果业务成功后还没 ack，消费者挂了呢？
  答：消息会有机会 redelivery，因此业务可能再执行一次。这就是为什么消费端要幂等。

- 问：`nack(requeue=true)` 一直重试可以吗？
  答：不建议无限重排队。持续失败的 poison message 会形成重投递循环，应限制次数并配合退避、死信/停车场和告警。

- 问：Quorum queue 就是 exactly-once 吗？
  答：不是。Quorum queue增强的是 broker 侧复制和数据安全；producer 重发与 consumer redelivery 仍可能产生重复，业务幂等仍然需要。

## 易错点

- 只说“消息持久化”，没有覆盖 producer、broker、consumer 三段故障窗口。
- 把 publisher confirm 和 consumer ack 当成同一套确认。
- 认为 socket `send` 成功就等于 RabbitMQ 已可靠接收。
- Durable queue 配了却忽略消息的持久语义。
- 只等 confirm，却不处理业务要求下的 unroutable 消息。
- 自动 ack 或在业务提交前 ack，导致消费者失败后消息无法重投。
- 为了“不丢”开启重试，却没有幂等，最终造成重复扣款/发奖等副作用。
- 把 DLX 当作自动的可靠性终点，不验证死信链路本身。
- 把 quorum queue 描述成无条件零丢失、零重复。
- 没有故障演练和监控，只凭配置项宣称“可靠投递已经保证”。
