# 三线程交替输出斐波那契数列

## 核心结论

原题只保留“三线程交替输出斐波那契数列”，没有给输出项数、起始定义或 API。结合题目所在的 Java 后端面试上下文，这里明确采用一个可执行契约：输出前 `n` 项，定义 `F(0)=0、F(1)=1`；三个 Java 线程按 `T0 → T1 → T2 → T0 ...` 轮转，第 `i` 项必须由 `Ti mod 3` 输出，而且整体 Fibonacci 值严格按索引顺序可见。实现用三个 `Semaphore` 组成令牌环：只有持有当前 permit 的线程能读取/推进共享 Fibonacci 状态，完成一项后把 permit 交给下一个线程。

## 1 分钟版

- `turn[0]` 初始 1 个 permit，`turn[1]`、`turn[2]` 初始为 0，所以 T0 首先执行。
- 每个线程只等待自己的 semaphore；拿到 permit 后输出当前 `(index, value)`，推进 `a,b,index`，再 `release()` 下一个线程的 semaphore。
- 最后一项完成后仍把令牌继续传一圈，使另外两个等待线程看到 `index >= n` 后也能退出，避免 join 永久等待。
- 共享状态不靠 `sleep` 猜调度顺序；顺序由 permit 所有权决定。
- 用 `BigInteger` 表示 Fibonacci 值，避免示例因为 `int/long` 溢出把并发问题和数值溢出混在一起。

## 3 分钟版

```java
import java.math.BigInteger;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Semaphore;

public final class ThreeThreadFibonacci {
    public record Output(int threadSlot, int index, BigInteger value) {}

    private static final class State {
        int index;
        BigInteger a = BigInteger.ZERO;
        BigInteger b = BigInteger.ONE;
        final List<Output> output = new ArrayList<>();
    }

    public static List<Output> generate(int terms) throws InterruptedException {
        if (terms < 0) throw new IllegalArgumentException("terms must be >= 0");

        Semaphore[] turn = {
            new Semaphore(1), new Semaphore(0), new Semaphore(0)
        };
        State state = new State();
        Thread[] workers = new Thread[3];

        for (int slot = 0; slot < workers.length; slot++) {
            final int id = slot;
            workers[slot] = new Thread(() -> {
                while (true) {
                    turn[id].acquireUninterruptibly();
                    if (state.index >= terms) {
                        turn[(id + 1) % 3].release();
                        return;
                    }

                    int index = state.index;
                    BigInteger value = state.a;
                    state.output.add(new Output(id, index, value));

                    BigInteger next = state.a.add(state.b);
                    state.a = state.b;
                    state.b = next;
                    state.index++;

                    turn[(id + 1) % 3].release();
                }
            }, "fib-" + slot);
        }

        for (Thread worker : workers) worker.start();
        for (Thread worker : workers) worker.join();
        return List.copyOf(state.output);
    }
}
```

如果面试官要“直接打印”，把 `state.output.add(...)` 换成单一格式化输出动作即可；为了让顺序和线程归属可重复测试，这里先返回不可变结果。题目未给 `n`，所以 `terms` 是候选 API 的显式输入，不冒充原题已有参数。

## 关键细节

- **令牌而不是时间控制顺序**：`sleep` 只能影响概率，不能证明 T0/T1/T2 的轮转；每次只有一个 semaphore 有 permit 才是同步协议。
- **结束传播**：不能让最后输出线程直接退出而不传 permit，否则另外两个线程可能永久阻塞。完成后继续传令牌，直到三个 worker 都观察到结束条件。
- **共享状态的可见性**：线程之间通过 `Semaphore.release/acquire` 交接执行权；JUC 同步器提供跨线程内存一致性保证。主线程 `join` 三个 worker 后再读取最终列表。
- **斐波那契推进不变量**：每次进入临界步骤时，`a=F(index)`、`b=F(index+1)`；输出 `a` 后令 `a=b, b=a+b`，于是下一轮不变量继续成立。
- **为什么不需要额外 mutex**：这个特定实现里 permit 令牌保证任意时刻只有一个 worker 进入共享状态推进区；不要把这个结论推广到 permit 数量大于 1 或存在别的共享访问者的实现。
- **中断边界**：为了让面试示例的令牌不会因某个 worker 在等待时被中断而丢失，这里使用 `acquireUninterruptibly`；若真实服务要求可取消，应增加共享取消状态并保证取消时释放/唤醒所有等待方，而不是简单把它替换成 `acquire()` 后吞掉异常。
- **复杂度**：生成 n 项需要 O(n) 次 BigInteger 加法和 O(n) 个输出记录；若只看同步次数是 O(n)，但 BigInteger 加法成本会随数值位数增长。

## 原理机制

三线程“交替”真正要证明的是一个状态机：令牌位置决定当前允许执行的线程，`index` 决定当前 Fibonacci 项。初态 `(turn=T0,index=0,a=0,b=1)`；一次合法转移只能由当前令牌持有者完成，它输出一项、推进 Fibonacci 状态，再把令牌转给 `(slot+1)%3`。因此线程调度可以任意变化，但可观察输出仍只能按这个状态机的边依次发生。

`Semaphore` 在这里既承担阻塞/唤醒，也承担线程间同步边界。它比“共享一个整数 turn + 忙等”更合适，因为没有轮到的线程可以阻塞，不持续消耗 CPU；也比 `sleep` 更可证明。用 `synchronized + wait/notifyAll`、`ReentrantLock + Condition` 同样能实现，核心都不是 API 名称，而是维护“当前轮到谁”和“结束时所有等待者都能退出”这两个不变量。

## 项目经验版

来源没有真实线上使用这个三线程 Fibonacci 程序的项目数据，因此不能虚构生产收益。真实工程如果只是按顺序输出 Fibonacci，单线程最简单；题目使用三个线程主要是在考同步协议。只有每一项还有独立耗时计算、并且业务仍要求按序提交时，才需要进一步讨论“并发计算 + 有序提交”是否值得，以及取消、超时、异常传播和监控如何设计。

## 常见追问

- 问：为什么不能三个线程都 `while` 检查 `index % 3`？答：如果没有阻塞原语就会忙等，浪费 CPU；而且检查与修改共享状态还需要正确的可见性/互斥协议。
- 问：为什么初始 permit 是 `1,0,0`？答：这样唯一可执行的是 T0；T0 完成后只唤醒 T1，再由 T1 唤醒 T2，形成确定令牌环。
- 问：最后怎么防止线程挂住？答：任何线程看到 `index >= terms` 时仍向下一个 semaphore `release` 一次再退出，结束令牌会走完剩余线程。
- 问：为什么用 `BigInteger`？答：Fibonacci 增长很快，固定宽度整数会溢出；BigInteger 把数值范围问题和并发顺序问题分离。
- 问：Semaphore 公平模式要不要开？答：不需要。每个 semaphore 只有对应 slot 的单个 worker 等待，顺序由三个独立 semaphore 的令牌传递决定，不依赖同一 semaphore 上多个竞争者的公平队列。
- 问：真实业务还要支持取消怎么办？答：把取消作为状态机的一部分：设置共享 stop/failure 状态并释放所有可能等待的 turn，使每个 worker 都能观察终止；不要让一个线程静默退出后留下断掉的令牌环。

## 易错点

- 用 `Thread.sleep` 或线程优先级“控制”输出顺序。
- 最后一个输出线程直接 return，忘记唤醒另外两个等待线程。
- 三个线程都能同时读写 `a/b/index`，却只用普通字段且没有任何同步关系。
- 用 `int` 跑较长 Fibonacci 后把溢出误判成并发错误。
- 忽略题目没有给项数和起始定义，把候选 API 的 `n`、`F(0)=0` 当成原题事实。
- 为了面试题强行引入三个线程后，反过来宣称这种实现比单线程更高效；顺序依赖本身会限制并行收益。
