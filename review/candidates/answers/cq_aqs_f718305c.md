# AQS 的核心原理是什么？

## 核心结论

AQS（`AbstractQueuedSynchronizer`）是 JUC 用来实现阻塞锁和相关同步器的框架：它把“同步状态语义”交给子类，把失败线程的排队、阻塞、唤醒、取消等机械流程收敛在框架中。Java 21 公共契约可稳定概括为：一个原子 `int state` + 一个内部 FIFO 等待队列 + 独占/共享两种获取模式；至于节点字段、队列链接和具体唤醒扫描属于 JDK 实现细节，回答源码时必须绑定具体版本。

## 1 分钟版

- 子类通过 `getState/setState/compareAndSetState` 解释和修改同步状态，并实现 `tryAcquire/tryRelease` 或共享版 `tryAcquireShared/tryReleaseShared`。
- `acquire` 的稳定抽象是：先调用 `tryAcquire`；失败就进入内部 FIFO 等待队列，必要时阻塞；被唤醒后继续重试，直到成功。`release` 在 `tryRelease` 表示可以释放后，会使队首等待者有机会继续竞争。
- 独占模式一次只有一个线程能够成功持有；共享模式允许多个线程成功，并可能传播后继唤醒。
- AQS 的内部队列不等于“严格公平锁”。Java 21 文档明确说明获取前会先尝试一次，新线程可能 barging；公平同步器通常在 `tryAcquire` 中利用 `hasQueuedPredecessors()`限制插队。
- `ConditionObject` 是另一条等待路径：`await` 会释放已持有状态并等待，`signal` 只把满足条件的等待者转移到同步器的获取路径，线程仍需重新获取同步状态后才能从 `await` 返回。

## 3 分钟版

先把职责分开。同步器子类负责回答“什么条件算获取成功、释放后状态怎么变化”，AQS 负责“获取失败后怎么办”。这就是模板方法式的分工：子类只实现受保护的状态方法，公共获取/释放方法负责队列与阻塞机制。

以 Java 21 的独占 `acquire(arg)` 契约看，调用线程至少尝试一次 `tryAcquire(arg)`。如果失败，线程会被排队，并可能经历多次“重试获取 → 阻塞 → 被唤醒 → 再重试”，直到成功。对应的 `release(arg)` 调用 `tryRelease(arg)`；只有子类报告释放后可能允许等待者获取时，框架才推进唤醒。共享模式复用同一个 FIFO 队列，但 `tryAcquireShared` 的返回值还能表达“当前共享获取成功后，后继共享获取是否可能继续成功”，所以共享释放可能形成级联传播。

公平性要单独解释。AQS 使用 FIFO 等待队列来组织等待者，但文档明确说它不会自动强制 FIFO 获取，因为新线程会在入队前先尝试获取，从而可能插队。默认 barging 往往有更好的吞吐和扩展性；如果业务需要更可预测的先来先服务，子类可在获取逻辑里用 `hasQueuedPredecessors()`等检查限制插队，但通常要接受更多调度和上下文切换成本。

条件等待也不是“另一个锁”。`ConditionObject.await` 的契约是保存并释放当前同步状态，等待条件信号，之后在返回前重新获得之前的同步状态。`signal` 表示条件可能成立，并不直接把锁交给等待线程；等待者还要进入同步器获取流程再次竞争。

## 关键细节

- Java 21 API 明确把 AQS 定义为基于单个原子 `int` 同步状态和内部 FIFO 等待队列的同步器框架；其他业务状态可以由子类维护，但 AQS 跟踪的同步状态是这个 `int`。
- `tryAcquire/tryRelease/tryAcquireShared/tryReleaseShared/isHeldExclusively` 是子类按需覆盖的受保护方法；这些实现应短小、线程安全，通常不在其中阻塞。
- 独占与共享等待者共享同一内部 FIFO 队列；“FIFO 队列”只描述排队结构，不自动等价于严格公平的获取策略。
- 公平策略能减少插队，但默认 barging 通常吞吐和扩展性更高；这是公平性与吞吐之间的显式取舍。
- 超时、可中断获取以及取消会让等待生命周期比“入队一次、唤醒一次”复杂；依赖队列长度等监控 API 时要把返回值当动态估计，而不是一致性控制依据。
- 如果面试继续追问 `Node`、`prev/next`、`park/unpark`、取消节点清理等源码细节，应先声明“以下针对 JDK 21/OpenJDK 对应实现”；这些内部结构不是 AQS 公共 API 契约。

## 原理机制

稳定的状态机可以写成：`尝试获取同步状态` → 成功则返回；失败则 `登记到等待队列` → `必要时阻塞` → 释放或共享传播使等待者获得再次竞争机会 → `再次调用子类获取规则` → 成功后离开等待路径。CAS/原子 state 解决“同步状态如何安全改变”，FIFO 等待队列解决“失败者如何被组织和重新调度”，两者职责不同。

从资源成本看，低竞争时快速路径主要是一次或少量状态检查/CAS；高竞争时会增加队列操作、阻塞/唤醒、线程调度和上下文切换。默认非公平策略允许新到线程直接尝试，可减少某些调度开销并提高吞吐；公平策略牺牲一部分吞吐换取更强的排队顺序约束。

## 项目经验版

排查大量 `WAITING (parking)` 或锁竞争时，先用线程栈确认具体同步器，再结合锁持有者、等待时间、队列长度估计、超时/中断策略和业务临界区定位瓶颈。只有真实写过自定义 AQS 同步器时才描述实现经历；只做过源码阅读或使用 `ReentrantLock/Semaphore` 时就按真实边界说明，不把阅读源码包装成项目成果。

## 常见追问

- 问：AQS 有 FIFO 队列，为什么还不能说它天然公平？答：因为公共契约明确允许获取先走一次快速尝试，新线程可能在已排队线程之前成功；是否禁止 barging 由子类获取策略决定。
- 问：CAS 已经能原子修改 state，为什么还需要等待队列？答：CAS 只解决某次状态竞争是否成功，等待队列负责组织失败线程、阻塞它们并在状态可能可用时让其重新竞争，避免长期忙等。
- 问：共享模式和独占模式最大的机制差异是什么？答：独占成功意味着其他独占获取不能同时成功；共享获取成功后还可能允许后继共享获取继续成功，因此 AQS 的共享路径支持传播。
- 问：`Condition.signal()` 后等待线程会立即拿到锁吗？答：不会。条件信号只让等待线程进入重新获取同步状态的流程；`await` 返回前还必须重新获得之前释放的同步状态。
- 问：面试官追问 AQS 是不是 CLH 双向链表怎么办？答：先区分抽象与实现：公共 API只承诺内部 FIFO 等待队列；具体节点布局、链接方式和清理算法要绑定到所讨论的 OpenJDK 版本后再展开，不能把某版源码细节当永久契约。

## 易错点

- 把 AQS 当成一把具体锁，而不是构建锁/同步器的框架。
- 看到 FIFO 等待队列就直接推出“严格公平”。
- 把 `signal` 说成直接把锁交给条件等待线程。
- 把某个 JDK 版本的 `Node` 字段、CLH 变体或取消清理策略说成所有版本都不变的 API 事实。
- 只讲 CAS，不解释竞争失败后的排队、阻塞和重新竞争成本。
