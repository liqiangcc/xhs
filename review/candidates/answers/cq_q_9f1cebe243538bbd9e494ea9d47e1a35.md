# MySQL 索引“失效”的常见场景有哪些？

## 核心结论

面试里说“索引失效”，更准确地应该拆成两类：

```text
A. 这个索引不能形成期望的高效查找范围
B. 索引其实可用，但优化器判断走它不划算，最终选择了别的访问路径
```

常见原因包括：

- **联合索引没有形成可用的最左前缀**，例如索引 `(a,b,c)` 却只拿 `b`、`c` 做普通查找条件；
- **索引列发生不利的隐式类型转换**，典型是字符串索引列拿数值去比较；
- **`LIKE` 从通配符开头**，例如 `LIKE '%abc'`，无法像 `LIKE 'abc%'` 那样形成 B-Tree 的常量前缀范围；
- **在索引列上使用与现有索引不匹配的表达式/函数**，使原列索引无法直接服务这个表达式；但 MySQL 支持 functional key parts，所以不能背成“函数一定让索引失效”；
- **联合索引前部出现范围条件后，后续列不能继续像连续等值条件那样扩展同一个查找区间**；这不等于“后续列完全没用”，也不等于“整个索引失效”；
- **选择性太差、表很小、统计信息或成本估计认为全表扫描更便宜**，优化器可能主动不选索引。

最终不要靠口诀判断。应该用 `EXPLAIN`，需要实际执行信息时用 `EXPLAIN ANALYZE`，确认 `key`、访问类型、估算/实际行数和过滤位置。

## 1 分钟版

我会先纠正一个词：多数所谓“索引失效”不是索引坏了，而是**这个查询没有形成合适的索引访问路径，或者优化器没有选择它**。

最常见的几类：

1. **联合索引不满足可用前缀**：`(a,b,c)` 只查 `b`，通常不能做普通的最左前缀定位；不过 MySQL 还有 Skip Scan 等优化，不能把口诀说成绝对定律。
2. **隐式类型转换**：尤其字符串索引列和数值常量比较，可能让该列无法做快速索引查找。
3. **前导模糊匹配**：`LIKE '%abc'` 没有固定左边界；`LIKE 'abc%'` 则可以形成前缀范围，两者不能混为一谈。
4. **函数/表达式不匹配现有索引**：例如对普通列索引做另一个表达式，原索引未必能直接用于定位；但 functional index 可以改变这个结论。
5. **联合索引中的范围条件**：范围列之后的 key parts 往往不能继续扩展同一个 range interval；不是一句“范围后全失效”就能概括。
6. **成本原因**：低选择性、命中大量行、小表、统计信息等，都可能让优化器觉得扫描更便宜。

另外，`!=`、`<>`、`IS NOT NULL`、`OR`、`IN` 也不能简单背成“必然不走索引”，MySQL 的 range optimizer 在一些形式下仍能使用索引。

最后一句：**规则只能帮助预测，执行计划才是验证。**

## 3 分钟版

### 1. 联合索引与最左前缀

假设有：

```sql
INDEX idx_abc(a, b, c)
```

B-Tree 的排序首先按 `a`，`a` 相同再按 `b`，然后才是 `c`。因此普通查找最容易利用的是：

```text
(a)
(a, b)
(a, b, c)
```

如果查询只有：

```sql
WHERE b = ?
```

它缺少最左侧 `a` 的定位条件，通常不能像 `WHERE a=? AND b=?` 那样直接缩小到连续的左前缀区间。

不过这里必须加一个现代 MySQL 边界：优化器存在 **Skip Scan** 等策略，在特定数据分布和成本下，即使缺少第一列等值条件，也可能利用复合索引。因此“违反最左前缀 = 绝对不可能使用索引”是过时的绝对化表达。

### 2. 隐式类型转换

这是原题实体里明确要求覆盖的一类。

假设某索引列语义上是字符串：

```text
varchar_column
```

如果查询拿数值去和它比较，MySQL 的类型转换规则可能把比较变成数值语义。官方文档明确指出：**有索引的字符串列与数值值比较时，不能用这个字符串列索引做快速查找**，因为不同字符串可能转换成同一个数值。

因此写 SQL 时应尽量让参数类型和列类型一致，也要检查 ORM/驱动的参数绑定类型，而不是只看 SQL 字面量。

### 3. `LIKE` 的左边界

对 B-Tree 来说，关键是能不能从模式推导出连续前缀范围。

```sql
LIKE 'abc%'
```

有固定前缀 `abc`，MySQL 可以据此构造 range。

而：

```sql
LIKE '%abc'
LIKE '_abc%'
```

从一开始就是通配符，没有固定左侧前缀，不能用同样的普通前缀 range 定位。

所以“LIKE 不走索引”也是错误口诀，真正要看模式有没有可利用的常量前缀以及实际执行计划。

### 4. 对索引列做函数或表达式

例如只有普通列索引：

```text
INDEX(col)
```

查询却按：

```sql
WHERE some_expression(col) = ?
```

如果现有索引保存的是 `col` 的排序，而查询需要的是另一套表达式结果，原列索引可能无法直接作为这个表达式的 lookup key。

但不能说“只要有函数索引就废了”。MySQL 支持 **functional key parts**；如果建立了与查询表达式匹配的函数索引，就可能重新获得索引访问路径。因此正确问题是：

> 查询表达式和可用索引的 key expression 是否匹配？

### 5. 范围条件与联合索引后续列

另一个常见口诀是：

> “联合索引遇到范围，后面的列全部失效。”

这也太粗糙。

对多列 B-Tree 构造 range interval 时，连续的等值类条件可以继续缩小后续 key parts；当前面的 key part 使用 `<`、`>`、`BETWEEN` 等范围条件后，后面的列通常不能再继续扩展**同一个连续查找区间**。

但后续列并不因此在所有意义上“完全没用”：它们还可能参与过滤、覆盖、Index Condition Pushdown 或其他优化，具体取决于执行计划。

所以要区分：

```text
用于构造查找边界
≠
整个执行过程完全没有使用该列/该索引
```

### 6. `!=`、`<>`、`IS NOT NULL`、`OR`、`IN` 不能一刀切

这些条件经常出现在“索引失效口诀”里，但 MySQL 8.4 的 range optimizer 可以处理多种 range 条件和区间组合。

例如 `OR` 有时可以被转换成多个 range 的并集；`IN` 本质上也可能形成多个等值区间。某些不等条件虽然选择性可能差，也不代表语法层面“必定不能使用索引”。

因此应该说：

```text
这些条件可能让选择性、range 构造或成本变差
→ 是否选索引必须看具体谓词、数据分布和执行计划
```

而不是：

```text
出现某关键字
→ 索引必然失效
```

### 7. 索引可用，但优化器故意不选

即使谓词形式支持索引，优化器仍然是成本驱动的。

例如：

- 表本身很小；
- 条件命中表里很大比例的数据；
- 通过索引回表的成本比顺序扫描高；
- 统计信息使优化器估计索引路径收益不高。

这时全表扫描可能是合理选择，不应该把它诊断成“索引坏了”。

如果统计信息可能陈旧，可以结合 `ANALYZE TABLE` 等手段刷新统计，再重新观察执行计划。

### 8. 最后用 `EXPLAIN` 验证

真正排查时，我不会只问“SQL 有没有踩口诀”，而会按顺序看：

```text
SQL 谓词
→ 列类型 / 参数类型
→ 可用索引结构
→ 选择性 / 统计信息
→ EXPLAIN 访问路径
→ 必要时 EXPLAIN ANALYZE 实际行数与耗时
```

核心是回答两个问题：

1. **理论上有哪些 access path 可用？**
2. **优化器最终为什么选择了这个 plan？**

这样才能区分“不能用”和“不值得用”。

## 关键细节

- **“索引失效”不是严格的优化器术语。** 更准确地描述“索引无法用于期望的 lookup/range”或“优化器没有选择索引”。
- **最左前缀是 B-Tree 排序结构带来的访问约束，不是 SQL 关键字规则。**
- **Skip Scan 是重要例外边界。** 缺少复合索引第一列谓词时，不能再绝对宣称“完全不可能利用这个索引”。
- **隐式类型转换要看转换方向和类型语义。** MySQL 官方给出的典型反例是 indexed string column 与 numeric value 的比较。
- **`LIKE 'abc%'` 和 `LIKE '%abc'` 完全不是一回事。** 前者有可构造的左前缀，后者没有。
- **函数不是绝对禁区。** 普通列索引与函数表达式不匹配时可能无法直接 lookup，但 functional key part 可以为表达式建立索引。
- **范围条件影响的是后续 key parts 如何参与区间构造。** 不要把它错误扩张成“后续列永远没用”。
- **低选择性不意味着索引结构失效。** 它可能只是让扫描计划成本更低。
- **统计信息会影响成本估算。** 计划异常时除了改 SQL，也要验证 stats 是否反映当前数据。
- **最终看 plan，不看口诀。** `EXPLAIN` 用来查看计划；需要实际执行统计时使用 `EXPLAIN ANALYZE`。

## 原理机制

为什么这些现象会被统称为“索引失效”？

因为 B-Tree 索引本质上提供的是一种**有序 key space 上的快速缩小搜索范围能力**。

一个条件要高效利用它，通常要满足两层条件：

```text
第一层：结构上能不能把谓词映射成索引 key 的有序范围？
        ↓
最左前缀 / 类型兼容 / 表达式匹配 / 可构造 range

第二层：即使能，成本上值不值得走？
        ↓
选择性 / 回表成本 / 表大小 / stats / 其他 access path
```

所以“索引没走”的根因可以写成：

```text
predicate
  ↓
能否转换成有效 key range / lookup？
  ├─ 否 → 索引难以作为期望的定位路径
  └─ 是
      ↓
成本比较是否占优？
      ├─ 否 → optimizer 选择 scan / 其他路径
      └─ 是 → 使用索引路径
```

这也解释了为什么死背关键字会出错：同一个 `OR`、范围条件或表达式，在不同索引设计和数据分布下可能产生完全不同的 access path。

## 项目经验版

来源没有给出真实线上慢 SQL、表结构、索引、行数、选择性、`EXPLAIN` 或延迟数据，因此不能虚构“某次线上通过加索引把查询从几秒降到几毫秒”。

真实排查我会做的是：

- 先拿到完整 SQL、绑定参数和值的类型；
- 查看表定义和真实索引列顺序，确认联合索引左前缀和表达式是否匹配；
- 用 `EXPLAIN` 看候选/实际访问路径，不因为看到 `ALL` 就直接下结论；
- 关注估算 rows、过滤比例、回表需求和排序/临时表等额外成本；
- 如果估算明显偏离数据现实，检查统计信息并考虑 `ANALYZE TABLE`；
- 对风险可控的查询使用 `EXPLAIN ANALYZE` 对比估算和真实执行，再决定改 SQL、改索引还是接受扫描。

这些是验证流程，不是当前来源已经发生过的项目事实。

## 常见追问

- 问：联合索引 `(a,b,c)`，只查 `b` 一定不走索引吗？答：普通最左前缀 lookup 不成立，但现代 MySQL 可能使用 Skip Scan 等策略，所以不能绝对说“完全不会用”；最终看 `EXPLAIN`。
- 问：范围查询后面的索引列是不是完全失效？答：不准确。范围列通常限制后续 key parts 继续扩展同一个 range interval，但后续列仍可能参与过滤、覆盖或其他优化。
- 问：`LIKE` 一定不走索引吗？答：不是。`LIKE 'abc%'` 有固定前缀，可以形成 B-Tree range；`LIKE '%abc'` 因为左侧没有固定前缀，不能用同样方式定位。
- 问：对索引列加函数一定失效吗？答：原普通列索引可能与表达式不匹配，但 MySQL 支持 functional key parts；应该看是否存在匹配表达式的索引，而不是看有没有函数两个字。
- 问：为什么字符串列和数字比较会有问题？答：类型转换可能改变比较语义。MySQL 明确记录了 indexed string column 与 numeric value 比较时不能用该字符串列索引做快速 lookup 的情况。
- 问：`!=`、`OR`、`IN` 都不能走索引吗？答：不能这样背。range optimizer 可以处理多种不等、区间并集和等值集合；选择性和成本仍决定最终计划。
- 问：SQL 看起来都满足索引规则，为什么还是全表扫？答：索引“可用”不等于“最便宜”。小表、低选择性、大量回表、统计信息等都可能让扫描成本更低。
- 问：怎么证明到底有没有使用索引？答：先看 `EXPLAIN`，需要实际执行数据时再看 `EXPLAIN ANALYZE`，结合列类型、索引定义和统计信息解释计划。

## 易错点

- 把“没有走索引”说成“索引结构坏了”。
- 机械背“联合索引必须从第一列开始”，完全忽略 Skip Scan 等现代优化。
- 看到范围条件就说“后面的列全部失效”，没有区分 range boundary、过滤和覆盖用途。
- 把 `LIKE`、`OR`、`IN`、`!=`、`IS NOT NULL` 当成绝对禁用索引的关键字。
- 把隐式转换只理解成“SQL 写法不好看”，忽略它可能改变可索引的比较语义。
- 说“只要对列加函数就永远不能用索引”，忽略 functional index。
- 忽略选择性和成本模型，认为“建了索引就必须使用”。
- 不看 `EXPLAIN` 就凭口诀宣布索引失效。
