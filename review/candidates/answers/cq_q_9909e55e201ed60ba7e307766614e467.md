# 手写 Double-Checked Locking 单例：为什么必须加 volatile？

## 核心结论

来源明确要求“手写 double check 单例，为什么加 volatile，以及原理”。一个正确的 Java DCL 实现需要同时解决两件不同的事：**互斥初始化**与**安全发布**。内层 `synchronized` 让竞争初始化的线程一次只有一个进入创建分支；`volatile` 则让对单例引用的写入与之后其他线程对该引用的读取建立 Java Memory Model 的同步关系。JLS 17.4.5 明确规定：对 `volatile` 字段的写 happens-before 之后对该字段的读；因此读到非 `null` 引用的线程能够按 JMM 规则看到发布线程在该 volatile 写之前的初始化动作。

这里使用 Java 21 可编译的经典线性化实现；构造器无参数且不让 `this` 在构造期间逸出。Java 版本、构造器副作用以及反射/序列化是否也必须保持绝对单例，来源没有规定，因此不把这些额外边界冒充成原题要求。

## 1 分钟版

- `instance` 必须是 `static volatile`，因为第一次 `null` 检查发生在锁外。
- 外层检查让单例创建完成后的常见路径不再进入锁。
- 进入 `synchronized` 后必须再检查一次：多个线程可能都在第一次检查时看到 `null`，但只有第一个拿到锁的线程应该创建对象。
- `synchronized` 主要解决“谁来创建”；`volatile` 主要解决“创建结果如何安全发布给不加锁的快速路径”。
- JMM 保证 volatile 写 happens-before 后续 volatile 读，因此发布线程在写 `instance` 前的初始化动作可以经 happens-before 传递给读线程。
- 不能只解释成“volatile 让变量立刻刷新到主内存”；面试时应落到 **happens-before / visibility / safe publication**。

## 3 分钟版

```java
final class Singleton {
    private static volatile Singleton instance;

    private Singleton() {
    }

    static Singleton getInstance() {
        Singleton local = instance;
        if (local == null) {
            synchronized (Singleton.class) {
                local = instance;
                if (local == null) {
                    local = new Singleton();
                    instance = local;
                }
            }
        }
        return local;
    }
}
```

执行路径可以分成两类。第一次初始化时，多个线程都可能在锁外读到 `null`，随后竞争 `Singleton.class` 的监视器。第一个进入临界区的线程再次检查仍为 `null`，创建对象并通过 volatile 写发布；后续进入临界区的线程第二次检查已经是非 `null`，不会重复创建。

初始化完成后的普通调用只做一次 volatile 读，把结果放到局部变量后直接返回。局部变量不是正确性的必要条件，但可以避免同一次调用里重复读取 volatile 字段，同时让两次检查对应同一个局部引用更清楚。

## 关键细节

- **为什么两次检查都需要**：第一次检查优化已初始化后的快速路径；第二次检查保证排队进入锁的线程不会重复构造。
- **为什么 `volatile` 不能省**：外层读取没有持有创建时的锁。若字段不是 volatile，这个锁外读与写之间缺少本实现所需的 happens-before 发布边；不能依据“最终总会看到最新值”来证明正确性。
- **volatile 的规范语义**：JLS 17.4.5 规定 volatile 写 happens-before 每个后续对同一字段的 volatile 读；JLS 8.3.1.4 说明 volatile 字段由 JMM 提供跨线程一致可见语义。
- **happens-before 的传递性**：构造线程中，对对象字段的初始化动作按程序顺序发生在 `instance = local` 之前；volatile 写又 happens-before 读线程随后读到该发布，因此初始化动作可以通过传递性排在读线程使用对象之前。
- **不要把原理简化成“三步重排”**：实现层面常用“分配内存 → 初始化 → 写引用可能重排”帮助理解，但 Java 正确性应以 JMM 的数据竞争、同步动作和 happens-before 规则来证明。
- **`synchronized` 仍不可少**：volatile 不提供“检查为 null + 构造 + 写回”这一整段复合操作的互斥；没有锁时多个线程仍可同时创建多个对象。
- **构造期间 `this` 逸出**：即使引用字段使用 volatile，如果构造器把 `this` 通过别的路径提前发布，仍会引入额外安全发布问题；本候选明确不这么做。
- **反射与序列化**：DCL 只解决正常代码路径下的并发懒加载；若题目要求抵抗反射创建或序列化产生新实例，需要另外设计，常见替代是枚举单例。

## 原理机制

DCL 的关键不是“锁两次”，而是把昂贵的互斥限制在初始化阶段，同时给锁外读取建立合法的发布关系。创建线程在监视器内构造对象，最后对 volatile `instance` 写入；读线程以后从同一个 volatile 字段读到该引用。volatile 的 synchronizes-with / happens-before 规则把两条线程的执行连接起来，而同线程程序顺序与 happens-before 传递性把构造期间的初始化也纳入这个可见性链条。

如果把 `volatile` 去掉，内层 `synchronized` 仍能约束那些真正进入锁的线程，但快速路径根本不进锁，因此不能用监视器 unlock→lock 规则证明快速路径看到的是被正确发布的对象。DCL 的特殊点正是“读大多在锁外”，所以需要 volatile 来补上跨线程发布边。

## 项目经验版

来源没有真实项目背景，不能虚构线上使用经历。工程上如果只是需要一个无参数、延迟初始化的单例，我会先评估静态初始化 holder 或枚举是否更简单；只有确实需要 DCL 的懒加载形态时，才承担这套并发推理成本。若构造过程可能失败、需要参数、需要可替换依赖或生命周期管理，则应重新设计，而不是把所有状态都塞进单例。

## 常见追问

- 问：`synchronized` 已经有可见性，为什么还要 volatile？答：只有进入同一监视器的线程才能直接利用 unlock→lock 的 happens-before；DCL 的快速路径不加锁，因此需要 volatile 为发布写和快速路径读建立同步关系。
- 问：volatile 能保证 `instance == null` 到 `new Singleton()` 的原子性吗？答：不能。volatile 保证其规范定义的可见性和有序性语义，不会把多步复合操作变成互斥临界区，所以仍需要 `synchronized`。
- 问：第二次 `if (local == null)` 能删吗？答：不能。多个线程可能在外层同时看到 `null` 并依次拿到锁；没有第二次检查，每个线程进入后都可能重新创建实例。
- 问：为什么先读到局部变量 `local`？答：正确 DCL 也可以直接多次读 volatile 字段；局部变量主要用于减少同一调用中的 volatile 读取并让返回值与检查值一致。
- 问：volatile 是不是保证所有对象字段都变成 volatile？答：不是。它作用于 `instance` 这个字段；安全发布效果来自 volatile 写/读的 happens-before 边以及程序顺序和传递性，不是把被引用对象的每个字段改成 volatile。
- 问：更简单的单例写法是什么？答：如果需求允许，可以使用类初始化 holder 利用 JVM 类初始化语义，或用 `enum`；它们通常比手写 DCL 更不容易出错。

## 易错点

- `instance` 忘记声明为 `volatile`，却仍在锁外读取。
- 只有外层一次 `null` 检查，多个排队线程重复创建。
- 认为 volatile 可以代替互斥锁完成复合初始化。
- 只背“禁止指令重排”，说不清 volatile 写→读 happens-before 与安全发布链条。
- 构造器中提前泄露 `this`，破坏候选所依赖的发布边界。
- 把 DCL 能解决的并发懒加载问题扩张成“天然防反射、防序列化”的绝对单例保证。
