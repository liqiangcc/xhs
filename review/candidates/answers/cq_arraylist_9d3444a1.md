# ArrayList 和 LinkedList 的区别

## 核心结论

在 Java SE 21 中，`ArrayList` 是可扩容数组，适合按下标随机读写和主要在尾部追加；`LinkedList` 是双向链表，同时实现 `Deque`，适合明确需要双端队列语义的场景。不要把“链表头尾插删快”简化成“业务里总该用 LinkedList”：按下标定位前仍要遍历链表，常规 `List` 场景应先按访问模式和实测选择。

## 1 分钟版

- 底层：`ArrayList` 用连续的可扩容数组；`LinkedList` 由双向节点连接，并实现 `List` 和 `Deque`。
- 访问：`ArrayList` 的 `get`、`set` 和 `size` 是常数时间；`LinkedList` 按下标访问从较近的一端开始遍历。
- 修改：`ArrayList` 中间插入或删除要移动后续元素；尾部 `add` 是摊销常数时间。`LinkedList` 在已经拿到节点/迭代器位置后改链即可，但先按 index 找位置的遍历成本不能省略。
- 选择：大量随机访问、遍历和尾部追加优先 `ArrayList`；确实要 `Deque` 的首尾入队/出队可选 `LinkedList`，也要与其他 `Deque` 实现一起按需求评估。

## 3 分钟版

两者都实现 `List`、都允许 `null`，差异来自数据布局。`ArrayList` 的元素在内部数组中按下标存放；官方文档明确 `size`、`isEmpty`、`get`、`set` 和迭代器操作是常数时间，尾部 `add` 是摊销常数时间，其他操作大体线性。数组满时会扩容并复制；扩容策略的具体细节并不是 API 契约，不能把某个 JDK 源码里的倍率背成通用规则。

`LinkedList` 是双向链表，并实现 `Deque`。它按 index 操作时从头或尾中较近的一端遍历，所以随机访问仍是线性量级。不能只说“链表插删 O(1)”：如果只有 index，定位成本已经是一次遍历；只有已定位的插删才不需要像数组那样移动后续元素。

两者都不是线程安全容器；发生结构性并发修改时需要外部同步。两者的 fail-fast 迭代器只是尽力发现并发修改错误，不能依赖 `ConcurrentModificationException` 保证并发正确性。选型时先问访问是否随机、插删位置是否已知、是否需要双端队列和并发策略；最后用真实负载压测，而不是只按 Big-O 下结论。

## 关键细节

- `ArrayList` 的容量不等于 `size`；可用 `ensureCapacity` 预留已知的大批量容量以减少增量重新分配，但增长策略细节未由规范承诺。
- `ArrayList.add(index, e)` 会右移该位置及其后的元素，因此中间插入的搬移成本与尾部追加不同。
- `LinkedList` 的 `addFirst`、`addLast`、`removeFirst`、`removeLast` 是其 `Deque` 能力；按下标访问则需要走链。
- 两者都允许 `null`。若业务把 `null` 当作“空队列”的信号，要特别注意 `peek`/`poll` 的返回约定与数据含义，不要仅凭容器名推断。
- 文档结论的适用边界是 Java SE 21 API；复杂度只能说明增长趋势，具体工作负载仍应以压测验证，不能把 API 的复杂度说明当成端到端延迟承诺。

## 原理机制

`ArrayList` 的状态是“数组 + 当前 size”。读取 `i` 时用下标直接定位；在中间插入时，要为新元素腾出连续位置，后半段元素右移；容量不足时需要扩容。API 契约由此给出尾部追加的摊销常数成本，而不是每次追加都恒定成本。

`LinkedList` 是双向链表；但 `get(i)`、`add(i, e)` 或 `remove(i)` 先要从离 `i` 更近的一端走到目标位置。也就是说，链表可能避免已定位位置附近的数组搬移，却不提供免费获得任意位置的插删。

## 项目经验版

项目映射提示：用真实调用链说明列表是“按 id 随机取第 i 个”“批量尾部积累”“已持有迭代器删除”还是“队列首尾消费”；再提供容量、元素数量和压测数据。没有这些证据时，只陈述 Java SE 21 的容器语义，不要编造一次集合替换带来的吞吐或延迟收益。

## 常见追问

- 问：为什么 `ArrayList` 尾插不是每次都 O(1)？答：容量不足时必须分配更大数组并复制元素；API 保证的是一系列尾插的摊销常数成本，不是单次永远常数。
- 问：为什么不能说 `LinkedList` 的中间插入一定 O(1)？答：只有已拿到目标节点或迭代器位置时，改链接才是常数；若从 index 开始，要先遍历到该位置。
- 问：两者能否在多线程下直接安全遍历和修改？答：不能。两者都要求对结构性并发修改做外部同步；fail-fast 只是尽力报错，不能作为同步机制。
- 问：`LinkedList` 为什么还能当队列或双端队列？答：它实现了 `Deque`，提供首尾插入、删除和查看操作；是否采用仍应结合并发、容量和吞吐要求。

## 易错点

- 不要把某个 JDK 的数组扩容倍率说成 `ArrayList` 的稳定 API 契约；官方只承诺自动增长和尾插摊销常数时间。
- 不要把 `LinkedList` 的“链表插删快”说成“按 index 插删总是 O(1)”；定位成本没有消失。
- 不要因 fail-fast 会抛异常就把它当作并发正确性保证；文档明确它只是 best-effort 的 bug 检测。
- 不要只按复杂度选型；API 的复杂度说明不是端到端性能承诺，真实工作负载需要验证。
