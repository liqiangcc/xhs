# 链表大数求和：高位在头、个位在尾时从尾部进位

## 核心结论

仓库原始图片转写 `note_img_txt/694512cd000000001e004d1a.txt` 明确保留了题目：两个链表表示大数，**头节点是最高位、尾节点是个位**，要求输出两数之和的新链表；紧接着还要求说明时间和空间复杂度。

因为单链表的遍历方向与加法进位方向相反，直接从头同时遍历无法在不知道低位进位的情况下确定高位。若不假设可以修改输入，一个清晰稳定的做法是：分别把两个链表的数字压栈，再从栈顶（个位）向高位做逐位加法，并把新节点不断头插到结果链表。

设两条链表长度为 `m`、`n`：遍历入栈 `O(m+n)`，逐位相加仍是 `O(m+n)`；两个栈使用 `O(m+n)` 辅助空间，结果链表本身需要 `O(max(m,n))` 输出空间。

源材料没有规定输入是否允许被修改、空链表语义、是否允许前导零。这里把“非空、每节点为 0..9、不修改输入、不主动去除前导零”作为候选实现契约，而不是伪装成原题逐字条件。

## 1 分钟版

这题的关键是“高位在头、低位在尾”，而加法必须从个位开始传播 carry，所以单链表遍历方向和运算方向冲突。

我会把两条链表分别压入栈。之后每轮弹出一个最低剩余位，计算 `sum = digitA + digitB + carry`；新节点保存 `sum % 10`，carry 更新为 `sum / 10`。因为我们是从低位往高位计算，所以每次把新节点插到结果链表头部。两个栈都空以后，如果 carry 还不为 0，再补一个最高位节点。

时间复杂度 `O(m+n)`，额外空间 `O(m+n)`；优点是不修改输入，边界和正确性都比较直观。

## 3 分钟版

用栈以后可以维护一个清晰不变量：每轮开始时，两个栈顶分别是各自**尚未处理部分的最低位**，`carry` 是已经处理完的更低位向当前位产生的唯一进位。当前位求和后，把结果数字头插，就能保证 `result` 始终表示已经计算出的低位后缀，但链接顺序已经恢复为最高位在头。

长度不一致时，较短链表的栈先空，缺失位按 0 处理即可。最后的 carry 可能新增一位，例如 `999 + 1 = 1000`。

如果面试官允许修改输入，也可以先反转两条链表再逐位相加，把额外辅助结构降到 `O(1)`（不计输出），但反转会改变输入，不能在题目未授权时默认采用。递归回溯也能从尾部开始处理，不过需要 `O(max(m,n))` 调用栈，并且超长链表存在栈深风险。

不能先把链表转成 `long` 再相加：题目叫“大数”，长度可能超过固定宽度整数；正式算法应按位计算而不是依赖机器整数容量。

## 关键细节

- 原题明确的是“头为高位、尾为个位、输出新链表、说明复杂度”；输入可变性、null 和前导零语义没有给出，必须单独声明实现契约。
- 两条链表长度不同时，已经耗尽的一侧按 0 参与当前位计算。
- 循环条件必须包含 `carry != 0`，否则 `999 + 1` 会漏掉最高位 `1`。
- 新节点必须头插；如果尾插，会得到从个位到高位的反向结果。
- 每个输入节点只读一次且不改 `next`，因此候选实现满足“不修改输入”的自选契约。
- 节点 digit 必须限制在十进制 `0..9`；否则“逐位十进制进位”的证明前提不成立。
- 测试 oracle 使用 `java.math.BigInteger` 只用于验证，不用于正式解法，避免用同构算法自证正确。

## 原理机制

```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Objects;

public final class LinkedListBigIntegerAdd {
    public static final class ListNode {
        public final int digit;
        public ListNode next;

        public ListNode(int digit) {
            this(digit, null);
        }

        public ListNode(int digit, ListNode next) {
            if (digit < 0 || digit > 9) {
                throw new IllegalArgumentException("digit must be in [0, 9]");
            }
            this.digit = digit;
            this.next = next;
        }
    }

    public static ListNode add(ListNode left, ListNode right) {
        Objects.requireNonNull(left, "left");
        Objects.requireNonNull(right, "right");

        Deque<Integer> a = digits(left);
        Deque<Integer> b = digits(right);
        ListNode result = null;
        int carry = 0;

        while (!a.isEmpty() || !b.isEmpty() || carry != 0) {
            int sum = carry;
            if (!a.isEmpty()) sum += a.pop();
            if (!b.isEmpty()) sum += b.pop();
            result = new ListNode(sum % 10, result);
            carry = sum / 10;
        }
        return result;
    }

    private static Deque<Integer> digits(ListNode head) {
        Deque<Integer> stack = new ArrayDeque<>();
        for (ListNode node = head; node != null; node = node.next) {
            stack.push(node.digit);
        }
        return stack;
    }
}
```

正确性可以按“已处理低位数”归纳：初始尚未处理任何位，`carry=0`。每轮从两个栈弹出的正是当前最低未处理位，加上上一轮唯一可能产生的进位，`sum % 10` 因此就是当前结果位，`sum / 10` 是传给下一高位的唯一进位。把当前结果位头插后，已处理后缀在链表中的高低位顺序保持正确。循环结束意味着两侧所有位和最终进位都已消费，结果即完整和。

确定性验证包含 8 个固定用例和 5000 个随机大数用例，随机数最长 80 位；oracle 把输入链表序列化为十进制字符串后交给 `BigInteger` 求和，再与候选结果字符串比较。测试还在调用前后序列化两条输入，验证没有修改输入，并覆盖 null 与非法 digit 的 fail-fast 契约。

## 项目经验版

这是算法手撕题，源记录没有提供生产项目背景，不应虚构线上落地经验。可迁移的工程思想是：当数据结构的访问方向与计算依赖方向相反时，要么改变结构方向（反转），要么显式保存待处理状态（栈），并根据“是否允许修改输入”选择方案。

## 常见追问

- 问：如果允许修改输入链表，能不能降低辅助空间？答：可以先反转两条链表再逐位相加；代价是破坏输入，因此必须先确认契约，必要时还要恢复输入结构。
- 问：为什么结果节点要头插而不是尾插？答：计算顺序是个位到最高位，而输出要求最高位在头；头插正好把计算顺序反转回目标链表顺序。
- 问：两条链表长度不同怎么处理？答：某一栈耗尽后该侧当前位按 0 处理，继续消费另一栈和 carry。
- 问：为什么超长链表更倾向显式栈而不是递归？答：两者都是线性辅助状态，但递归会占 JVM 调用栈，链表很长时存在栈深风险。
- 问：为什么测试可以用 `BigInteger`，正式解法却不该直接用？答：测试需要结构不同的可信 oracle；正式解法若直接转 `BigInteger` 会绕过链表逐位进位这一考察点。

## 易错点

- 把“尾节点是个位”读反，误以为可以从头直接进位。
- 找到低位后把结果尾插，最终得到逆序数字。
- 循环只写成“两个栈任一非空”，遗漏最后一个 carry。
- 为了省空间直接反转输入，却没有先确认题目是否允许修改原链表。
- 用 `long`、`double` 或字符串转固定宽度整数处理“大数”，在长输入上溢出或丢精度。
- 把候选自己选择的 null、前导零策略写成“原题要求”，破坏 source-first 边界。
