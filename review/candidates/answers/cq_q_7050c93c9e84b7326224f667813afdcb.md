# 充值记录表建表 + 最近一个月累计充值金额最高用户

## 核心结论

这题有两个输出：先设计一张能表达“谁、什么时候、充了多少钱、这笔充值是否成功”的充值记录表，再在明确的时间窗口内只统计应计入的成功充值，按用户汇总金额并取累计金额最高者。

原题没有保存数据库方言、表名/字段名、充值成功口径、“最近一个月”到底是滚动一个月还是自然月，以及最高金额并列时如何处理。这里明确采用答案侧契约：选择一种支持示例中自增主键、定点金额与月份区间表达式的 SQL 方言；表名 `recharge_record`；金额用 `DECIMAL(18,2)`；只有 `status=1` 的成功充值计入；查询以参数 `:as_of` 为右开边界，统计 `[DATE_SUB(:as_of, INTERVAL 1 MONTH), :as_of)`；并列第一时用 `user_id ASC` 稳定地返回一名用户。具体方言不是原题约束，真实环境应按目标数据库改写 DDL 和日期函数。

## 1 分钟版

- 表至少要有主键、`user_id`、充值金额、状态、成功/支付时间和创建时间。
- 金额不要用浮点数，使用定点 `DECIMAL`，避免二进制浮点表示导致金额累计误差。
- “最近一个月”必须先定义边界；这里用滚动一个月、左闭右开区间，避免相邻批次在右边界重复统计。
- 查询先按 `status=1` 和 `paid_at` 时间窗口过滤，再 `GROUP BY user_id`，`SUM(amount)` 得到每个用户的累计充值金额。
- 最后 `ORDER BY total_amount DESC, user_id ASC LIMIT 1`。第二排序键只解决并列结果不稳定，不代表原题要求按用户 ID 排序。
- 若业务要求“并列第一全部返回”，不要 `LIMIT 1`，应对聚合结果做显式排名或与最大值再比较。

## 3 分钟版

一种具体 SQL 方言的示例建表（DDL 用于表达建模，不把方言细节冒充成原题约束）：

```text
CREATE TABLE recharge_record (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id     BIGINT UNSIGNED NOT NULL,
    amount      DECIMAL(18,2) NOT NULL,
    status      TINYINT UNSIGNED NOT NULL COMMENT '0=pending,1=success,2=failed',
    paid_at     DATETIME(3) NULL,
    created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (id),
    KEY idx_recharge_paid_status_user (paid_at, status, user_id),
    CONSTRAINT chk_recharge_amount_positive CHECK (amount > 0),
    CONSTRAINT chk_recharge_status CHECK (status IN (0,1,2))
);
```

最近一个月累计成功充值金额最高用户：

```sql
SELECT
    user_id,
    SUM(amount) AS total_amount
FROM recharge_record
WHERE status = 1
  AND paid_at >= DATE_SUB(:as_of, INTERVAL 1 MONTH)
  AND paid_at < :as_of
GROUP BY user_id
ORDER BY total_amount DESC, user_id ASC
LIMIT 1;
```

`:as_of` 最好由调用方显式传入，而不是把业务统计口径偷偷绑死到数据库服务器的 `NOW()`。这样重跑历史报表、测试边界和跨时区业务时更可控。

## 关键细节

- **金额类型**：`DECIMAL(18,2)` 是答案侧示例精度；真实业务若支持更多小数位或币种，需要按实际货币/产品口径调整。核心原则是金额采用定点语义，而不是 `FLOAT/DOUBLE`。
- **状态与时间一致性**：当前统计要求 `status=1` 且 `paid_at` 落在窗口内。真实系统还应定义成功状态写入与 `paid_at` 落库的一致性约束；来源没有这些细节，不应虚构。
- **时间窗口**：`DATE_SUB(:as_of, INTERVAL 1 MONTH)` 是“滚动一个月”，不是“上一个自然月”。如果题目要自然月，应改成月初/月末边界。
- **左闭右开**：`>= start AND < end` 让相邻窗口可以无重叠拼接，比两边都 `BETWEEN` 更容易避免边界重复。
- **并列第一**：当前只返回一名用户；`user_id ASC` 是确定性 tie-breaker。要求并列第一全返回时，语义必须改变。
- **索引**：示例索引以时间范围为第一列，适合先按最近一个月缩小候选记录；是否把 `status` 放第一列、是否需要覆盖 `amount`，必须根据数据分布、查询频率与执行计划验证，不能把示例索引当成万能最优方案。
- **退款/冲正**：来源只说充值金额，没有保存退款、撤销、冲正模型；若真实业务存在，应先定义净充值口径，再决定是过滤、负向流水还是另表关联。

## 原理机制

查询的数据粒度从“单笔充值流水”转换成“用户在统计窗口内的累计充值”。`WHERE` 负责确定哪些流水属于统计集合，`GROUP BY user_id` 建立用户分组，`SUM(amount)` 把每组多笔流水压缩成一条累计金额，最后才在用户聚合结果之间比较大小。

如果把 `LIMIT 1` 放到聚合前，就会变成“先挑一笔充值再统计”，完全改变问题；如果不先过滤成功状态或时间窗口，则累计金额的输入集合也错误。正确性先来自统计集合和粒度定义，索引只是让同一逻辑更高效。

## 项目经验版

来源没有真实充值表规模、QPS、成功率、退款模型、分库分表规则或执行计划，因此不虚构线上数据。真实落地会用生产 schema、状态机、时区口径和 `EXPLAIN` 验证时间范围扫描、状态过滤、聚合与排序成本，并根据统计频率评估明细表直接聚合、日汇总表或离线数仓方案。

## 常见追问

- 问：为什么金额不用 `DOUBLE`？答：金额通常要求十进制定点语义；二进制浮点无法精确表示很多十进制小数，累计时可能出现不期望的舍入误差。
- 问：为什么不直接 `WHERE paid_at >= NOW() - INTERVAL 1 MONTH`？答：可以，但把统计截止时间绑到数据库当前时间，不利于可复现重跑。显式 `:as_of` 更容易测试和重放历史统计。
- 问：最近一个月是不是上一个自然月？答：不一定。原题没说明；本答案采用滚动一个月。如果业务说“上月”，应改成自然月边界。
- 问：两个用户累计金额一样怎么办？答：当前契约按 `user_id ASC` 返回一个稳定结果；若要求全部并列第一，则需要显式排名或先求最大累计金额再过滤。
- 问：为什么索引是 `(paid_at, status, user_id)`？答：这是面向时间范围查询的示例起点，不是无条件最优；最终列顺序要看时间窗口选择性、状态分布和执行计划。
- 问：`paid_at` 为什么允许 NULL？答：示例让未完成/失败记录可以没有成功支付时间；成功记录是否强制非空应由更完整的业务状态约束保证，原题没有给出该状态机。

## 易错点

- 没定义“最近一个月”，直接把滚动月和自然月混为一谈。
- 用 `FLOAT/DOUBLE` 保存并累计金额，却不说明精度风险。
- 把失败/待支付记录也加入充值总额。
- 先 `LIMIT` 明细再聚合，导致统计集合错误。
- 忽略并列第一的业务语义，却声称结果唯一。
- 把示例字段名、状态编码、金额精度和索引顺序说成原题已给条件。
