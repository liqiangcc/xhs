# TCP 三次握手和四次挥手：状态如何推进，以及为什么不能只背“三”和“四”

## 核心结论

TCP 建立连接的三次握手，本质是**双方分别提出自己的初始序列号，并让对方明确确认这个序列号已经收到**；第三个 ACK 使被动打开方知道自己的 SYN/初始序列号已被主动打开方接收，避免只凭一个可能是旧重复的 SYN 就把连接当成完全建立。正常关闭常见“四次挥手”，则是因为 TCP 的两个发送方向独立关闭：收到对端 FIN 后可以先 ACK，而本端应用什么时候结束自己的发送方向是另一个决定，所以自己的 FIN 往往稍后才发。

## 1 分钟版

以 A 主动建立、B 被动监听为例：

1. A 发送 `SYN(seq=x)`，进入 `SYN-SENT`。
2. B 收到 SYN 后发送 `SYN(seq=y, ACK=x+1)`，进入 `SYN-RECEIVED`。这个报文既确认 A 的 SYN，也给出 B 自己的初始序列号。
3. A 收到后发送 `ACK=y+1` 并进入 `ESTABLISHED`；B 收到这个可接受的 ACK 后也进入 `ESTABLISHED`。

第三次不是“为了凑三次”。两次只能让 A 知道 B 收到了 A 的 SYN，也让 A 得到 B 的序列号；**B 还缺少一个证据：A 确实收到了 B 的 SYN/序列号。** 最后 ACK 补上这条确认链，同时让旧重复 SYN 更难直接形成一个被误认为已完全建立的新连接。

关闭时，A 的 `FIN` 只关闭 A→B 的发送方向。B 收到后先 ACK，此时 B 仍可能有数据要发；等 B 的应用也关闭，再发送自己的 FIN，A 再 ACK。因此抓包里常见 `FIN -> ACK -> FIN -> ACK`，但如果 ACK 与本端 FIN 能合并，正常关闭也可能少于四个报文，所以“四次”不是不可变化的包数规则。

## 3 分钟版

### 建立连接

先把三个报文分别回答成“谁在证明什么”：

`A -- SYN(seq=x) --> B`

A 告诉 B：“如果要建立这条连接，我这一方向的初始序列号从 x 开始。”SYN 本身占用一个序列号，因此后续确认值是 `x+1`。

`A <-- SYN(seq=y), ACK(x+1) -- B`

B 一边确认已经收到 A 的 SYN，一边提出自己的初始序列号 y。此时 A 已经能确认两件事：自己的 SYN 到了 B，B 的 SYN 也到了 A。

`A -- ACK(y+1) --> B`

最后这个 ACK 告诉 B：“你的 SYN 和初始序列号 y 我也收到了。”B 收到可接受的 ACK 后，双方对两个发送方向的初始序列空间都完成同步。

所以，比“确认双方都在线”更准确的表述是：**三次握手同步双方的初始序列号与连接状态，并形成双向的 SYN 确认闭环。** RFC 9293 还用旧重复连接请求的场景解释为什么三次握手能避免把历史 SYN 误当成一条新的、已经完全建立的连接。

### 关闭连接

假设 A 先主动关闭：

`A: ESTABLISHED --FIN--> FIN-WAIT-1`

B 收到 FIN 后确认它并进入 `CLOSE-WAIT`。这个 FIN 表示 A 不再发送新的数据，但不表示 B 也必须立刻结束自己的发送方向。B 的应用可能还需要把剩余响应发完。

当 A 收到对自己 FIN 的 ACK 后，通常进入 `FIN-WAIT-2`。之后 B 的应用执行关闭，B 发送自己的 FIN 并进入 `LAST-ACK`；A 收到 B 的 FIN 后回复最终 ACK，并进入 `TIME-WAIT`。B 收到最终 ACK 后关闭；A 在 TIME-WAIT 的协议安全窗口结束后再删除旧连接状态。

因此“建立三次、关闭四次”的关键差异不是 TCP 设计者任意选了两个数字，而是：

- 建立时，B 可以把“确认 A 的 SYN”和“发送自己的 SYN”合并到同一个 `SYN+ACK`；最后仍需要 A 再确认 B 的 SYN。
- 关闭时，“确认对端 FIN”和“本端应用决定发送自己的 FIN”不是同一件事，通常不能立即合并，所以常见两个方向各一次 FIN，并各自得到确认。

如果 B 在收到 A 的 FIN 时也正好准备关闭，ACK 与 B 的 FIN 可以合并；同时关闭时双方还可能经过 `CLOSING`。所以应按 TCP 状态机解释，而不是把抓包强行套成固定三包/四包模板。

## 关键细节

- **SYN 和 FIN 会占用序列号空间。** 这使它们可以像序列空间中的控制事件一样被确认和重传；纯 ACK 在不携带 SYN/FIN/数据时不会因为“只是 ACK”额外消耗一个序列号。
- **第三次 ACK 的核心是确认 B 的 SYN。** “验证客户端还能发一次包”只是现象层描述；协议层关键是让 B 知道自己的初始序列号已经到达 A，并完成双方序列空间同步。
- **旧重复 SYN 是三次握手的重要边界。** 如果旧连接遗留的 SYN 迟到，仅靠“收到 SYN -> 回一个 SYN+ACK 就认为连接完全建立”会更容易制造错误状态；三次握手要求对端针对当前 SYN/序列空间给出后续确认。
- **第三个 ACK 丢失不等于双方立刻永久失联。** B 仍在 `SYN-RECEIVED`，会按 TCP 重传/超时规则处理未确认的 SYN；A 如果再次收到相应的 SYN+ACK，会继续按当前连接状态响应。具体重试次数和超时数值属于实现参数，不能当成 RFC 的统一常量。
- **四次挥手是常见逻辑，不是固定报文数量。** ACK 可以和本端 FIN 合并；同时关闭、异常 RST、半关闭都会产生不同于教材标准时序的抓包。
- **FIN 只表达发送方向结束。** 收到 FIN 的一方仍可能继续发送数据，这就是为什么 `CLOSE-WAIT` 与应用何时关闭自己的发送方向有关。
- **TIME-WAIT 属于正常关闭语义的一部分。** 主动关闭方发送最终 ACK 后仍保留连接状态，用于处理关闭阶段的重传并隔离旧连接报文；具体 2MSL 机制可单独展开，不能用“浪费资源”概括。
- **连接建立存在状态与时延成本。** 在基本三次握手中，主动方至少要收到对端的 SYN+ACK 才能确认对端序列空间并发送第三次确认；半建立状态也需要 TCP 保存必要连接控制信息。具体 backlog、SYN flood 防护和快速建立机制取决于操作系统与扩展规范，应按目标实现单独验证。

## 状态机视角

### 主动建立方 A

`CLOSED -> SYN-SENT -> ESTABLISHED`

A 发送 SYN 后不能直接进入 ESTABLISHED，因为还不知道 B 为自己选择的初始序列号，也没有确认 B 接受了 A 的 SYN。收到合法 SYN+ACK 后，A 才具备发送最终 ACK 并进入已建立状态的条件。

### 被动建立方 B

`LISTEN -> SYN-RECEIVED -> ESTABLISHED`

B 在 `SYN-RECEIVED` 已经知道 A 的序列号并发送了自己的 SYN，但还不知道 A 是否真的收到了这个 SYN。只有收到针对当前握手的可接受 ACK，B 才完成这条确认链。

### 主动关闭方 A 的典型路径

`ESTABLISHED -> FIN-WAIT-1 -> FIN-WAIT-2 -> TIME-WAIT -> CLOSED`

### 被动关闭方 B 的典型路径

`ESTABLISHED -> CLOSE-WAIT -> LAST-ACK -> CLOSED`

这些是典型路径，不是所有连接唯一合法路径；同时打开、同时关闭、RST、半关闭都会走其他分支。

## 资源与性能边界

- **握手有网络时延成本。** 主动方必须等到 SYN+ACK 才能完成对服务端 SYN 的确认；如果应用频繁创建短连接，这个建立成本会反复出现。是否能通过连接复用或特定 TCP 扩展优化，要结合协议、内核和安全边界评估。
- **半建立连接有状态成本。** 服务端在握手完成前需要维护建立过程所需的信息；SYN flood 因而是经典攻击面。但“半连接队列多大、什么时候丢包、是否使用 SYN cookie”等都属于具体实现，不应从抽象状态机直接推断固定阈值。
- **关闭也有状态成本。** TIME-WAIT、CLOSE-WAIT 的数量本身不是故障结论，要结合连接创建/关闭速率、端口压力、应用 close 路径和真实错误指标判断。

## 项目经验版

真实排障时，不编造“项目里一定遇到过某次握手故障”。可验证的证据链通常是：先用连接指标确认建立失败或关闭异常，再用抓包核对 SYN/SYN+ACK/ACK 或 FIN/ACK 时序和重传，随后把四元组映射到进程、监听端口、代理链路和应用连接生命周期。若问题涉及 backlog、SYN cookie、重试次数、TIME-WAIT 复用等实现参数，再查目标内核版本的一手文档并做可回滚压测，而不是把某个 Linux 版本的默认值当成 TCP 协议常量。

## 常见追问

- **问：为什么三次，不能两次吗？** 答：两次后 B 还不能确认 A 已经收到 B 的 SYN/初始序列号。第三个 ACK 完成 B→A 方向 SYN 的确认，也让当前连接的序列空间与旧重复连接请求更清楚地区分。
- **问：三次握手是不是为了确认“双方收发能力都正常”？** 答：可以作为面试速记，但更准确的是同步双方初始序列号并互相确认 SYN。所谓收发能力，是这条确认链表现出的结果，不应替代协议机制本身。
- **问：第三个 ACK 丢了会怎样？** 答：B 仍未完成从 `SYN-RECEIVED` 到 `ESTABLISHED` 的确认条件，会继续按未确认 SYN 的重传/超时逻辑处理；A 收到重传的 SYN+ACK 后会再次响应。实现层具体超时和次数要查目标 TCP 栈。
- **问：为什么断开常见四次？** 答：两个发送方向独立关闭。收到 FIN 后可以先 ACK，但本端应用可能仍有数据要发，所以自己的 FIN 经常晚于 ACK。
- **问：挥手一定四个包吗？** 答：不一定。被动方如果已准备关闭，可以把 ACK 与自己的 FIN 合并；同时关闭或 RST 也会改变报文与状态路径。
- **问：FIN 后还能发数据吗？** 答：发送 FIN 的那个方向不再发送新的数据；另一方向仍可以继续，所以收到 FIN 后进入 CLOSE-WAIT 的一方仍可能把自己的剩余数据发送完。
- **问：为什么最后 ACK 的一方进入 TIME-WAIT？** 答：它需要保留旧连接状态以处理对端可能重传的 FIN，并给旧连接报文一个隔离窗口；不要把 TIME-WAIT 只理解为“多等一会儿”。
- **问：SYN flood 和三次握手是什么关系？** 答：攻击利用握手未完成阶段的状态/计算资源。防护手段和队列细节是实现相关问题，回答时要把 RFC 状态机与具体操作系统机制分开。

## 易错点

- 不要只说“三次握手是确认双方在线”；核心是**双方初始序列号的提出与确认闭环**。
- 不要说“两次绝对无法通信”，而应说明两次缺失了 B 对自身 SYN 已被 A 接收的确认，会破坏 TCP 建连所需的状态与旧重复保护语义。
- 不要把“客户端/服务端”与状态永久绑定；主动打开、主动关闭都可能由任意一侧承担。
- 不要说“断开连接协议规定抓包必须严格四个报文”；ACK 与 FIN 可以合并，同时关闭也有其他路径。
- 不要说收到 FIN 后双方都不能再发数据；TCP 两个方向独立关闭。
- 不要给握手重试次数、backlog 大小、TIME-WAIT 秒数等跨平台固定值；这些是实现和配置边界。
- 不要把 RST 当成正常 FIN 挥手的一部分；RST 是复位路径，语义与有序关闭不同。
