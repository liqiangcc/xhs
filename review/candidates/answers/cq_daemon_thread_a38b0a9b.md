# Java 守护线程的特点与应用边界

## 核心结论

守护线程是 JVM 不用来维持应用存活的线程：Java SE 21 中，所有已启动的非守护平台线程结束后，JVM 开始关闭流程。因此守护线程适合可随进程结束而放弃的辅助工作，不适合承载必须完成的订单写入、数据落盘或资源关闭。

## 1 分钟版

- 生命周期：守护/非守护只影响 JVM 是否等待它；守护线程仍是正常并发执行的线程，并非“低优先级”或“自动可靠退出”。
- 退出条件：所有已启动的非守护平台线程终止后，关闭流程开始；未启动的非守护线程不阻止它。
- 设置：平台线程的 daemon 状态在启动前用 `setDaemon(true)` 设置；对已存活线程调用会抛 `IllegalThreadStateException`。
- 场景：可中断的监控采样、缓存清理等辅助任务可考虑；必须提交、刷盘或释放关键资源的工作应由非守护线程配合显式停止和等待。

## 3 分钟版

Java SE 21 把平台线程区分为 daemon 与 non-daemon。守护线程不会延长 JVM 生命周期：当所有已启动的非守护平台线程已终止，JVM 开始关闭。它不是任务取消协议，因此不能用“设成 daemon”替代 shutdown、interrupt、join 和超时控制。

新建的平台线程默认是否为 daemon 会继承创建线程的状态；需要明确语义时，应在 `start()` 前设置。`setDaemon` 在平台线程已存活时会抛异常。Java 21 还要区分虚拟线程：虚拟线程总是 daemon，且不能通过 `setDaemon(false)` 改为非守护；不要把平台线程的运维结论直接套到虚拟线程。

选择的关键是任务丢失是否可接受。定期收集可丢弃的本地诊断信息可以使用守护线程，但任务本身仍要能接受进程关闭；写入、事务收尾、消费确认等有交付语义的工作，必须由应用的停止流程显式协调。守护线程不是 GC 的同义词，也不是任务完成协议。

## 关键细节

- `setDaemon(true)` 必须在 `start()` 前调用；对已存活的平台线程调用会抛 `IllegalThreadStateException`。
- 父线程创建的平台线程初始 daemon 状态继承父线程；线程工厂应显式设置并记录命名和异常处理策略，避免依赖调用方上下文。
- Java SE 21 中虚拟线程恒为 daemon，不能改为 non-daemon；平台线程与虚拟线程的这一边界必须分开说明。
- “JVM 开始关闭”不等于业务任务被优雅完成；有交付义务时，应用应维护自己的停止协议和超时。

## 原理机制

JVM 在存活性判断中关注已启动的非守护平台线程。它们全部结束后，JVM 不再因为守护线程继续运行而维持进程；所以守护线程适合依附于主业务生命周期的辅助循环。这个规则减少了后台线程忘记退出导致进程悬挂的风险，但代价是守护任务在进程关闭时不能承诺完成。

## 项目经验版

项目映射提示：说明后台任务是否允许丢失、应用停止时如何发出停止信号、如何等待关键任务以及超时后如何告警。没有真实生命周期日志和停止结果时，不要编造“守护线程保证了优雅停机”。

## 常见追问

- 问：守护线程会不会阻止 JVM 退出？答：不会。Java SE 21 的关闭条件是所有已启动的非守护平台线程结束；守护线程本身不维持 JVM 存活。
- 问：线程启动后还能改成守护线程吗？答：不能；对已存活的平台线程调用 `setDaemon` 会抛 `IllegalThreadStateException`，应在启动前设置。
- 问：守护线程能做消息消费和落盘吗？答：若结果必须交付就不应只依赖守护线程，因为 JVM 关闭不保证其工作完成；应使用显式停止、等待和超时处理。
- 问：虚拟线程能改成非守护吗？答：Java SE 21 中不能，虚拟线程的 daemon 状态始终为 true。

## 易错点

- 不要把 daemon 说成线程优先级、异常处理或自动资源回收机制。
- 不要只因任务在后台就设为 daemon；先判断中断或丢失是否可接受。
- 不要把“所有线程都结束”说成退出条件；Java SE 21 规定的是所有已启动的非守护平台线程终止。
- 不要忽略虚拟线程的 daemon 状态固定这一 Java 21 边界。
