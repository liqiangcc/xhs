# 如何设计支持 50 万 QPS/OPS 的站内未读消息系统？

## 核心结论

先把“50 万”变成可验证的工作负载契约，而不是直接把它等同于某个 Redis 节点、数据库分片或消息队列分区的能力。题目来源同时出现 QPS 和 OPS，因此设计前必须拆开：消息写入速率、定向 fanout 写入速率、未读列表查询 QPS、未读计数查询 QPS、标记已读写入速率，以及广播流量占比。**50 万是系统目标，单分片安全吞吐必须通过目标环境压测得到，再按容量公式扩容。**

我的默认架构是：

- **持久事实层**保存消息事实、收件关系/广播事实和用户已读状态，不能把 Redis 当成不可丢失的唯一事实源。
- **异步 fanout / materialization 层**把定向消息投递为“recipient -> ordered message reference”的收件索引；处理器按 `event_id + recipient_id` 幂等，副作用成功或可恢复后才推进消费确认。
- **Redis Cluster**承载热点未读计数、近期收件索引等可重建派生状态，按 recipient/user key 分片；Redis Cluster 能做 hash-slot 分片，但不等于强一致或绝对不丢写。
- **读状态**先定义语义：支持单条已读还是“读到某个 cursor 为止”，未读计数是否必须实时精确。能够使用单调 cursor 的场景优先保存 `last_read_seq/cursor`，避免每次读一条消息都更新大量记录。
- **广播与定向消息分流**：定向低/中 fanout 可按 recipient 写收件索引；全站广播不能每条消息都同步 O(用户数) fanout，应保留共享广播/topic 日志，再用用户 cursor/segment 状态计算或异步物化。
- **恢复闭环**必须包含 replay、幂等、非回退修复和 reconciliation。重复、乱序、mark-read 竞争或 Redis 丢失都不能永久把未读数多算、少算或把已读消息“复活”。
- **容量证明**按 `required_shards = ceil(target_rate / measured_safe_rate_per_shard)` 计算，并保留复制、峰值和故障 headroom；最终必须在目标环境做 50 万级负载、热点倾斜、故障切换和 backlog 恢复测试。

一句话：**真正要设计的是“持久消息/读状态事实 + 可重放 fanout + 可重建 Redis 索引 + 明确未读语义 + 可测的分片容量”，而不是用一个 Redis 大 key 扛 50 万。**

## 1 分钟版

我会按六步回答：

1. **先定语义和流量**：50 万到底是总请求、查询 QPS、消息 ingest OPS 还是 fanout writes/s；单条已读、读到 cursor、精确计数和广播占比分别是什么。
2. **分开事实与派生状态**：消息、收件/广播事实、read cursor/receipt 放持久层；Redis 只做热点 inbox index/count/cache，可从事实或事件日志重建。
3. **定向消息按 recipient 分片**：`recipient_id -> ordered message refs`，方便用户侧分页；Redis Sorted Set 可以作为一种近期有序索引实现，但一个用户 key 仍只落一个 slot，不能假设均匀哈希消除超级热点。
4. **异步 fanout 可重放**：Kafka partition 或其他可重放日志分片 worker；事件带唯一 `event_id`，以 `event_id + recipient_id` 做幂等，完成副作用后才 ack/commit。
5. **广播避免写放大**：全站广播保留共享不可变消息流，再用用户 cursor、分群 segment 或异步物化，避免同步向所有用户写一份。
6. **压测证明 50 万**：测每个 Redis/DB/queue shard 在目标数据大小和 p99 SLO 下的安全吞吐，再套容量公式；还要测 failover、热点用户、积压恢复和 Redis 重建。

核心不变量是：**持久事实不丢、读状态不回退、重复事件不重复计数、旧事件不能把已读状态复活，Redis 丢了可以重建。**

## 3 分钟版

### 1. 先把 50 万拆成容量模型

来源没有给流量构成，所以不能直接假定“50 万 QPS 都是 Redis GET”。我会先定义变量：

```text
R_list   = 未读列表查询 QPS
R_count  = 未读计数查询 QPS
W_msg    = 原始消息写入 OPS
F_target = 定向消息平均 fanout
W_read   = 标记已读/推进 cursor OPS
B        = 广播消息 OPS
```

定向 fanout 的逻辑写入量约为：

```text
fanout_write_rate ≈ W_msg_targeted × F_target
```

对于任一资源池：

```text
required_shards
  = ceil(target_rate / measured_safe_rate_per_shard)
```

`measured_safe_rate_per_shard` 必须在目标机器、目标消息大小、真实 key 分布和目标 p99 延迟约束下压出来，并留峰值、复制和单节点/单分片故障 headroom。不能从通用 benchmark 抄一个“Redis 单机 XX 万 QPS”就结束。

### 2. 数据模型：先定义“未读”

我会把状态拆成三类。

**消息事实**

```text
message(message_id, sender/topic, created_seq, payload_ref, ...)
```

**收件事实**

定向消息需要知道哪些 recipient 应该看到它。可以持久化：

```text
delivery(recipient_id, message_id, event_id, created_seq, ...)
```

如果业务使用 durable event log 作为可重放收件事实，也必须保证日志保留、checkpoint 和重建路径满足业务恢复目标。

**读状态**

如果产品允许“读到这里为止”，优先使用单调 cursor：

```text
read_cursor(recipient_id, stream_or_box, last_read_seq)
```

这样“全部读到 N”只需要推进一个单调值，读取时判断 `message.seq > last_read_seq`。如果必须支持“单条消息独立已读/未读”，再额外保存 receipt/exception set；不能拿 cursor 语义硬套所有产品。

未读 count 可以是派生值，但必须明确它是否要求实时精确。如果为了低延迟在 Redis 维护计数，就必须有从 durable delivery + read state 重算/对账的路径。

### 3. 定向消息：recipient index + 异步 fanout

题目提到“倒排索引”，这里我会先消歧：对于主读路径，我把它解释为 **recipient/user -> ordered message references**，不是全文搜索意义上的 token inverted index。

写入链路可以是：

```text
producer
  -> durable message/event log
  -> partitioned fanout workers
  -> durable delivery/read model
  -> Redis hot inbox/count materialization
```

worker 的关键不是“异步”两个字，而是恢复语义：

- 每个原始事件有稳定 `event_id`；
- 对每个 recipient 建立 `event_id + recipient_id` 或等价唯一约束；
- 重试/重复投递不能重复生成 delivery，也不能重复 +1 未读数；
- 只有 delivery/派生状态已经成功，或副作用已经被可靠记录可继续恢复后，才推进 ack/checkpoint；
- worker 崩溃后从 pending/未提交位置重放。

Redis Streams 的 consumer group 有 pending、ack、claim 机制；Kafka partition 则提供分片日志和消费者并行度。它们都只是实现选择，真正的契约是“可重放 + 幂等 + 副作用后确认”。

### 4. Redis：热点派生索引，不当唯一事实源

近期收件索引可以使用类似：

```text
inbox:{recipient_id}
  score  = created_seq
  member = message_id
```

Redis Sorted Set 能按 score 排序、范围读取；Redis Cluster 能把 keyspace 分散到 hash slots。但这里要明确三个边界：

1. 一个 `inbox:{user}` key 在稳定状态仍属于一个 slot，超级用户/热点账号会形成单 key、单 shard 热点；
2. Redis Cluster 的复制/故障切换不构成强一致保证，某些故障窗口里已确认写仍可能丢失；
3. `WAIT` 可以改善副本确认的数据安全性，但不能把 Redis 变成强一致事实库。

因此 Redis 丢失或回退后，系统必须能从 durable message/delivery/read state 或可重放日志重建。

### 5. 广播：避免 O(用户数) 同步 fanout

如果一条系统广播面向所有用户，直接为每个用户同步写一条 delivery，会产生巨大写放大：

```text
1 broadcast -> N recipients -> N delivery writes
```

我会把广播和定向消息分开：

```text
shared broadcast/topic log
        +
per-user / per-segment read cursor
        +
optional hot materialization
```

列表查询时把“个人 inbox + 可见广播区间”合并排序；对超热点 segment 可以提前物化或本地缓存。这样广播写入成本主要与广播条目/segment 数相关，而不是每次都同步乘用户总数。

如果业务要求广播也必须立刻得到一个绝对精确的 per-user unread count，就要明确承认这会把计算/物化成本重新引入系统，并通过异步分批、segment counters 或读时计算等方案折中。

### 6. 已读竞争、重复和乱序：禁止状态回退

最危险的问题不是正常请求，而是重放和竞态。

例如用户已经把 cursor 推进到 `100`，后来一个迟到 fanout/replay 事件又到达。系统必须保证：

```text
read_cursor_new = max(read_cursor_old, requested_cursor)
```

旧事件可以补齐缺失 delivery，但不能把 cursor 从 100 改回 90，更不能无条件把未读 count 再 +1。

如果维护 materialized count，可以采用“事实变更 + version/seq + 幂等事件”组合：

- duplicate delivery：唯一键拦截，不重复计数；
- out-of-order read：cursor 只单调前进；
- fanout-after-read race：消息 seq 若已经落在已读 cursor 之前，不应重新成为未读；
- Redis count 漂移：周期 reconciliation 从 durable state 重算并修复；
- cache rebuild：先取得一致的基线/水位，再 replay 后续事件，避免重建过程倒退。

### 7. 热点和分片

普通用户可以按 `hash(recipient_id)` 分片，获得良好局部性；但这只解决平均分布，不解决 skew。

对热点用户/热点广播，我会组合：

- 共享不可变广播数据，避免复制到一个巨大用户 key；
- 对超大 inbox 按时间 bucket/segment 拆 key，而不是无限增长单 ZSET；
- 批量 fanout、批量写和批量 ack，降低网络/协议放大；
- 热数据做进程内/边缘缓存，但仍保持 durable truth；
- admission control / rate limit，避免 backlog 无界增长；
- 单独监控 shard skew、hot-key rate 和最老积压年龄，热点达到阈值时迁移/拆分。

### 8. 观测、压测和故障验证

上线前不只测平均吞吐。至少验证：

- unread list/count 的 p50、p99、p999 latency；
- ingest、fanout、mark-read throughput；
- queue lag、oldest-event age、pending/retry；
- Redis hit rate、slot/shard skew、hot-key rate；
- durable store latency/错误率；
- unread-count drift 和 reconciliation delta；
- Redis shard 故障后的 rebuild time；
- worker 故障/重复消费后的幂等正确性；
- failover 时是否丢 delivery、是否出现 cursor 回退；
- backlog 恢复期间线上读路径是否仍满足 SLO。

最终必须在目标环境证明“50 万目标 + 规定 headroom + 一个关键组件故障”仍然满足业务 SLO，而不是只测正常状态峰值。

## 关键细节

- **QPS 与 OPS 先拆开**：查询、原始写入和 fanout write amplification 是不同维度。
- **倒排/收件索引先消歧**：这里的主索引是 recipient -> ordered message references，服务用户拉未读列表。
- **Redis 是派生状态**：Cluster 分片解决容量分布，不自动解决持久真值和强一致。
- **一个用户 key 仍是一个 slot 热点**：均匀 hash 不能消除 celebrity/hot-user skew。
- **广播与定向消息采用不同 fanout 策略**：系统广播默认避免每条同步复制到全部用户。
- **确认点在副作用之后**：无论 Streams ack 还是 Kafka offset/消费位置，都不能先确认再做不可恢复副作用。
- **幂等键要绑定 recipient**：一个 message/event 面向多个 recipient 时，只用 `event_id` 不能区分每个收件副作用。
- **read cursor 必须单调**：旧请求、迟到事件和 replay 都不能把已读水位拉低。
- **count 是派生数据就必须可修**：不要只有 `INCR/DECR` 没有重算/对账。
- **扩容要看顺序契约**：改变日志分区数或 sharding 策略时，要验证同 key 的顺序和映射假设是否仍成立。
- **容量数字必须压测得出**：不能把某篇 benchmark 的单机结果直接变成当前系统 shard count。

## 原理机制

这个系统可以理解为三个相互约束的状态机：

```text
Durable message/delivery facts
          ↓ materialize / replay
Hot recipient index + unread count
          ↑ repair / rebuild

Durable monotonic read state
          ↓ filters / corrects
What is actually unread for a user
```

正常路径追求低延迟，异常路径追求可恢复。Redis materialization 可以短暂落后、丢失或重建，但系统必须保持几个不变量：

1. durable message/delivery 事实不能因为 cache failure 消失；
2. 同一 `event_id + recipient` 重放不会重复生成逻辑 delivery；
3. read cursor/version 单调不回退；
4. 已经落在 read cursor 之前的消息不会被迟到事件永久复活为未读；
5. materialized count/index 可以从事实重新计算并收敛。

只要这五个不变量成立，缓存、worker 和分片可以通过重试、replay 和 reconciliation 恢复；如果它们不成立，单纯把 Redis 或 Kafka 节点堆多并不能证明系统正确。

## 项目经验版

来源没有给真实生产的用户数、读写比例、消息大小、保留期、节点规格、Redis/Kafka 版本、单 shard 吞吐或故障数据，因此不能虚构“线上就是多少台机器”。

真实落地时，我会先做 workload capture 和容量实验：

- 按接口拆分真实 RPS/OPS 与 payload；
- 统计 fanout 分布，不只看平均值，要看 P99 recipient fanout 和广播比例；
- 统计每用户 inbox 长度、活跃度和 hot-key skew；
- 测 Redis/持久层/消息日志在目标数据体量下的 safe throughput 与 p99；
- 故障注入一个 Redis shard/一个 consumer group worker，观察 lag 和恢复时间；
- 人工制造 duplicate、out-of-order、ack-before-crash 等情况，验证幂等和 read-state 不回退；
- 删除一部分 Redis materialization，验证能否从 durable facts 重建并让 drift 回到零；
- 以小流量 shadow/双读对比上线，出现 count drift、lag 超标或 p99 恶化时可切回 durable/read-through 路径。

我会把“50 万”最终落成一份可重复的 load-test + failover report，而不是一张架构图上的数字。

## 常见追问

- **问：为什么不直接把每个用户的未读消息全放 Redis？**  
  答：Redis 可以承载热点派生索引，但 Cluster 不提供强一致事实语义，故障窗口仍有写安全边界；而且一个超级用户 key 仍会形成单 slot 热点。高价值消息应保留 durable truth 和重建路径。

- **问：为什么不用一个全局未读表，查询时 `WHERE user_id=? AND read=0`？**  
  答：小规模完全可以。高并发下要根据真实查询模式、索引体量和写放大测容量；recipient 分片和热索引是为了把主读路径局部化，不是为了否定数据库方案。

- **问：广播消息怎么处理？**  
  答：默认不做同步全用户 fanout。保留共享 broadcast/topic log，用户侧保存 cursor/segment 状态，查询时合并；只有压测证明必要时才对热点 segment 做异步物化。

- **问：Kafka/Streams 会重复消费怎么办？**  
  答：把 delivery 写设计成幂等，以 `event_id + recipient_id` 或等价业务唯一键去重；副作用成功后再 ack/commit，失败重放不会重复生成逻辑消息。

- **问：未读数怎么保证不乱？**  
  答：不要把 Redis 的 `INCR/DECR` 当事实。read state 要单调，delivery 要幂等，count 是 materialized view；出现漂移时从 durable delivery/read state 重算或 reconciliation 修复。

- **问：Redis `WAIT` 能不能保证消息不丢？**  
  答：`WAIT` 可以提高副本确认的数据安全性，但官方边界明确它不会让 Redis 变成强一致系统，所以不能用它替代 durable source/replay 设计。

- **问：怎么证明 50 万真的能扛？**  
  答：先测每类资源的安全单 shard 吞吐，再按容量公式和 headroom 算 shard/consumer 数；随后在目标环境做 50 万级混合流量、hot-key、failover 和 backlog-recovery 测试。没有这些证据就只能说“方案可水平扩展”，不能声称容量已证明。

## 易错点

- 把“50 万 QPS/OPS”直接解释成一个 Redis 节点要扛 50 万。
- 没定义未读语义就先选 ZSET、Bitmap 或数据库表。
- 把 Redis Cluster/`WAIT` 描述成强一致、绝对不丢的事实库。
- 定向消息和全站广播都使用同步 write-to-all fanout，忽略写放大。
- 只用 `event_id` 去重，却忘记同一事件对不同 recipient 有不同 delivery 副作用。
- ack/checkpoint 先于副作用完成，崩溃后永久漏投递。
- 重放时只会 `INCR unread`，没有版本/cursor 条件，导致重复计数或已读消息复活。
- 认为 `hash(user_id)` 后所有热点都会自动均匀，忽略单用户 key 仍只属于一个 slot。
- 只监控 queue depth，不监控 oldest-event age、shard skew、count drift 和 rebuild time。
- 用通用 benchmark 或虚构生产节点数证明 50 万容量。
