# SQL：三表关联查询与子查询

## 核心结论

来源只保留“三表关联查询及子查询的应用实现”，没有保留真实表结构、字段、业务口径或目标结果，所以不能虚构唯一 SQL。下面明确给出一个可执行参考练习：`students(student_id,name)`、`courses(course_id,name)`、`scores(student_id,course_id,score)` 三表；查询“平均分高于全体成绩平均分的学生”，返回学生学号、姓名、其平均分和有成绩的课程数。主查询用三表关联，相关粒度在学生层聚合；标量子查询计算全体 `scores.score` 的基准平均值。

## 1 分钟版

- 先确定结果粒度：一名学生一行，因此最终按学生主键/姓名分组。
- `scores` 是学生与课程的事实表，用 `student_id` 关联 `students`、用 `course_id` 关联 `courses`，避免缺失连接条件造成笛卡尔积。
- `AVG(sc.score)` 是每名学生自己的平均分；`COUNT(DISTINCT c.course_id)` 是有成绩的课程数。
- 子查询 `SELECT AVG(score) FROM scores` 返回一个全局标量，放在 `HAVING` 中和每个学生聚合结果比较。
- 这里采用 `INNER JOIN`，因此只返回至少有一条成绩的学生；是否保留无成绩学生是业务契约，来源没有规定。

## 3 分钟版

参考 schema 与目标如上，SQL 可以写成：

```sql
SELECT
    s.student_id,
    s.name,
    AVG(sc.score) AS avg_score,
    COUNT(DISTINCT c.course_id) AS course_count
FROM students AS s
JOIN scores AS sc
  ON sc.student_id = s.student_id
JOIN courses AS c
  ON c.course_id = sc.course_id
GROUP BY s.student_id, s.name
HAVING AVG(sc.score) > (
    SELECT AVG(score)
    FROM scores
)
ORDER BY s.student_id;
```

这里三表关联的作用不是“为了凑三张表”：`students` 提供学生维度，`scores` 提供成绩事实和两侧外键，`courses` 证明每条成绩对应有效课程并提供课程粒度计数。子查询只计算一次逻辑上的全局基准；主查询先按学生聚合，再由 `HAVING` 过滤聚合后的组。

## 关键细节

- **WHERE 与 HAVING**：行级过滤应尽量在聚合前用 `WHERE`；依赖 `AVG(sc.score)` 这类聚合值的条件必须在聚合后处理，因此使用 `HAVING`。
- **连接键完整性**：三表查询要逐条写清连接关系；遗漏 `c.course_id = sc.course_id` 会放大行数并污染平均值与计数。
- **为什么不用 `AVG(DISTINCT sc.score)`**：两门课程分数相同并不代表重复成绩；是否去重要依赖业务唯一键，不能按数值去重。
- **空集语义**：当 `scores` 为空时，全局 `AVG(score)` 为 `NULL`，主查询本身也没有学生分组，结果为空；若产品要求其他行为应另行定义。
- **重复成绩记录**：当前参考契约把 `scores` 每行都视为有效成绩。若同一学生/课程只允许一条有效成绩，应由 schema 唯一约束或题目口径保证，而不是查询里偷偷去重。
- **性能**：实际规模下先保证连接外键有合适索引，再看执行计划；是否重写为 CTE/派生表、是否物化全局平均值应根据目标数据库与数据量验证。

## 原理机制

关系代数上，先把学生、成绩、课程按键做连接，形成“学生 × 课程成绩”的事实行；`GROUP BY` 把事实行收缩到学生粒度；每个分组上的 `AVG` 产生学生平均分。标量子查询在独立的全体成绩集合上产生一个基准值，`HAVING` 再比较“组内聚合值”和“全局聚合值”。关键不变量是：任何过滤或连接都不能无意改变一名学生应该参与平均计算的成绩行集合。

## 项目经验版

来源没有真实项目 schema、数据量或执行计划，不能虚构线上优化收益。实际落地我会先核对主外键、成绩唯一性、无成绩学生语义和是否存在逻辑删除，再用目标数据库的 `EXPLAIN`、样本结果与基准数据验证行数和成本；这些是验证步骤，不是本题来源事实。

## 常见追问

- 问：子查询能改成 JOIN/CTE 吗？答：可以先在 CTE/派生表算全局平均值再与主查询比较；应以可读性和执行计划为准，不能假设某种写法永远更快。
- 问：为什么过滤平均分用 HAVING？答：因为学生平均分只有在分组聚合后才存在；`WHERE` 发生在分组前，不能直接过滤这个聚合结果。
- 问：没有成绩的学生怎么办？答：当前 `INNER JOIN` 明确排除；若要求保留，应改 `LEFT JOIN` 并继续定义 `AVG(NULL)`、课程数和比较基准的业务语义。
- 问：三表关联怎样避免重复统计？答：先确认 `scores` 的业务唯一键和表间基数；不能用 `DISTINCT score` 掩盖重复，应该从数据模型或明确的去重规则解决。
- 问：怎样验证 SQL 正确？答：准备单成绩、多成绩、相同分数、低于/等于/高于全局平均值、空表等 fixture，对照手算结果，同时检查三表连接后的行数。

## 易错点

- 在来源没有 schema 时把示例表名、字段和业务目标写成“原题就是这样”。
- 漏写某一条 JOIN 条件，形成笛卡尔积后仍对错误行集聚合。
- 用 `WHERE AVG(...)` 过滤聚合值，混淆 SQL 逻辑处理阶段。
- 用 `AVG(DISTINCT score)` 或无依据的 `DISTINCT` 掩盖数据模型问题。
- 没定义外连接、NULL、重复记录和空表语义，却把一种实现当成通用答案。
