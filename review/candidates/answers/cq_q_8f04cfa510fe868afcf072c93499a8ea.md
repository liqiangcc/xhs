# 两个线程交替打印 abababab：wait/notify 与 Semaphore

## 核心结论

这题本质是维护一个只有两个状态的“轮到谁”协议，而不是靠线程调度碰运气。`Semaphore` 版最直观：给打印 `a` 的线程初始 1 个许可、打印 `b` 的线程初始 0 个许可，每打印一次就把许可交给对方；`wait/notify` 版则用同一把 monitor 保护 `aTurn` 条件，线程在 `while` 条件不满足时 `wait()`，打印后切换状态并 `notifyAll()`。下面两种实现都让 `b` 线程先启动，证明顺序来自同步协议而不是启动先后。

## 1 分钟版

- `Semaphore`：`aPermit=1`、`bPermit=0`；A `acquire -> print a -> release b`，B `acquire -> print b -> release a`，许可像接力棒一样来回传递。
- `wait/notify`：共享 `aTurn=true`；所有条件读写都放在同一个 `synchronized(lock)` 里，条件不满足必须 `while (...) lock.wait()`，不能用一次 `if`。
- `wait()` 会释放当前对象 monitor，返回前会重新竞争并获得它；`notifyAll()` 只是唤醒等待者，真正继续执行仍要等当前线程退出同步块。
- 打印 2n 个字符的工作量是 O(n)；同步状态额外 O(1)。示例为了可测试返回字符串，因此结果缓冲本身是 O(n)，真实直接输出时不把输出介质算作同步辅助空间。

## 3 分钟版

```java
import java.util.concurrent.Semaphore;

public final class Solution {
    public String withSemaphores(int pairs) throws InterruptedException {
        if (pairs < 0) throw new IllegalArgumentException("pairs must be >= 0");
        StringBuilder out = new StringBuilder(pairs * 2);
        Semaphore aPermit = new Semaphore(1);
        Semaphore bPermit = new Semaphore(0);

        Thread a = new Thread(() -> {
            try {
                for (int i = 0; i < pairs; i++) {
                    aPermit.acquire();
                    out.append('a');
                    bPermit.release();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "print-a");

        Thread b = new Thread(() -> {
            try {
                for (int i = 0; i < pairs; i++) {
                    bPermit.acquire();
                    out.append('b');
                    aPermit.release();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "print-b");

        b.start();
        a.start();
        a.join();
        b.join();
        return out.toString();
    }

    public String withWaitNotify(int pairs) throws InterruptedException {
        if (pairs < 0) throw new IllegalArgumentException("pairs must be >= 0");
        Object lock = new Object();
        boolean[] aTurn = {true};
        StringBuilder out = new StringBuilder(pairs * 2);

        Thread a = new Thread(() -> runWithMonitor(lock, aTurn, true, 'a', pairs, out), "print-a");
        Thread b = new Thread(() -> runWithMonitor(lock, aTurn, false, 'b', pairs, out), "print-b");

        b.start();
        a.start();
        a.join();
        b.join();
        return out.toString();
    }

    private void runWithMonitor(Object lock, boolean[] aTurn, boolean myTurn,
                                char ch, int pairs, StringBuilder out) {
        try {
            for (int i = 0; i < pairs; i++) {
                synchronized (lock) {
                    while (aTurn[0] != myTurn) {
                        lock.wait();
                    }
                    out.append(ch);
                    aTurn[0] = !aTurn[0];
                    lock.notifyAll();
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

两种方案都把“谁能继续”编码成同步状态。Semaphore 把状态放在 permit 数量里；monitor 版把状态放在受锁保护的 `aTurn` 里。两者都不依赖 `sleep`，也不依赖哪个线程先获得 CPU。

## 关键细节

- **Semaphore 初始许可决定首字符**：A 为 1、B 为 0，因此 B 即使先启动也会阻塞，直到 A 打印后释放 B 的许可。
- **`wait` 必须放在 `while` 中**：JDK 明确允许 spurious wakeup；被唤醒后也可能需要重新检查条件，所以不能把 `if` 当成等待协议。
- **必须持有 monitor 才能 wait/notify**：`wait`、`notify`、`notifyAll` 都要求当前线程拥有该对象 monitor，否则会抛 `IllegalMonitorStateException`。
- **notify 不是“立刻交棒”**：被唤醒线程要等通知方释放 monitor 后才能继续；状态修改和通知应放在同一同步块中。
- **为什么这里用 `notifyAll`**：当前只有两个工作线程时 `notify` 也能设计正确，但 `notifyAll + while` 更不依赖“恰好唤醒正确等待者”的假设，也更容易在扩展等待者时保持条件协议。
- **中断边界**：示例线程在 `InterruptedException` 后恢复中断标记并退出。真实生产代码若要求“即使一方中断也不让另一方永久等待”，需要额外的取消状态和对端唤醒；这属于题目未要求的生命周期协议。
- **共享 `StringBuilder` 为什么可用**：Semaphore 版每次只有持有当前许可的线程执行 append，monitor 版 append 在同一 monitor 内；同步交接使两个 append 不并发执行。若改成其他访问模式，应使用线程安全输出策略。

## 原理机制

交替打印可以抽象成状态机 `A_TURN -> B_TURN -> A_TURN ...`。正确性需要两个不变量：第一，任意时刻最多只有当前状态对应的线程能执行打印；第二，一次打印完成后必须原子地把下一执行权交给另一方。Semaphore 用 `acquire/release` 实现许可交接，JUC 还定义了 release 之前的动作对另一线程成功 acquire 之后的动作具有 happens-before 关系。monitor 版则依靠 `synchronized` 保护条件状态，`wait()` 把线程放入该对象等待集并释放 monitor，醒来后重新获取 monitor，再由 `while` 重新验证状态。

## 项目经验版

来源没有真实项目经历，不能虚构“线上用 wait/notify 做过打印器”。工程里若只是两方轮流执行，Semaphore、Condition、BlockingQueue 等都能表达交接；选择时更重要的是取消、超时、异常传播和可观测性，而不是把面试题写法直接搬进生产代码。这里仅说明同步模型，不声称个人生产实践。

## 常见追问

- 问：为什么 `sleep` 不能保证严格交替？答：`sleep` 只延迟当前线程，不建立“下一次必须轮到谁”的同步关系；调度抖动后仍可能连续打印同一字符。
- 问：`wait()` 为什么一定要用 `while`？答：既要防 spurious wakeup，也要在重新拿到 monitor 后重新验证共享条件；JDK API 也推荐围绕条件使用 `while`。
- 问：`notify()` 和 `notifyAll()` 有什么区别？答：`notify` 任意唤醒一个等待线程，`notifyAll` 唤醒等待集里的全部线程；它们都不会让被唤醒线程绕过 monitor 竞争。
- 问：Semaphore 为什么能从 `a` 开始，即使 B 先启动？答：B 的初始许可是 0，会阻塞在 `acquire()`；A 初始许可是 1，可以先打印并 `release` 给 B。
- 问：两个方案怎么选？答：两线程接力时 Semaphore 更直接；若等待条件是多个业务状态且都受同一共享数据保护，monitor/Condition 往往更自然。真实系统还要把超时、中断和取消协议一起设计。

## 易错点

- 用 `sleep` 猜测线程调度顺序，把时间等待误当同步协议。
- `wait()` 前没有持有同一个对象的 monitor，直接触发 `IllegalMonitorStateException`。
- 用 `if` 包住 `wait()`，忽略虚假唤醒和重新竞争后的条件变化。
- Semaphore 两边初始许可都设成 1，导致 `a`、`b` 都能先打印；或都设成 0，直接死锁。
- 打印后忘记释放对方许可 / 切换状态并通知，第二轮开始永久阻塞。
