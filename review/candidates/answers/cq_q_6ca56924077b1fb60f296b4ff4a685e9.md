# 如何保证 Redis 缓存与数据库之间的数据一致性？

## 核心结论

先确定“一致性”到底要求什么。Redis 和 MySQL 是两个独立系统，Redis 的事务只能保证 Redis 内部命令的执行语义，不能和 MySQL 自动组成一个跨存储原子事务。因此多数读多写少业务不会承诺“缓存与数据库任意时刻绝对一致”，而是把 **MySQL/数据库作为事实源，Redis 作为可丢弃、可重建的派生状态**，明确一个可接受的短暂陈旧窗口，并用“正常路径 + 失败重试 + CDC/对账兜底”把不一致时间控制在 SLO 内。

我的默认方案是 cache-aside：

- 读：先查 Redis；miss 后查数据库，再写缓存并设置 TTL。
- 写：先提交数据库事务，成功后**删除缓存**，不直接把新值双写到缓存；删除失败进入可靠重试。
- 更高可靠性：用事务内 outbox 或 MySQL binlog/Canal 驱动异步失效，把数据库提交事实转换成可重放的缓存失效事件。
- 并发保护：如果做“刷新缓存”而不是单纯 `DEL`，事件必须带 version/change-position，旧事件不能覆盖新值；删除事件也要考虑去重、顺序和重放。
- 延时双删：可以作为并发读回填旧值时的**补充清理手段**，但固定 delay 只能降低概率，不是强一致性证明。
- TTL + 定期 reconciliation：作为最后安全网，避免一次失效消息永久丢失后缓存无限陈旧。

如果业务要求“数据库提交成功后任何读取都绝不能看到旧值”，我不会把普通 cache-aside、延时双删或 Canal 包装成强一致方案，而会让该读路径在一致性窗口内绕过缓存/做版本门禁，或者重新选择能把读写落到同一一致性边界的数据架构。

## 1 分钟版

我会按五层回答：

1. **先定目标**：数据库是真值，缓存允许多大的 stale window？是最终一致还是必须 read-after-write？
2. **正常写路径**：数据库事务先提交，提交成功后删 Redis。`DEL` 天然适合作为幂等失效动作；删失败必须可靠重试，不能只打日志。
3. **并发读竞争**：极端情况下，读线程先查 cache miss、读到旧 DB 值，随后写事务提交并删除 cache，最后这个读线程又把旧值回填。可加短 TTL、singleflight/互斥回填、版本校验，延时第二次删除也能缩短这类窗口，但不能保证零窗口。
4. **可靠异步修复**：通过 MySQL binlog + Canal/CDC 在数据库提交后异步删除或刷新 Redis；消费要有 checkpoint、重试、幂等、lag 监控，日志过期则用 DB 对账重建。
5. **兜底**：TTL、定期 reconciliation、告警和降级；一致性要求特别高的接口可临时绕过缓存或按版本确认缓存已追上。

一句话：**不要追求“神奇的双写顺序”，而要把 DB 当事实源，允许缓存失效，设计可检测、可重试、可重放、可对账的收敛机制。**

## 3 分钟版

先给一个明确的示例假设，数字只是容量设计输入，不冒充题目事实：

```text
读流量：20,000 QPS
写流量：500 QPS
热点对象缓存 TTL：5~10 min + jitter
允许普通读陈旧：<= 2 s
CDC 正常 lag SLO：P99 < 500 ms
一致性修复目标：异常后 5 min 内完成 backlog/reconciliation 收敛
```

在这个目标下，我会这样设计。

### 1. 读路径：cache-aside

```text
GET redis:key
  ├─ hit  -> return
  └─ miss -> SELECT DB
             -> SET redis:key value EX ttl
             -> return
```

缓存 miss 回填要防击穿：热点 key 可以用 singleflight/短锁让一个请求回源，其余等待或走受控降级。TTL 加随机抖动，避免大量 key 同时过期。

### 2. 写路径：DB 提交后失效缓存

```text
BEGIN
UPDATE mysql ...
COMMIT
  ↓
DEL redis:key
```

我优先“删缓存”而不是直接 `SET newValue`，因为缓存是派生状态，删除后下一次读可以从数据库重建；这减少“数据库和缓存两个新值谁才算提交成功”的双写协调面。

关键是 `COMMIT` 后的 `DEL` 仍可能失败：进程崩溃、Redis 超时、网络分区都会造成“DB 已新、cache 仍旧”。因此生产设计不能把这一步当成 best effort。

我会把失效任务做成可靠事件：

- **outbox**：在同一数据库事务里写业务数据 + cache-invalidation outbox，后台 worker 可靠投递/执行 `DEL`；
- 或 **binlog/CDC**：由 Canal 等从 MySQL binlog 订阅已提交变更，再生成缓存失效事件。

失效操作优先使用 `DEL`，重复消费只会多一次 cache miss，通常比“旧 CDC 事件直接 SET 旧值”更安全。

### 3. 最难的并发窗口

即便是“DB 后删 cache”，也有一个经典竞态：

```text
R: cache miss
R: SELECT old_value  ─────┐
W: UPDATE + COMMIT new    │
W: DEL cache              │
R: SET cache old_value  ◀─┘
```

结果是数据库已经是新值，但读线程把旧值在删除之后重新塞回缓存。

解决思路不是只背一个名词，而是按一致性目标组合：

- 回填加较短 TTL，限制最坏陈旧时间；
- 热点回填用 singleflight/互斥减少并发回源；
- 如果数据有单调 `version` / `updated_at`，缓存值也携带版本，只允许新版本覆盖旧版本；
- 数据库提交后的 CDC 再做一次失效；
- 对特别关键的写后读，客户端携带写入版本，缓存版本小于该版本则直接回源 DB。

### 4. 延时双删怎么理解

题目来源明确提到了“双删/延时双删”，我会说明它的作用和边界。

一种常见做法是在更新过程做一次删除，再等待一个略大于典型“旧读 + 回填”耗时的窗口后做第二次删除。第二次删除的目标，是清掉刚才竞态中重新写回的旧缓存。

但它有三个问题：

- delay 只是经验值，线程调度、GC、慢查询、网络抖动可能超过它；
- 第二次删除本身也可能失败；
- 高写入频率下，盲目延迟删除会制造额外 miss 和 DB 压力。

所以我把延时双删定位成**概率性补强**，而不是最终一致性的唯一基础。若使用，第二次删除也应该进入可重试任务，而不是业务线程 `sleep` 后赌一次。

### 5. Canal / binlog CDC 方案

Canal 的官方定位就是解析 MySQL 增量 binlog，提供增量订阅/消费，并明确包含 cache refresh 类用途。

```text
MySQL COMMIT
   ↓
binlog
   ↓
Canal / CDC
   ↓
cache invalidation topic / worker
   ↓
DEL Redis key
```

它的优势是数据库提交事实与缓存修复解耦：即使应用写请求在 commit 后立刻崩溃，CDC 仍可以看到数据库变更并补做缓存失效。

但 CDC 不是“自动强一致”：

- consumer 会有 lag；
- 消息可能重试、重复；
- checkpoint 必须在副作用成功后推进；
- binlog 有保留/清理边界，长时间停机后可能不能无限重放；
- 如果事件直接刷新值而不是删除，必须用 version/change-position 防止旧事件覆盖新状态。

因此要监控 oldest-event age、consumer lag、retry/DLQ、失效失败数和 reconciliation 差异。

### 6. 最终兜底：reconciliation

异步链路再可靠，也要有独立对账能力。例如按分片扫描最近更新的数据：

```text
DB version/value
      vs
Redis version/value
```

发现 cache 缺失或落后时删掉/刷新；如果 CDC 所需 binlog 已被清理，也可以从 DB 快照重新建立缓存基线。

## 关键细节

- **不要把 Redis 事务理解成 Redis + MySQL 分布式事务**。`MULTI/EXEC` 解决的是 Redis 内部命令队列执行问题。
- **数据库先提交**：DB 是事实源；只有 DB commit 成功后才允许缓存失效/刷新事件代表新事实。
- **删除通常比更新缓存安全**：重复 `DEL` 的副作用较小；直接更新缓存则需要更严格的版本/乱序保护。
- **延时双删不是强一致**：它依赖有限延迟假设，还存在第二次删除失败问题。
- **TTL 不是一致性协议**：它只提供“最迟多久旧 key 会自行消失”的时间上界的一部分，期间仍可能读旧。
- **CDC checkpoint 要和副作用语义绑定**：如果先提交消费位置、后删缓存失败，重启后可能永久跳过这次失效。
- **CDC 刷新必须防倒退**：缓存已是 v12 时，迟到 v11 不能把它覆盖；删除后的旧事件也不能把旧值复活。
- **删除消息可以重复，刷新消息要版本化**：幂等策略应随动作语义决定。
- **一致性和可用性有成本**：缓存版本门禁、强制回源会提高 DB 压力；过于频繁的失效会降低命中率。
- **高一致性读要有单独契约**：例如写请求返回 `version=42`，随后的读取发现 cache version < 42 就绕过缓存，而不是向所有流量强制关闭缓存。

## 原理机制

这个问题本质上不是“Redis 的某个命令怎么用”，而是**两个独立状态机之间没有共同原子提交点**。

设数据库状态为 `D(v)`，缓存状态为 `C(v)`。写入后真正要维持的不是“两个操作永远同时成功”，而是下面的收敛不变量：

```text
数据库版本单调前进
D(v+1) 成为事实
      ↓
缓存允许短暂 miss 或旧
      ↓
失效 / CDC / retry / reconciliation
      ↓
C 不得长期停在 v，也不得被迟到事件从 v+1 回退到 v
```

因此方案里有两类机制：

1. **正常路径缩小窗口**：DB-first、cache invalidation、singleflight、短 TTL；
2. **异常路径保证收敛**：可靠重试、outbox、binlog/Canal、幂等/version、防旧覆盖、reconciliation。

延时双删属于第一类的补强；CDC 和对账属于第二类。只设计正常路径，不设计异常后如何恢复，就不能说“保证一致性”。

## 项目经验版

来源没有提供真实项目的 QPS、Redis 拓扑、MySQL 版本、Canal 部署、允许陈旧窗口或事故数据，所以不能虚构“线上就是 20k QPS、500 QPS 写入”。

真实落地时，我会先收集这些量：

- cache hit ratio、miss QPS、热点 key 分布；
- DB 读/写 QPS 和回源余量；
- cache invalidation P50/P99 延迟和失败率；
- CDC lag / oldest event age；
- 同一 key 的最大写频率；
- 业务允许的 stale window；
- reconciliation 每分钟可扫描/修复的 key 数。

然后再决定是“DB-first + delete + retry”已经够用，还是需要 outbox/Canal、版本门禁，甚至某些关键读完全绕过缓存。上线时先对小流量 key 开 shadow reconciliation，观察 DB 与 Redis 的版本差异，再逐步扩大；回滚时保留“直接禁用缓存并回源 DB”的开关。

## 常见追问

- 问：为什么一般是更新 DB 后删缓存，而不是先更新缓存？
  答：数据库是事实源。缓存写成功但 DB 失败会把一个从未提交的值暴露出去；DB 成功后删缓存失败虽然也会暂时不一致，但可以通过 retry、TTL、CDC、reconciliation 收敛。

- 问：先删缓存再更新数据库行不行？
  答：可以作为某些双删流程的一部分，但会产生“删除后并发读从尚未更新的 DB 取旧值并回填”的窗口，所以仍依赖第二次删除或其他版本/CDC 修复，不能因为顺序换了就宣称强一致。

- 问：延时双删的 delay 设多少？
  答：没有通用常数。若使用，应基于旧读、DB 查询、回填和调度的高分位时延设定并留余量，但任何固定值都不能覆盖无限故障，所以第二次删除仍要可靠重试，并保留 TTL/CDC/对账。

- 问：Canal 为什么比业务代码自己删缓存可靠？
  答：它订阅数据库已经提交到 binlog 的事实，应用在 commit 后崩溃也不会让这次数据库变化天然消失；但 Canal/消费者仍会 lag 或失败，因此只是把修复变成可重放异步链路，而不是变成同步强一致。

- 问：CDC 用 `DEL` 还是直接 `SET` 新值？
  答：默认我更倾向 `DEL`，因为重复或迟到删除最多降低命中率；如果直接刷新值，则必须携带可比较的版本/change-position，防止迟到旧事件覆盖新值。

- 问：TTL 能不能解决所有问题？
  答：不能。TTL 只能让 stale key 最终过期，过期前依然可能错误；如果 key 被不断错误刷新，甚至可能一直延长错误状态。

- 问：怎么验证方案真的有效？
  答：压测正常读写之外，还要故障注入：Redis 超时、应用 commit 后崩溃、CDC 停 10 分钟、重复/乱序事件、binlog 缺口、热点 key 并发 miss；验证 stale window、DB 回源峰值、恢复时间和 reconciliation 差异是否满足 SLO。

- 问：如果必须做到写后读绝不旧呢？
  答：普通异步 cache-aside 不应冒充这个保证。可以让写请求返回版本，写后读在 cache 未追上该版本时强制回源，或者关键接口不走缓存；若整个系统都要求强一致，需要重新评估是否应该把 Redis 作为该数据的独立缓存副本。

## 易错点

- 直接说“先 DB 后 Redis 就能保证强一致”。
- 把 Redis `MULTI/EXEC` 当成能覆盖 MySQL 的分布式事务。
- 只背“延时双删”，不分析旧读回填竞态和第二次删除失败。
- Canal 消费先提交 checkpoint，再执行缓存失效，导致失败后永久漏修。
- CDC 直接 `SET` 值却没有版本保护，迟到旧事件把缓存回退。
- 把 TTL 当成一致性保证，而不是 stale-window/回收兜底。
- 只监控消费 backlog 条数，不看 oldest-event age 和 DB/Redis 实际差异。
- 为提高一致性盲目把所有读都强制回源，造成 DB 雪崩。
- 虚构具体项目 QPS、拓扑、版本和事故指标。
