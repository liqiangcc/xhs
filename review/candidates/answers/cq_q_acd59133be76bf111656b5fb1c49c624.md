# 如果你是 JDK String 类的设计者，如何实现 equals？

## 核心结论

`String.equals(Object)` 的语义不是“引用相同”，而是“对方也是 String，且字符序列完全相同”。实现顺序应先走 `this == obj` 快路径，再做类型检查，最后比较底层内容；`null` 会自然返回 `false`。如果自己设计一个不可变字符串类，还要保证构造时不泄漏可变数组，并让 `hashCode()` 与 `equals()` 保持一致。当前 OpenJDK 的实现也是这个结构，只是底层已不是简单的 `char[]`：在 Compact Strings 表示下会检查 coder 并比较内部 `byte[]`。

## 1 分钟版

- 第一层是引用快路径：`this == obj` 直接返回 `true`。
- 第二层是类型边界：只有同一种字符串值类型才继续比较；`null` 或其他类型直接 `false`。
- 第三层是内容比较：长度不同立即 `false`，长度相同再逐位置比较；第一个不同字符即可短路。
- 如果字符串类对外承诺不可变，构造时必须复制传入数组，不能让调用方之后改数组而改变对象的相等性。
- 重写 `equals()` 就必须同步实现与之相容的 `hashCode()`：两个 `equals` 为真的对象必须有相同哈希值。

## 3 分钟版

先区分“语义设计”和“某个 JDK 版本的物理表示”。语义上，String 是不可变的字符序列值对象，所以 `equals` 要判断字符序列是否相等，而不是对象地址是否相等。下面给一个可直接运行的最小参考实现；为了把边界说清，它用私有 `char[]` 保存内容，并在构造时 defensive copy：

```java
import java.util.Arrays;

public final class Solution {
    public static final class MyString {
        private final char[] value;

        public MyString(char[] value) {
            if (value == null) {
                throw new NullPointerException("value");
            }
            this.value = Arrays.copyOf(value, value.length);
        }

        @Override
        public boolean equals(Object obj) {
            if (this == obj) {
                return true;
            }
            if (!(obj instanceof MyString other)) {
                return false;
            }
            if (value.length != other.value.length) {
                return false;
            }
            for (int i = 0; i < value.length; i++) {
                if (value[i] != other.value[i]) {
                    return false;
                }
            }
            return true;
        }

        @Override
        public int hashCode() {
            int h = 0;
            for (char c : value) {
                h = 31 * h + c;
            }
            return h;
        }

        public int length() {
            return value.length;
        }
    }
}
```

这个实现的关键顺序是“identity → type → cheap shape check → content”。identity 能快速处理同一对象；类型检查同时处理 `null`；长度不同可以在 O(1) 条件下失败；只有前面都通过才做 O(n) 的内容扫描。

当前 OpenJDK 源码可以作为“真实 JDK 如何做”的对照：`String.equals` 先判断 `this == anObject`，再判断 `anObject instanceof String`，随后在 Compact Strings 开启时要求两个字符串的 `coder` 一致，最后调用 `StringLatin1.equals(value, aString.value)`；该 helper 会先比较内部数组长度，再逐字节短路比较。这里的 `byte[] + coder` 是当前实现细节，不应倒推成所有历史/未来 JDK 的语义契约。

## 关键细节

- **`null`**：`obj instanceof MyString` 对 `null` 为 `false`，因此不需要单独 `obj == null` 分支。
- **类型策略**：参考类是 `final`，不存在子类对称性问题；如果值类型允许继承，`instanceof` 与 `getClass()` 的选择必须结合跨子类相等语义，否则容易破坏对称性/传递性。
- **不可变性**：若直接保存调用方传入的 `char[]`，外部修改数组会改变对象值、`equals` 和 `hashCode`，尤其会破坏对象作为 HashMap key 时的行为；因此示例构造器复制数组。
- **短路顺序**：先做便宜检查，再线性扫描；第一个不同位置即可返回 `false`。
- **复杂度**：最坏时间 O(n)，其中 n 是字符数；`equals` 自身额外空间 O(1)。构造器 defensive copy 是 O(n) 时间和 O(n) 存储，但那不是一次 `equals` 调用的额外开销。
- **哈希契约**：相等对象必须产生相同 hash code；不同对象允许哈希碰撞，所以不能只比较 hash 就断言相等。
- **版本边界**：当前 OpenJDK 使用 `byte[] value` 与 `coder` 支持 Compact Strings；面试中如果讲源码，应把它标成当前实现，而不是把它写成 String 语义定义。

## 原理机制

`equals` 的核心是给值对象定义等价关系。对字符串，等价关系由字符序列决定：长度必须相同，且每个位置的字符相同。实现上的 identity 快路径不改变这个定义，只是利用“同一对象必然具有同一值”提前返回。

不可变性又让这个等价关系稳定：对象创建后字符序列不再变化，于是一次计算出来的相等关系和哈希值不会因为外部数组被修改而失效。哈希表先用 `hashCode` 缩小候选桶，最终仍靠 `equals` 确认键是否真正相等，因此二者必须遵守“equals 相等 ⇒ hash 相等”的契约。

当前 OpenJDK 的 Compact Strings 只是把同一语义映射到更紧凑的物理表示。它可以先检查 coder，再比较内部字节；优化改变的是比较路径与存储，不改变“字符序列相同才相等”的外部语义。

## 项目经验版

仓库没有提供用户亲自设计 JDK String 或线上修改字符串实现的经历，不能虚构。工程映射时可以说明：设计不可变值对象（ID、金额、版本号等）时，也应先定义值语义、封装可变状态，并成对设计 `equals/hashCode`，再用集合行为测试验证契约；这只是方法映射，不是个人生产经历。

## 常见追问

- 问：为什么不能只写 `return this == obj`？答：那是引用相等，只能判断是不是同一个对象；两个不同 String 对象完全可以表示相同字符序列。
- 问：为什么不能只比较 `hashCode()`？答：相同字符串必须有相同哈希，但不同字符串允许碰撞；hash 只能快速筛选，不能代替最终内容比较。
- 问：为什么构造时要复制 `char[]`？答：因为值对象要保持不可变。若外部还能修改内部字符，`equals/hashCode` 会随时间变化，放进 HashMap/HashSet 后可能再也找不到。
- 问：`instanceof` 和 `getClass()` 哪个更合适？答：如果类是 `final`，两者不会产生跨子类差异；允许继承时要先定义跨类型值语义，否则随意选择可能破坏 equals 的对称性或传递性。
- 问：当前 JDK 为什么还要比较 coder？答：当前 OpenJDK 的 Compact Strings 用不同编码形式保存内容；coder 是物理表示的一部分，可在内容扫描前排除不可能相等的表示。它是实现优化，不是 `equals` 的外部语义。
- 问：最坏复杂度为什么还是 O(n)？答：两个等长字符串只有检查到最后一个位置仍相同或最后一个位置才不同，才能得出结果；因此最坏必须检查与长度同阶的内容。

## 易错点

- 把 `==` 当成字符串内容相等。
- 忘记类型/null 边界，直接强转导致异常。
- 比较内容却不先检查长度，代码更复杂且容易越界。
- 重写 `equals` 却不重写兼容的 `hashCode`。
- 内部直接保存外部可变数组，破坏不可变值语义。
- 把当前 OpenJDK 的 `byte[] + coder` 实现细节说成所有 JDK 版本都固定如此。
