# 分割银行卡号：每 4 位插入空格，但不制造尾随空格

## 核心结论

原题只要求“实现分割银行卡号（如每 4 位加空格）”，没有说明是否要清洗用户输入、允许哪些分隔符或如何处理非数字。因此先把契约收窄到可验证的核心：**输入是只包含 ASCII 数字 `0-9` 的字符串；从左到右每 4 位分一组，组间插入一个空格；最后一组不足 4 位时原样保留；不在末尾追加空格。**

JavaScript 可以用带前瞻的正则直接表达“只有后面还有数字时，才在当前 4 位后加空格”：

`digits.replace(/(\d{4})(?=\d)/g, '$1 ')`

如果面试官说输入来自输入框、可能已经含空格或 `-`，应先另外确认“清洗”规则；不要把删除字符的行为偷偷塞进这个格式化函数。

## 1 分钟版

关键不是简单写 `/(\d{4})/g`，而是避免 16 位这类恰好 4 的倍数在末尾多一个空格。前瞻 `(?=\d)` 要求当前 4 位后面至少还有一位数字，所以只在真正的组间边界插入空格。

例如：

- `"" -> ""`
- `"123" -> "123"`
- `"1234" -> "1234"`
- `"12345" -> "1234 5"`
- `"1234567812345678" -> "1234 5678 1234 5678"`

本实现对非数字输入抛 `TypeError`。这样“格式化”和“输入清洗”是两个不同职责，源题没有规定清洗规则时不会静默删字符。

## 3 分钟版

实现分两层判断。

第一层是输入契约：参数必须是字符串，并且每个字符都是 `0-9`。空字符串允许，因为格式化空值自然得到空值。这里不把空格、短横线等字符自动剥掉，因为原题没有说明用户输入如何规范化；如果直接 `replace(/\D/g, '')`，会把字母、标点甚至误输入都静默吞掉，改变了题意。

第二层是分组。正则 `/(\d{4})(?=\d)/g` 的捕获组消费 4 个数字，`(?=\d)` 只检查下一位是不是数字但不消费它。这样每次匹配都正好落在“不是末尾的 4 位组”上，然后替换成 `$1 `。最后一组无论是 1～4 位都不会产生尾随空格。

如果不想用正则，也可以线性扫描：第 `i` 个字符写入结果后，当 `(i + 1) % 4 === 0` 且 `i + 1 < length` 时追加空格。两种写法的时间复杂度都是 `O(n)`；返回新字符串本身需要 `O(n)` 输出空间。

## 关键细节

- 题目中的“如每 4 位加空格”是分组示例，不等于“每遇到 4 个字符无条件加空格”；末尾不能多分隔符。
- 本实现只接受 ASCII 数字字符串。`null`、数字类型、已有空格、短横线和字母都不会被静默转换。
- 空字符串、少于 4 位、恰好 4 位、4 的倍数、非 4 的倍数都要覆盖。
- `(?=\d)` 是零宽前瞻，只判断后面还有数字，不把下一位吃掉。
- 不要用 `parseInt` / `Number` 做格式化：银行卡号是标识符字符串语义，数值转换会丢失前导零，并且没有必要。
- 复杂度是 `O(n)`；输出字符串长度同阶，除输出外只需要常量级状态。
- 如果产品需求是“输入时边输边格式化”，还要单独讨论光标位置、粘贴内容、已有分隔符和 IME 等交互问题；这些都不在原始题干里。

## 原理机制

```javascript
function formatBankCardNumber(digits) {
  if (typeof digits !== 'string' || !/^\d*$/.test(digits)) {
    throw new TypeError('bank card number must contain ASCII digits only');
  }
  return digits.replace(/(\d{4})(?=\d)/g, '$1 ');
}

module.exports = { formatBankCardNumber };
```

这个实现的核心不变量是：替换只发生在“已经完整消费 4 个数字且后面至少还有 1 个数字”的位置。因此每个插入的空格一定是两个非空数字组之间的分隔符，而不会出现在字符串末尾。

仓库的确定性测试使用一个不依赖正则的扫描器作为 oracle：每读取一个字符就复制到结果，只有在第 4、8、12……位且后面仍有字符时才插入空格。固定用例覆盖空字符串、短输入、恰好 4 位、5 位、16 位、19 位、前导零和非法输入；另外用固定随机种子生成 5000 个 0～64 位数字字符串，比较正则实现与扫描 oracle 的完整输出。

## 项目经验版

这是手撕题，原始面试记录没有给生产项目背景，因此不编造“银行卡输入组件上线后转化率提升”之类结果。工程上真正要拆开的职责是：**规范化输入**、**校验业务规则**、**展示分组**。本答案只做第三件事并验证字符契约；业务允许哪些卡号长度、哪些字符可以清洗，应该由上层需求决定。

## 常见追问

- 问：为什么不用 `/(\d{4})/g` 直接替换？答：恰好 4 的倍数时会在最后一个完整组后也加空格；前瞻 `(?=\d)` 保证只有后面还有数字时才插入。
- 问：为什么不先 `replace(/\D/g, '')`？答：那是在定义输入清洗策略，原题没有给这个契约；静默删除非法字符可能掩盖输入错误，所以这里显式拒绝。
- 问：银行卡号可以当数字处理吗？答：格式化目标是字符分组，不需要数值运算；用字符串还能保留前导零并避免无意义的数值转换。
- 问：不用正则怎么写？答：线性扫描，每写入 4 个字符且后面还有字符时追加空格，复杂度同样是 `O(n)`。
- 问：输入框实时格式化还要注意什么？答：需要另行设计光标恢复、粘贴、删除、已有分隔符与输入法行为；这超出了当前手撕题的最小契约。

## 易错点

- 每 4 位无条件追加空格，导致尾随空格。
- 用 `\D` 静默清洗所有非数字，却没有说明这是额外业务规则。
- 把字符串先转成数字，破坏前导零或引入不必要的数值语义。
- 只测 16 位示例，不测 4 位、5 位和最后不足 4 位的情况。
- 把“展示分组”与“卡号是否合法”的业务校验混成一个函数。
