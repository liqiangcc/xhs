# 如何设计一个海量网盘，重点说上传、秒传、分片、断点续传和限速？

## 核心结论

我会把网盘拆成“逻辑文件元数据”和“物理对象数据”两层：控制面负责用户目录、上传会话、权限、内容指纹与引用关系，数据面让客户端按分片把字节写入对象存储。上传使用可恢复的 multipart 会话，服务端记录 `upload_id + part_number + checksum + state`；完成时先验证所有分片和对象完整性，再幂等地发布逻辑文件。秒传不能只凭客户端给出的 hash 就把别人已有文件挂到当前用户目录，必须同时满足授权/内容所有权证明和内容一致性校验。下载用 HTTP Range 支持断点续传，限速按用户、租户和出口做令牌桶/带宽配额；所有跨数据库与对象存储的失败都通过状态机、幂等和对账回收处理。

## 1 分钟版

- 上传初始化：客户端提交文件大小、可选内容指纹和目标目录，服务端鉴权后创建 `upload_session`，返回 `upload_id`、分片大小和待上传分片；大文件进入 multipart 流程。
- 分片上传：每个分片用稳定 `part_number`，携带校验值；成功后记录分片状态。客户端重连先查询会话/已完成 parts，只补缺失分片，因此不是“从头再传”。
- 秒传：服务端发现相同内容指纹时也不能直接确认“你拥有这份文件”；需要证明客户端确实持有内容，且目标用户有权建立逻辑引用，再增加引用关系。
- 完成上传：校验 parts、完整对象和会话版本，只允许一次 `UPLOADING → VERIFYING → READY` 发布；重复 finalize 返回同一结果。对象完成而数据库提交失败时由对账任务回收孤儿对象，数据库绝不提前暴露未验证对象。
- 下载与限速：支持 `Range: bytes=...` 的部分读取做断点续传；鉴权后发短期下载凭证/受控代理，网关按用户和全局出口预算做令牌桶限速，热点对象由 CDN/边缘缓存减轻源站压力。

## 3 分钟版

先定义边界和容量。不能把“万亿 GB”当已知现网事实；我会先拿到总逻辑容量、物理去重后容量、日新增字节、峰值上传/下载带宽、文件大小分布、跨地域需求和可接受 RPO/RTO。举例来说，如果峰值有 20 万个并发上传，每个连接平均 4 MiB/s，入口理论带宽就是约 800 GiB/s，实际设计必须据真实分布做分区、地域和带宽预算，而不是靠单机参数推导。

元数据至少有四类：`file_entry` 表示用户目录里的逻辑文件；`blob` 表示不可变物理对象及内容指纹、大小、校验状态；`upload_session` 保存会话状态、目标 blob、过期时间和幂等键；`upload_part` 保存分片号、大小、校验值和对象存储返回的 part 标识。目录/权限和 blob 生命周期分开，避免用户改名、移动、分享时复制大对象。

上传状态机可以是 `INITIATED → UPLOADING → VERIFYING → READY`，失败进入 `ABORTED/EXPIRED`。初始化会话后，对象存储创建 multipart upload；客户端可并发上传不同 part。Amazon S3 的 multipart 模型就是先创建 multipart upload、逐个 `UploadPart`，最后 `CompleteMultipartUpload`；完成前 parts 是独立上传单元。每个 part 做传输完整性校验，服务端还要保存自己认可的 part 清单，恢复时用会话记录并可与对象存储的 `ListParts` 对账。会话设置 TTL；过期后 abort multipart 并删除元数据，避免长期占用未完成分片。

断点续传的关键不是“客户端记住传到第几个”，而是服务器端有可重建的 truth。客户端带 `upload_id` 查询已确认 part 集合，再补缺失分片；同一个 finalize 请求必须有幂等键或 CAS 状态检查。两个客户端同时 finalize 时，只有一个状态迁移成功；另一个读取既有 READY 结果。跨对象存储和数据库没有天然单事务，所以顺序要保守：对象存储完成并验证后，再提交逻辑文件引用；若后一步失败，留下的是可回收孤儿 blob，而不是一个指向不存在对象的已发布文件。

秒传建立在去重上，但“内容 hash 相同”只说明客户端知道一个指纹，不等于它拥有文件。经典客户端去重研究已经指出，这种机制会带来存在性侧信道；Proof-of-Ownership 工作专门提出用内容所有权证明来降低只凭短 hash 获得去重收益的风险。因此我会区分两种策略：可信同用户/同安全域内可在严格授权后直接复用；跨用户全局去重则要求 PoW/随机块挑战或等价的持有证明，并对高敏感/低熵内容关闭客户端可观察的“是否命中”差异。逻辑层只新增 `file_entry → blob` 引用；物理 blob 的引用计数/引用集合在事务中更新，删除逻辑文件只减少引用，引用归零后经过宽限期再异步 GC，防止并发删除/恢复竞态。

下载链路先鉴权和检查分享策略，再由 CDN/对象存储或受控下载服务输出。HTTP RFC 9110 定义 `Range` 请求可只取表示的一部分字节，服务器可返回 `206 Partial Content`；客户端记录已落盘字节区间，重试时请求缺口，就能实现下载断点续传。必须绑定对象版本/ETag 或等价不可变版本，避免文件内容变化后把旧片段和新片段拼在一起。

限速分“公平”和“保护系统”两层。用户/租户维度用令牌桶限制长期平均速率并允许小突发；节点维度再有并发、连接数和出口带宽水位。分布式精确全局令牌桶会增加共享状态开销，所以可以按地域/节点下发配额做近似控制，再周期汇总；只有计费或强 SLA 才为关键配额支付更强一致成本。对下载热点优先 CDN 缓存和源站请求合并，不应仅靠把单用户限速调低掩盖源站瓶颈。

## 关键细节

- **分片大小**：按文件大小、网络 RTT、并发数、对象存储限制和失败重传成本动态选择；小分片恢复粒度好但请求/元数据开销大，大分片吞吐好但失败重传成本高。不要把固定 8 MiB 或 32 MiB 当通用答案。
- **完整性**：part 级 checksum 解决传输/分片损坏，完成后的对象级 checksum/大小校验确认最终对象。S3 官方文档支持在 multipart 流程中为各 part 记录并在完成阶段校验 checksum。
- **幂等与并发**：`create_session`、`upload_part`、`complete`、`create_file_entry` 都要有稳定幂等键；状态迁移用版本/CAS，数据库唯一约束保护重复逻辑引用。
- **清理**：定时扫描长期 INITIATED/UPLOADING 会话，abort 未完成 multipart；扫描对象存在但无 READY 逻辑引用的孤儿 blob，满足宽限期后删除。S3 文档也明确未完成 multipart 的 parts 要在 complete 或 abort 后才释放。
- **安全**：上传凭证只允许指定对象前缀/part，短有效期；最终发布前做类型/恶意内容策略检查。秒传接口要限流并防止通过命中/不命中批量探测他人文件。
- **一致性**：目录元数据是用户可见事实源；对象存储是字节事实源。缓存、CDN 和搜索索引都是可重建派生层，不能反向决定文件是否存在。

## 原理机制

multipart 的收益来自把一个大对象变成可独立重试、可并发传输的小工作单元；断点续传则把“已确认的 part 集合”变成持久状态，所以连接断开不等于业务状态丢失。系统真正需要保持的是会话和对象的单调状态，而不是某个 TCP 连接。

去重把“逻辑拥有关系”和“物理字节”解耦：多个 `file_entry` 可以引用同一个不可变 `blob`。这样秒传只需新增元数据引用，但前提是服务端已经验证客户端对内容的持有/访问资格。引用计数只是 GC 优化，不能替代可审计的引用事实；发生计数漂移时应能从逻辑引用重新计算。

完成上传是最危险的跨系统边界。若先写 READY 元数据再完成对象，故障会产生用户可见的空文件；若先完成对象再提交 READY，故障最多产生后台可清理的孤儿对象。因此选择“先让字节完整、后让元数据可见”，再以 outbox/扫描对账回收边界故障。

## 项目经验版

项目映射时补真实数据：文件大小 P50/P95/P99、上传并发、失败率、平均重试字节、秒传命中率、物理/逻辑容量比、对象存储请求费、CDN 命中率、出口峰值、未完成 multipart 数量、孤儿对象数量和 GC 延迟。没有这些事实时不要编造“节省 90% 带宽”或“TB/s 级吞吐”之类结果。

## 常见追问

- 问：为什么秒传不能只传 MD5/SHA-256 就返回成功？答：短指纹可被已知文件或猜测内容的人获得，只看 hash 会把“知道指纹”错误当成“拥有内容”；跨用户去重应增加所有权证明/随机内容挑战和授权边界。
- 问：断点续传为什么不能只存在客户端？答：客户端状态可能丢失、伪造或落后；服务器必须能根据 `upload_id` 和对象存储 part 状态重建已确认集合，客户端只是缓存。
- 问：完成 multipart 成功但写数据库失败怎么办？答：不发布 READY；把已完成对象标记/识别为 orphan，通过重试提交或宽限期后的对账 GC 处理。
- 问：Range 下载如何避免文件变化导致拼错？答：绑定不可变 blob 版本或强校验标识；若版本不匹配就拒绝续传并重新下载。
- 问：全局限速一定要一个中心 Redis 计数器吗？答：不一定。严格全局一致会放大延迟和热点；普通带宽保护可按节点/地域分配预算，计费型强 SLA 再选择更强一致方案。

## 易错点

- 不要把“对象存储支持 multipart”误写成“数据库和对象存储完成动作原子提交”。
- 不要用固定分片大小、固定重试次数冒充通用最优参数。
- 不要把内容 hash 当作跨用户秒传的完整授权证明，也不要泄露“某个文件是否已存在”的可观察侧信道。
- 不要只讲上传成功路径，遗漏未完成 parts、孤儿对象、并发 finalize、删除与 GC 竞态。
- 不要把 CDN、缓存或搜索索引当文件存在性的权威状态。
