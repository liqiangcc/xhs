# LBS 系统如何实现附近的人查询？

## 核心结论

我会把“附近的人”拆成位置写入、空间候选召回、业务过滤与距离排序四步，而不是只回答“用 GeoHash 或 Redis”。以城市/地理格网分片的 Redis GEO 索引做低延迟候选召回，按用户位置和半径查询并取过采样候选；再从用户状态、可见性和位置版本过滤，最后按距离和业务分排序。位置更新带单调版本和幂等键，索引允许短暂最终一致；隐私、陈旧位置、跨格边界、热点和 Redis 不可用必须在主链路中设计。

## 1 分钟版

- 先定边界：例如只展示已授权、在线、最近 5 分钟有有效定位的用户；半径、页大小、精度和是否允许最终一致要先确认。
- 写入：客户端提交 `user_id + 经纬度 + location_version + event_id`，服务端鉴权、校验坐标和版本；只让较新的版本更新当前位置与 GEO 索引。
- 查询：Redis ≥ 6.2.0 时，按中心点和半径从相关地理格网分片用 `GEOSEARCH ... FROMLONLAT ... BYRADIUS ... ASC COUNT ... WITHDIST` 召回；业务层合并、过滤、按距离/业务分排序并分页。
- 可靠性：索引只是加速层；持久当前位置和更新日志用于重建。Redis 失败时限流或返回“附近服务暂不可用”，不把过期位置伪装成实时结果。

## 3 分钟版

先给出可讨论的假设，而不是编造现网指标：假设峰值在线 500 万、每人平均 30 秒上报一次，则位置写入预算约 `5,000,000 / 30 ≈ 16.7 万次/秒`；查询峰值 5 万 QPS，默认半径 3 km、每页 20 人，位置新鲜度目标 5 分钟，允许索引相对持久记录有秒级最终一致。实际数值应由产品、终端上报策略和压测替换。

数据分两类。持久表 `user_location_current(user_id, location_version, lon, lat, updated_at, visibility, online_status)` 保存最新被接受的位置与版本；更新事件表或消息流保存 `event_id`，用于去重、重放和索引重建。加速层按城市/格网组织 `geo:{city}:{cell}`，member 是 `user_id`；旁路保存用户最后活跃时间和可见性摘要。Redis 的 `GEOADD` 用经纬度和 member 写入地理索引。`GEOSEARCH` 自 Redis 6.2.0 起可用，可按圆或矩形检索并支持距离顺序、数量和坐标/距离回传；低于该版本的存量集群只能使用其已验证兼容的半径查询实现（Redis 文档中的 `GEORADIUS` 是 6.2.0 起被标为 deprecated 的旧命令），迁移前须对半径、排序、数量和分页边界做回归测试。

写路径是：认证与隐私校验 → 按 `user_id` 串行或条件更新比较 `location_version` → 持久化当前记录/投递事件 → 消费者更新目标格网的 GEO 索引并清理旧格网 member。`event_id` 和 `location_version` 使网络重试、乱序上报不把旧位置覆盖新位置；索引消费失败可从事件流或当前表回放。若产品要求“写入成功后立即可查询”，须为采用的存储和索引方案单独定义并验证读己之写语义；本方案默认接受持久状态到索引之间的秒级最终一致，不能把未验证的脚本原子性当作跨分片保证。

查询路径是：将中心点映射到格网，取覆盖半径的格网集合，向每个分片发送半径检索，`ASC` 返回距离有序候选。每个分片先取 `page_size × overscan`，应用层去重、读取可见性/封禁/在线/新鲜度状态，剔除自己和已拉黑对象，再合并为全局按距离优先、业务分为次序的结果。格网边界必须扩展相邻格网；否则中心点靠边时会漏召回。使用 cursor（由查询中心、半径、排序键、最后一名候选版本组成）避免 offset 在位置变化下跳页或重复。

## 关键细节

- 幂等键：同一 `event_id` 重放不重复执行；同一 `user_id` 只接受更大的 `location_version` 或更新的服务端序列，客户端时间戳只能作为辅助，不能单独决定新旧。
- 一致性：当前位置持久记录是重建依据，GEO 索引是可回放的派生数据；查询结果必须二次检查 `updated_at`、`online_status` 和 `visibility`。
- 精度与隐私：索引可保存原始坐标以完成半径计算，但对外返回可做模糊化；权限校验在召回过滤前或至少在返回前完成，禁止用客户端传入的可见性代替服务端状态。
- 热点：超大城市/商圈拆得更细，单个热点格网的候选数、命令耗时和跨分片 fan-out 是扩容信号；不能只按行政区一个大 key。
- Redis `GEOSEARCH` 的官方复杂度是 `O(N + log(M))`，其中 `N` 是图形周围格网对齐包围区域的元素数、`M` 是形状内元素数，因此半径上限、每页候选上限和热点分片是容量控制手段。

## 原理机制

空间索引的目的不是替代精确业务判断，而是把“全量用户扫描”缩小成局部候选集合。写入把用户移动事件投影到一个或多个地理分片；读取只访问覆盖查询圆的分片，再让 Redis 的地理查询做半径筛选。候选数由半径、人口密度和格网大小共同决定：格网越粗，单 key 越热、无效候选越多；越细，边界格网和 fan-out 越多。需要根据热点、半径分布和 p99 实测选择，而不是固定一种 GeoHash 精度。

状态转换为 `received → validated → version_accepted → persisted → indexed`。在 `persisted` 与 `indexed` 之间允许最终一致，但查询过滤会拒绝陈旧或无权限状态；消费者重试与回放把索引恢复到持久状态。索引更新失败时记录 backlog、告警并按版本重放；查询 Redis 超时则短路、限流、熔断，不能退化为扫描主库。

上线前按真实城市密度和移动轨迹回放压测，分别测位置写入、单格/跨格查询、热点格网和 Redis 故障时的 p99、候选数、过滤率、索引积压与陈旧结果比例。灰度先双写但只读旧链路，再在影子流量比较两条链路的候选集合和距离排序；差异超过阈值或陈旧率上升就停止扩大并回滚读取开关，保留事件流用于修复后回放。

## 项目经验版

项目映射提示：补入实际 DAU/在线数、上报频率、半径和 p99、位置来源及精度、隐私规则、Redis 集群槽位/分片策略、压测结果和一次索引积压或热点治理的真实数据。没有这些事实时，不要虚构“某城市爆热”或“延迟降低了多少”。

## 常见追问

- 问：为什么不能只用一个城市级 GEO key？答：高密度城市会使候选集合和单 key 热点变大；按格网分片可以限制单分片负载，但要处理边界格网与合并排序。
- 问：位置上报乱序怎么办？答：以服务端维护的单调 `location_version` 或等价序列判新旧，`event_id` 去重；旧事件不能覆盖当前位置，也不应回写 GEO 索引。
- 问：Redis GEO 是否直接等于最终“附近的人”列表？答：不是。它给出空间候选和距离信息；在线、权限、屏蔽、位置新鲜度、业务排序和分页仍由业务层完成。
- 问：Redis 不可用时为何不查主库全表？答：全表或大范围地理扫描会把故障扩散到主库；应返回受控降级、限流或暂不可用，并用持久事件重建索引。

## 易错点

- 不要只说“用 GeoHash”，遗漏写入版本、边界格网、排序和隐私过滤。
- 不要把客户端时间戳当唯一顺序依据，也不要让重试覆盖更新的位置。
- 不要把 GEO 索引当权威状态；它是可重建的候选召回层。
- 不要为追求低 fan-out 把格网粗化到热点 key 不可控，或为追求细粒度忽略跨格查询成本。
