# Promise.all：语义、边界与手写聚合器

## 核心结论

原始题目只留下了“promise.all”四个字，没有说明面试官要考 API 语义、并发使用方式，还是手写一个等价聚合器。因此回答的第一步不是直接背实现，而是先确认考查口径。若问原生 `Promise.all(iterable)`，核心语义是：把输入逐项转换/吸收到 Promise，全部 fulfilled 后按**输入顺序**返回结果数组；任一输入先发生 rejection，聚合 Promise 就用该 rejection reason 拒绝。`Promise.all` 负责**聚合结果**，不会替已经创建的异步任务增加取消能力，也不是“创建线程”的并发原语。

若面试官要求手写，可以实现一个满足常见面试语义的 `interviewPromiseAll`：支持 iterable、普通值/thenable、保持输入顺序、空输入、首个观察到的 rejection，以及迭代期间的同步异常。它不是 ECMAScript 原生方法的逐步骤 polyfill：原生算法还涉及构造器泛化、迭代器协议与规范内部槽等细节，回答时要明确这个边界。

## 1 分钟版

- 先问清：是解释 `Promise.all`，还是手写实现。
- 所有输入成功才成功；结果数组按输入顺序，不按完成顺序。
- 普通值和 thenable 会通过 Promise 解析流程参与聚合，不要求输入全是原生 Promise。
- 谁先 reject，聚合结果就先以谁的 reason reject；这不等于自动停止其它异步任务。
- 空 iterable 得到 fulfilled 的空数组；非空输入即使都已完成，后续 `.then`/`await` 观察仍遵循 Promise job/microtask 语义。
- 手写时最容易错的是顺序、空数组、普通值/thenable、重复计数和异常路径。

## 3 分钟版

可以把聚合器理解成两个共享状态：`values[index]` 保存每个输入位置的结果，`remaining` 记录还有多少项没有 fulfilled。遍历 iterable 时为每一项固定当前 `index`，再用 `Promise.resolve(item)` 做吸收。某项成功后把值写回自己的索引并把 `remaining` 减一；当它减到 0 时，说明所有输入都 fulfilled，可以 resolve 整个结果数组。任一输入失败则直接调用外层 `reject`，Promise 一旦 settled，后续成功/失败不会改变聚合结果。

为什么结果顺序不会被异步完成顺序打乱？因为索引在**遍历输入时**就固定，而不是在回调执行时 `push`。例如第二项先完成，它也只能写 `values[1]`；等全部完成后数组仍然保持输入次序。

为什么不能把 `Promise.all` 说成“让任务并行执行”？很多 Promise 对应的工作在 Promise 创建时已经开始，`Promise.all` 只是订阅并聚合这些结果。真正的并发度取决于浏览器/Node 事件循环、底层 I/O、线程池、连接池以及任务本身；如果要限流，需要额外的队列/信号量，而不是仅靠 `Promise.all`。

## 关键细节

- 原始来源只有“promise.all”，没有“实现 polyfill”“限制并发数”等额外条件，不能把常见题型冒充原题要求。
- fulfilled 结果按输入顺序排列，与完成先后无关。
- rejection 是 fail-fast 的聚合语义，但并不取消其它已经开始的任务；如果任务需要取消，要显式使用它们支持的取消机制，例如 `AbortSignal`。
- `Promise.resolve(item)` 可以统一普通值、原生 Promise 和 thenable；手写实现不要只判断 `instanceof Promise`。
- 空 iterable 必须能完成，否则 `remaining===0` 但永远没有回调触发，会产生永久 pending。
- 遍历 iterable 的同步异常发生在 Promise executor 内，会让返回的 Promise 进入 rejected；面试实现也应保留这个行为。
- 本实现使用原生 `Promise`/`Promise.resolve`，没有复刻规范中 `this` 构造器泛化等行为，所以它是面试级聚合器，不宣称与原生 `Promise.all` 100% 等价。

## 原理机制

ECMAScript 规范中的 `Promise.all` 会获取输入 iterable，逐项通过构造器的 promise resolve 能力转换，并为每个位置创建 resolve-element 逻辑。每个位置持有自己的 index、共享 values 列表和 remaining count；某个位置 fulfilled 时只写自己的槽位并递减 remaining，最后一项完成时创建结果数组并 resolve 聚合 Promise。这解释了“输入顺序稳定”和“全部成功才成功”。拒绝路径共享聚合 Promise 的 reject capability，因此第一个让聚合 Promise settled 的 rejection 决定最终失败原因。

面试级实现可以压缩为下面的 JavaScript：

```js
function interviewPromiseAll(iterable) {
  return new Promise((resolve, reject) => {
    const values = [];
    let remaining = 0;
    let index = 0;

    for (const item of iterable) {
      const currentIndex = index++;
      remaining++;
      Promise.resolve(item).then(
        (value) => {
          values[currentIndex] = value;
          remaining--;
          if (remaining === 0) resolve(values);
        },
        reject,
      );
    }

    if (index === 0) resolve([]);
  });
}
```

仓库对这段**完全相同的实现字节**做了确定性 Node 测试：空输入、普通值混合 Promise、逆完成顺序仍保持输入顺序、thenable 吸收、两个输入按与数组位置相反的顺序 reject 时保留先观察到的 rejection、以及 iterable 在迭代中抛异常，六类检查全部通过。这个测试证明的是上面的面试级语义，不把它扩大成规范逐步骤兼容证明。

## 项目经验版

这道题本身没有提供项目经历，不应该虚构“线上用 Promise.all 提升了多少性能”。更可靠的工程回答是讲边界：只有彼此没有依赖的异步工作才适合同时发起；批量请求过大时 `Promise.all` 不提供限流，可能把压力一次性推给连接池或下游；如果需要收集每一项成功/失败结果而不是首错即失败，应考虑 `Promise.allSettled`；如果需要取消，要把取消信号传给真实任务。

## 常见追问

- 问：为什么结果数组不会按完成顺序排列？答：每一项在遍历输入时就绑定自己的 index，完成时写固定位置，最后才统一 resolve 数组。
- 问：第二个输入先 reject、第一个输入后 reject，最终 reason 是谁？答：聚合 Promise 由最先让它 settled 的 rejection 决定，不按输入位置挑最小索引。
- 问：`Promise.all([1, 2])` 合法吗？答：合法；输入值会经过 Promise resolve/thenable assimilation 语义，最终得到 `[1, 2]`。
- 问：`Promise.all([])` 会不会一直 pending？答：不会；空 iterable 返回的 Promise 已经 fulfilled，值是空数组。
- 问：一个输入 reject 后，其它请求会自动取消吗？答：不会。聚合 Promise 已经失败，但其它已启动工作仍按各自机制继续，除非任务自身接入了显式取消。
- 问：什么时候用 `allSettled`？答：当业务需要等所有任务结束并保留每项成功/失败状态，而不是任一失败就把整组视为失败时。
- 问：手写版和原生 `Promise.all` 完全一致吗？答：不是。这里覆盖面试常见可观察语义；原生规范还处理构造器泛化和更完整的迭代器/内部能力细节。

## 易错点

- 用回调完成时 `push`，导致结果顺序变成完成顺序。
- 忘记空 iterable，返回 Promise 永久 pending。
- 只接受 `Promise` 实例，漏掉普通值和 thenable。
- 把 fail-fast 误解为“其它任务已被取消”。
- 说 `Promise.all` 自己启动并行线程，混淆结果聚合与底层并发机制。
- 把一个简化面试实现称为“100% Promise.all polyfill”，忽略 ECMAScript 构造器和迭代器语义。
