# 如果查询优化器选错了索引怎么办？

## 核心结论

优化器疑似选错索引时，不先永久写 FORCE INDEX：固定真实参数与版本，用 EXPLAIN/EXPLAIN ANALYZE 对比估算、扫描和耗时，核对谓词、复合索引与统计信息；先修 SQL/索引并 ANALYZE TABLE，只有可复现且回归验证后才用局部 hint 兜底，并设置移除条件。

## 1 分钟版

- 变更前收集待采集输入：目标 SQL、代表参数集、当前与目标 P95/P99、允许变更窗口、表规模和回滚时限；缺任一项不得断言某索引更优。
- 比较 actual/estimated rows、key、key_len、access type、回表/临时表/排序和延迟；确认是统计失真、索引设计还是成本模型选择。
- 仅统计更新、SQL/hint 变更、索引 DDL 是三类不同风险变更：分别演练、灰度和回滚。
- hint 与 SQL 一起做基线压测、灰度、监控和回滚；数据分布、MySQL 版本或索引变化后重新验证。

## 3 分钟版

诊断任务把同一参数的原 SQL、候选 SQL 和候选索引计划保存为基线。EXPLAIN 显示优化器计划，EXPLAIN ANALYZE 用实际执行确认估算偏差；若 cardinality 过期，先在变更窗口 ANALYZE TABLE。若谓词破坏索引可用性或复合索引顺序不匹配，修 SQL/索引优先。FORCE INDEX 只限制当前表当前语句的候选路径；仅统计更新可回滚到原统计策略，SQL/hint 灰度通过版本开关回退，索引 DDL 必须先在影子/预发布验证并按 DDL 回退方案执行。任何灰度若 P95/P99、rows examined、DB CPU/IO、锁等待或错误率相对基线回退到预先批准的停止条件，立即停止扩量、回退 SQL/hint；DDL 依变更方案暂停或回退。

## 关键细节

- 变更前收集待采集输入：目标 SQL、代表参数集、当前与目标 P95/P99、允许变更窗口、表规模和回滚时限；缺任一项不得断言某索引更优。
- 比较 actual/estimated rows、key、key_len、access type、回表/临时表/排序和延迟；确认是统计失真、索引设计还是成本模型选择。

- hint 与 SQL 一起做基线压测、灰度、监控和回滚；数据分布、MySQL 版本或索引变化后重新验证。
- 结论以 MySQL 8.4 文档为边界；不同版本的 hint、EXPLAIN 输出和优化器策略需复核。
- FORCE INDEX 使表扫描仅在无法使用指定索引时才选择，不能作为缺统计、缺索引或任意慢查询的通用修复。
- ANALYZE TABLE 会更新统计；执行窗口、锁/资源影响和复制策略应在生产变更流程评审。
- 查询计划调整不改变业务数据模型或幂等语义；索引 DDL 则需评审写放大、存储、复制和在线变更风险。
- 复杂度：诊断和变更成本由表规模、统计采样、查询执行、索引维护及压测负载决定；答案不声明通用固定阈值。

## 原理机制

输入是带参数 SQL 与运行时证据；EXPLAIN/ANALYZE 将优化器选择、估算与实际暴露出来；统计更新和索引/谓词修复改变候选路径与成本信息；局部 hint 是最后的受监控约束。输出是已验证计划或可回滚的变更，不是静态的永远强制某索引。

## 常见追问

- 问：什么时候用 FORCE INDEX？答：先确认统计和索引修复后仍稳定选错，且真实参数基准证明指定路径更好；上线后持续监控并设移除条件。
- 问：为什么 EXPLAIN 不够？答：它主要给计划与估算；要用实际执行、慢日志和代表参数验证估算偏差及真实耗时。
- 问：ANALYZE TABLE 能解决什么？答：它更新影响选择的统计信息；若索引设计/谓词本身不适配，仍需改 SQL 或索引。
- 问：灰度回退信号是什么？答：按预批准基线比较延迟、扫描行数、CPU/IO、锁等待和错误率；达到停止条件即停止扩量并回退对应 SQL/hint 或 DDL 方案。

## 易错点

- 不要只凭 key 不是预期索引就判错。
- 不要忽略绑定参数和数据倾斜。
- 不要把 hint 当永久补丁。
- 不要在线上直接 ANALYZE/改索引而无变更评审和回滚。
