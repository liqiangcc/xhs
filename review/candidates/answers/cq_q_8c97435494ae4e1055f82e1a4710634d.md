# SQL：统计每天新增用户和老用户数量

## 核心结论

来源只说明“用户登录日志表”，没有给真实表名、字段名、时区和同日多次登录的计数口径。这里先声明最小契约：`login_log(user_id, login_time)` 每行是一条登录事件；统计粒度是“用户-自然日”，同一用户同一天登录多次只算 1 人；某用户第一次出现的自然日算新增用户，之后再次出现的日期算老用户。先去重得到每日活跃用户，再求每个用户的首次登录日，最后按日期条件聚合。

## 1 分钟版

- 先把事件日志去重成 `DISTINCT user_id + login_date`，避免一个人当天多次登录被重复计数。
- 再按 `user_id` 求 `MIN(login_date)`，得到首次登录日 `first_date`。
- 当 `login_date = first_date` 时计入新增；当 `login_date > first_date` 时计入老用户。
- 最终按 `login_date` 分组，分别对两个条件求和；该口径下每天 `新增 + 老用户 = 当天去重活跃用户数`。

## 3 分钟版

假设登录表为 `login_log(user_id, login_time)`，并以数据库当前会话的自然日切分：

```sql
WITH daily_users AS (
    SELECT DISTINCT
           user_id,
           DATE(login_time) AS login_date
    FROM login_log
),
first_login AS (
    SELECT
        user_id,
        MIN(DATE(login_time)) AS first_date
    FROM login_log
    GROUP BY user_id
)
SELECT
    d.login_date,
    SUM(CASE WHEN d.login_date = f.first_date THEN 1 ELSE 0 END) AS new_users,
    SUM(CASE WHEN d.login_date > f.first_date THEN 1 ELSE 0 END) AS old_users
FROM daily_users AS d
JOIN first_login AS f
  ON f.user_id = d.user_id
GROUP BY d.login_date
ORDER BY d.login_date;
```

如果面试官明确希望用 `NOT EXISTS` 判断“当天是否第一次出现”，也可以在已经去重的 `daily_users` 上判断是否存在更早日期：

```sql
WITH daily_users AS (
    SELECT DISTINCT user_id, DATE(login_time) AS login_date
    FROM login_log
)
SELECT
    d.login_date,
    SUM(CASE WHEN NOT EXISTS (
            SELECT 1
            FROM daily_users AS p
            WHERE p.user_id = d.user_id
              AND p.login_date < d.login_date
        ) THEN 1 ELSE 0 END) AS new_users,
    SUM(CASE WHEN EXISTS (
            SELECT 1
            FROM daily_users AS p
            WHERE p.user_id = d.user_id
              AND p.login_date < d.login_date
        ) THEN 1 ELSE 0 END) AS old_users
FROM daily_users AS d
GROUP BY d.login_date
ORDER BY d.login_date;
```

两种写法的业务定义相同；第一种先物化“首次日期”通常更容易解释和验证，第二种更直接体现题干提示的 `NOT EXISTS` 思路。

## 关键细节

- **先定义人数而不是事件数**：题目问“用户数量”，本答案按用户-日去重；若业务要统计登录次数，口径会完全不同。
- **新增只发生一次**：某用户第一次登录日是新增；同一用户当天后续登录不会再次计数，未来日期都属于老用户。
- **自然日依赖时区**：`DATE(login_time)` 的具体日界线取决于数据库和时间字段语义；生产环境应先把 UTC 时间转换到业务时区再截日。
- **NULL 用户**：真实表若允许 `user_id IS NULL`，需要先定义匿名日志是否参与用户统计；本最小契约假设 `user_id` 非空。
- **性能**：大表上真正的成本来自按用户求首次日期和按用户-日去重。可考虑维护用户首登维表，或根据查询引擎设计 `(user_id, login_time)` 等访问路径，并用执行计划验证。
- **增量数仓**：若只扫描当天分区就无法判断“是否历史首次”。需要历史首登状态、用户维表或可访问的历史数据，不能把“当天第一次出现”误当成“生命周期第一次出现”。

## 原理机制

这道题的核心是把事件流映射成用户状态。原始日志是一对多事件：一个用户一天可能有多行。`daily_users` 先把它压成“用户-日”集合；`first_login` 再为每个用户计算生命周期最小日期。于是每一条用户-日记录只有两种互斥状态：日期等于最小日期就是新增，晚于最小日期就是老用户。最后按日期聚合这些状态即可。这个分解让“去重口径”和“新老判定”相互独立，也方便分别验证。

## 项目经验版

来源没有真实业务表规模、分区策略或生产执行计划，不能虚构项目数据。真实数仓里我会先确认业务时区、用户唯一键、是否包含匿名登录、迟到数据如何回补，以及是否已有“用户首次登录日”维度；再根据分区和索引/排序键设计增量方案，并用执行计划和分区扫描量验证成本。这些是落地检查项，不是本题来源事实。

## 常见追问

- 问：为什么必须先 `DISTINCT`？答：因为统计的是人数而不是登录事件；不去重时一个用户当天多次登录会把同一个人累加多次。
- 问：为什么不能只看当天分区判断新增？答：新增是生命周期首次登录；只看当天无法知道用户过去是否出现过，除非另有首登维表或历史状态。
- 问：用左连接怎么写？答：把当天去重用户 `d` 左连接更早日期的同用户记录 `p`；若 `p.user_id IS NULL` 则当天是首次出现。不过要防止一名老用户匹配多条历史记录造成行数膨胀，通常应先聚合历史或使用 `NOT EXISTS`。
- 问：`MIN(login_date)` 和 `NOT EXISTS` 哪个更好？答：语义都能表达首次出现；选择取决于数据布局和优化器。先求首登日更容易复用，`NOT EXISTS` 则直接表达“不存在更早记录”，最终应看执行计划与数据量。
- 问：跨时区怎么办？答：先把时间戳转换到明确的业务时区，再截取自然日；否则 UTC 午夜和业务午夜不同会让首登日期及每天人数漂移。

## 易错点

- 直接按登录事件 `COUNT(*)`，把同一用户一天多次登录重复计数。
- 把“当天第一次登录”当成“用户生命周期首次登录”。
- 用左连接历史明细后直接聚合，导致一个老用户因匹配多条历史登录而被重复放大。
- 没有定义自然日时区，却把 `DATE(timestamp)` 的结果当成绝对业务日期。
- 为了省扫描只看当天数据，却没有任何历史首登状态支撑新老判断。
