# 手写 `useFetch`：用 `.then` / `.catch` 管理请求状态

## 核心结论

来源明确要求手写 React 自定义 Hook `useFetch`，并使用 `.then` / `.catch` 处理异步请求，但没有保留既有函数签名、响应数据格式、重试/缓存规则。这里声明一个最小可执行答案侧契约：`useFetch(url, fetcher = fetch)` 请求 JSON；`fetcher(url, { signal })` 返回 `Promise<Response>`；Hook 返回 `{ data, error, loading }`。Effect 在 `url` 或 `fetcher` 变化时发起新请求，cleanup 取消旧请求并阻止旧 Promise 回写状态。

## 1 分钟版

- 用 `useState` 保存 `data / error / loading`，把网络请求放进 `useEffect`，因为请求属于与外部系统同步的副作用。
- Effect 开始时设 `loading=true`、清空旧 error，然后调用 `fetcher(url, { signal })`，严格用 `.then(...).then(...).catch(...)` 串起 HTTP 检查、JSON 解析和状态更新。
- `fetch()` 对 HTTP 4xx/5xx 本身仍可能 resolve，所以要检查 `response.ok`，非成功响应主动抛错后统一进入 `.catch`。
- cleanup 调用 `AbortController.abort()`，并把 `active=false`；这样 URL 改变或组件卸载后，旧请求即使晚返回，也没有资格覆盖当前状态。
- 原题后续还有独立的 `params` 变化需求，那是另一个 Canonical；当前答案只给基础 Hook，不把后续参数 identity / 深比较规则偷偷合并进来。

## 3 分钟版

```javascript
import { useEffect, useState } from 'react';

export function useFetch(url, fetcher = fetch) {
  const [state, setState] = useState({
    data: null,
    error: null,
    loading: false,
  });

  useEffect(() => {
    const controller = new AbortController();
    let active = true;

    setState(prev => ({ ...prev, error: null, loading: true }));

    fetcher(url, { signal: controller.signal })
      .then(response => {
        if (!response.ok) {
          throw new Error(`HTTP ${response.status}`);
        }
        return response.json();
      })
      .then(data => {
        if (!active) return;
        setState({ data, error: null, loading: false });
      })
      .catch(error => {
        if (!active) return;
        if (error?.name === 'AbortError') return;
        setState({ data: null, error, loading: false });
      });

    return () => {
      active = false;
      controller.abort();
    };
  }, [url, fetcher]);

  return state;
}
```

这段代码的状态机很简单：`idle/success/error -> loading -> success | error`。每一次 Effect setup 都对应一个请求版本；cleanup 让旧版本失效。这样既满足 `.then/.catch` 的题目要求，也避免只写“请求成功就 setData”而漏掉错误、卸载和竞态边界。

## 关键细节

- **依赖完整性**：Effect 内读取了 `url` 和 `fetcher`，因此依赖数组包含两者。调用方若每次 render 都创建一个新的 `fetcher` 函数，会导致额外请求；实际项目应传稳定导入或用合适方式稳定函数引用。
- **HTTP 错误与 Promise reject 不是一回事**：原生 `fetch()` 在收到 HTTP 错误状态时通常仍返回 fulfilled Promise；用 `response.ok` 判断 200–299，再主动抛错，才能让 404/500 进入统一错误分支。
- **JSON 契约是答案侧假设**：原题没说响应格式。本实现调用 `response.json()`；如果实际返回文本、Blob 或流，应替换解析步骤。
- **竞态与卸载**：仅仅 abort 不足以假设所有自定义 `fetcher` 都会遵守 `signal`。`active` 作为状态写入门禁，保证已 cleanup 的请求不能再更新 UI。
- **取消不是业务失败**：旧请求被取消时不应该把 `AbortError` 展示成用户错误；cleanup 已把该请求版本判定为失效。
- **状态策略**：新请求开始时保留旧 `data`、清空旧 `error` 并设置 loading；失败时这里清空 data。是否保留失败前数据属于产品策略，原题没有规定。
- **与后续 `params` 题的边界**：当前 `url` 是基础请求输入；题库把“`params` 变化自动重发”单独保存为另一个来源问题和 Canonical，因此这里不定义 params 的对象 identity、深比较或 request-key 规则。

## 原理机制

自定义 Hook 本质上是把一组 Hook 状态和副作用生命周期封装成可复用函数。`useState` 保存渲染需要的数据；`useEffect` 在提交后启动网络同步，并在依赖变化或卸载时先执行 cleanup。对请求而言，可以把每次 setup 看成一个版本：只有仍处于 `active=true` 的当前版本可以写状态，旧版本通过 cleanup 撤销写权限。

Promise 链里第一段 `.then` 负责把 Fetch API 的 `Response` 转成“成功数据或显式 HTTP 错误”，第二段 `.then` 只处理解析后的数据，`.catch` 汇总网络失败、主动抛出的 HTTP 错误和解析错误。这样正常路径和失败路径边界清晰。

## 常见追问

- 问：为什么 `fetch` 返回 404 时 `.catch` 不一定执行？答：Fetch API 在收到 HTTP 响应后会 resolve 为 `Response`，HTTP 状态失败不等于网络 Promise reject；所以示例先检查 `response.ok`，再主动抛错。
- 问：为什么请求要放在 `useEffect`？答：网络是 React 外部系统，Effect 用 setup/cleanup 描述一次同步过程；依赖变化时 React 会先清理旧过程再启动新过程。
- 问：为什么既 `abort()` 又需要 `active`？答：`abort()` 尽量取消底层 Fetch，但注入的 `fetcher` 未必真正支持取消；`active` 是最终状态写入门禁，保证旧 Promise 不覆盖当前 UI。
- 问：为什么依赖里有 `fetcher`？答：Effect 读取了它；如果它是响应式值就应纳入依赖。调用方应避免每次 render 无意义地创建新函数。
- 问：如果不是 JSON 接口怎么办？答：把 `response.json()` 换成与接口契约一致的解析，例如 `text()` 或 `blob()`；原题没规定响应格式，所以 JSON 只是当前答案侧假设。
- 问：`params` 变化自动重发怎么加？答：题库把它保留成独立后续题。核心是把 params 纳入请求构造和 Effect 依赖，并明确对象 identity / 稳定引用与旧请求失效语义；不应在基础题里假装这些规则已经由来源给出。

## 易错点

- 只写 `fetch(...).then(setData)`，没有 loading、错误路径和 cleanup。
- 以为 HTTP 404/500 一定会让 `fetch()` Promise reject，漏掉 `response.ok` 检查。
- URL 已变化或组件已卸载，旧响应仍然 `setState`，造成陈旧数据覆盖。
- Effect 读取 `url/fetcher` 却故意漏依赖，形成 stale closure；或反过来每次 render 创建新 fetcher 导致无意义重跑。
- 把 JSON、缓存、重试、params 深比较等答案侧选择说成原题已经规定。
