# 场景：百万级别数据的Excel如何快速导入到数据库中

## 核心结论

百万级 Excel 不在 HTTP 请求线程内一次性读完再全量入库；上传后创建导入任务，EasyExcel 行监听器做轻量校验并按可配置批次写入暂存表或消息队列，后台消费者幂等落业务表。批大小和并发度由压测、数据库连接池与行大小共同决定。

## 1 分钟版

- 先限定目标：允许的文件大小/列数、完成时限、错误回执粒度、是否允许部分成功和重复提交。
- 对象存储保存原文件，导入任务保存状态、文件 hash、模板版本、操作者和进度；同一业务键在目标表设唯一约束。
- 行监听器只做解析、格式/字典预校验和批量投递，不能把百万行积在 JVM List。
- 消费者分批事务写暂存/目标表，唯一键冲突按幂等规则处理；失败记录行号、列、原因并支持可重试或下载错误清单。

## 3 分钟版

上传校验文件类型、大小和模板后生成 importId，原文件落对象存储并异步执行。EasyExcel 的逐行 listener 将合格行累积到有上限的 batch；batch 进入有背压的工作队列。消费者按 importId、分片序号和业务键写入：先写可审计的暂存记录，再校验跨行约束并 upsert/插入业务表。任务状态只能单向推进（UPLOADED→PARSING→WRITING→SUCCEEDED/PARTIAL_FAILED/FAILED）；每批提交后更新已处理数，重试以 importId+业务键去重。

- 官方 README 展示逐行 listener 读取；其内存/速度数字只适用于说明中的版本、文件和机器，不能作为本题容量承诺。
- 批大小、线程数、队列深度、连接池上限和事务超时必须由行大小、索引、数据库写能力和压测结果确定。
- 大文件采用异步任务与进度查询；同步接口只返回 importId。
- 高失败率、毒性行、重复上传、消费者重启、对象存储不可用和数据库限流均需可观测和可恢复。

## 原理机制

入口是上传服务，输出 importId；解析状态逐行转为有界 batch；队列把解析与写库解耦并提供背压；写库消费者以幂等键保证重试不重复，以批事务缩短锁持有时间；错误数据进入错误表/文件，任务聚合结果供用户查询。

## 常见追问

- 问：为什么不能直接多线程读同一个 listener？答：先保持解析顺序和有界 batch；并发应放在独立、受背压控制的写入阶段，并验证库连接与锁承载能力。
- 问：如何防止重复导入？答：文件 hash 防止重复创建任务，业务唯一键和 importId/业务键保证批次重试幂等。
- 问：部分行失败怎么处理？答：成功批提交，失败行带行号和原因落错误清单；任务标 PARTIAL_FAILED，修正后只重导失败行或新建任务。
- 问：如何上线？答：先用脱敏样本压测不同批参数，监控队列积压、行耗时、DB 错误率和连接池，再灰度放开文件大小。

## 易错点

- 不要把固定 500/1000 行批次说成通用最优值。
- 不要用一个超长事务包住百万行。
- 不要只靠内存 Set 去重。
- 不要吞掉错误而只返回导入成功。
