# TIME_WAIT 与 CLOSE_WAIT：谁在等待什么，以及为什么要 2MSL

## 核心结论

`CLOSE_WAIT` 和 `TIME_WAIT` 不是“同一种等待的两个名字”，它们处在关闭流程的不同责任边界。

- **CLOSE_WAIT：等待本地应用完成关闭。** 本端在 `ESTABLISHED` 收到对端 `FIN` 后，TCP 会确认这个 `FIN`、把“连接正在关闭/读方向结束”通知给本地应用，并进入 `CLOSE_WAIT`。之后要等本地应用调用 `close`/等价关闭动作，TCP 才发送自己的 `FIN` 并进入 `LAST_ACK`。所以大量、长时间、超出业务预期的 `CLOSE_WAIT`，首先应查应用的 socket 生命周期、异常路径、阻塞逻辑和连接归还，而不是调 TCP 重传参数。
- **TIME_WAIT：已经完成主动关闭路径后继续保留连接状态。** RFC 9293 要求主动关闭的 TCP 在 `TIME_WAIT` 保留 `2 × MSL`。这段时间让端点仍能处理对端因“最后 ACK 丢失”而重传的 `FIN`，同时给旧连接残留的重复报文足够时间从网络中消失，降低同一连接标识过早复用时被旧报文干扰的风险。
- **角色不要和客户端/服务端绑定。** 谁先发起关闭，谁才通常走主动关闭路径；服务端同样可能主动关闭，客户端也可能成为收到 `FIN` 后等待本地关闭的一方。TCP 还允许半关闭与同时关闭，因此排查时应看真实状态机和报文，而不是按“客户端一定 TIME_WAIT、服务端一定 CLOSE_WAIT”背结论。

## 1 分钟版

正常关闭可以先记住两句话：

1. **CLOSE_WAIT 等应用。** 对端已经发来 `FIN`，本端 TCP 已经知道对端不会再在这个方向发送数据；如果本地应用迟迟不调用关闭，本端就会停在 `CLOSE_WAIT`。
2. **TIME_WAIT 等协议安全窗口。** 主动关闭方在完成关闭握手后保留状态 `2MSL`，既能在最后 ACK 丢失时再次响应对端重传的 `FIN`，也能让旧连接的延迟重复报文过期。

因此排查方向也不同：`CLOSE_WAIT` 持续增长时优先定位进程、fd、线程栈和 close/归还路径；`TIME_WAIT` 多时先看短连接创建速率、谁在主动关闭、连接池/keep-alive 是否合理、四元组复用压力和实际失败指标，不要只因为“数量多”就改内核参数。

## 3 分钟版

以 A 主动关闭、B 被动接收关闭为例：

`A: ESTABLISHED --send FIN--> FIN_WAIT_1/FIN_WAIT_2`

`B: ESTABLISHED --receive FIN, send ACK--> CLOSE_WAIT`

此时 B 已经收到 A 的 `FIN`。按 RFC 9293，TCP 会把连接关闭状态通知给应用；在半关闭语义下，B 仍可能把本方向剩余数据发送给 A。只有当 B 的应用也执行关闭，B 才发送自己的 `FIN` 并进入 `LAST_ACK`。

A 收到 B 的 `FIN` 后发送 ACK，并进入 `TIME_WAIT`。如果这个最后 ACK 在网络中丢失，B 还停在 `LAST_ACK`，会重传 `FIN`；因为 A 没有立刻删除这条连接的控制状态，它仍可以再次 ACK。RFC 9293 还要求 `TIME_WAIT` 对再次收到的 `FIN` 重启 2MSL 计时，这正说明这个状态不是“纯粹睡眠”，而是关闭可靠性的一部分。

第二个目的与旧重复报文有关。同一个本地地址/端口、远端地址/端口如果过早形成新的连接 incarnation，上一条连接迟到的旧 segment 可能与新连接发生混淆。`TIME_WAIT` 的等待窗口让旧 segment 有时间耗尽其最大生存期；RFC 1337 对提前破坏 TIME-WAIT 后旧重复报文造成的新连接风险做了专门分析。

这里不要把 2MSL 解释成“第一 MSL 给最后 ACK 去、第二 MSL 给 FIN 回来”这样的固定物理旅程。**MSL 是单个 TCP segment 在网络中允许存活的最大时间参数，RFC 9293 的规范要求是主动关闭后保留 2 × MSL；2MSL 的工程含义是关闭握手可靠性与旧重复报文隔离窗口。** 具体操作系统里能观察到的 TIME_WAIT 时长、MSL 取值、时间戳辅助复用规则和调优开关属于实现细节，不能把某个平台的秒数当成 TCP 的跨平台常量。

## 对比表

| 维度 | CLOSE_WAIT | TIME_WAIT |
|---|---|---|
| 直接触发 | 在同步连接状态收到对端 `FIN` | 主动关闭路径完成后进入；典型是收到对端 `FIN` 并发送最终 ACK |
| 此时主要在等什么 | 等本地应用发起自己的关闭 | 等 2MSL 协议安全窗口结束，并继续处理关闭阶段可能到达的报文 |
| 谁负责结束 | 本地应用调用 `close`/等价动作后，TCP 继续发 `FIN` | TCP 定时器到期后删除连接状态；收到重复 `FIN` 会按规范重新计时 |
| 长时间堆积的第一排查方向 | 应用 socket 生命周期、异常/超时路径、线程阻塞、连接池归还 | 主动关闭位置、短连接速率、keep-alive/连接池、四元组/端口压力、真实错误率 |
| 是否天然代表故障 | 否；半关闭可以合法存在，但长期超出业务预期很可疑 | 否；短连接服务出现较多 TIME_WAIT 可以是正常协议结果 |

## 关键细节

- RFC 9293 对 `CLOSE_WAIT` 的定义是：已经收到远端 TCP 的连接终止请求，正在等待本地用户/应用的终止请求。收到 `FIN` 后从 `ESTABLISHED` 进入 `CLOSE_WAIT`；本地 `CLOSE` 后发送 `FIN` 并进入 `LAST_ACK`。
- 正常 TCP 关闭是双向独立的，所以“对端发 FIN”只代表对端的发送方向关闭。TCP 支持 half-close；本端在 `CLOSE_WAIT` 期间仍可能完成自己尚未发送完的数据。
- RFC 9293 的明确规范是：主动关闭的连接必须在 `TIME_WAIT` 停留 `2 × MSL`。因此最稳妥的回答是“2MSL 是规范的关闭安全窗口”，而不是给出一个所有 OS 都相同的固定秒数。
- `TIME_WAIT` 能保留必要状态来再次 ACK 重传的 `FIN`。如果最后 ACK 丢失而本端已经彻底忘掉旧连接，对端重传的关闭报文就失去了原状态机上下文。
- TIME_WAIT 同时帮助隔离旧连接的 duplicate segments。RFC 1337 展示了旧重复 segment 在连接过早重新建立时可能导致数据误接收或状态失步等风险，因此“强行尽快消灭 TIME_WAIT”不是免费的优化。
- RFC 9293 允许在满足严格序列号条件时从 `TIME_WAIT` 接受新的 SYN，并建议可利用 TCP timestamps 缩短 TIME-WAIT 的影响；这说明安全复用依赖协议条件，不等于任意开启一个“reuse”开关就安全。
- “主动关闭方”是协议角色，不等于“客户端”。HTTP 服务端在超时、负载均衡、连接策略等情况下也可能主动关闭连接。
- 同时关闭时双方都可能经过 `CLOSING` 并最终进入 `TIME_WAIT`，所以现场状态应以抓包和状态机为准。

## 排查方法

### CLOSE_WAIT 持续增长

先回答三个问题：**是哪一个进程持有、这些连接停了多久、应用为什么没有进入本地 close？**

Linux 上可以先用 `ss -tanp` 按状态和端点聚合，再把 socket 映射到 pid/fd；随后结合线程栈、应用日志、连接池指标和代码路径检查：

1. 收到 EOF、协议结束或对端断开后是否走到 `close`/`finally`/资源自动释放；
2. 异常、超时、取消、提前 return 是否绕开归还连接；
3. 业务线程是否阻塞，导致关闭逻辑迟迟不能执行；
4. 连接池借还是否对称，是否把已经半关闭的连接继续保留；
5. 是否确实有业务采用半关闭，`CLOSE_WAIT` 的存活时间是否符合该协议预期。

关键证据是**状态持续时间与代码生命周期不一致**，而不是看到一个 `CLOSE_WAIT` 就判定泄漏。

### TIME_WAIT 很多

先区分“协议正常现象”和“容量问题”。检查：

1. 每秒新建 TCP 连接数是否很高，是否本可复用长连接；
2. 哪一侧在主动关闭，是否因为应用/代理的超时策略造成不必要的连接抖动；
3. 是否出现本地临时端口耗尽、connect 失败、四元组冲突或延迟上升等真实故障；
4. HTTP keep-alive、数据库/Redis 客户端连接池、反向代理 upstream 复用是否生效；
5. 若考虑 OS 的 TIME_WAIT 复用/缩短策略，先查当前内核版本的精确定义、时间戳前提、NAT/代理拓扑和回滚方案，再压测验证。

优先从**减少无意义的连接 churn**入手；内核参数是实现相关的容量工具，不应代替应用连接生命周期设计。

## 原理机制

把关闭阶段看成两个独立方向会更容易理解：A 的发送方向通过 `A FIN -> B ACK` 关闭，B 的发送方向通过 `B FIN -> A ACK` 关闭。`CLOSE_WAIT` 位于“我已经收到对端 FIN，但我自己的发送方向还没有由应用关闭”这个边界；`TIME_WAIT` 位于“我的主动关闭流程已经完成最后确认，但旧连接状态还不能立即销毁”这个边界。

因此二者体现了不同的控制责任：

- `CLOSE_WAIT` 的推进依赖**应用层动作**；TCP 不应替应用擅自决定何时丢掉尚可能发送的数据。
- `TIME_WAIT` 的退出主要依赖**传输层时间与报文规则**；它保护关闭握手和连接 incarnation 隔离。

这也是为什么处理手段不能互换：给 `CLOSE_WAIT` 调短 TIME_WAIT 定时器没有解决根因；为了减少 `TIME_WAIT` 强迫应用尽快 `close` 也没有意义。先确定状态属于哪个边界，再改对应责任方。

## 项目经验版

如果要把这道题映射到真实项目，只记录可验证事实：服务是否使用连接池/keep-alive、哪一侧主动关闭、典型连接创建率、出现过哪些 socket 状态、是否发生临时端口或 fd 压力、最终通过什么抓包/线程栈/指标定位。没有真实事故记录时，可以说明“按 TCP 状态机给出排查方法”，不要编造某次生产故障或声称调某个 sysctl 一定提升了多少性能。

## 常见追问

- **问：TIME_WAIT 为什么不能收到最后 ACK 后马上删除？** 答：最终 ACK 可能丢失，对端会重传 `FIN`；保留 TIME_WAIT 状态使本端能继续按原连接状态响应。同时等待窗口让上一 incarnation 的旧重复报文有时间消失，避免过早复用同一连接标识。
- **问：为什么是 2MSL，而不是 1MSL？** 答：RFC 9293 给出的规范就是主动关闭后保留 `2 × MSL`。MSL 描述单个 segment 的最大生存期；2MSL 构成 TCP 关闭与旧报文隔离的安全窗口。不要把它机械解释成“固定一趟出去加一趟回来”，也不要把某个 OS 的具体秒数当成协议常量。
- **问：CLOSE_WAIT 很多一定是连接泄漏吗？** 答：不一定。合法半关闭可以停留在该状态；但如果数量持续增长、存活时间超过协议预期、fd 不释放，就应优先查应用没有 close、异常路径遗漏、线程阻塞或连接池归还问题。
- **问：TIME_WAIT 很多一定影响性能吗？** 答：不一定。它首先说明系统存在较多主动关闭后的连接。只有结合端口耗尽、连接失败、内存/CPU、延迟等指标才能判断是否形成容量问题。
- **问：客户端才会 TIME_WAIT、服务端才会 CLOSE_WAIT 吗？** 答：不是。决定状态的是谁先发 FIN、谁收到 FIN，以及后续关闭时序，不是客户端/服务端标签。
- **问：能不能通过内核参数快速减少 TIME_WAIT？** 答：可以存在实现相关的复用或时间戳优化，但语义、版本和拓扑前提必须查目标 OS 文档并压测。更通用的第一选择是减少不必要短连接、使用合理 keep-alive/连接池，并确认主动关闭策略。
- **问：抓包时怎样区分两者？** 答：找到连接的 FIN/ACK 时序：收到对端 FIN 后本端尚未发自己的 FIN，对应本端 CLOSE_WAIT；本端完成主动关闭并对对端 FIN 发出最后 ACK 后，对应 TIME_WAIT。再把四元组映射到实际进程和代码生命周期。

## 易错点

- 不要把 `CLOSE_WAIT` 说成“等对端再次关闭”；它等的是**本地应用**完成关闭请求。
- 不要把 `TIME_WAIT` 简化成“浪费资源所以应该消灭”；它承担关闭可靠性和旧报文隔离职责。
- 不要把客户端/服务端身份当作状态决定因素，应按主动/被动关闭和真实 FIN 时序判断。
- 不要把 2MSL 说成“两个方向各一个 MSL”的规范定义；RFC 的要求是 2 × MSL 的 TIME_WAIT 安全窗口。
- 不要给出跨平台统一的 TIME_WAIT 秒数；先区分协议规范与目标 OS 实现。
- 不要在没有端口耗尽、连接失败或时延证据时，仅凭 TIME_WAIT 数量就修改内核参数。
- 不要把合法 half-close 与泄漏混为一谈；是否异常要结合业务协议和持续时间判断。
