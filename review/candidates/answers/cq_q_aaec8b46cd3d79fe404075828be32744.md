# 合并两个有序链表：递归与迭代

## 核心结论

原始面试笔记明确要求：**把两个升序链表合并成一个升序链表，同时给出递归和迭代两种实现，并比较堆栈空间消耗**。来源没有保存节点类、语言、是否允许复用原节点、相等元素的稳定性规则等接口细节。本候选采用一个明确的参考契约：Java 单向链表节点 `ListNode(int val, ListNode next)`，输入链表都按 `val` 非递减排列；实现通过重连已有节点完成合并，不复制数据节点。相等时优先取第一个链表的节点只是参考实现的确定性选择，不冒充来源要求。

两种实现的时间复杂度都是 `O(m+n)`。主要差异在辅助空间：递归版本每选择一个节点都会继续递归，最坏调用深度可达 `m+n`，因此调用栈空间为 `O(m+n)`；迭代版本只维护若干指针，辅助空间为 `O(1)`（dummy 节点也是常数空间）。

## 1 分钟版

- 两个链表都已升序，所以每一步只需要比较当前头节点，较小者一定是剩余结果的下一个节点。
- **递归**：较小头节点作为当前答案头，把它的 `next` 指向“剩余两条链表的合并结果”。
- **迭代**：用 `tail` 指针维护结果链表尾部，每轮摘下较小头节点接到 `tail` 后面；某一条耗尽后直接挂上另一条剩余部分。
- 两种方法都最多访问每个节点一次，时间 `O(m+n)`。
- 递归最坏需要 `O(m+n)` 调用栈；迭代只用常数个指针，辅助空间 `O(1)`。
- 本实现会重连输入节点；如果调用方要求输入链表保持不变，则必须改为创建新节点，空间口径也会变化。

## 3 分钟版

这里用 Java 作为参考语言，节点/API 不是来源固定要求：

```java
static final class ListNode {
    int val;
    ListNode next;

    ListNode(int val) {
        this.val = val;
    }
}

static ListNode mergeRecursive(ListNode a, ListNode b) {
    if (a == null) return b;
    if (b == null) return a;

    if (a.val <= b.val) {
        a.next = mergeRecursive(a.next, b);
        return a;
    } else {
        b.next = mergeRecursive(a, b.next);
        return b;
    }
}

static ListNode mergeIterative(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(0);
    ListNode tail = dummy;

    while (a != null && b != null) {
        if (a.val <= b.val) {
            tail.next = a;
            a = a.next;
        } else {
            tail.next = b;
            b = b.next;
        }
        tail = tail.next;
    }

    tail.next = (a != null) ? a : b;
    return dummy.next;
}
```

递归版的正确性可以用一个简单不变量理解：假设 `a` 和 `b` 各自升序，那么两者当前头节点中较小的那个，一定是所有剩余节点中的最小值，所以它可以安全成为合并结果的下一个节点；剩下的问题仍然是“合并两个升序链表”，规模至少减少一个节点。任一链表为空时，另一条链表本身已经升序，可以直接返回。

迭代版保持不变量：`dummy.next ... tail` 始终是已经确定的升序前缀，`a` 与 `b` 分别指向两条链表尚未处理的第一个节点。每轮把更小的头节点接到 `tail` 后，前缀仍升序，而且待处理节点总数减少 1。循环结束时，未耗尽链表的剩余部分本身已升序且所有值都不小于已接入的最后一个节点，因此可以整体挂接。

例如：

```text
a: 1 -> 2 -> 4
b: 1 -> 3 -> 4
```

结果：

```text
1 -> 1 -> 2 -> 3 -> 4 -> 4
```

相等值取哪条链表的节点不会影响“值序列升序”的正确性；本实现使用 `<=`，让第一条链表中的相等节点先出现，便于行为确定。

## 关键细节

- **空链表**：`null + null` 返回 `null`；一边为空时直接返回另一边。
- **重复值**：允许重复；`<=` 只决定相等时的节点先后，不会丢节点。
- **节点复用**：本候选重连原节点，不新建结果数据节点。调用后原链表的 `next` 关系可能改变，因此不能再把输入当作未修改链表使用。
- **递归栈**：最坏情况下直到最后才命中空链表基线，例如一条链表所有值都小于另一条链表时，调用深度可以接近 `m+n`；大链表上可能触发栈溢出风险。
- **迭代空间**：`dummy`、`tail`、`a`、`b` 都是常数数量引用，所以辅助空间 `O(1)`。这里的 `dummy` 不计入与输入规模增长的空间。
- **输入前置条件**：算法依赖两条输入链表已经非递减排序；若输入无序，不能保证结果有序。
- **环形链表**：来源没有要求支持带环链表；本参考契约假设输入为有限无环链表。
- **整数溢出**：实现只比较 `int`，不做加减运算，因此 `Integer.MIN_VALUE / MAX_VALUE` 不会因算术溢出破坏比较。

## 原理机制

这道题利用的是“两个有序序列归并”的局部最优性质。对于两个升序链表，剩余元素的全局最小值一定出现在两个当前头节点之一，因此不需要扫描后续节点。选择更小头节点后，问题规模缩小，但“两个剩余链表仍然各自有序”的结构不变，这也是递归定义成立的原因。

递归和迭代实际上执行的是同一条决策链，只是**状态保存位置不同**：

- 递归把“当前选了谁、返回后要把谁的 `next` 接到结果”保存在运行时调用栈帧里；
- 迭代把待处理位置显式保存在 `a / b / tail` 三个指针里。

所以二者时间复杂度相同，但递归把控制状态线性积累在栈上，而迭代把状态压缩成常数个指针。这正是题目要求比较的“堆栈空间消耗”差异。

## 项目经验版

来源没有真实项目背景，不虚构线上使用经历。面试现场我会先确认三个接口问题：是否允许修改/复用输入节点、是否需要对相等键保持跨链表稳定顺序、链表规模是否可能大到递归栈不可接受。若链表规模没有上界或来自外部大数据流，我会优先给迭代版本作为生产参考，因为它避免了输入规模相关的调用栈风险。

## 常见追问

- 问：为什么递归是 `O(m+n)` 栈空间，不是 `O(min(m,n))`？答：每次递归只消费一个节点；即使某条链表先后一直被选择，另一条仍未空，调用链可以累计接近两条链表总节点数，直到命中空链表基线。
- 问：迭代为什么可以直接把剩余链表整体接上？答：进入该分支时另一条链表已经为空；剩余链表自身有序，而且之前每次选择的节点都不大于当前剩余头，所以整体挂接仍保持升序。
- 问：`a.val <= b.val` 必须写成 `<=` 吗？答：不是。`<` 也能得到按值升序的结果，只是相等元素的跨链表先后不同；来源没有保存稳定性要求，本实现选择 `<=` 让行为确定。
- 问：如果要求不能修改原链表怎么办？答：每次选择值时创建新节点，而不是重连原节点。时间仍是 `O(m+n)`，但结果节点需要 `O(m+n)` 额外堆空间；递归版还要再叠加调用栈。
- 问：哪个版本更适合超长链表？答：在没有尾递归优化保证的普通 Java 环境里优先迭代，因为它的辅助空间不随链表长度增长，避免深递归带来的栈溢出风险。

## 易错点

- 忘记处理一条链表为空，导致空指针访问。
- 递归选择了 `a` 却写成 `a.next = mergeRecursive(a, b.next)`，没有推进 `a`，造成无限递归或错误链接。
- 迭代接入节点后忘记推进对应输入指针或 `tail`。
- 循环结束后忘记挂上未耗尽链表，丢失尾部节点。
- 一边宣称 `O(1)` 空间，一边实际为每个值创建新结果节点。
- 只说“递归更耗空间”，却没有说明最坏调用深度为何随 `m+n` 增长。
