# 三个线程按 1,4,7... / 2,5,8... / 3,6,9... 协同顺序打印

## 核心结论

可以把“当前该谁打印”变成一个受锁保护的共享状态。设 `next` 是下一个全局数字：线程 0 只负责 `next % 3 == 1` 的数字，也就是 `1,4,7...`；线程 1 负责 `2,5,8...`；线程 2 负责 `3,6,9...`。每个线程拿锁后，如果还没轮到自己就进入对应 `Condition` 等待；轮到时打印并把 `next++`，再唤醒下一位线程。

来源只描述协同规律，没有给停止条件。为了让代码可执行，下面额外定义一个 `limit`：打印 `1..limit`。`limit` 是实现/测试契约，不冒充原题隐藏条件。示例还显式定义协作取消语义：任一等待线程被中断，或输出回调失败，就把共享 `cancelled` 置为 `true` 并唤醒全部等待线程，避免某个轮次永久缺席后其余线程死锁。

## 1 分钟版

- 共享变量 `next` 决定当前数字，同时也唯一决定应该由哪个线程处理。
- 三个线程共享同一把 `ReentrantLock`，这样“检查轮次 → 输出 → next++ → 唤醒”是一个原子临界区。
- 每个线程用独立 `Condition` 等待，条件是 `owner(next) == workerId`。
- 等待必须使用 `while`，不能用 `if`，因为 Condition 允许虚假唤醒，线程被唤醒后必须重新检查共享状态。
- 正常打印后只唤醒下一位；打印结束、线程中断或输出失败时统一唤醒全部等待者。
- 共享 `cancelled` 是协作组的终止状态：一条线程无法继续履行后续轮次时，其余线程不会继续等待一个永远不会出现的 owner。
- 正确性不依赖线程启动顺序或调度速度；谁先拿到锁都必须经过 owner 条件判断。
- 总共打印 `limit` 个数，业务工作量 `O(limit)`；共享状态是常数级，线程数固定为 3。

## 3 分钟版

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;
import java.util.function.BiConsumer;

public final class ThreeThreadOrderedPrinter {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition[] turns = {
            lock.newCondition(), lock.newCondition(), lock.newCondition()
    };
    private final int limit;
    private final BiConsumer<Integer, Integer> output;
    private int next = 1;
    private boolean cancelled;

    ThreeThreadOrderedPrinter(
            int limit,
            BiConsumer<Integer, Integer> output) {
        this.limit = limit;
        this.output = output;
    }

    void runWorker(int workerId) {
        lock.lock();
        try {
            while (true) {
                while (!cancelled && next <= limit && owner(next) != workerId) {
                    turns[workerId].await();
                }

                if (cancelled || next > limit) {
                    signalAllTurns();
                    return;
                }

                int value = next++;
                try {
                    output.accept(workerId, value);
                } catch (RuntimeException | Error e) {
                    cancelled = true;
                    signalAllTurns();
                    throw e;
                }

                if (next <= limit) {
                    turns[owner(next)].signal();
                } else {
                    signalAllTurns();
                }
            }
        } catch (InterruptedException e) {
            cancelled = true;
            signalAllTurns();
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    private void signalAllTurns() {
        for (Condition turn : turns) {
            turn.signalAll();
        }
    }

    private static int owner(int value) {
        return Math.floorMod(value - 1, 3);
    }
}
```

启动 3 个线程，分别执行 `runWorker(0)`、`runWorker(1)`、`runWorker(2)`。当 `limit=9` 时，全局输出应为 `1,2,3,4,5,6,7,8,9`，同时线程 0 实际负责 `1,4,7`，线程 1 负责 `2,5,8`，线程 2 负责 `3,6,9`。

## 关键细节

- **全局顺序与线程子序列同时满足**：不能让三个线程分别一次性打印 `1,4,7...`、`2,5,8...`、`3,6,9...`，否则全局输出顺序不可控。必须每打印一个数字就转交下一轮。
- **为什么用 while 等待**：`await()` 可能虚假唤醒，也可能多个线程在调度切换后竞争锁；重新检查谓词才能保证安全。
- **为什么状态检查和打印要在同一锁内**：如果检查 owner 后先释放锁，另一线程可能改变 `next`，当前线程随后打印的就不是它拥有的数字。
- **退出要唤醒所有等待者**：最后一个数字打印后，剩余线程可能仍阻塞在 `await()`；如果没人唤醒，它们无法观察 `next > limit`。
- **为什么中断需要共享取消状态**：如果某个等待线程只恢复中断标记然后退出，等 `next` 轮到它负责的余数类时，其余线程会永远等待这个已经退出的 owner。把 `cancelled=true` 与 `signalAll` 放在同一锁内，能让所有线程醒来观察统一终止状态。
- **输出失败也必须传播取消**：`output.accept` 是外部回调；若它抛异常而当前线程直接离开，后续同样可能卡在缺失 owner 上。示例先取消协作组、唤醒等待者，再把原异常抛回调用方。
- **Condition 不是唯一方案**：三个 `Semaphore` 以 `1,0,0` 初始化也很自然；`wait/notifyAll`、`LockSupport` 也能实现。选择 Condition 的价值是把三个轮次的等待队列显式分开。

## 原理机制

并发正确性的核心不在“有三条线程”，而在两个不变量：正常运行时，进入输出临界区必须满足 `workerId == owner(next)`；协作无法继续时，所有线程最终都能观察到 `cancelled == true` 并退出。`next` 从 1 开始且每次只在持锁状态下增加一次，所以正常输出不会重复、不会跳号；owner 映射又保证数字 1/4/7...、2/5/8...、3/6/9... 分别归属固定线程。

Condition 只是把“谓词不成立时不要占 CPU”实现成阻塞等待。锁提供共享状态的互斥和可见性，while 谓词提供面对任意唤醒/调度顺序时的正确性，signal 负责推进状态机到下一轮，`cancelled + signalAll` 则负责把异常终止也纳入同一个状态机。

## 项目经验版

来源是并发手写题，没有真实项目背景，因此不虚构生产经历。工程里更常见的原则是：不要用多个线程人为串行化本来可并行的工作；这种模式主要用于理解条件等待、状态机和线程协作。如果真实业务真的要求严格有序，多数情况下还应比较单线程事件循环、队列/Actor 等更简单的串行化模型。

## 常见追问

- 问：为什么不能三个线程各自 `for (i=id+1; i<=n; i+=3)` 直接打印？答：它只能保证各线程内部子序列，不能保证全局输出是 1,2,3,4...；调度可能产生 1,4,7,2...。
- 问：为什么 await 外面必须是 while？答：因为虚假唤醒和竞争都可能让线程醒来时仍未轮到它；while 会重新验证共享谓词。
- 问：能用 Semaphore 吗？答：可以，三个信号量初始化为 `1,0,0`，每个线程打印后 release 下一位，是这个三状态环的另一种直接编码；异常取消仍需额外设计统一终止语义。
- 问：`volatile next` 能替代锁吗？答：不能单独替代。`检查 owner + 打印 + next++` 是复合操作，需要原子协调；而且 Condition 的 await/signal 本身也要求持有对应锁。
- 问：如何避免程序结束时线程挂住？答：正常结束和异常取消都要让所有等待线程有机会醒来检查终止条件；示例分别通过 `next > limit` 和 `cancelled` 表达这两类终止状态。
- 问：某条线程在 await 时被 interrupt 会怎样？答：它在重新获得锁后进入 catch，设置共享取消状态、唤醒所有等待者并恢复自己的中断标记；其它线程醒来后看到 `cancelled` 即退出，不会等一个已经消失的轮次。
- 问：怎样验证并发实现不是“偶尔碰巧正确”？答：重复用真实三线程运行，随机化启动顺序并设置超时，同时检查无死锁、输出恰好 1..N、每个值只出现一次、每个值由正确 worker 打印；还应专门注入等待线程中断和输出异常，验证整个协作组可终止。

## 易错点

- 只保证每个线程自己的等差子序列，没保证三个线程之间的全局顺序。
- 用 `if` 包住 `await()`，忽略虚假唤醒。
- 在锁外执行 `next++` 或判断 owner，制造竞态。
- 最后一个数字打印完没有唤醒其它等待线程，导致 join 永远不结束。
- 某个 worker 中断/异常退出后只 `signalAll` 却没有共享取消状态，导致后续轮次等待一个已经不存在的 owner。
- 用忙等 `while(turn != id) {}` 消耗 CPU，却没有解释内存可见性和调度成本。
- 把示例里的 `limit` 当成来源条件；原题只保留了协同规律。
