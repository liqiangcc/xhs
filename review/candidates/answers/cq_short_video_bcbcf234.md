# 如何设计三千万用户同时在线的短视频系统？

## 核心结论

这题的关键不是先堆“Redis、Kafka、CDN”，而是先把 **3000 万在线**拆成可计算的播放、上传、推荐和互动负载，再把**视频大流量数据面**与**推荐/互动控制面**分开。视频文件走“客户端直传对象存储 → 异步审核/转码 → 多码率切片 → CDN”，播放尽量不穿过业务应用服务器；推荐走“候选召回 → 排序 → Feed 返回”；点赞、关注、评论等写路径以业务事实和幂等键为准，展示计数允许异步聚合。容量、SLO、缓存命中率和降级策略必须先写成假设并通过压测验证，不能把“3000 万在线”直接等同于“3000 万人同时以最高码率播放”。

## 1 分钟版

我会先问 5 个数字：**在线用户数、同时播放比例、平均有效码率、峰值 Feed QPS、上传/互动峰值 QPS**。例如只做容量演示，假设 3000 万在线里 10% 同时播放、平均 2 Mbit/s，则 CDN 边缘侧视频下行约 `3,000,000 × 2 Mbit/s = 6 Tbit/s`；如果视频对象的边缘命中率假设为 95%，粗略回源量才约是剩余 5%，也就是约 300 Gbit/s，真实设计还要按地域、协议开销、码率分布和峰值冗余重新测。

架构分四条链路：

1. **上传发布链路**：客户端拿上传凭证后分片直传对象存储；上传完成写视频元数据，异步做审核、转码、封面和多码率 HLS/DASH/CMAF 包，产物进入 CDN。
2. **播放链路**：Feed 只返回视频 ID、元数据和播放授权；客户端直接从 CDN 拉清单和分片。热点由 CDN 缓存、请求合并/Origin Shield 一类机制保护源站，应用服务不代理视频字节。
3. **推荐链路**：先召回候选，再用用户/视频/上下文特征排序；热门榜、关注流、最近成功结果作为降级路径。
4. **互动链路**：点赞/关注/评论先落可幂等的业务事实，计数和画像异步更新；队列积压时宁可计数稍旧，也不要让核心播放链路被拖垮。

核心指标看首帧时间、卡顿率、播放成功率、CDN 命中/回源带宽、Feed P99、转码队列年龄、互动写失败率和异步积压，而不是只看服务器 CPU。

## 3 分钟版

### 1. 先把“3000 万在线”转成容量模型

我不会直接用注册用户或在线用户乘码率，而是定义：

- `U_online`：在线用户，题目给 3000 万；
- `r_play`：某时刻真正处于播放状态的比例；
- `b_avg`：经过 ABR 后的平均有效视频码率；
- `H_cdn`：按字节计算的 CDN 命中率；
- `Q_feed`：Feed 刷新峰值 QPS；
- `Q_write`：点赞、关注、评论、上传元数据等写请求峰值。

视频边缘出口近似：

`B_edge = U_online × r_play × b_avg`

粗略回源流量近似：

`B_origin ≈ B_edge × (1 - H_cdn)`

这里只是容量公式。比如 `r_play=10%`、`b_avg=2 Mbit/s` 时是约 6 Tbit/s 边缘下行；若再假设 `H_cdn=95%`，理论回源基线约 300 Gbit/s。上线前要按国家/运营商/机型/清晰度分别建模，并用 P95/P99 峰值、突发热门视频和缓存冷启动做压力测试。**这些百分比和码率都是演示假设，不是声称某真实业务的生产数据。**

### 2. 上传与媒体处理：异步化，避免视频字节穿业务服务

上传流程我会设计成：

`创建上传会话 -> 返回短期上传凭证/UploadId -> 客户端分片直传对象存储 -> 完成上传 -> 生成 video_id -> 审核/转码任务 -> 多码率媒体包 -> 发布元数据 -> CDN 可访问`

大文件采用 multipart 的价值是每个 part 可以独立上传，失败只重传失败 part；业务服务只负责鉴权、会话和元数据，不转发整个视频文件。上传完成后异步转码生成多档码率和 HLS/DASH/CMAF 等 ABR 产物，客户端根据网络情况选择合适 rendition。

这里要有状态机，例如：

`UPLOADING -> UPLOADED -> PROCESSING -> REVIEWED -> PUBLISHED`

失败进入 `PROCESS_FAILED/REVIEW_REJECTED`，重试必须按 `video_id + job_type + version` 幂等。旧版本转码任务晚到时不能覆盖新版本发布结果。

### 3. 播放与 CDN：缓存键稳定，热点不把源站打穿

Feed 服务不返回视频文件本身，只返回 `video_id`、封面、作者、展示信息、媒体清单 URL/授权信息。客户端请求 CDN，CDN miss 才回对象存储或媒体源站。

热点保护我会做三层：

- **缓存键收敛**：与内容无关的用户参数不要进入媒体对象 cache key，避免同一分片被切成大量缓存副本；
- **热点预热与请求合并**：新热视频在发布或快速升温时预热核心地域；同一个 cache key 的并发 miss 由 CDN 的 request collapsing / Origin Shield 类机制合并，减少回源惊群；
- **回源保护**：源站按区域限流，异常时优先保证已经缓存的热门内容，允许低优先级冷内容稍晚加载，并准备第二源/多地域对象复制或多 CDN 切换方案。

权衡是：缓存 TTL 越长，回源越少，但内容撤回、权限变更和版本更新的失效治理越重要。因此媒体对象最好使用内容版本化 URL；需要强撤回时走 manifest/授权层阻断，并配合 CDN invalidation，而不是依赖所有边缘节点“立刻自然过期”。

### 4. 推荐 Feed：召回和排序分开，允许可控降级

短视频 Feed 的在线路径可以是：

`用户请求 -> 用户/上下文特征 -> 多路候选召回 -> 合并去重/规则过滤 -> 排序 -> 重排 -> 返回视频 ID 列表`

Google Research 的 YouTube 推荐论文展示过“候选生成 + 排序”的两阶段模式；这里把它当作可解释的参考架构，不把某个模型当成唯一正确实现。

为了防止推荐服务拖垮播放体验，我会设置明确超时预算。例如召回或排序超时后按层次降级：

1. 上一次成功 Feed 的未消费候选；
2. 关注流/分区热门；
3. 全站热门或冷启动池。

推荐结果可以短 TTL 缓存，但必须保留去重、已看过滤和安全/审核过滤。模型更新、特征服务和在线推理分别监控，不能把离线训练故障直接传播成首页不可用。

### 5. 互动与计数：事实强约束，展示计数可最终一致

点赞的核心不是“Redis 自增”本身，而是用户行为事实不能重复生效。一个可落地的约束是：

- 唯一业务键：`(user_id, video_id, action_type)`；
- 点赞/取消点赞按状态或版本更新；
- 先把事实写入可持久化的主存储或可靠事件入口；
- 计数、推荐特征、作者统计通过事件异步派生；
- 消费者用 `event_id`/版本做幂等，失败重试进入可观测的重试/DLQ 流程；
- 定期用事实表重新校准计数，修复重复消费或异步丢失造成的漂移。

这样“我是否点赞”可以读事实状态，而“123.4 万赞”允许短时间延迟。评论正文、关注关系同理按各自的一致性要求设计，不能把所有数据都塞进一个最终一致计数器。

### 6. 数据分片与热点

元数据按 `video_id` 做稳定分片，用户关系/画像按 `user_id` 做分片起点；但真正的热点通常来自“一个爆款视频”，因此不能指望简单 hash 就消灭热点。

热门视频的**大字节流量**交给 CDN；热点计数采用本地/分片聚合再异步合并，避免所有实例争一个中心计数键；评论第一页、视频元数据等热点小对象可以多级缓存。所有缓存都要定义权威源、版本、TTL 和失效方式，不能把缓存当数据库。

### 7. 故障、降级与恢复

我会把故障演练写进 DoD：

- **推荐服务超时**：降级为缓存 Feed/关注流/热门流，播放链路继续；
- **转码积压**：限制新上传发布速率、提高队列优先级，不影响已发布视频播放；
- **互动事件队列积压**：保住事实写入，暂停非关键画像/统计消费，展示计数允许延迟；
- **对象源站或单地域故障**：优先依赖边缘已缓存内容，同时切换已演练的备用 origin/地域；
- **热点冷启动**：预热 + 请求合并 + 回源限流，必要时降低高码率 rendition 的可用优先级；
- **数据库分片故障**：只影响对应元数据/互动分区，不能让媒体 CDN 数据面跟着全站失败。

恢复时关注“是否还能服务在线流量”之外，还要算 backlog 清空时间：若积压 `N` 条，在线新增速率为 `λ`，希望 `T` 秒追平，则恢复消费能力至少要满足 `μ > λ + N/T`。

## 关键细节

- **SLO 分层**：播放成功率、首帧和卡顿是用户主链路；Feed 延迟是控制面；上传/转码允许分钟级异步。三者不能共用一个超时和线程池。
- **媒体对象不可变/版本化**：转码产物用版本化 key，降低缓存失效歧义；权限/撤回通过授权和 manifest 层收敛。
- **连接数不是吞吐量**：3000 万在线连接可能主要消耗网关/长连接资源，真正带宽由同时播放比例和码率决定。IM/实时推送应与视频分发独立容量规划。
- **ABR 是容量工具也是体验工具**：多档 rendition 让客户端能在网络变化时选择不同码率；容量预算要用真实分布而不是永远取最高码率。
- **缓存命中按字节看**：对视频系统只看“请求命中率”可能掩盖大文件/大分片回源，应同时监控 byte hit ratio 与 origin egress。
- **一致性分级**：审核状态、视频发布版本、用户点赞事实要求明确权威状态；展示计数、热门榜和推荐特征可以异步收敛。
- **灰度与回滚**：新播放器、转码模板、推荐模型、缓存策略分别灰度，保留旧 manifest/模型/策略的快速回滚入口。

## 原理机制

整个系统可以理解为三条彼此隔离但通过事件连接的主干：

`媒体数据面：Upload -> Object Storage -> Transcode/Package -> CDN -> Player`

`推荐控制面：Behavior/Features -> Candidate Generation -> Ranking -> Feed API`

`业务事实面：Like/Follow/Comment -> Durable Fact/Event -> Async Consumers -> Counters/Features/Analytics`

媒体数据面承担最大字节流量，因此尽量使用对象存储和 CDN 的水平扩展能力；推荐控制面承担高 QPS、低延迟的小报文计算；业务事实面负责把用户动作变成可重放、可幂等的状态变化。三条链路只通过稳定 ID、版本和事件契约耦合，因此某一条链路退化时可以单独限流/降级，而不是把故障放大成全站不可用。

## 项目经验版

如果面试官继续追问项目经验，我只会把这套设计映射到真实经历：说明当时的在线规模、播放比例、实际 CDN 命中率、码率分布、本人负责的服务、做过的压测/故障演练和最终指标。没有真实数据时就明确说“上面的 10%、2 Mbit/s、95% 都是容量演示假设”，不把假设包装成生产成绩。

## 常见追问

- **问：3000 万在线到底需要多少带宽？**  
  答：不能只用在线人数算。先测同时播放比例 `r_play` 和平均有效码率 `b_avg`，边缘出口约 `U_online × r_play × b_avg`；再用 CDN byte hit ratio 算回源。比如题内演示假设 10%×2 Mbit/s 得 6 Tbit/s，但真实结果必须按地域、设备和峰值分布重算。

- **问：一个爆款视频突然把 CDN 缓存打冷了怎么办？**  
  答：先让媒体 cache key 稳定，再做热点预热、请求合并/Origin Shield、回源限流和备用 origin；如果仍超预算，优先保低码率和已缓存内容，不能让所有 miss 无限制穿透到对象源站。

- **问：点赞为什么不直接 Redis INCR？**  
  答：INCR 只能解决一个计数操作的原子性，不能证明同一个用户的业务动作没有重复。先用 `(user_id, video_id, action_type)` 或事件版本保存权威事实，再异步聚合计数；这样重复消息可以幂等，计数还能从事实重建。

- **问：推荐系统挂了是不是首页就不能播？**  
  答：不应该。推荐结果与视频字节链路分离，Feed 超时就降级到上次结果、关注流或热门流；客户端拿到 video_id 后仍直接走 CDN。推荐质量下降和视频不可播放应该是两个不同故障等级。

- **问：为什么要多码率而不是只存一个高清文件？**  
  答：ABR 允许为同一内容准备多档 rendition，客户端按网络/设备选择合适码率；它同时降低弱网卡顿风险并让带宽成本可控。代价是转码计算、存储和缓存对象数增加，所以要按实际观看分布决定档位。

- **问：如何证明这个架构真能扛住？**  
  答：先用上面的公式得到各链路预算，再分别做 Feed/互动 QPS 压测、媒体 CDN 冷热缓存压测、源站故障和热门冷启动演练；验收看播放首帧/卡顿、CDN byte hit、origin egress、Feed P99、错误率和 backlog 恢复时间，不以“机器数量够多”作为证明。

## 易错点

- 把“3000 万在线”直接等于“3000 万同时播放”，导致容量估算差一个数量级。
- 让业务应用服务器代理视频文件，导致 Java/API 层被大字节吞吐拖垮。
- 只说“CDN + Redis + MQ”而没有上传、播放、推荐、互动四条数据流和各自一致性边界。
- 把 CDN 缓存命中率当常数，却不设计热门冷启动、cache key 膨胀、回源限流和内容撤回。
- 把点赞计数的原子自增误当成业务去重；业务事实与展示计数必须分开。
- 推荐服务没有超时/降级，模型或特征故障直接变成首页不可用。
- 使用假设数字时不声明假设，或者把论文/云产品的能力外推成自己生产环境已经达到的性能。
