# 算法手撕：多线程实现数组排序

## 核心结论

来源只保留“多线程实现数组排序”，没有给语言、元素类型、排序方向、稳定性、线程数或 API。这里明确一个可执行的答案侧契约：Java `int[]` 原地升序排序，调用方提供 `parallelism` 和串行阈值 `threshold`。实现采用并行归并排序：把数组递归切成互不重叠的左右区间，两个子任务并行排序，等待两边完成后再由父任务顺序合并；共享临时数组只写当前任务负责的区间，因此不需要给每个元素加锁。

## 1 分钟版

- 先把契约说清楚：`int[]`、升序、原地修改；`null` 拒绝，`parallelism`/`threshold` 必须至少为 1。
- 大区间二分为 `[lo, mid)` 和 `[mid, hi)`，用 Fork/Join 并行处理；小于阈值时退化为单线程 `Arrays.sort`，避免任务创建成本压过排序收益。
- 两个子区间完成后再 merge。子任务只写各自不重叠区间，父任务在 join 之后才读两边并写整个父区间，所以并发边界清晰。
- 总工作量仍是 `O(n log n)`，主要额外数组空间是 `O(n)`；这个版本每层 merge 本身是串行的，所以并行度不是无限的，数组很小时单线程反而更合适。

## 3 分钟版

```java
import java.util.Arrays;
import java.util.Objects;
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveAction;

public final class ParallelMergeSort {
    private ParallelMergeSort() {}

    public static void sort(int[] values, int parallelism, int threshold) {
        Objects.requireNonNull(values, "values");
        if (parallelism < 1) {
            throw new IllegalArgumentException("parallelism must be >= 1");
        }
        if (threshold < 1) {
            throw new IllegalArgumentException("threshold must be >= 1");
        }
        if (values.length < 2) return;

        int[] tmp = new int[values.length];
        ForkJoinPool pool = new ForkJoinPool(parallelism);
        try {
            pool.invoke(new SortTask(values, tmp, 0, values.length, threshold));
        } finally {
            pool.shutdown();
        }
    }

    private static final class SortTask extends RecursiveAction {
        private static final long serialVersionUID = 1L;

        private final int[] a;
        private final int[] tmp;
        private final int lo;
        private final int hi;
        private final int threshold;

        SortTask(int[] a, int[] tmp, int lo, int hi, int threshold) {
            this.a = a;
            this.tmp = tmp;
            this.lo = lo;
            this.hi = hi;
            this.threshold = threshold;
        }

        @Override
        protected void compute() {
            int len = hi - lo;
            if (len <= threshold) {
                Arrays.sort(a, lo, hi);
                return;
            }

            int mid = lo + (len >>> 1);
            invokeAll(
                new SortTask(a, tmp, lo, mid, threshold),
                new SortTask(a, tmp, mid, hi, threshold)
            );
            merge(a, tmp, lo, mid, hi);
        }
    }

    private static void merge(int[] a, int[] tmp, int lo, int mid, int hi) {
        int i = lo;
        int j = mid;
        int k = lo;

        while (i < mid && j < hi) {
            tmp[k++] = a[i] <= a[j] ? a[i++] : a[j++];
        }
        while (i < mid) tmp[k++] = a[i++];
        while (j < hi) tmp[k++] = a[j++];

        System.arraycopy(tmp, lo, a, lo, hi - lo);
    }
}
```

不变量是：进入 `merge(lo, mid, hi)` 时，左右两个半开区间都已经各自有序；merge 结束后整个 `[lo, hi)` 有序。并发正确性的关键也在这个区间所有权上：左右任务运行时不写同一索引，父任务只有在两个子任务完成之后才开始合并，因此不会出现“一个线程正在改左半段，另一个线程同时拿未完成数据 merge”的竞态。

## 关键细节

- **来源边界**：原始面经只有“多线程实现数组排序”，没有指定 Java、归并排序、稳定性或线程池；这些都必须明确标成答案侧实现选择。
- **为什么要阈值**：递归到很小的区间仍继续拆任务，会增加任务调度、对象创建和同步成本。阈值把小区间交给串行排序。
- **为什么共享一个 `tmp` 可以不加锁**：同一时刻并行的兄弟任务只操作不相交区间；每个任务的 merge 也只写自己的 `[lo, hi)`。父区间 merge 在子任务完成之后发生。
- **复杂度**：归并排序总工作量 `O(n log n)`，临时数组 `O(n)`，递归深度 `O(log n)`。这个实现的 merge 是串行的，因此顶层 merge 会成为并行加速的上限之一。
- **异常契约**：`null` 直接拒绝；`parallelism < 1` 或 `threshold < 1` 拒绝。长度 0/1 的数组直接返回。
- **并行度不是越大越好**：线程数超过可用 CPU、数组规模太小或阈值太低，都可能让调度开销超过并行收益；真实场景应通过基准测试选择参数，而不是写死“线程越多越快”。
- **如果题目要求稳定排序对象**：要把 `int[]` 契约改成对象 + Comparator，并确保叶子排序和 merge 对相等键都保持原相对顺序；不能从本题当前来源中假设有这个要求。

## 原理机制

这道题本质上把“数据分治”和“线程并行”对齐。数组先按索引区间形成一棵任务树：叶子节点负责一个小区间的串行排序，内部节点只在两个孩子完成后做一次 merge。这样依赖关系天然是 DAG：两个兄弟任务可以并发，父任务必须等待孩子。正确性来自两个条件：第一，叶子排序保证小区间有序；第二，父节点把两个已经有序的子区间合并成更大的有序区间。沿任务树自底向上归纳，根区间最终有序。

并发控制不靠粗粒度互斥锁，而靠“区间所有权 + 完成依赖”：并行阶段各写各的区间，交汇阶段等子任务结束后再合并。这样避免了多个线程争抢一个全局锁，但仍保留了明确的任务完成边界。

## 项目经验版

来源没有真实生产数据，不能虚构“线上多线程排序提速多少”。项目映射时我会先确认数组规模、元素类型、CPU 核数、是否已处于共享线程池、延迟还是吞吐优先，然后用 JMH 或等价基准同时测单线程 `Arrays.sort` 与不同 `parallelism/threshold` 的版本。重点看总耗时、CPU 利用率、任务数量和 GC，而不是只看“用了几个线程”。如果调用链本身已经高并发，额外在每个请求里创建并行池还可能放大 CPU 竞争，这需要单独评估。

## 常见追问

- 问：为什么不用多个线程同时对同一个数组直接快排？答：可以做并行快排，但必须同样定义每个任务拥有的分区，并保证 partition 完成后才能并行递归左右区间。这里选归并排序只是为了让“独立区间并行 + join 后合并”的边界更容易证明和测试。
- 问：为什么不为每个小块创建一个原生线程？答：线程创建和切换成本高，而且任务数随递归增长。Fork/Join 用受控并行度复用工作线程，阈值则限制过度拆分。
- 问：这个实现有没有数据竞争？答：兄弟任务只写不相交区间；父 merge 在两个子任务完成后才开始。只要维持这个区间所有权和完成顺序，同一索引不会被两个并行任务同时写。
- 问：为什么多线程不一定更快？答：小数组的排序工作不足以摊薄任务调度和同步成本；大数组还会受到内存带宽和串行 merge 的限制，所以需要基准而不是凭线程数判断。
- 问：如果要求稳定排序怎么办？答：当前 `int[]` 没有对象相对顺序语义。若改成对象排序，应让叶子排序稳定，并在 merge 遇到相等键时优先取左侧元素，从而保留原始相对顺序。

## 易错点

- 把“多线程”理解成“线程越多越快”，没有阈值和并行度上限。
- 两个线程直接操作重叠区间，却没有定义所有权和完成依赖。
- 子任务还没结束就开始父区间 merge，读到未排序完成的数据。
- 只给并发框架，没有真正可运行的排序实现或边界测试。
- 把 Java、归并排序、线程池大小、稳定性等答案侧选择说成原题已经明确要求。
