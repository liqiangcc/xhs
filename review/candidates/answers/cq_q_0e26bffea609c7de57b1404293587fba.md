# 在上一家公司中如何实现蓝绿发布？

## 核心结论

这道题带有“上一家公司”的个人经历前提，但当前仓库没有保存可核验的真实公司实现、个人职责、流量规模或结果，因此不能替用户编造“我们当时就是这么做的”。

技术上，一个可落地的蓝绿发布参考方案是：同时保留当前生产版本 Blue 和待发布版本 Green；先让 Green 在独立预览入口完成启动、依赖、功能和关键指标验证，再把稳定的生产流量入口切到 Green；Blue 在一段回滚窗口内继续保留。如果切换后的错误率、延迟或业务指标异常，就把流量入口切回 Blue。Kubernetes 场景可以通过 Service 目标版本切换实现，也可以使用 Argo Rollouts 这类控制器编排 active/preview Service、发布前后分析和延迟缩容。这个参考方案必须与用户真实经历分开，后续只有拿到真实项目事实后才能改写成第一人称答案。

## 1 分钟版

1. **两套版本并存**：Blue 承载当前生产流量，Green 部署新版本；不要先销毁 Blue 再验证 Green。
2. **先验证再切流**：Green 通过 readiness、核心接口、依赖连通和关键业务检查后，再进入发布门禁；可通过 preview Service 或独立预览入口验证。
3. **切流和回滚是一对动作**：生产 Service/流量入口从 Blue 指向 Green，同时保留 Blue 一段时间；指标异常就反向切回，而不是现场重新构建旧版本。
4. **容量和兼容性要提前算**：切换窗口两套版本会重叠运行，容量要覆盖并存成本；数据库/API 变更也要能容忍新旧版本短时共存。

如果面试官追问“你上一家公司具体怎么做”，这里必须换成真实事实：实际用了什么入口、谁负责切流、门禁指标是什么、回滚用了多久、你个人负责哪一段。当前仓库没有这些事实，不能虚构。

## 3 分钟版

先把参考场景限定清楚：假设是一个无状态 Java 服务，运行在 Kubernetes，目标是低中断发布；生产流量通过稳定 Service 进入应用。Blue 是当前稳定版本，Green 是新版本。这里的 Kubernetes/Argo 只是参考实现，不代表用户上一家公司真实采用了它们。

发布链路可以设计成：

```text
构建并冻结版本
      ↓
部署 Green，但生产入口仍指向 Blue
      ↓
Green readiness + 依赖检查 + 冒烟/回归
      ↓
预览入口做发布前分析
      ↓
满足门禁
      ↓
生产 Service / 流量入口切到 Green
      ↓
持续观察错误率、P95/P99、资源、业务成功率
      ↓
稳定 → 延迟缩容 Blue
异常 → 流量切回 Blue
```

Kubernetes 原生 `Deployment` 的替换策略是 `RollingUpdate` 或 `Recreate`，不能把 `blueGreen` 说成 Deployment 自带策略。若自己实现，可以维护两套独立 workload，通过 Service selector 或其他路由层切换目标版本；若采用 Argo Rollouts，它的 BlueGreen 策略要求 `activeService`，可选 `previewService`，在新 ReplicaSet 可用并通过发布前分析后再更新 active Service。

**容量**方面，Green 验证期间 Blue 仍在线。如果 Blue 需要 `R` 个副本，Green 也全量拉到 `R`，应用副本峰值大致要按 `2R` 再叠加基础设施余量准备；如果参考实现支持较小的 preview 副本数，可以先用 `p < R` 验证，但正式切流前仍要把 Green 扩到生产所需容量。这个公式只是容量规划方法，不是历史项目数据。

**数据与一致性**方面，蓝绿只能安全切应用流量，不会自动解决数据库兼容。若 Blue 与 Green 会短时共存，数据库 schema、消息格式、缓存 key 和外部 API 应尽量满足双版本兼容；破坏性变更应拆成可兼容的多阶段迁移。请求幂等、消息重复消费等仍由业务协议保证，不能指望“蓝绿发布”本身提供。

**故障处理**方面，发布门禁失败就不切生产流量；切换后若错误率、延迟、业务成功率或依赖异常达到回滚阈值，就让生产入口重新指向 Blue。Service selector/节点转发表传播不是瞬时完成，所以旧版本不能在切流瞬间立即杀掉；参考控制器通常提供延迟缩容窗口来降低传播期间的失败风险。

**观测**方面至少要看：实例 readiness、5xx/异常率、P95/P99、吞吐、CPU/内存/GC、下游依赖错误，以及业务成功率。发布前用预览流量/回归验证，发布后观察一个明确窗口；回滚动作也要演练，而不是只验证“上线成功”。

## 关键细节

- **蓝绿不是 RollingUpdate 的别名**：Kubernetes Deployment 原生策略只有 `Recreate` 和 `RollingUpdate`；蓝绿需要额外的两版本与流量切换机制，或使用支持 BlueGreen 的控制器。
- **切 Service 不等于全网瞬时原子切换**：Service selector 更新存在传播时间。旧版本应保留一个 scale-down delay / 回滚窗口，避免节点还在向旧端点发流量时旧 Pod 已经被杀掉。
- **发布门禁要分前后**：切流前检查 Green 自身健康和核心功能；切流后再检查真实生产流量下的错误率、延迟和业务指标。只有前置 readiness 不足以证明生产稳定。
- **数据库变更是高风险边界**：如果 Green 写入了 Blue 无法理解的数据，应用流量虽然能切回 Blue，业务也未必能真正回滚。因此 schema 与消息协议需要单独做向前/向后兼容设计。
- **容量不能只按一套算**：全量蓝绿会在一段时间内同时保留两套副本；资源不足时，发布本身可能成为故障源。
- **入口实现不是固定答案**：Service selector、Ingress/Gateway、LB、服务网格或 Argo Rollouts 都可能承担流量切换。实际方案必须以真实基础设施为准，不能把任一组件说成蓝绿发布的唯一实现。

## 原理机制

蓝绿发布的核心是把“部署新版本”和“让新版本接收生产流量”拆成两个状态转换：

```text
deploy(Green) ≠ promote(Green)
```

Green 可以先存在、先验证，但在 promotion 前不承担正常生产流量。真正的发布边界是**流量归属改变**，因此回滚也主要是把流量归属重新指向仍然存活的 Blue。

以 Argo Rollouts 的参考机制为例，active Service 指向当前稳定 ReplicaSet，preview Service 可以提前指向新 ReplicaSet；新版本可用且分析通过后，控制器更新 active Service 指向新 ReplicaSet，再延迟缩容旧 ReplicaSet。延迟缩容不是多余等待，而是为了覆盖 Service selector/节点转发表传播时间，并保留快速回退空间。

这也解释了蓝绿的主要取舍：

```text
优点
部署与切流解耦
回滚路径短
新版本可在生产拓扑旁预验证

代价
两套版本短时并存，资源成本更高
数据库/消息协议必须考虑双版本兼容
流量切换层自身要可靠且可观测
```

## 常见追问

- 问：蓝绿和滚动发布最大的区别是什么？  
  答：蓝绿强调完整的旧/新版本并存，并把流量从一套切到另一套；滚动发布是在一个工作负载里逐步用新实例替换旧实例。两者的资源峰值、回滚路径和流量控制方式不同。

- 问：为什么切流后还要保留 Blue？  
  答：一是给 Service/路由传播留时间，二是保留快速回退目标。若切完立刻缩掉旧版本，发现生产问题时就失去了蓝绿最重要的快速回滚优势。

- 问：数据库已经执行了不可逆变更，还能直接切回 Blue 吗？  
  答：不能假设可以。应用流量回退不等于数据状态回退；需要兼容 schema、expand/contract、多阶段迁移或独立数据回滚策略，否则 Blue 可能已无法读取新数据。

- 问：为什么不用 readiness 通过就自动全量切流？  
  答：readiness 只证明实例达到配置的可服务条件，不等于核心业务链路和真实负载稳定。还需要发布前功能/依赖检查以及发布后的错误率、延迟和业务指标观察。

- 问：蓝绿一定要两倍机器吗？  
  答：不是固定的“两倍”。全量并存时应用副本可能接近两套容量；某些控制器允许预览阶段只启动较少副本，但切流前仍要准备目标生产容量。真实峰值还要加上调度、基础设施和安全余量。

- 问：Kubernetes Deployment 直接写 `strategy: blueGreen` 可以吗？  
  答：原生 Deployment 不可以，它的策略类型是 `Recreate` 或 `RollingUpdate`。`blueGreen` 是例如 Argo Rollouts 这类扩展控制器提供的策略，或者由团队自行用两套 workload + 流量切换机制实现。

## 易错点

- 把“上一家公司”当成允许自由发挥，虚构组件、个人职责、流量规模和收益。
- 把 Kubernetes Deployment 的 `RollingUpdate` 误说成原生 `blueGreen`。
- 只讲“两套环境切一下流量”，不讲发布前门禁、切流后观测和回滚窗口。
- 切流后立刻销毁 Blue，忽略路由传播和快速回退需要。
- 只设计应用回滚，不考虑数据库、消息格式和缓存数据已经发生的不兼容变化。
- 用固定“两倍资源”“零停机”等绝对口号代替实际容量和流量入口的边界分析。
