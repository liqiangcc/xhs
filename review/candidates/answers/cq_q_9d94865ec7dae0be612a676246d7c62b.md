# SQL：80 分以上科目数排名前三，并展示姓名和及格科目数

## 核心结论

来源只保留了“按 80 分以上科目数量取前三名，并展示姓名和及格学科数”，没有保留真实表名、列名、及格线、同分并列规则或一门课是否允许多次成绩。下面先声明一个可执行的答案侧契约：`students(student_id, name)` 与 `scores(student_id, subject_id, score)`，每个 `(student_id, subject_id)` 只有一条最终成绩；“80 分以上”按 `score >= 80`；及格线由参数 `:pass_score` 传入；“前三名”取恰好 3 个学生，按 80+ 科目数降序，同数时按 `student_id` 升序稳定打破并列。

## 1 分钟版

- 先按学生聚合，一次扫描同时算两个条件计数：`score >= 80` 的科目数，以及 `score >= :pass_score` 的及格科目数。
- 再对聚合结果按 80+ 科目数降序排名，而不是先对成绩明细排序。
- 本答案为了得到恰好 3 个学生，用 `ROW_NUMBER()` 并以 `student_id` 作为稳定 tie-breaker；如果题目要求“前三个名次且并列都保留”，应改为 `DENSE_RANK()`。
- 及格线来源没有给出，所以保留为参数，不能把 60 分冒充成原题事实。
- 如果同一学生同一科目存在多次考试记录，必须先明确取最高分、最新分还是最终分；不能直接把多条记录当成多个科目计数。

## 3 分钟版

在上述答案侧 schema 与“每科一条最终成绩”契约下：

```sql
WITH per_student AS (
    SELECT
        s.student_id,
        s.name,
        SUM(CASE WHEN sc.score >= 80 THEN 1 ELSE 0 END) AS high_score_subjects,
        SUM(CASE WHEN sc.score >= :pass_score THEN 1 ELSE 0 END) AS passed_subjects
    FROM students AS s
    JOIN scores AS sc
      ON sc.student_id = s.student_id
    GROUP BY s.student_id, s.name
), ranked AS (
    SELECT
        student_id,
        name,
        high_score_subjects,
        passed_subjects,
        ROW_NUMBER() OVER (
            ORDER BY high_score_subjects DESC, student_id ASC
        ) AS rn
    FROM per_student
)
SELECT
    name,
    passed_subjects
FROM ranked
WHERE rn <= 3
ORDER BY rn;
```

调用时把真实及格线绑定到 `:pass_score`。如果面试官明确规定及格线为 60，才绑定 60；如果要求并列第三名全部返回，则把 `ROW_NUMBER()` 换成 `DENSE_RANK() OVER (ORDER BY high_score_subjects DESC)`，再筛 `rank_no <= 3`。

## 关键细节

- **两个计数口径不同**：排名键是 `score >= 80` 的科目数，展示值是 `score >= :pass_score` 的科目数，不能把同一个条件复用两次。
- **先聚合再排名**：窗口函数应作用在“每个学生一行”的聚合结果上，否则排名的是成绩明细行而不是学生。
- **80 分边界**：“80 分以上”在本候选按包含 80 处理；如果业务明确要求严格大于 80，需要把条件改成 `> 80`。
- **并列语义**：`ROW_NUMBER` 保证恰好最多 3 人；`DENSE_RANK` 表示前三个名次，人数可能超过 3。来源没有说明，因此必须把选择写成答案侧契约。
- **成绩唯一性**：本候选假设每科一条最终成绩。若有补考/重考，必须先按业务规则把每科归一到一条有效成绩，再做条件聚合。
- **无成绩学生**：当前使用 `JOIN`，只让至少有一条成绩的学生参与排名；如果题目要求所有学生参与，需要改为 `LEFT JOIN` 并定义零成绩计数。
- **可移植性**：`CASE WHEN ... THEN 1 ELSE 0 END` 比依赖某一数据库布尔转整数的写法更明确；命名参数语法由实际客户端绑定层决定。

## 原理机制

这题有两层粒度。第一层从“学生 × 科目成绩”明细收缩到“一名学生一行”，通过条件聚合得到 `high_score_subjects` 和 `passed_subjects`；第二层只在学生级结果上排序/排名。把这两层分开后，排名目标和展示指标不会互相污染，也能清楚处理 tie、及格线和多次成绩这些边界。

## 常见追问

- 问：为什么不能直接 `ORDER BY score DESC LIMIT 3`？答：因为题目排名的是“80 分以上的科目数量”，必须先按学生聚合成计数，再按计数排名。
- 问：第三名并列怎么办？答：来源没有定义。本候选选择恰好 3 人，用 `ROW_NUMBER + student_id` 稳定打破并列；若要求前三个名次全部保留，改用 `DENSE_RANK`。
- 问：及格是不是默认 60 分？答：来源没有保留这个阈值，所以答案保留 `:pass_score` 参数；面试官确认 60 后再绑定 60。
- 问：同一科补考两次会怎样？答：直接计数会把一门课算多次，因此必须先按业务规则选出该科有效成绩，再聚合。
- 问：为什么 `GROUP BY` 里带 `student_id` 和 `name`？答：结果粒度是一名学生；主键保证身份稳定，姓名只是展示属性。实际 schema 若允许改名或同名，仍应以学生主键作为关联和排名 tie-breaker。
- 问：80 分整算不算 80 分以上？答：本候选按中文通常的包含边界解释为 `>= 80`，并把该解释显式写入答案侧契约；若面试官指定严格大于，则改成 `> 80`。

## 易错点

- 先对成绩明细排名，再去统计学生，导致排名粒度错误。
- 把“80+ 科目数”和“及格科目数”写成同一个条件。
- 未确认及格线却直接把 60 写成来源事实。
- 未声明并列规则，`LIMIT 3` 或窗口排名在 tie 时得到不可解释结果。
- 同一科存在多条成绩时直接 `COUNT`，把考试次数误当成科目数。
- 用姓名而不是稳定学生 ID 关联成绩，遇到同名学生产生错误聚合。
