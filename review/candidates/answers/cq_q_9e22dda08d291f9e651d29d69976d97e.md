# 算法：比较版本号（Compare Version Numbers）

## 核心结论

两条仓库来源都只要求“比较版本号大小”，没有保存输入格式细节。为了给出可执行实现，本候选明确采用一个**答案侧契约**：版本号由 `.` 分隔的非负十进制 revision 组成，每段至少一个数字；前导零不影响数值；一方缺少的尾部 revision 按 `0` 比较；不支持负号、空段或 `1.0-alpha` 这类 SemVer 预发布标签。逐段按“去前导零后的长度 + 字典序”比较，可以避免把超长 revision 解析成 `int/long` 时溢出。

## 1 分钟版

- 先声明输入契约，不能把题干没保存的 SemVer/异常格式规则当成原题事实。
- 两个版本按 `.` 拆成 revision，从左到右比较；第一个不同 revision 决定版本大小。
- revision 先去前导零；长度不同，位数更多的数更大；长度相同再按字符串字典序比较。
- 一方已经没有更多 revision 时，把缺失段看作 `0`，所以 `1.0.0 == 1`。
- 不转成 `int` 或 `long`，因此像 `2147483648` 甚至更长的数字段也不会发生整数溢出。

## 3 分钟版

下面实现返回 `-1 / 0 / 1`：

```java
public final class VersionCompare {
    public static int compareVersion(String left, String right) {
        if (left == null || right == null) {
            throw new IllegalArgumentException("version must not be null");
        }

        String[] a = left.split("\\.", -1);
        String[] b = right.split("\\.", -1);
        int n = Math.max(a.length, b.length);

        for (int i = 0; i < n; i++) {
            String x = i < a.length ? normalize(a[i]) : "0";
            String y = i < b.length ? normalize(b[i]) : "0";

            if (x.length() != y.length()) {
                return x.length() < y.length() ? -1 : 1;
            }
            int cmp = x.compareTo(y);
            if (cmp != 0) {
                return cmp < 0 ? -1 : 1;
            }
        }
        return 0;
    }

    private static String normalize(String segment) {
        if (segment.isEmpty()) {
            throw new IllegalArgumentException("empty revision");
        }
        for (int i = 0; i < segment.length(); i++) {
            char c = segment.charAt(i);
            if (c < '0' || c > '9') {
                throw new IllegalArgumentException(
                    "revision must contain only decimal digits");
            }
        }

        int i = 0;
        while (i < segment.length() - 1 && segment.charAt(i) == '0') {
            i++;
        }
        return segment.substring(i);
    }
}
```

不变量是：进入第 `i` 个 revision 时，前面的所有 revision 已经数值相等；因此如果当前段第一次出现大小差异，就可以立即返回，不需要再看后面的段。若所有实际段都相等，缺失尾段按 `0` 后仍全部相等，则两个版本在本契约下相等。

## 关键细节

- **前导零**：`1.01` 与 `1.001` 的第二段数值都为 `1`，应判相等。
- **尾部零**：`1`、`1.0`、`1.0.0` 在当前答案契约下相等。
- **超长 revision**：不调用 `Integer.parseInt` / `Long.parseLong`，而是比较规范化数字串的长度与字典序，避免整数范围成为隐含限制。
- **非法输入**：空段（如 `1..0`）、非数字段、`null` 明确拒绝；这只是本候选选择的可执行边界，不冒充仓库来源已经给出的规则。
- **复杂度**：设两个输入总长度为 `n`，拆分、校验、去零和比较总时间为 `O(n)`；当前实现使用 `split` 和规范化字符串，额外空间为 `O(n)`。若面试官要求 `O(1)` 额外空间，可改为双指针直接扫描原字符串。
- **不是 SemVer 比较器**：`1.0-alpha`、构建元数据和预发布优先级属于另一套契约；题干没有这些信息，不能自动套入。

## 原理机制

十进制非负整数在去掉前导零后有一个简单的全序：位数更多的一定更大；位数相同则字典序与数值序一致。把每个 revision 当成这样的非负整数，就能在不做有限宽整数解析的情况下逐段比较。

版本整体使用字典式的 revision 序：先比较第 0 段，再比较第 1 段，直到第一次不同。缺失尾段补零让 `1` 与 `1.0.0` 落到同一个等价类。若真实题目采用不同约定，例如缺失段不等价、允许负数或要求 SemVer 规则，只需更换输入契约和单段比较规则，不能直接复用当前结论。

## 项目经验版

仓库来源没有真实项目经历，不能虚构“线上版本比较器”。实际项目如果要比较 Maven、npm、Docker tag 或产品发布版本，应先确认它们各自的正式版本语法和优先级规则，再实现对应 parser/comparator；不能因为界面上都叫“版本号”就复用这道纯数字 revision 的比较逻辑。

## 常见追问

- 问：为什么不用 `Integer.parseInt`？答：题干没给 revision 的位数上限，有限宽整数会引入额外溢出边界；直接比较规范化数字串可以支持任意长度的十进制 revision。
- 问：为什么 `1.0` 和 `1` 相等？答：这是本候选明确采用的答案侧契约：缺失尾部 revision 按 `0`；如果面试官给出不同定义，应以题目定义为准。
- 问：`1.01` 和 `1.001` 怎么比？答：去掉前导零后两个 revision 都是 `1`，所以该段相等。
- 问：`1.10` 和 `1.2` 为什么不能直接字符串比较？答：第二段字符串字典序会把 `"10"` 与 `"2"` 比错；应按十进制数值语义比较，即先看规范化长度，再看同长度字典序。
- 问：如果要求 `O(1)` 额外空间呢？答：不用 `split`，两个指针在原字符串中逐段定位边界、跳过前导零并直接比较有效位数和字符即可，核心不变量不变。

## 易错点

- 直接比较整个版本字符串，导致 `1.10` 和 `1.2` 顺序错误。
- 每段转成 `int`，却没有题目位数上限，遇到超长 revision 溢出。
- 忽略前导零或尾部零，使常见等价版本判断错误。
- 没声明输入契约，就把 SemVer、负数、空段或预发布标签的规则混进纯数字版本比较题。
- 只给代码，不解释“第一次不同 revision 决定结果”的比较不变量和复杂度。
