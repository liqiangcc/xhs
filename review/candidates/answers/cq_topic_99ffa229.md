# MySQL 索引失效的常见场景

## 核心结论

“索引失效”不是建了索引就完全不能读索引，而是当前谓词不能形成该索引可用的查找范围，或优化器估算走索引不划算。先看索引定义与谓词能否匹配：联合 B-tree 是否使用了左前缀、`LIKE` 是否以通配符开头、表达式是否有匹配的函数/生成列索引；再用 `EXPLAIN` 验证实际计划，不能只背一串口诀。

## 1 分钟版

- 联合索引 `(a,b,c)` 的可查找左前缀是 `(a)`、`(a,b)`、`(a,b,c)`；只按 `b` 或 `c` 过滤时，不能把它当作通常的左前缀查找。
- 普通 B-tree 的 `LIKE 'abc%'` 可以形成范围条件，`LIKE '%abc'` 不能；前导通配符是最常见的“看起来有索引却不能做该范围访问”的例子。
- `WHERE f(col)=...` 不要一概说“函数必失效”：原列索引未必能匹配表达式；在 MySQL 8.4，若有定义匹配的索引生成列，优化器可以考虑该索引。
- 即使条件可用，若要访问大部分行，顺序读可能比经索引逐行取数便宜。因此结论必须由实际版本、统计信息、参数和 `EXPLAIN` 共同确认。

## 3 分钟版

先澄清“失效”的两层含义：第一层是访问条件不能用某个索引做预期的范围/前缀查找；第二层是索引可作为候选，但成本估算后未被选中。两层修复方法不同，不能混为“优化器不走索引”。

对联合 B-tree，MySQL 官方说明任一左前缀都可以用于查找。因此索引 `(a,b,c)` 与查询约束应从 `a` 连续开始匹配；跳过前导列时，不能把它承诺为普通左前缀定位。由此不能反过来背成“跳过首列就必定全表扫描”：是否使用别的访问路径仍须以实际执行计划为准。

对字符串前缀，范围优化文档把不以通配符开头的 `LIKE 'pattern'` 列为范围条件。`LIKE '%abc'` 没有固定的开头，不能用普通 B-tree 为该模式构造同样的前缀范围；若需求改为任意位置匹配，应重新评估查询与索引设计，不能强行套普通前缀索引。

对表达式，先区分“在原列上建了普通索引”和“为表达式建立了可匹配的索引”。MySQL 8.4 支持索引生成列；当 `WHERE`、`ORDER BY` 或 `GROUP BY` 的表达式匹配该生成列定义时，优化器可以考虑这个索引。因此把 `DATE(created_at)` 之类的条件改为与原列可比较的范围，或在确认表达式与版本条件后设计生成列索引；不要把任何函数条件说成永久失效。

最后看选择性和读放大。官方文档说明，多个候选索引时优化器通常选择能找到最少行的索引；当查询需要访问大部分行时，顺序读可能更快。排查顺序是：保留真实 SQL 和参数，使用 MySQL 官方建议的 `EXPLAIN` 核验索引使用，核对联合索引顺序和统计信息，再用实际负载验证改索引带来的读收益是否抵得过写入、空间和维护成本。

## 关键细节

- 本文以 MySQL 8.4 Reference Manual 为边界；访问路径仍受存储引擎、统计信息、数据分布、查询形状和版本影响。
- “最左前缀”描述的是多列索引可供查找的前缀，不等于每个跳过首列的查询都绝无其他优化路径。
- 前导 `%` 的结论针对普通 B-tree 的 `LIKE` 范围访问；若查询需求改变，应重新核对所用索引类型和执行计划。
- 类型混用会触发隐式转换，但转换方向和计划依赖具体类型与上下文；不要把“字符串列和数字字面量”背成无条件的索引失效，应统一参数类型并以计划验证。

## 原理机制

普通 B-tree 能高效定位等值、前缀和连续范围：联合键按 `(a,b,c)` 的字典序组织，已约束的连续左侧 key part 才能缩小起始范围；`LIKE 'abc%'` 有固定前缀，`LIKE '%abc'` 没有。表达式改变了优化器看到的比较对象，只有原始列谓词可直接利用原列索引，或表达式与一个可识别的生成列索引定义匹配时才有相应路径。即使存在路径，优化器仍比较“索引定位 + 回表/取行”与顺序扫描成本；返回行占比高时后者可能更低。索引还会占空间，并增加插入、更新、删除时维护索引的成本。

## 项目经验版

项目映射提示：带上真实表结构、MySQL 版本、`SHOW INDEX`/统计信息、慢 SQL 的绑定参数、`EXPLAIN`（必要时实际执行观测）、返回行数与写入负载。按“改写谓词、调整联合索引顺序、生成列索引、全文/搜索方案、维持现状”比较，记录读延迟、扫描行数、索引空间与写放大；没有这些事实时不要声称某次线上优化收益。

## 常见追问

- 问：联合索引 `(a,b,c)`，只查 `b` 能不能用？答：不能把它承诺为通常的左前缀查找，因为官方定义的可查找前缀从 `a` 开始；实际访问路径必须用 `EXPLAIN` 核验。
- 问：为什么 `%abc` 不适合普通 B-tree 前缀索引？答：它没有确定开头，不能形成与 `abc%` 相同的固定前缀范围；应按真实查询需求重新设计并用计划验证。
- 问：对索引列使用函数一定不能优化吗？答：不是。MySQL 8.4 可在表达式匹配索引生成列定义时考虑该索引；否则应改写为原列范围或重新设计索引，并用计划确认。
- 问：`EXPLAIN` 没选索引，是否一定要 `FORCE INDEX`？答：不一定。先确认返回行占比、统计信息和查询参数；官方文档明确大量行访问时顺序读可能更快，强制索引可能把成本选择改坏。

## 易错点

- 不要把“索引未被选中”“只能扫描索引”“不能做预期范围定位”混成一个“索引失效”。
- 不要把最左前缀、前导 `%`、函数表达式写成跨版本和跨索引类型的绝对规则。
- 不要只因某列选择性低就断言不会走索引；优化器按具体成本与统计信息选择。
- 不要只看 SQL 文本就下结论；必须结合真实参数、索引定义与 `EXPLAIN`。
