# HashMap 和 Hashtable 的区别

## 核心结论

`HashMap` 和 `Hashtable` 都是基于哈希表的 `Map` 实现，但它们的设计时代和并发契约不同：

- `HashMap` **默认不提供同步保证**；单线程或由外部同步保护时通常优先使用它。
- `Hashtable` 的公共访问/修改操作采用同步设计，官方文档明确称它是 synchronized；但现代代码如果需要高并发线程安全 Map，官方更推荐 `ConcurrentHashMap`，而不是把 `Hashtable` 当默认方案。
- `HashMap` 允许一个 `null` key 和多个 `null` value；`Hashtable` 不允许 `null` key 或 `null` value。
- `HashMap` 从 Java Collections Framework 时代按 `Map` 体系设计；`Hashtable` 从 Java 1.0 就存在，后来才 retrofit 为 `Map`，同时仍继承 `Dictionary` 并保留 `keys()/elements()` 等老接口。
- 两者都不应该被理解成“有同步就一定更好”。选型要看是否需要并发、并发强度和 API 语义；需要并发时通常先看 `ConcurrentHashMap`。

面试里最重要的是把**线程安全、null 语义、历史/API 形态和现代选型**讲清楚，而不是只背初始容量之类的实现数字。

## 1 分钟版

可以从四点回答：

1. **线程安全**：`HashMap` 不同步；`Hashtable` 是同步实现。多线程高并发通常用 `ConcurrentHashMap`。
2. **null**：`HashMap` 允许 `null` key/value；`Hashtable` 的 key/value 都不能为 `null`。
3. **API 历史**：`HashMap` 是 Collections Framework 的常用 `Map`；`Hashtable` 是 Java 1.0 的老类，后来实现 `Map`，还保留 `Dictionary`、`Enumeration` 风格接口。
4. **选型**：单线程/外部同步优先 `HashMap`；普通现代并发 Map 优先评估 `ConcurrentHashMap`，而不是因为 `Hashtable` “带 synchronized”就直接选它。

不要把答案简化成“HashMap 快、Hashtable 慢”。同步方式和真实 workload 才决定性能，且现代并发场景还有更合适的数据结构。

## 3 分钟版

### 1. 并发契约

Java 21 `HashMap` 文档明确说它不是 synchronized 的。如果多个线程并发访问，并且至少一个线程做结构性修改，就需要外部同步；文档给出的一个办法是 `Collections.synchronizedMap(new HashMap(...))`。

`Hashtable` 文档则明确说它是 synchronized 的。这意味着它把同步作为类自身契约的一部分。

但这不等于“并发场景就选 Hashtable”。Java 21 `Hashtable` 文档直接建议：如果需要线程安全且高并发的实现，应使用 `ConcurrentHashMap` 代替 `Hashtable`。

所以现代选型通常是：

```text
不需要共享并发写
    → HashMap

需要一个整体同步包装、已有外部锁协议
    → HashMap + 外部同步 / synchronizedMap（按场景）

需要高并发 Map
    → 优先评估 ConcurrentHashMap

兼容旧 API / 旧代码
    → 可能继续遇到 Hashtable
```

### 2. null 语义

`HashMap` 允许 `null` key 和 `null` value。因为一个 Map 最多只有一个相等的 key，所以最多有一个 `null` key，但可以有多个 key 映射到 `null`。

这也带来一个 API 细节：`HashMap.get(key)` 返回 `null` 时，既可能是“不存在这个 key”，也可能是“存在但 value 就是 null”，需要 `containsKey` 区分。

`Hashtable` 不接受 `null` key 或 `null` value；例如 `put(null, x)`、`put(k, null)` 会抛 `NullPointerException`。

### 3. 历史和类型体系

`Hashtable` 从 Java 1.0 就存在，继承老的 `Dictionary<K,V>`；Java 2 / 1.2 才 retrofit 去实现 `Map<K,V>`。因此它同时保留了 `keys()`、`elements()` 这类 `Enumeration` 风格接口。

`HashMap` 从 Java 1.2 起作为 Collections Framework 的 `Map` 实现出现，继承 `AbstractMap`，API 形态更贴近现代集合框架。

所以 `Hashtable` 不是“线程安全版 HashMap 的现代默认实现”，而更像一个仍被兼容保留的历史同步 Map。

### 4. 数据结构与性能不要背死

两者都是 hash table，但内部实现会随 JDK 版本变化。以 Java 21 为例，`HashMap` 在碰撞严重时包含树化等实现策略；`Hashtable` 的当前实现细节不同。

面试回答时更稳妥的是先讲**规范可观察行为**：同步契约、null、API、现代替代方案。只有面试官继续追问源码时，再明确绑定具体 JDK 版本讨论桶、扩容、链表/树等细节。

## 关键细节

- **Hashtable 线程安全 ≠ 任意复合业务操作原子**：即使单个方法有同步语义，“先判断再更新”等跨多次调用的业务不变量仍需要选择合适的原子 API 或额外同步。
- **HashMap 的 fail-fast 不能当并发控制**：文档明确说明迭代器的 fail-fast 是 best effort，不能依赖 `ConcurrentModificationException` 保证程序正确。
- **不要用 null 差异推导所有并发语义**：`ConcurrentHashMap` 也不允许 `null` key/value，但它的并发设计与 `Hashtable` 不是一回事。
- **`Collections.synchronizedMap` 也不是自动解决所有迭代问题**：如果采用同步包装器，仍应按其文档约定持有正确的锁完成需要一致视图的复合访问/遍历。
- **类名是 `Hashtable`，不是 `HashTable`**：面试题常写 HashTable，但 Java 标准库类型名是 `java.util.Hashtable`。

## 原理机制

核心区别可以抽象成“同步策略属于哪里”：

```text
HashMap
  数据结构本身不承诺同步
      ↓
  并发控制由调用方/包装器/更合适的并发容器承担

Hashtable
  类自身把同步纳入公共操作契约
      ↓
  兼容早期 Java 的同步哈希表设计

ConcurrentHashMap
  专门为并发访问设计
      ↓
  不以 Hashtable 的粗粒度历史模型作为现代高并发默认方案
```

这说明“是否线程安全”不是只看某个方法有没有 `synchronized` 关键字，而是看整个类型对并发访问给出了什么契约、需要哪些复合原子操作，以及竞争下的可伸缩性要求。

## 项目经验版

来源没有真实项目经历，不能虚构“生产上曾把 Hashtable 换成 ConcurrentHashMap 提升多少性能”。

实际工程里我会先问：

- Map 是否跨线程共享？
- 是否只有读，还是有并发写？
- 是否需要 `computeIfAbsent`、条件更新等原子复合操作？
- 是否允许 `null` 表达业务状态？
- 是否存在旧接口必须接收 `Hashtable` / `Dictionary`？
- 是否需要按一次外部锁保护多个对象/多个步骤的不变量？

如果只是方法内临时 Map，就用 `HashMap`。如果是共享并发状态，通常直接从 `ConcurrentHashMap` 等并发容器的语义出发设计，而不是先选 `Hashtable` 再优化。

## 常见追问

- 问：Hashtable 线程安全，为什么不推荐它做高并发 Map？  
  答：线程安全只回答“并发访问是否合法”，不代表竞争下可伸缩性最好。Java 21 官方文档直接推荐高并发线程安全场景使用 `ConcurrentHashMap`。

- 问：HashMap 能不能放 null？  
  答：能。允许 `null` key 和 `null` value；`get` 返回 null 时要用 `containsKey` 区分“缺失”和“映射到 null”。

- 问：Hashtable 为什么不能放 null？  
  答：这是它公开 API 的明确契约，key/value 为 null 的相关操作会抛 `NullPointerException`；不要用“因为线程安全”去解释，这是不同维度的设计约束。

- 问：给 HashMap 外面加 synchronized 就等同 Hashtable 吗？  
  答：只能说可以获得某种同步保护，不能说类型和所有 API 语义完全等同；null、历史接口、迭代约定以及组合操作设计都仍不同。

- 问：HashMap 的 ConcurrentModificationException 能防并发问题吗？  
  答：不能。fail-fast 只是尽早暴露 bug 的 best-effort 机制，不是同步保证。

- 问：Hashtable 和 ConcurrentHashMap 都不能放 null，它们是不是一样？  
  答：不是。null 契约只是一点相似；并发算法、可扩展性和可用的原子复合操作是另一组设计维度。

## 易错点

- 把 Java 类名写成 `HashTable`，忽略标准库实际叫 `Hashtable`。
- 只回答“HashMap 不安全、Hashtable 安全”，却不说明现代并发场景通常用 `ConcurrentHashMap`。
- 说 Hashtable 的线程安全意味着任意多步业务逻辑自动原子。
- 说 HashMap 的 fail-fast 能作为线程安全机制。
- 把内部桶/链表/树的某个 JDK 实现细节当成所有版本固定规范。
- 用“Hashtable 一定慢、HashMap 一定快”替代真实的并发与 workload 分析。
