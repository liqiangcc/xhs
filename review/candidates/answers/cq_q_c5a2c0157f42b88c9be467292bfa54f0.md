# 2000 万行、每行 5 个 UTF-8 字符的 txt 文件有多大？

## 核心结论

题目信息不足以得到唯一数值，因为 UTF-8 中“一个字符”不等于固定 1 字节，而且每行通常还要算换行符。若 5 个字符全是 ASCII 且使用 LF（`\n`，1 字节），每行约 6 字节，2000 万行约 `120,000,000` 字节，即 **120 MB（十进制）≈ 114.4 MiB**；若是常见 3 字节 UTF-8 汉字并使用 LF，则每行约 16 字节，总计 **320 MB ≈ 305.2 MiB**。Windows CRLF 会再多 1 字节/行，所以回答时先声明字符内容和换行约定。

## 1 分钟版

- 先写公式：`总字节数 = 行数 × (每行正文编码后的字节数 + 换行字节数)`。
- UTF-8 是变长编码，5 个“字符”不能直接当作 5 字节；ASCII 通常 1 字节/字符，很多常用汉字通常 3 字节/字符。
- 若按 5 个 ASCII + LF：`20,000,000 × (5 + 1) = 120,000,000 B`，约 120 MB / 114.4 MiB。
- 若按 5 个 3 字节汉字 + LF：`20,000,000 × (15 + 1) = 320,000,000 B`，约 320 MB / 305.2 MiB。
- 所以面试里最好先给“不能唯一确定”，再给一两个明确假设下的数量级，而不是把 UTF-8 字符固定说成 1 或 3 字节。

## 3 分钟版

这题真正考的是“字符数、编码后字节数、换行符和容量单位要分开”。文件大小取决于实际字节流。对每一行，先把 5 个字符按 UTF-8 编码成若干字节，再加行结束符；最后乘 2000 万行。

在最常见的两种估算下：

1. 5 个 ASCII 字符，例如 `abcde`，UTF-8 正文是 5 B；Linux/Unix 风格 LF 是 1 B，所以一行 6 B，总计 120,000,000 B。
2. 5 个常见汉字，若每个编码后是 3 B，正文 15 B；加 LF 后一行 16 B，总计 320,000,000 B。

如果文件是 CRLF，每行结束符是 2 B，于是 ASCII 场景为 140,000,000 B，5 个 3 字节字符场景为 340,000,000 B。若最后一行没有换行，还要减掉最后一个行结束符，但对 2000 万行的“约数”影响极小。

可执行的计算器只在“已经知道正文每字符占几字节且每行同构”的假设下使用；真实混合文本应直接对实际字符串做 UTF-8 编码后统计字节数：

```java
public final class FileSizeEstimate {
    public static long estimateHomogeneous(
            long lines, int charsPerLine, int bytesPerCharacter, int newlineBytes) {
        if (lines < 0 || charsPerLine < 0 || bytesPerCharacter < 0 || newlineBytes < 0) {
            throw new IllegalArgumentException("sizes must be non-negative");
        }
        long body = Math.multiplyExact((long) charsPerLine, bytesPerCharacter);
        long bytesPerLine = Math.addExact(body, newlineBytes);
        return Math.multiplyExact(lines, bytesPerLine);
    }
}
```

复杂度是 O(1)，因为这里只做已知参数下的算术估算；若扫描真实文件或逐行编码统计，则时间复杂度是 O(B)，B 为实际处理的字节/字符规模。

## 关键细节

- **UTF-8 是变长编码**：ASCII 范围通常 1 B；许多常用汉字通常 3 B；其他 Unicode 字符可能占不同字节数，因此不能只由“5 个字符”推出正文固定大小。
- **换行也占空间**：LF 为 1 B，CRLF 为 2 B；题目没说明操作系统或文件格式，必须作为假设写出来。
- **MB 与 MiB 不同**：120,000,000 B 是 120 MB（10^6），换算成 MiB（2^20）约 114.4；面试中给“约 120 MB”通常已经表达了数量级，但不要把两种单位混写成完全相等。
- **最后一行**：文本文件最后一行可以有也可以没有行结束符；精确计算需要确认，粗略估算可忽略一行的差异。
- **磁盘占用 vs 文件逻辑大小**：题干通常是在估算文件内容字节数；真正“占用磁盘空间”还可能受文件系统分配块、稀疏文件、压缩等影响。没有这些条件时不应把文件系统开销硬加进答案。
- **溢出**：通用计算器使用 `Math.multiplyExact` / `addExact`，参数极大时显式失败，避免 long 静默溢出。

## 原理机制

字符是抽象文本单位，文件最终保存的是字节。UTF-8 把 Unicode 码点编码成 1 到多个字节，因此“字符个数”只有结合具体内容才能映射到字节数；换行符同样是写入文件的字节序列。于是计算链路是：字符内容 → UTF-8 编码字节 → 加行结束符 → 乘行数 → 再选择十进制 MB 或二进制 MiB 展示。

这也解释了为什么“5 × 2000 万 = 100 MB”只在忽略换行且每字符恰好 1 B 的特殊假设下成立；为什么“每个 UTF-8 字符 3 B”也不通用。正确回答要把假设暴露出来，让数值可以被复算。

## 常见追问

- 问：为什么不能直接算 `5 × 2000 万 = 100 MB`？答：这默认每字符 1 B 且完全忽略每行换行符；题目只给 UTF-8，没有给字符内容和换行格式，所以这个数只能作为更窄假设下的正文大小。
- 问：如果 5 个字符都是中文呢？答：若这些字符各自的 UTF-8 编码都是 3 B，正文每行 15 B；加 LF 是 16 B，约 320 MB。仍应说这是“每字符 3 B”的具体假设，而不是所有中文/所有 Unicode 字符都固定 3 B。
- 问：为什么 120 MB 又说约 114.4 MiB？答：MB 按 10^6 字节，MiB 按 2^20 字节；120,000,000 / 1,048,576 ≈ 114.4。
- 问：Windows 会怎样？答：若每行用 CRLF 两个字节，ASCII 场景每行从 6 B 变成 7 B，总计约 140 MB。
- 问：怎么得到精确值？答：确认实际文本内容、UTF-8 编码、是否带 BOM、每行结束符和最后一行换行；对真实数据直接编码/写文件后统计字节长度，而不是用固定“字符字节数”猜。

## 易错点

- 把 UTF-8 误说成“每个字符固定 1 字节”或“固定 3 字节”。
- 忘记每行的 LF/CRLF，导致 2000 万行时少算 20–40 MB。
- 把 MB 和 MiB 当成同一个单位，数字看起来对不上。
- 题目问内容大小，却未经条件就加入文件系统 block、压缩、元数据等额外假设。
- 为了给单一数字而隐藏字符集与换行假设，造成无法复算的答案。
