# UTF-8 文本文件大小估算：先把“字符”换成实际字节数

## 核心结论

仅凭“每行 5 个字符、UTF-8、2000 万行”**不能得到唯一文件大小**，因为 UTF-8 是变长编码，而且换行符也占字节。准确估算式是：

`总逻辑字节数 = 20,000,000 × (每行 5 个字符实际 UTF-8 字节数 + 换行符字节数)`。

若用 LF (`\n`)：
- 5 个 ASCII 字符：每行 `5 + 1 = 6` 字节，总计约 **120 MB（十进制）≈ 114.4 MiB**；
- 5 个常见中文汉字（通常每个 3 个 UTF-8 字节）：每行 `15 + 1 = 16` 字节，总计约 **320 MB ≈ 305.2 MiB**；
- 5 个四字节 Unicode 码点：每行 `20 + 1 = 21` 字节，总计约 **420 MB ≈ 400.5 MiB**。

所以如果面试上下文默认“5 个中文字符 + LF”，常见口算答案约 320 MB；但这个前提必须说出来。

## 1 分钟版

- 不要直接把“5 个字符”当成 5 字节；UTF-8 中 ASCII 常见是 1 字节，常见汉字是 3 字节，部分 Unicode 码点是 4 字节。
- 每行还要算换行：LF 是 1 字节，CRLF 是 2 字节。
- 公式是 `行数 × (记录 UTF-8 字节数 + 行结束符字节数)`。
- 2000 万行、5 个 ASCII + LF：`20,000,000 × 6 = 120,000,000 B`。
- 2000 万行、5 个常见汉字 + LF：`20,000,000 × 16 = 320,000,000 B`。
- 文件系统块、稀疏文件、压缩等会影响“磁盘占用”，但普通大文本的第一层估算先算逻辑文件字节数。

## 3 分钟版

如果有一条真实样例记录，Java 可以直接按 UTF-8 计算，而不是猜“一个字符几字节”：

```java
import java.nio.charset.StandardCharsets;

public final class Utf8TextSize {
    public static long logicalBytes(
            String fiveCodePointRecord,
            String lineEnding,
            long lines) {
        if (fiveCodePointRecord == null || lineEnding == null || lines < 0) {
            throw new IllegalArgumentException("invalid input");
        }
        if (fiveCodePointRecord.codePointCount(0, fiveCodePointRecord.length()) != 5) {
            throw new IllegalArgumentException("record must contain exactly 5 Unicode code points");
        }

        long recordBytes =
                fiveCodePointRecord.getBytes(StandardCharsets.UTF_8).length;
        long newlineBytes =
                lineEnding.getBytes(StandardCharsets.UTF_8).length;
        return Math.multiplyExact(lines, recordBytes + newlineBytes);
    }
}
```

例如：
- `logicalBytes("abcde", "\n", 20_000_000)` = `120,000,000`；
- `logicalBytes("你好世界啊", "\n", 20_000_000)` = `320,000,000`；
- `logicalBytes("😀😀😀😀😀", "\n", 20_000_000)` = `420,000,000`。

## 关键细节

- **字符不等于字节**：Java `String.length()` 统计 UTF-16 code unit，也不能直接拿来当 Unicode 字符数；示例用 `codePointCount` 检查 5 个 Unicode 码点，再用 UTF-8 编码后的字节数组取真实字节数。
- **ASCII 场景**：5 字节正文 + 1 字节 LF = 6 字节/行，2000 万行是 120,000,000 B。
- **常见汉字场景**：常见 CJK 汉字通常在 UTF-8 中占 3 字节，因此 5 个汉字是 15 字节；加 LF 后是 16 字节/行，即 320,000,000 B。
- **四字节码点**：如很多 emoji 在 UTF-8 中占 4 字节，5 个这样的码点 + LF 是 21 字节/行，即 420,000,000 B。
- **CRLF**：若使用 `\r\n`，每行比 LF 多 1 字节；2000 万行就会再增加约 20 MB。
- **MB 与 MiB**：十进制 MB 用 `10^6` 字节；MiB 用 `2^20` 字节。320,000,000 B 约为 320 MB，但约 305.2 MiB。
- **逻辑大小与占用空间**：`ls -l` 看到的逻辑长度和文件系统实际分配块数不是完全同一概念；普通连续大文本通常同量级，但块大小、压缩、稀疏特性会造成差异。

## 原理机制

UTF-8 不是定长字符集编码，而是把 Unicode 码点编码成 1 到 4 个字节。因此题目给“字符数”只能确定码点数量，不能直接确定 payload 字节数。必须先知道字符内容或至少知道字符类别，才能把每行字符数换算成编码后的字节数。

换行符属于文件内容的一部分，也必须按实际行结束符计入。2000 万行时，即使每行只差 1 个字节，总量也会差 20,000,000 字节，所以不能把换行当成可以忽略的小数。

## 项目经验版

来源没有真实文件样例、操作系统、文件系统或压缩方式，不能虚构。实际容量评估时应直接抽样若干真实行做 UTF-8 编码长度统计，再结合行数、换行格式和压缩策略估算；如果关心磁盘配额，还要区分逻辑文件大小和实际分配块数。

## 常见追问

- 问：为什么很多人会答 300 MB 左右？答：通常隐含了“5 个常见中文汉字，每个约 3 字节，再加换行”的假设；用 LF 算出来是约 320 MB。
- 问：UTF-8 一个中文字符一定 3 字节吗？答：不能绝对化。很多常用 CJK 汉字是 3 字节，但 UTF-8 对 Unicode 码点总体是 1–4 字节。
- 问：为什么 Java 不能直接用 `String.length()`？答：`String.length()` 是 UTF-16 code unit 数；某些码点会占两个 code unit。要数 Unicode 码点可用 `codePointCount`，要算文件大小应直接取 UTF-8 编码后的字节数。
- 问：Windows 会有差别吗？答：如果文件使用 CRLF，每行是 2 个换行字节，比 LF 每行多 1 字节；2000 万行多约 20 MB。
- 问：磁盘占用会不会比计算值大？答：可能。文件系统按块分配并带有元数据；但对于几百 MB 的普通连续文件，第一层容量估算仍以逻辑字节数为主。

## 易错点

- 把“5 个字符”直接当成 5 字节。
- 忘记每行的换行符。
- 把 MB 和 MiB 当成同一个单位。
- 说“UTF-8 中文永远 3 字节”，忽略 Unicode 范围。
- 没有实际字符内容却给出一个唯一精确值，并隐藏了自己的编码假设。
