# 实现 RandomSet：set/remove/contains/randomGet 都是 O(1)

## 核心结论

来源只要求实现 `RandomSet`，并让 `set/remove/contains/randomGet` 都达到 `O(1)`，但没有规定重复插入、空集合随机读取、泛型类型或“最坏/均摊/期望 O(1)”的口径。经典做法是 **动态数组 + 值到数组下标的哈希表**：数组负责 `randomGet` 的常数时间随机下标访问，哈希表负责定位元素；删除时把数组最后一个元素搬到被删位置，再删尾元素，从而避免中间删除的 `O(n)` 搬移。下面采用 Java 泛型实现，重复 `set` 返回 `false`，删除不存在元素返回 `false`，空集合 `randomGet` 抛 `NoSuchElementException`。

严格说，基于 `HashMap` / `ArrayList` 的常见实现提供的是哈希操作的期望常数时间以及动态数组追加的均摊常数时间；如果面试官把“保证 O(1)”解释为每一次操作都必须确定性最坏 `O(1)`，需要进一步限定键模型和底层字典实现，不能把 Java 标准容器的平均/均摊复杂度冒充成严格最坏界。

## 1 分钟版

- 用 `ArrayList<T> values` 存所有元素，保持 `[0, size)` 连续无洞；`randomGet` 直接随机一个下标，所以是常数时间访问。
- 用 `HashMap<T, Integer> index` 保存 `value -> values 下标`；`set`、`contains` 都直接查表。
- `remove(x)` 先从哈希表拿到 `x` 的下标 `i`，再把数组最后一个元素 `last` 放到 `i`，同时把 `index[last]` 改成 `i`，最后删数组尾部。
- 关键不变量是：`values.size() == index.size()`，且对每个 `i` 都有 `index.get(values.get(i)) == i`。
- 不能直接 `ArrayList.remove(i)` 删除中间元素，否则后面元素整体左移，会退化成 `O(n)`。

## 3 分钟版

```java
static final class RandomSet<T> {
    private final ArrayList<T> values = new ArrayList<>();
    private final HashMap<T, Integer> index = new HashMap<>();
    private final Random random;

    RandomSet(Random random) {
        this.random = Objects.requireNonNull(random);
    }

    boolean set(T value) {
        if (index.containsKey(value)) {
            return false;
        }
        index.put(value, values.size());
        values.add(value);
        return true;
    }

    boolean remove(T value) {
        Integer pos = index.remove(value);
        if (pos == null) {
            return false;
        }

        int lastIndex = values.size() - 1;
        T last = values.get(lastIndex);
        if (pos != lastIndex) {
            values.set(pos, last);
            index.put(last, pos);
        }
        values.remove(lastIndex);
        return true;
    }

    boolean contains(T value) {
        return index.containsKey(value);
    }

    T randomGet() {
        if (values.isEmpty()) {
            throw new NoSuchElementException("RandomSet is empty");
        }
        return values.get(random.nextInt(values.size()));
    }

    int size() {
        return values.size();
    }
}
```

例如集合内部是 `values=[10,20,30,40]`，`index={10:0,20:1,30:2,40:3}`。删除 `20` 时，不做数组中间删除，而是把 `40` 搬到下标 1：先得到 `[10,40,30,40]`，同步更新 `index[40]=1`，再删除尾部，最终得到 `[10,40,30]`。这样只改常数个位置。

## 关键细节

- **为什么随机读取需要数组**：哈希集合能常数时间判断成员，但没有“第 k 个元素”的常数时间索引；密集数组把每个元素映射到 `0..size-1`，随机一个下标即可取样。
- **为什么删除要 swap-with-last**：数组中间删除会移动后缀；把最后元素覆盖到洞位，再删尾，只涉及常数个数组/哈希位置。
- **删除最后一个元素**：当 `pos == lastIndex` 时不能再给已从 `index` 删除的同一个值写回映射，所以代码显式跳过搬移分支。
- **重复元素语义**：这是 Set，不保存重复值；`set` 已存在元素返回 `false`。如果业务要允许重复，就不是普通 Set，需要额外维护重复实例或计数。
- **空集合语义**：来源没定义；本实现选择抛 `NoSuchElementException`，调用方可以先检查 `size/contains` 或自行封装 Optional 风格接口。
- **随机均匀性**：只要随机下标在 `[0,size)` 上等概率，连续数组中的每个当前元素就获得相同被选概率；swap-delete 不会产生洞，因此不会改变这一性质。
- **复杂度口径**：`ArrayList.get` 和删尾是常数时间；追加是均摊 `O(1)`；`HashMap` 的查找/写入通常按期望 `O(1)` 分析。因此整套经典方案应表述为期望/均摊常数时间，而不是无条件严格最坏 `O(1)`。
- **空间**：数组和哈希表都各保存 `n` 规模的信息，总额外空间 `O(n)`。
- **并发**：该实现不是线程安全容器。若要并发 `set/remove/randomGet`，必须重新定义线性化、随机快照和锁粒度，不能只把两个底层容器换成并发容器就认为复合不变量自动安全。

## 原理机制

这个设计本质上用两种数据结构互补：哈希表解决“按值定位”，数组解决“按下标定位”。删除是唯一容易破坏常数复杂度的操作，因此维护一个双向可恢复关系：数组的下标隐式指向值，哈希表显式从值反查下标。

每次操作后保持不变量：

1. `values` 中没有重复元素且没有空洞；
2. `values.size() == index.size()`；
3. 对所有合法下标 `i`，`index.get(values.get(i)) == i`。

`set` 在尾部增加一个新位置并写映射；`remove` 用最后元素填洞并修正一条映射；`contains` 不改变状态；`randomGet` 只读数组。正因为所有状态修改都局限在常数个位置，才避免了线性扫描或线性搬移。

## 常见追问

- 问：为什么不能只用 `HashSet`？答：它适合按值查找，但不能常数时间按随机序号取得一个元素；为了随机取样需要密集的可索引数组。
- 问：为什么删除不是 `values.remove(pos)`？答：中间删除会把后续元素整体左移，导致 `O(n)`，而且还要更新大量下标映射；swap-with-last 只更新一个搬来的元素。
- 问：删除的正好是最后一个元素怎么办？答：直接删哈希映射和数组尾即可；必须跳过 `index.put(last,pos)`，否则会把已删除元素重新写回映射。
- 问：这个实现真的“保证”最坏 `O(1)` 吗？答：经典 Java 方案是哈希操作期望 `O(1)`、数组追加均摊 `O(1)`；若题目严格要求每次操作最坏 `O(1)`，要先补充字典和键模型约束，不能偷换复杂度口径。
- 问：怎样保证 `randomGet` 不会返回已删除元素？答：删除后数组尾被真实移除，洞位由仍存在的最后元素覆盖；数组始终只保存当前集合成员，随机下标只落在 `[0,size)`。
- 问：怎么测试 swap-delete 没写错？答：除了功能样例，还要在随机 `set/remove/contains/randomGet` 序列中持续检查数组和哈希表的一一映射不变量，并与独立 `HashSet` oracle 对比成员状态。

## 易错点

- 直接删除数组中间位置，复杂度退化成 `O(n)`。
- 把最后元素搬到洞位后忘记更新它在 `index` 中的新下标。
- 删除最后一个元素时又把它写回 `index`，造成幽灵成员。
- 允许数组出现空洞，再随机下标时可能抽到无效位置或引入重试成本。
- 没定义重复插入、空集合读取等边界，却让测试和实现各自隐含不同语义。
- 把 `HashMap` 平均/期望 `O(1)` 和 `ArrayList` 均摊 `O(1)` 写成无条件确定性最坏 `O(1)`。
- 并发下分别操作两个容器却没有把复合不变量放在同一同步边界内。
