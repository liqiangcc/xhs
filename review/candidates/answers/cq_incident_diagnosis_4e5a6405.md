# 如何复盘一次线上突发故障排查？

## 核心结论

这是一道必须基于本人真实事故的项目题。当前资料没有任何真实故障、职责、日志或结果，不能编造“我用 jstack/jmap/Arthas 修复过某问题”。合格回答应按“影响与止血 → 假设与证据 → 根因与修复 → 防复发”还原一条可验证时间线，并清楚区分个人动作和团队动作。

## 1 分钟版

- 先补齐事实：故障发生时间、受影响用户/接口、告警、SLO、本人角色和当时的限制。
- 说明止血：在何时由谁执行了什么可回滚动作，以及如何确认影响没有继续扩大。
- 说明定位：每个假设对应什么证据，例如监控、日志、线程栈、heap dump 或链路追踪；工具输出不能替代因果证明。
- 说明闭环：根因修复、验证方式、发布/回滚、告警和演练如何防止同类事故重发。

## 3 分钟版

请先把真实事故材料整理成时间线：告警何时触发、什么指标越过哪条真实阈值、哪些用户或服务受影响、当班人如何分工、哪一项止血措施先执行、效果由哪些指标确认。没有这些材料时，回答必须停在事实收集阶段，而不是用通用的“CPU 高、Full GC、慢 SQL”故事补全。

定位按假设驱动推进。先用业务错误率、延迟、容量与依赖状态确定故障域；再对每个可证伪假设保存原始证据和采样时间。若真实环境使用 JDK 21 的 `jstack`，它可打印指定 Java 进程的线程栈；Arthas dashboard 可显示当前系统实时统计和线程、内存等信息。工具只能支撑观察到的现象，例如某线程栈或某时段 CPU，根因仍需要与代码、发布变更、依赖日志或复现结果交叉验证。

复盘口述应明确个人边界：谁决定降级或回滚，谁采集证据，自己具体做了哪些判断和修改；不要把团队动作写成个人功劳。然后按“根因修复 → 回归/压测 → 灰度或回滚条件 → 监控与告警 → 复盘行动项责任人和截止时间”闭环。最终效果只能引用真实可核对的恢复时间、错误率、延迟或告警数据；缺失时写明尚未提供。

## 关键细节

- 需要提交的证据：告警截图或指标查询、关键日志/trace、线程栈或 heap 证据、相关发布记录、修复变更、验证结果和复盘行动项。
- 工具边界：JDK 21 文档将 `jstack` 标为实验性且不受支持；使用前要确认运行时版本、容器权限和生产采集风险，不能把命令当作所有环境的无风险标准操作。
- 排障顺序：先保留证据并止血，再缩小故障域；不要先认定 JVM、数据库或网络任一组件是根因。
- 结果边界：恢复指标和长期改进指标必须来自实际监控；没有数据时只能说明验证计划。

## 原理机制

排障不是按工具清单逐项执行，而是一个状态转换：异常信号 → 影响范围与止血状态 → 可证伪假设集合 → 带时间戳的观察证据 → 根因结论 → 已验证的修复 → 防复发行动。每一步都要保留“当时已知什么、据此排除了什么、下一步为什么做”，这样才能在面试追问中证明不是事后编故事。

## 项目经验版

当前缺少真实项目事实，不能生成第一人称成稿。请提供一次实际事故的背景与规模、个人职责、告警与时间线、采取的止血动作、每个诊断工具的原始观察、根因证据、修复提交或配置变更、验证数据、复盘行动项和后续结果。收到这些材料后，才能将本框架改写为可背诵的 STAR/时间线回答。

## 常见追问

- 问：为什么不是一看到 CPU 高就直接抓 jstack？答：CPU 高只是现象；先确认影响范围、采样时点和是否存在发布/依赖变化，再用线程栈与其他证据验证具体假设。
- 问：jstack 或 Arthas 输出能直接证明根因吗？答：不能。它们提供某时刻的线程、内存或运行态观察，仍需与代码、日志、变更和复现交叉验证。
- 问：如何证明止血不是把问题转移给下游？答：要提供止血前后的端到端指标、下游容量/错误率和回滚条件；没有这些事实不能下结论。
- 问：复盘中最容易被追问什么？答：个人具体做了什么、为什么选择这条路径、有哪些反证、修复为何能防复发，以及结果数据是否可核对。

## 易错点

- 不要虚构事故规模、恢复分钟数、个人职责或工具输出。
- 不要把“执行过一个命令”说成完成根因定位；必须说明观察、假设、反证和验证。
- 不要只讲成功路径，遗漏错误止血、回滚条件和后续防复发。
- 不要把通用排障流程包装成真实项目经历；没有事实时必须明确它只是待补全框架。
