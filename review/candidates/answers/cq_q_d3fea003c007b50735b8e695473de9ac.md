# CMS 和 G1 垃圾收集器的区别？如何按场景选择？

## 核心结论

CMS 和 G1 都曾以“降低长时间停顿”为重要目标，但它们解决问题的结构完全不同：

```text
CMS
→ 主要面向老年代做并发标记 + 并发清除
→ 尽量把追踪和清扫放到应用线程运行期间
→ 不做常规压缩，因此要承担空闲空间碎片、并发期间 CPU 竞争和 concurrent mode failure 风险

G1
→ 把堆划成多个 Region
→ 并发标记后按回收收益和预计代价选择 Collection Set
→ 在 STW evacuation 中复制存活对象
→ 回收 Region 的同时完成压缩，并用暂停预测模型控制每次收集规模
```

所以真正的差异不是“CMS 并发、G1 也并发”，而是：

**CMS 以并发 mark-sweep 缩短老年代回收停顿；G1 以 Region + remembered set + evacuation + pause model，把“回收哪些区域、一次做多少工作”也纳入调度。**

如果讨论现代 JDK，还必须先加版本边界：G1 从 JDK 9 起成为默认 GC；CMS 在 JDK 9 被弃用，并在 JDK 14 被移除。因此在 JDK 14+ 上，“CMS 还是 G1”已经不是一个可选参数对比题，而更接近历史机制与迁移决策题。

## 1 分钟版

我会从五个维度回答：

1. **堆组织方式**：CMS 仍基于传统分代里的老年代；G1 把整个堆划成许多 Region，年轻代和老年代是 Region 的逻辑集合。
2. **回收方式**：CMS 主要是并发标记、并发清除，不做常规压缩；G1 会在 young/mixed collection 的 STW evacuation 中复制存活对象，因此可以持续压缩并回收 Region。
3. **暂停控制**：CMS 的目标是把大部分老年代工作并发化，但遇到空间不足可能 concurrent mode failure；G1 用历史成本模型和 `MaxGCPauseMillis` 这类软目标决定 Collection Set 大小，但它不是实时 GC，也不保证每次都达到目标。
4. **额外成本**：CMS 并发阶段会和应用抢 CPU，并产生 floating garbage；G1 为了独立回收 Region，需要 remembered set、写屏障和并发 refinement，这些也会消耗 CPU/内存。
5. **版本与选择**：JDK 9 起 G1 是默认 GC，CMS 同期弃用，JDK 14 已移除 CMS。现代 JDK 不应再把 CMS 当成长期生产选项；历史 JDK 8 场景下若做迁移，应以同一业务负载比较暂停分位数、吞吐、CPU、堆占用和失败事件，而不是凭“G1 一定更快”做结论。

## 3 分钟版

### 1. CMS：把老年代的大部分工作并发化

CMS 的一个 major collection 会短暂停两次：

- **Initial Mark**：标记 GC Roots 直接可达对象；
- **Remark**：修正并发标记期间应用修改引用造成的遗漏。

两次暂停之间是并发追踪，Remark 之后是并发 sweeping。也就是说，大部分 tracing/sweeping 与应用同时执行。

它的收益是减少“整个老年代长时间停下来做完全部工作”的概率，但代价也很明确：

- 并发 GC 线程会占用本可供应用使用的 CPU；
- 应用在并发周期仍继续分配和修改引用，因此会产生 floating garbage；
- CMS 不做常规压缩。连续 mark-sweep 后可能出现“总空闲空间还有，但缺少足够大的连续空闲块”的问题；
- 如果 CMS 来不及在老年代填满前完成，或者当前空闲块无法满足分配，就会发生 **concurrent mode failure**，应用被停下来完成回收，暂停会显著变长。

因此 CMS 的核心交换是：

```text
更短的常规老年代暂停
↔
并发 CPU 开销 + 空间余量要求 + 不压缩带来的空间管理风险
```

### 2. G1：Region 化，再决定“这次回收哪些 Region”

G1 把 Java heap 划成多个等大小 Region。年轻代、老年代不再要求是连续物理区间，而是由一组 Region 组成。

G1 的关键不是只“并发标记”，而是：

```text
并发标记
→ 得到各 Region 的存活/可回收信息
→ 根据历史成本模型和暂停目标挑选 Collection Set
→ STW evacuation：把选中 Region 的存活对象复制出去
→ 原 Region 整体释放
```

复制存活对象本身同时完成了压缩，所以 G1 能持续降低碎片问题。

G1 的 young collection 和 mixed collection 都包含 STW evacuation。它不是“无停顿 GC”。`MaxGCPauseMillis` 也只是软目标：G1 根据过去收集的数据估计在目标时间内能处理多少 Region，提高满足目标的概率，但不是硬 SLA。

### 3. 为什么 G1 需要 remembered set

Region 可以被独立回收，就必须知道“其他 Region 有没有对象指向这个 Region”。

如果每次都扫描整个堆，就失去了 Region 独立回收的意义。因此 G1 为 Region 维护 remembered set，并通过写屏障记录跨 Region 引用变化。这样收集某个 Region 时，可以重点扫描它的 remembered-set/root 信息，而不是重新遍历整个堆。

这也解释了 G1 的一个成本来源：remembered set、card/refinement 不是免费的。跨 Region 引用很多时，更新和扫描这些结构会增加 CPU、内存以及 pause 中的 Merge/Scan Heap Roots 工作。

### 4. 暂停与失败模式怎么比较

CMS 的典型风险之一是 **concurrent mode failure**：并发周期还没完成，老年代已经没有足够空间，退化为更重的停顿式处理。

G1 的核心约束不同：evacuation 需要有目标 Region 接收存活对象；Region 选择、年轻代大小、并发标记启动时机和 remembered-set 工作都会影响 pause。G1 通过预测模型控制每次 collection set 的规模，但不能把它理解成“设 200ms 就永远不超过 200ms”。

所以对比时应该问：

```text
CMS：能否在老年代耗尽前把并发周期做完？空闲块是否足够？
G1 ：能否在暂停预算下完成选定 Region 的根扫描 + evacuation？并发标记/Refinement 是否跟得上？
```

### 5. 场景怎么选

先看 JDK 版本：

- **JDK 14+**：CMS 已不存在，不能作为正常候选。
- **JDK 9~13**：CMS 已弃用，G1 是默认 GC；除非维护历史系统，一般应优先走迁移和验证，而不是继续增加 CMS 依赖。
- **JDK 8 历史系统**：两者都可能存在，这时才有真正的迁移 A/B 对比价值。

迁移时不要只看平均停顿。至少固定同一应用版本、堆大小和业务流量模型，比较：

```text
pause p50 / p95 / p99 / max
吞吐与请求尾延迟
GC 与应用 CPU
allocation / promotion 速率
old-gen 或 Region 占用
Full GC / concurrent mode failure / evacuation 类失败事件
```

如果目标是现代 JDK 上的可维护低停顿方案，版本事实已经把方向明显推向 G1 或其他仍受支持的现代收集器；如果是维护 JDK 8 老系统，则要让真实 workload 的数据决定迁移收益。

## 关键细节

- **CMS 不是完全无 STW。** Initial Mark 和 Remark 都会暂停应用；年轻代回收也可能暂停。
- **G1 也不是完全并发。** young/mixed evacuation 是 STW；并发标记只是其中一部分。
- **CMS 的“Concurrent Mark Sweep”名字已经说明其空间回收方式。** Oracle 的 G1 文档明确把 G1 evacuation 的压缩能力和 CMS 不压缩作了对比。
- **floating garbage 是 CMS 并发性的直接代价之一。** 并发追踪期间已经被标记为存活的对象之后可能失去引用，只能留到后续周期再回收。
- **G1 的 Region 不等于“每个 Region 自己就能独立判断所有引用”。** remembered set 和写屏障正是为了记录跨 Region 引用。
- **`MaxGCPauseMillis` 不是 SLA。** G1 是 soft real-time 风格的目标控制，不是实时收集器。
- **版本边界不能漏。** G1 从 JDK 9 起成为默认 GC；CMS 在 JDK 9 弃用，JDK 14 移除。
- **不要把“G1 会压缩”说成“G1 永远不会 Full GC/失败”。** Collector 仍受堆容量、分配速率、存活率和 evacuation 空间等约束。
- **不要把“CMS 不压缩”直接等价成“每次都碎片化到失败”。** 正确说法是它没有 G1 evacuation 这种持续压缩机制，因此空间布局和大对象分配风险更敏感。

## 原理机制

两种 GC 的根本差异可以抽象为“回收单位和空间恢复方式不同”。

CMS：

```text
老年代
→ 找出存活对象
→ 并发 sweep 死对象
→ 空闲块留在原位置
```

它主要优化的是**什么时候做标记和清扫**：尽量与应用并发。

G1：

```text
很多 Region
→ 并发估算每个 Region 的存活情况
→ 选一批 Collection Set
→ 暂停并 evacuation 存活对象
→ 整批 Region 归还空闲列表
```

它除了优化“什么时候做”，还优化**这次做多少、优先回收哪一批、如何通过复制恢复连续空闲空间**。

因此：

```text
CMS 的低停顿主要来自“把工作移出暂停”
G1 的可预测性主要来自“Region 化 + 成本模型 + 每次限制工作集合”
```

而两者都不是免费午餐：CMS 用并发 CPU 和更高空间余量换暂停；G1 用 remembered-set/refinement、复制成本和 Region 管理换更好的空间整理与暂停调度能力。

## 项目经验版

当前来源只给了“CMS 和 G1 的区别 / 如何按场景选择”，没有给真实项目的 JDK 版本、堆大小、GC 日志、流量、暂停分位数或迁移结果，所以不能虚构“线上从 CMS 换成 G1 后延迟降低多少”。

真实迁移我会先做三件事：

1. 确认 JDK 版本，先排除已经不存在或已弃用的选项；
2. 固定同一业务 workload 和堆参数，采集统一口径的 GC 日志、请求尾延迟和 CPU；
3. 用 p95/p99/max pause、吞吐、堆占用和失败事件做 A/B，再决定是否调整 `MaxGCPauseMillis`、堆大小或其他参数。

这能把“哪个 GC 更好”改写成一个可验证的问题，而不是面试口诀。

## 常见追问

- **问：CMS 为什么容易遇到碎片问题？**  
  答：CMS 的正常老年代回收是 mark-sweep，不做 G1 evacuation 式的持续压缩；死对象原地释放后形成多个空闲块，大对象分配对空闲块布局会更敏感。

- **问：G1 为什么能减少碎片？**  
  答：它对 Collection Set 做 evacuation，把存活对象复制到其他 Region，原 Region 整体释放，因此复制过程同时完成压缩。

- **问：G1 有并发标记，为什么还会 STW？**  
  答：并发标记负责获得存活信息；真正 young/mixed collection 中的 evacuation、部分 root/remembered-set 处理仍在 STW pause 内完成。

- **问：`MaxGCPauseMillis=200` 是否意味着暂停一定小于 200ms？**  
  答：不是。它是目标值，G1 用历史预测决定本次 collection set 大小，官方明确说明并非绝对保证。

- **问：CMS 的 concurrent mode failure 是什么？**  
  答：CMS 还没在并发阶段完成回收，老年代就已填满，或现有空闲块无法满足分配，此时应用会被停下来完成回收。

- **问：今天还应该选 CMS 吗？**  
  答：先看版本。JDK 14 起 CMS 已被移除；JDK 9 起已经弃用且 G1 成为默认 GC。因此现代 JDK 上 CMS 主要是历史知识和迁移背景，不是长期新部署选项。

## 易错点

- 把 CMS 说成“完全不 STW”。
- 把 G1 说成“全程并发”或“没有 Full GC 风险”。
- 把 `MaxGCPauseMillis` 当硬性实时保证。
- 只背“CMS 标记清除、G1 标记整理”，却不解释 Region、Collection Set、evacuation 和 remembered set。
- 忽略 CMS concurrent mode failure 与 floating garbage。
- 忽略版本事实，在 JDK 14+ 仍把 CMS 当作可部署候选。
- 虚构某个项目迁移后的停顿、吞吐、CPU 数字来证明 G1 一定更好。
