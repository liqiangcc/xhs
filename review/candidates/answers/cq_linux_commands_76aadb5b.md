# Linux 线上排查常用命令有哪些？

## 核心结论

线上排查不要从“背命令”开始，而要从**症状 → 资源压力 → 责任进程/线程 → 具体等待点或系统调用 → 业务证据**逐层收敛。常用命令可以按 CPU/调度、内存、块 I/O、网络、进程与文件描述符、历史指标六组组织；先用低开销、聚合型观测定位方向，再对单个 PID、设备或连接做细化。任何百分比和 load 都必须结合采样窗口、CPU 数、设备模型、容器/cgroup 边界和业务 SLO 解读。

## 1 分钟版

- **先看全局**：`uptime` / `top` 看 load 和 CPU 分布；`vmstat 1` 看 runnable、blocked、swap、CPU 等趋势。不要把 load average 直接等同于 CPU 利用率。
- **定位进程**：`pidstat -u -r -d -p <pid> 1` 分别看目标进程的 CPU、缺页/内存、I/O；需要线程级定位时再看 task/thread 维度。
- **查内存压力**：`free -h` 看系统内存概览，结合 `/proc/meminfo`、`vmstat` 和 `/proc/pressure/memory` 判断回收、swap 与真实 stall；Linux 空闲内存少本身不等于内存泄漏。
- **查磁盘 I/O**：`iostat -xz 1` 看吞吐、请求延迟、队列和 `%util`。现代 SSD/RAID 能并行处理请求，`%util` 接近 100% 不能单独证明设备已到性能极限。
- **查网络**：`ss -lntp` 看监听，`ss -tan`/按状态过滤看连接；再结合应用错误、重传/丢包及接口指标判断，不能只凭连接数下结论。
- **查历史**：如果部署了 sysstat，用 `sar` 回看事故时间窗，避免“故障已经过去，只能看当前值”。
- **深入工具要收窄范围**：`lsof -p <pid>` 看打开文件/FD；`strace -p <pid>`、`perf` 只在明确目标、限时限范围时使用，因为跟踪本身有开销，也可能暴露敏感参数或数据。

## 3 分钟版

我会按“先确认现象，再逐层缩小范围”的顺序排查。

### 1. 先固定时间窗和业务症状

先记下故障开始时间、最近变更、受影响接口、错误率、P95/P99 延迟和吞吐。然后判断是**资源饱和、排队、错误、外部依赖变慢还是进程自身异常**。这一步很重要，因为系统指标只是证据，最终要和业务症状对齐。

### 2. CPU 与调度：先区分“忙”和“等”

`top`、`pidstat`、`vmstat` 可以回答不同层次的问题：系统整体 CPU 是否持续接近饱和；热点集中在哪个进程/线程；run queue、blocked task 是否增长。

load average 不是简单的“CPU 使用率”。在 Linux 中，它反映一段时间内可运行任务以及不可中断睡眠任务的平均数量，所以高 load 既可能来自 CPU 竞争，也可能来自大量任务等待某些内核资源。应同时看 CPU 核数、`%user/%system/%idle`、阻塞任务和 I/O/pressure 证据。

### 3. 内存：区分缓存利用、回收压力和真正不足

`free -h` 适合快速看总量，但不要只盯 `free` 一列。Linux 会积极利用内存做 page cache；更关键的是系统是否发生持续回收、swap、major fault，应用是否因内存压力出现 stall，是否接近 cgroup 内存上限。

因此我会结合 `vmstat 1`、`/proc/meminfo`，在支持 PSI 的内核上再看 `/proc/pressure/memory`。如果容器里出问题，还必须看对应 cgroup 的 `memory.current`、`memory.events`、`memory.pressure` 等，而不是只看宿主机总内存。

### 4. 块 I/O：看延迟和队列，不把单个指标当结论

`iostat -xz 1` 的重点是**连续采样**。iostat 官方手册明确说明：默认第一次报告通常是自开机以来的累计平均，后续报告才对应相邻采样区间；排障时常用 `-y` 跳过第一次累计报告。

判断磁盘问题时同时看吞吐、请求延迟、队列和应用侧延迟。尤其不要把 `%util=100%` 机械解释成“磁盘性能已经打满”：sysstat 当前手册明确提醒，对 RAID 和现代 SSD 这类能并行服务请求的设备，`%util` 不反映其性能上限。

### 5. 网络：先确认监听与连接，再看错误和传输质量

`ss` 先确认服务是否监听正确地址/端口、连接状态是否异常集中，再结合接口统计、内核 TCP 指标和应用日志判断。大量 `TIME-WAIT`、`CLOSE-WAIT` 或连接数上涨本身只是线索，必须结合谁主动关闭、FD 是否耗尽、上游/下游超时和重试行为解释。

### 6. 进程、FD 与深度定位

当范围已经缩到某个进程，再使用 `lsof` 查看文件和 socket，必要时看 `/proc/<pid>/fd`、`/proc/<pid>/status`、线程栈或运行时专用工具。`strace` 能观察系统调用和信号，适合确认“卡在 connect/read/futex 还是频繁失败重试”等问题，但应指定 PID、过滤 syscall、设置时间窗口；`perf` 也应从受控采样开始。线上高开销工具不是第一步。

### 7. 用历史指标闭环

如果问题已经恢复，当前的 `top` 往往没有意义。sysstat 的 `sar` 可以读取之前保存的系统活动记录，回看事故时间窗的 CPU、内存、I/O、网络等变化。最后把系统证据和应用日志、trace、发布记录放到同一时间线上，形成可以复现或证伪的根因链。

## 关键细节

- `load average` 高不等于“CPU 一定 100%”；先看 CPU 数、运行/阻塞任务和 pressure。
- `iostat` 第一次输出通常是自开机累计值；实时排障要关注连续采样区间，必要时用 `-y`。
- `iostat %util` 对串行服务请求的设备更接近饱和提示；对并行 SSD/RAID 不能单独当作性能上限。
- `free` 中“空闲内存少”不自动等于内存不足；应结合 available、回收、swap、major fault、PSI/cgroup 事件。
- 容器内看到的 CPU、内存和 PID 视图可能受 namespace/cgroup 限制；宿主机指标与容器配额必须同时对齐。
- `ss` 比“只看 netstat 输出”更适合现代 Linux 的 socket 排查，但连接状态仍需与应用主动/被动关闭行为一起解释。
- `strace`/`perf` 是深入工具，不是全局扫描工具；线上应限定 PID、事件、时长和输出位置。
- 所有指标都要保留采样时间窗。单次快照很容易把瞬时峰值或自开机平均值误判成持续问题。

## 原理机制

这套顺序的核心是**从聚合指标逐步降低观测粒度**。

第一层，系统级指标回答“哪类资源或等待在异常”；第二层，进程/线程级指标回答“谁贡献了异常”；第三层，设备、socket、FD、系统调用或运行时栈回答“它具体在做什么/等什么”；第四层，用业务日志、trace、发布记录验证这个系统现象是否真的解释了用户侧故障。

这样做既减少误判，也控制观测成本。比如一上来对所有进程 `strace` 或全局高频 `perf`，会制造额外负载并产生海量数据；相反，先用 `pidstat`/`iostat`/PSI 把范围缩小，再深挖目标对象，证据更容易形成闭环。

## 项目经验版

真实事故可以按“症状—证据—定位—验证—修复—防复发”讲。例如先给出真实的接口延迟/错误时间窗，再说明你如何用低开销指标确认资源方向，如何缩到具体 PID/设备/连接，最后用日志、trace、压测或故障复现实验验证根因。没有真实事故数据时只讲排查方法，不虚构 QPS、耗时下降比例或生产故障结论。

## 常见追问

- 问：load average 很高但 CPU 利用率不高，先怀疑什么？答：先看 runnable/blocked task、I/O 和 PSI；Linux load 不只包含正在争抢 CPU 的 runnable task，也会受到不可中断睡眠任务影响，所以要继续判断任务到底在等什么。
- 问：`iostat` 的 `%util` 到 100% 就说明 SSD 打满了吗？答：不能。sysstat 手册明确说明，对能并行服务请求的 RAID/现代 SSD，`%util` 不反映性能极限；必须结合请求延迟、队列、吞吐和业务延迟。
- 问：为什么 `iostat 1` 第一次和后面差异很大？答：默认第一次通常统计自开机以来的平均，后续才是相邻 interval；实时排障可用 `-y` 跳过第一次累计报告。
- 问：`free` 显示 free 很少，是不是马上 OOM？答：不是。先看 available、回收/swap、major fault、PSI 和 cgroup 限额/事件；Linux 会用空闲内存做缓存，单看 free 容易误判。
- 问：什么时候才用 `strace`？答：当问题已缩到具体进程，并需要确认系统调用、信号或等待点时。要限制 PID、syscall 和时长，同时考虑性能开销与敏感数据暴露。
- 问：故障已经恢复怎么查？答：优先回看已经持久化的历史指标，例如 sysstat/sar，再和应用日志、trace、发布记录按同一时间轴关联；没有历史采集时只能从残留日志和可复现实验补证据。

## 易错点

- 把 load average 直接除以 CPU 核数就当成精确 CPU 利用率。
- 看到 `free` 小就立刻认定内存泄漏。
- 把 `iostat %util=100%` 当成所有存储设备的绝对饱和线。
- 只看一次 `top`/`iostat` 快照，不确认采样窗口。
- 在容器故障中只看宿主机总资源，不看 cgroup 配额、pressure 和 OOM 事件。
- 一上来全局 `strace`/高频 `perf`，既扩大生产风险又难以分析。
- 只罗列命令，不说明每个命令回答什么问题、如何交叉验证以及下一步如何收敛。
