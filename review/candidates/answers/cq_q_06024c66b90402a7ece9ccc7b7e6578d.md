# MySQL 中 InnoDB 和 MyISAM 的区别

## 核心结论

以 **MySQL 8.4** 为版本边界，`InnoDB` 是默认且官方推荐的通用存储引擎；`MyISAM` 是非事务型、表级锁的老牌引擎，更偏向只读或读多写少的专门场景。

比较时重点看六个维度：

- **事务与恢复**：InnoDB 支持事务、提交/回滚和崩溃恢复；MyISAM 不支持事务。
- **并发控制**：InnoDB 以行级锁和一致性非锁定读支撑并发；MyISAM 的锁粒度是表级，读写并发能力通常受限。
- **MVCC**：InnoDB 有多版本并发控制；MyISAM 没有 MVCC。
- **外键**：InnoDB 支持 `FOREIGN KEY` 约束；MyISAM 不支持。
- **索引组织**：InnoDB 的用户数据存放在聚簇索引中；MyISAM 不使用聚簇索引。
- **现代选型**：普通业务表优先 InnoDB。只有明确接受“无事务、表级锁”等边界，并且 workload 与 MyISAM 的专门用途匹配时，才考虑 MyISAM。

如果题目还问“MySQL 有哪些存储引擎”，不要死背一个永远固定的清单：MySQL 是可插拔存储引擎架构，实际可用项应以目标实例的 `SHOW ENGINES` / `INFORMATION_SCHEMA.ENGINES` 为准。

## 1 分钟版

我会从“默认选型 + 五个差异”回答：

1. **默认**：MySQL 8.4 新表默认是 InnoDB，官方也建议除专门场景外优先用 InnoDB。
2. **事务**：InnoDB 支持 ACID 事务、提交/回滚和崩溃恢复；MyISAM 不支持事务。
3. **锁与并发**：InnoDB 支持行级锁和一致性读，适合并发读写；MyISAM 是表级锁，更偏读多写少。
4. **MVCC / 外键**：InnoDB 支持 MVCC 和外键；MyISAM 两者都不支持。
5. **索引组织**：InnoDB 数据组织在聚簇索引中；MyISAM 没有聚簇索引。
6. **选型**：现代 OLTP 默认 InnoDB，不要因为旧资料说“MyISAM 查询快”就直接选 MyISAM；性能必须结合真实查询、并发和持久性要求测。

常见引擎还包括 `MEMORY`、`CSV`、`ARCHIVE`、`BLACKHOLE` 等，但具体支持情况要用 `SHOW ENGINES` 查当前实例。

## 3 分钟版

### 1. 先明确存储引擎是什么

MySQL Server 采用可插拔存储引擎架构。SQL 层把表操作交给具体存储引擎处理，不同引擎对事务、锁、索引、持久化等能力的实现不同。

因此：

```sql
SHOW ENGINES;
```

比背一个静态列表更可靠。MySQL 8.4 文档列出的常见引擎包括 InnoDB、MyISAM、MEMORY、CSV、ARCHIVE、BLACKHOLE 等；某些引擎的可用性还与产品形态或配置有关。

### 2. 事务与故障恢复

InnoDB 是事务安全的存储引擎，支持 commit、rollback 和 crash recovery。服务器异常退出后，InnoDB 的恢复机制会完成已提交修改并撤销未提交修改。

MyISAM 不支持事务，所以不能把多个修改自然地包装成由存储引擎保证原子提交/回滚的事务。

这也是现代业务表默认选择 InnoDB 的核心原因之一：不是“功能更多”这么简单，而是数据一致性和故障恢复模型不同。

### 3. 锁粒度与并发模型

MySQL 8.4 对 InnoDB 的概括是支持行级锁和一致性非锁定读；MyISAM 的锁粒度是表级。

直观上：

```text
InnoDB
多个事务修改不同记录
        ↓
通常可以在更细粒度的锁范围内并发推进

MyISAM
写操作需要表级锁协调
        ↓
读写混合 workload 下更容易互相阻塞
```

但“行级锁”不能简化成“InnoDB 永远只锁一行”。InnoDB 还存在意向锁、记录锁、间隙/next-key 锁等机制；一条 SQL 扫描的索引范围越大，实际锁住的记录范围也可能越大。所以索引设计和访问路径仍然重要。

### 4. MVCC 与一致性读

InnoDB 支持多版本机制，可以让普通一致性读读取事务视图，而不是所有读都和写操作直接争抢同一把排他锁。

MyISAM 的 MySQL 8.4 特性表明确标记 MVCC 为不支持。

因此两者在“事务隔离 + 并发读写”上的能力模型本质不同，而不是仅仅“锁大一点、锁小一点”。

### 5. 外键与索引组织

InnoDB 支持外键引用完整性约束；MyISAM 不支持。

索引组织上，InnoDB 将用户数据存放在聚簇索引中，主键访问与二级索引回表都与这个组织方式有关；MyISAM 的特性表明确不支持 clustered indexes。

这个差异会继续影响索引设计、主键选择和 I/O 路径，但不要在“引擎区别”题里无限展开到完整 B+Tree 源码题。

### 6. 怎么选

MySQL 8.4 已把 InnoDB 作为默认且最通用的存储引擎，并建议除专门场景外使用 InnoDB。

MyISAM 文档把它描述为小 footprint、表级锁，并指出它常用于只读或读多写少的 Web / 数据仓库场景。也就是说，选择 MyISAM 必须是**明确接受其无事务、表级锁、无外键/MVCC等约束后的专门决策**，而不是沿用旧时代“查询快所以选 MyISAM”的经验口号。

## 关键细节

- **不要背旧版本结论**：当前答案绑定 MySQL 8.4。比如“只有 MyISAM 支持全文索引”在现代 MySQL 已经是错误说法，InnoDB 也支持 FULLTEXT。
- **InnoDB 行级锁 ≠ 永远只锁一行**：实际锁范围取决于 SQL、索引和隔离语义；范围扫描可能锁多个索引记录甚至间隙。
- **MyISAM 表级锁 ≠ 完全不能并发**：MyISAM 有特定条件下的 concurrent insert，但这不改变其锁粒度和缺少事务/MVCC的总体边界。
- **外键是引擎能力差异**：InnoDB 可以执行引用完整性约束；MyISAM 不支持，不应把“应用自己校验”当成等价数据库约束。
- **存储引擎列表不是常量**：MySQL 使用可插拔架构，实际实例支持哪些引擎要看 `SHOW ENGINES`，不能假设所有部署完全相同。
- **不要用单一“快慢”选型**：真实性能取决于读写比例、并发、数据量、索引、缓存命中和持久性要求；先按语义正确性选，再压测。

## 原理机制

可以把两者差异理解成两套不同的数据一致性与并发控制模型：

```text
InnoDB
事务状态 + redo/undo/恢复能力
        +
多版本读取 + 细粒度锁
        +
聚簇索引数据组织
        +
外键约束
        ↓
面向通用 OLTP 和并发读写

MyISAM
非事务表
        +
表级锁
        +
独立的 MyISAM 数据/索引组织
        ↓
实现更简单，适合明确的专门 workload
```

因此，“事务支持”和“锁粒度”并不是两条互不相关的面试记忆点。它们共同决定：发生并发修改时如何隔离、发生异常时能否回滚/恢复、读写操作怎样互相影响，以及应用需要承担多少一致性责任。

## 项目经验版

来源只包含存储引擎技术问题，没有真实项目经历，因此不能虚构“我在线上把 MyISAM 迁到 InnoDB 后性能提升多少”。

真实工程里我会按这个顺序判断：

1. 当前 MySQL 版本和 `SHOW ENGINES` 实际能力是什么？
2. 业务是否需要多语句事务、崩溃恢复和外键约束？
3. 是否存在高并发读写，锁等待和热点更新是什么分布？
4. 表的主键和二级索引如何设计，主要 SQL 的访问路径是什么？
5. 如果考虑 MyISAM，是否真的属于只读/读多写少的专门场景，并且能够明确接受无事务、无 MVCC、表级锁等限制？
6. 最后用目标版本、真实数据量和并发模型做压测，而不是拿历史 benchmark 替代当前 workload。

在普通现代业务系统中，如果没有非常明确的反例约束，起点通常就是 InnoDB。

## 常见追问

- 问：MySQL 里有哪些存储引擎？  
  答：MySQL 8.4 常见有 InnoDB、MyISAM、MEMORY、CSV、ARCHIVE、BLACKHOLE 等，但存储引擎是可插拔的，目标实例最终以 `SHOW ENGINES` 为准；InnoDB 是默认引擎。

- 问：为什么 InnoDB 更适合高并发读写？  
  答：核心不是一句“行锁更快”，而是它同时提供细粒度锁、一致性非锁定读和事务/MVCC 模型，使不同事务有更多并发推进空间；最终表现仍取决于索引和访问范围。

- 问：InnoDB 行锁是不是只锁命中的那一行？  
  答：不能这么绝对。InnoDB 的锁作用在索引记录/范围上，还可能涉及 gap/next-key 等锁；没有合适索引时扫描范围和锁范围都可能扩大。

- 问：MyISAM 完全不能并发写吗？  
  答：也不能说绝对。MyISAM 在特定条件下支持 concurrent insert，但总体仍是表级锁、无事务和无 MVCC，读写混合场景的并发模型与 InnoDB 不同。

- 问：MyISAM 的查询一定比 InnoDB 快吗？  
  答：没有这样的通用结论。不同版本、缓存状态、查询模式和并发模型会改变结果；现代 MySQL 应先按一致性/并发语义选引擎，再用真实 workload 测量。

- 问：只有 MyISAM 支持全文索引吗？  
  答：不是。MySQL 8.4 的 InnoDB 也支持 FULLTEXT，因此这是典型的旧版本知识污染，回答必须绑定版本。

## 易错点

- 说“InnoDB 支持行锁，所以一条语句永远只锁一行”。
- 说“MyISAM 完全不能并发”，忽略其特定 concurrent insert 条件。
- 说“只有 MyISAM 支持全文索引”，把旧版本结论当成当前事实。
- 只背“InnoDB 支持事务、MyISAM 不支持事务”，却解释不出事务、恢复、MVCC和锁模型如何共同影响并发与一致性。
- 说“MyISAM 查询一定更快”或“InnoDB 一定更快”，用绝对性能口号代替 workload 证据。
- 把存储引擎清单当成永久固定常量，不检查目标 MySQL 实例的 `SHOW ENGINES`。
