# 千亿级数据 Top100：顺序扫描 + 100 元素小顶堆

## 核心结论

题目只保留了“千亿数组 Top100”，没有说明元素类型、数据是否真的能整体放进内存、Top 是最大还是最小、是否去重、结果顺序以及数据入口。面对这个规模，先把“全量排序”排除为默认方案。这里采用明确的回答契约：求**最大的 100 个值，重复值按出现次数计入**，数据可以顺序读取但不要求整体驻留内存。维护容量为 100 的小顶堆：前 100 个元素入堆，此后只有新值大于堆顶时才替换堆顶。扫描结束后堆中恰好是当前看到数据的 Top100。

## 1 分钟版

- 规模极大时不要先全排序，也不要假设整个输入能放进单机内存；算法只需要顺序扫描一次。
- 用容量 `K=100` 的小顶堆保存当前最大的 100 个值，堆顶是这 100 个候选里最小的那个，也就是淘汰门槛。
- 堆未满就加入；堆满后，如果 `x <= heapMin`，它不可能进入 Top100，直接丢弃；如果 `x > heapMin`，用 `x` 替换堆顶并下沉恢复堆。
- 不变量：处理完任意前缀后，堆保存该前缀中最大的 `min(K, prefixSize)` 个值（按重复次数计）。
- 时间 `O(n log K)`，这里 `K=100` 基本可视为线性扫描；额外空间 `O(K)`。真正的瓶颈通常会转向输入读取、分片和 I/O，而不是这 100 个候选本身。

## 3 分钟版

```java
import java.util.Arrays;
import java.util.PrimitiveIterator;

public final class TopKStream {
    private TopKStream() {}

    public static long[] largestK(PrimitiveIterator.OfLong input, int k) {
        if (input == null) throw new IllegalArgumentException("input must not be null");
        if (k < 0) throw new IllegalArgumentException("k must be nonnegative");
        if (k == 0) return new long[0];

        long[] heap = new long[k];
        int size = 0;
        while (input.hasNext()) {
            long x = input.nextLong();
            if (size < k) {
                heap[size] = x;
                siftUp(heap, size);
                size++;
            } else if (x > heap[0]) {
                heap[0] = x;
                siftDown(heap, size, 0);
            }
        }

        long[] result = Arrays.copyOf(heap, size);
        Arrays.sort(result);
        reverse(result);
        return result;
    }

    private static void siftUp(long[] heap, int i) {
        while (i > 0) {
            int p = (i - 1) >>> 1;
            if (heap[p] <= heap[i]) return;
            long t = heap[p]; heap[p] = heap[i]; heap[i] = t;
            i = p;
        }
    }

    private static void siftDown(long[] heap, int size, int i) {
        while (true) {
            int left = i * 2 + 1;
            if (left >= size) return;
            int right = left + 1;
            int child = right < size && heap[right] < heap[left] ? right : left;
            if (heap[i] <= heap[child]) return;
            long t = heap[i]; heap[i] = heap[child]; heap[child] = t;
            i = child;
        }
    }

    private static void reverse(long[] a) {
        for (int l = 0, r = a.length - 1; l < r; l++, r--) {
            long t = a[l]; a[l] = a[r]; a[r] = t;
        }
    }
}
```

代码把输入抽象成 `PrimitiveIterator.OfLong`，是为了表达“顺序读即可”，而不是声称来源规定了 Java 或 `long`。返回结果按降序排列也是回答侧契约；如果调用方不要求排序，可以直接返回堆内容，省掉最终 `O(K log K)` 排序。

## 关键细节

- **Top 的语义**：来源只有“Top100”。本答案选择“最大的 100 个、允许重复”；若要求最小 100 个，把小顶堆对称改为容量 100 的大顶堆；若要求 100 个不同值，还要额外定义去重策略。
- **为什么是小顶堆**：我们关心的是“当前 TopK 中最弱的候选”。小顶堆以 `O(1)` 暴露这个门槛，以 `O(log K)` 完成替换。
- **不变量**：堆未满时保存全部已读值；堆满后保存已读前缀中最大的 K 个值。任何 `x <= heap[0]` 至少不比当前第 K 大候选更大，因此可以丢弃；更大的值必须进入候选并淘汰旧门槛。
- **重复值**：`x == heap[0]` 时直接丢弃仍然正确，因为当前堆已经有 K 个值都不小于它；若 TopK 中需要多个相同大值，它们会在堆填充或更早的替换阶段被保留下来。
- **输入规模**：来源没有给内存、机器数和存储介质，因此不能声称“单机数组一定能放下”。顺序输入接口只要求一遍读取，适用于文件、分片流或其他可迭代来源。
- **复杂度**：每个元素做一次门槛判断，至多一次 `O(log K)` 堆调整，所以时间 `O(n log K)`，空间 `O(K)`；`K=100` 时候选内存固定在很小规模，但全流程 I/O 成本仍取决于实际数据源。
- **分布式扩展**：如果数据已经分片，每个分片可先算本地 Top100，再把各分片最多 100 个候选汇总后再做一次 Top100；这是 TopK 的可合并性质。网络、失败重试和一致性语义仍需按真实执行环境定义。

## 原理机制

TopK 不要求知道所有元素之间的全序，只需要持续维护一个大小为 K 的“候选边界”。当候选已满，小顶堆的根就是当前第 K 大的下界：比它小或相等的新值不可能挤进结果，比它大的值一定应该替换根。于是全局问题被压缩成每个元素与一个动态阈值的比较，避免保存和排序全部 n 个元素。若数据分片，本地 TopK 之外的元素也不可能进入全局 TopK，因此只汇总各分片 TopK 仍然不会漏掉最终答案。

## 项目经验版

来源没有提供真实生产规模、磁盘格式、机器数量或吞吐指标，不能虚构“线上就是这么做的”。实际落地我会先确认数据落在哪里、是否允许一遍扫描、数值类型、重复语义、SLA 与机器内存，再决定单机流式堆、分片局部 TopK + 合并，还是借助已有批处理引擎；验证时重点测端到端扫描吞吐和 I/O，而不只测堆操作。

## 常见追问

- 问：为什么不直接快速排序？答：全排序解决了比 Top100 更强的问题，要付出 `O(n log n)` 时间并通常需要让全量数据参与排序；TopK 只维护 100 个候选即可。
- 问：快速选择不是平均 `O(n)` 吗？答：如果数据已经整体可随机访问并允许原地修改，quickselect 是候选；但“千亿级”首先要确认能否整体放入可随机访问存储。本答案选择只要求顺序扫描、`O(K)` 内存的方案。
- 问：如何做分布式？答：每个分片先取本地 Top100，把所有局部候选合并后再取 Top100；任一分片里没进本地 Top100 的值，不可能进全局 Top100。
- 问：如果要求 Top100 distinct 呢？答：当前实现按出现次数计入，不满足 distinct。需要在候选层增加去重，并明确相同值跨分片的合并方式。
- 问：如果数据少于 100 个呢？答：返回全部已读元素并按当前回答契约降序排列；这是代码显式定义的边界，不是来源额外要求。

## 易错点

- 看到“数组”就默认能把千亿级元素装进一个普通单机内存结构，再直接全排序。
- 用大顶堆维护“最大 TopK”，导致每次拿到的是最大候选而不是淘汰门槛；这里应使用小顶堆。
- 没有先说明“最大/最小、是否去重、结果是否排序”，却把自己的实现选择冒充成原题事实。
- 分布式场景把每个分片只取 Top10 后就想得到全局 Top100，局部候选数不足会漏解。
- 只报 CPU 复杂度，不考虑千亿级数据真正可能受输入扫描、网络和存储吞吐限制。
