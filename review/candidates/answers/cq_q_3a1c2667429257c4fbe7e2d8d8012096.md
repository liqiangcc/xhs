# 一天内 1 亿个包裹：找未取出数量的峰值时间段

## 核心结论

来源只给出“一天内约 1 亿个包裹的存入时间和取出时间，找未取出包裹数最多的时间段、持续时长，以及时间/空间复杂度”，没有规定时间戳精度、端点包含关系、编程语言，也没有指定必须使用某一种算法。先明确答案侧契约：每个包裹对应半开区间 `[putTime, takeTime)`，即存入时立即计入、取出时立即不再计入；时间以一天起点后的非负整数偏移表示。若时间精度的取值域 `T` 很小且固定，优先用差分计数，时间 `O(n+T)`、空间 `O(T)`；若时间戳是一般的稀疏值，则把 `2n` 个端点按时间排序后扫描，比较模型下时间 `O(n log n)`、额外空间 `O(n)`。下面的 Java 实现采用后一种通用方案，并返回所有峰值区间及峰值总持续时长。

## 1 分钟版

- 把每个包裹看成一个存续区间 `[put, take)`；在 `put` 时刻未取出数量 `+1`，在 `take` 时刻 `-1`。
- 同一时刻的所有变化要先合并，再看它到下一个不同时间戳之间的数量；这样能明确处理“一个刚取出、另一个同时存入”的情况。
- 一般时间戳：生成 `2n` 个事件、排序、按时间分组扫描。某个事件时刻 `t` 处理完净变化后，当前计数就是 `[t, nextTime)` 上的未取出数量。
- 记录扫描过程中最大的计数；出现更大值就清空旧峰值区间，等于最大值就追加，并把相邻峰值区间合并。
- 排序扫描时间 `O(n log n)`，事件数组空间 `O(n)`；如果时间只可能是秒级等固定桶，则差分数组可做到 `O(n+T)` 时间、`O(T)` 空间。

## 3 分钟版

```java
public static Result findPeak(List<Interval> intervals) {
    long[] events = new long[Math.multiplyExact(intervals.size(), 2)];
    int p = 0;
    for (Interval x : intervals) {
        if (x.putTime() < 0 || x.takeTime() <= x.putTime()
                || x.takeTime() > (Long.MAX_VALUE >>> 1)) {
            throw new IllegalArgumentException("invalid interval");
        }
        events[p++] = (x.putTime() << 1) | 1L; // put: +1
        events[p++] = (x.takeTime() << 1);     // take: -1
    }
    Arrays.sort(events);

    long current = 0, max = 0, totalPeakDuration = 0;
    List<Segment> peaks = new ArrayList<>();
    int i = 0;
    while (i < events.length) {
        long t = events[i] >>> 1;
        long delta = 0;
        while (i < events.length && (events[i] >>> 1) == t) {
            delta += ((events[i] & 1L) == 1L) ? 1 : -1;
            i++;
        }
        current += delta;
        if (i == events.length) break;

        long next = events[i] >>> 1;
        if (next == t || current <= 0) continue;
        if (current > max) {
            max = current;
            peaks.clear();
            totalPeakDuration = 0;
        }
        if (current == max) {
            totalPeakDuration += next - t;
            if (!peaks.isEmpty() && peaks.get(peaks.size() - 1).end() == t) {
                Segment last = peaks.remove(peaks.size() - 1);
                peaks.add(new Segment(last.start(), next));
            } else {
                peaks.add(new Segment(t, next));
            }
        }
    }
    return new Result(max, List.copyOf(peaks), totalPeakDuration);
}
```

代码把事件编码进 primitive `long[]`，避免为 2 亿个端点创建 2 亿个 Java 对象。最低位表示事件类型，其余位保存时间偏移；因此这个具体实现限制时间偏移不超过 `Long.MAX_VALUE >>> 1`，对“一天内”的常见秒/毫秒/微秒/纳秒偏移都足够。若输入时间是任意 64 位绝对时间戳，可改成两个 primitive 数组或显式事件结构，不改变扫描思想。

## 关键细节

- **端点语义必须先定**：这里使用 `[put, take)`。同一时刻的取出和存入先汇总成净变化，扫描的是事件时刻之间的连续时间段，而不是把一个瞬时时刻重复计数。
- **为什么看 `[t,next)`**：事件只会在端点改变数量。处理完时刻 `t` 的全部净变化后，到下一个事件前数量保持不变，所以这一整段可以一次比较。
- **“时间段”可能不止一个**：全天可能存在多个互不相邻、但峰值数量相同的区间。实现返回全部最大区间，并额外给出这些区间持续时长之和；如果业务只要第一个峰值，可在结果层再选取。
- **相邻峰值合并**：若某时刻净变化为 0，峰值数量实际上没有中断，`[a,t)` 与 `[t,b)` 应合并为 `[a,b)`。
- **1 亿规模的内存**：通用排序实现需要 `2n` 个 `long`，仅事件数组约 `16n` 字节；`n=1e8` 时约 1.6 GB（不含 JVM/输入/输出开销），因此工程上要结合机器内存、输入布局和时间精度选择 primitive 数组、分块/外排或固定时间桶。
- **固定精度时更优**：如果题目补充“时间精确到秒”，一天只有 `T=86400` 个桶，可以对 `put` 桶 `+1`、`take` 桶 `-1`，一次前缀扫描得到峰值，时间 `O(n+T)`、空间 `O(T)`，明显比对 2 亿事件比较排序更合适。
- **不能擅自假定精度**：来源没有说是秒、毫秒还是任意时间戳，所以正式答案同时给出有界离散域和一般稀疏域两种复杂度，而不把差分数组写成来源要求。

## 原理机制

这是“动态区间重叠数”的峰值问题。每个包裹在 `[put, take)` 内贡献 1，把区间端点转成 `+1/-1` 后，未取出数量就是这些变化量按时间的前缀和。排序的作用是得到变化发生的时间顺序；按相同时间分组则把端点并发事件压缩为一个净变化。由于两个相邻不同端点之间没有任何事件，前缀和在整个开区间上保持常数，所以只需要在每个 `[t,next)` 段上比较一次，就能完整找到峰值区间和持续时间。

若时间坐标本身来自一个很小的离散域，排序可以被“直接按坐标记增量”替代；本质仍然是同一个前缀和模型。区别只是如何得到按时间有序的增量序列，因此复杂度应根据时间域是否有界来选择，而不是机械固定为某一种算法名称。

## 项目经验版

来源没有真实线上实现、时间精度、机器配置或延迟指标，不能虚构“生产中就是这么做的”。真正处理 1 亿条记录时，我会先确认时间精度、输入是否已按时间排序、数据是否一次装得进内存、是否允许外排，以及需要返回一个峰值区间还是全部峰值区间。若是秒级/分钟级运营容量分析，固定桶通常最简单；若是高精度稀疏时间戳，则优先使用 primitive 事件数组或外部排序，并用样本与压力测试验证内存峰值。

## 常见追问

- 问：同一时刻一个包裹取出、另一个包裹存入，先算哪个？答：本答案定义半开区间 `[put,take)`，在同一时间点把所有 `+1/-1` 合并成净变化；随后 `[t,next)` 的数量是确定的，不依赖人为事件顺序。
- 问：为什么不是一定 `O(n)`？答：只有时间坐标有固定小域、输入已排序或有其它可利用约束时才能省掉一般排序；对无序的一般时间戳，先得到端点顺序通常需要排序。
- 问：如果时间精确到秒怎么做？答：一天 86400 个桶，`diff[put]++`、`diff[take]--`，扫描前缀和并合并最大值连续桶即可，复杂度 `O(n+86400)` 时间、`O(86400)` 空间。
- 问：为什么要返回多个区间？答：最大未取出数量可能在早晚两个不连续区间都出现。来源没有规定只取一个，因此保留全部峰值区间信息更完整。
- 问：2 亿个事件内存会不会太大？答：会。primitive `long[]` 单事件 8 字节，2 亿个约 1.6 GB；如果机器预算不允许，应利用固定时间桶、已排序输入、分块外排或流式归并等约束降低常驻内存。
- 问：包裹存入和取出时间相同怎么办？答：当前 API 把 `take <= put` 视为非法输入。若业务允许零持续时间记录，应先定义其是否贡献瞬时库存；对持续时间峰值统计通常可以把它视为不占用任何正长度区间并过滤掉。

## 易错点

- 没定义端点包含关系，就在同一时间的取出/存入事件上得到不稳定结果。
- 只找到“某个峰值时刻”，却没有计算峰值保持到下一个事件的持续时间。
- 最大值再次出现时覆盖旧区间，丢失多个不连续峰值区间。
- 净变化为 0 时错误地把连续峰值拆成两个时间段。
- 对 1 亿条数据使用事件对象列表，忽略对象头、引用和 GC 带来的巨大内存放大。
- 在来源没有时间精度约束时直接声称差分数组一定是 `O(1)` 空间，或反过来声称任何实现都必须 `O(n log n)`。
