# 三个线程轮流打印 A、B、C：用三个 Semaphore 做令牌传递

## 核心结论

来源只保留“算法：三个线程轮流打印 A、B、C”，没有给打印轮数、Java API、异常/中断策略，也没有说明是否允许忙等。这里采用一个明确的回答契约：创建三个固定线程分别负责 `A`、`B`、`C`，由 `A` 开始，按 `ABCABC...` 顺序打印 `rounds` 轮；`rounds=0` 什么也不打印，负数拒绝。用三个 `Semaphore` 表示唯一令牌：A 初始 1 个许可，B/C 初始 0 个许可；每个线程拿到自己的许可后打印一次，再释放下一个线程的许可，因此操作系统如何调度线程都不能越过同步门槛改变可见打印顺序。

## 1 分钟版

- 三个线程真正共享的核心状态不是“谁先被 CPU 调度”，而是谁当前持有打印许可。
- 初始化 `a=1, b=0, c=0`，所以只有 A 能先通过 `acquire()`；A 打印后 `b.release()`，B 再放行 C，C 再放行 A，形成闭环。
- `acquire()` 没有许可时会阻塞，不需要 `while(turn != me)` 这种忙等。
- 每个线程循环 `rounds` 次，因此总输出长度是 `3 * rounds`，并且每一轮严格是 `ABC`。
- 同步控制只维护固定数量的 Semaphore、Thread 和循环计数器；如果像示例一样把输出收集成字符串，返回结果本身需要 `O(rounds)` 空间，真正直接写到输出流时同步辅助状态是 `O(1)`。

## 3 分钟版

```java
import java.util.concurrent.Semaphore;

public final class RoundRobinABC {
    private RoundRobinABC() {}

    public static String print(int rounds) throws InterruptedException {
        if (rounds < 0) throw new IllegalArgumentException("rounds must be nonnegative");

        Semaphore a = new Semaphore(1);
        Semaphore b = new Semaphore(0);
        Semaphore c = new Semaphore(0);
        StringBuilder output = new StringBuilder();

        Thread ta = worker('A', rounds, a, b, output);
        Thread tb = worker('B', rounds, b, c, output);
        Thread tc = worker('C', rounds, c, a, output);
        Thread[] threads = {ta, tb, tc};

        for (Thread thread : threads) thread.start();
        try {
            for (Thread thread : threads) thread.join();
        } catch (InterruptedException e) {
            for (Thread thread : threads) thread.interrupt();
            throw e;
        }
        return output.toString();
    }

    private static Thread worker(
            char value,
            int rounds,
            Semaphore mine,
            Semaphore next,
            StringBuilder output) {
        return new Thread(() -> {
            for (int i = 0; i < rounds; i++) {
                try {
                    mine.acquire();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
                output.append(value);
                next.release();
            }
        }, "printer-" + value);
    }
}
```

这里返回字符串只是为了让顺序可以被测试；面试现场也可以把 `output.append(value)` 换成真实输出动作。`StringBuilder` 虽然不是通用线程安全容器，但在这个实现里任意时刻只有持有唯一许可的线程会执行追加，并且主线程在 `join()` 完成后才读取结果。

## 关键细节

- **起始顺序**：来源写的是轮流打印 A、B、C，本答案把它具体化为 A→B→C；A 的 Semaphore 初始许可为 1，另外两个为 0。
- **为什么不会乱序**：即使 B 线程先获得 CPU，它的 `b.acquire()` 也会阻塞；只有 A 打印并释放 B 的许可后，B 才能继续。调度先后和业务顺序被同步原语解耦。
- **为什么不用忙等**：Semaphore 在没有许可时阻塞线程；持续自旋检查 `turn` 会无意义占用 CPU，除非题目另有低延迟/自旋约束。
- **重复轮次**：C 每次打印完都把许可归还给 A，形成 A→B→C→A 的闭环；三个线程各循环相同的 `rounds` 次，所以正常完成时不会留下某个线程永远等不到最后一个许可。
- **输出内存**：代码为了可测试性返回完整字符串，所以结果占 `O(rounds)`；若直接流式打印，Semaphore 等同步辅助状态不随轮数增长，是 `O(1)`。
- **中断边界**：来源没有定义取消语义。示例在调用者等待 `join()` 被中断时会中断三个工作线程并向上抛出；如果真实业务要求可靠取消、错误传播或输出动作可能失败，应把取消状态和失败协调作为额外契约设计，而不能假装题目已经要求。
- **替代方案**：`synchronized + wait/notifyAll` 或 `ReentrantLock + Condition` 也能实现。核心不变量都一样：任何时刻只有轮到的角色能完成一次打印，并在完成后把执行权交给下一个角色。

## 原理机制

可以把三个 Semaphore 看成沿 A→B→C→A 环移动的一枚令牌。初始令牌在 A；一次 `acquire` 消耗自己的许可，一次 `release` 把许可交给后继。只要每次打印都发生在“拿到自己的令牌”和“交出下一枚令牌”之间，就不存在两个角色同时拥有可打印资格。这样正确性可以归纳证明：初始只有 A 可打印；假设当前只允许角色 X 打印，X 完成后只释放唯一后继 Y 的许可，因此下一次只能是 Y。循环后得到严格的 `ABC` 重复序列。

## 项目经验版

来源没有真实项目、吞吐量、线程数量或故障数据，不能虚构“线上就是用 Semaphore”。实际工程里我会先问为什么需要多个线程按固定顺序串行执行：如果只是为了输出 ABC，这种并发本身没有吞吐收益，题目的价值主要是验证线程协调机制；如果真实场景是多阶段流水线，还需要结合背压、失败传播、取消、监控和任务队列重新设计，而不是直接照搬三线程示例。

## 常见追问

- 问：为什么 B 线程先启动也不会先打印？答：它的 Semaphore 初始是 0，先调度只会让它阻塞在 `acquire()`；A 释放许可后它才有资格继续。
- 问：为什么三个线程不会死锁？答：正常路径上始终有且只有一枚可推进的许可沿 A→B→C 循环，每个线程执行相同轮数；最后 C 的额外 `a.release()` 不会再被使用，但所有线程已经完成，不会有人等待缺失的许可。
- 问：能不能用 `synchronized`？答：可以。共享 `turn`，在 monitor 中用 `while(turn != mine) wait()`，打印后更新 `turn` 并 `notifyAll()`；要用 `while` 而不是 `if` 重新检查条件。
- 问：这里为什么不用 `volatile turn`？答：Semaphore 已经承担顺序协调；再增加一个轮次变量并不能替代阻塞/唤醒协议。若采用共享 `turn` 方案，则应让它受同一个锁保护，而不是只靠 volatile 复合出等待协议。
- 问：如果要打印很多轮，复杂度是多少？答：一共执行 `3 * rounds` 次打印/许可交接，所以同步与输出动作数量是 `O(rounds)`；示例返回字符串占 `O(rounds)` 结果空间，纯流式输出时同步辅助状态是 `O(1)`。

## 易错点

- 三个 Semaphore 都初始化为 1，导致 A/B/C 都能立即打印，顺序失控。
- 打印后释放错了后继许可，例如 B 又释放 B，自身会连续打印。
- 用 `while(true)` 自旋看轮次，功能可能对但白白消耗 CPU。
- 三个线程循环次数不一致，某个线程提前退出后后继可能永久阻塞。
- 把返回字符串的 `O(rounds)` 结果空间忽略掉，却声称整个实现总空间严格是 `O(1)`。
- 没有定义中断/失败语义，却把一个面试同步示例包装成生产级任务编排方案。
