# MySQL 备份与基于 binlog 的恢复流程

## 核心结论

可靠的 MySQL 容灾不是只留一份备份，而是“可恢复的全量备份 + 连续保留的 binary log + 定期演练”。发生误删或需要回到指定时间点时，先把实例恢复到全量备份的已记录一致性坐标，再从该坐标之后按连续 binlog 文件链重放到误操作前已确认的事件边界；恢复前必须在隔离环境验证目标点和数据范围，避免把错误再次应用到生产。

## 1 分钟版

- 先明确恢复目标：恢复整库、单表，还是回到某个时间点；同时明确可接受的数据丢失窗口和恢复时长。
- 基线备份可选择物理或逻辑方式：物理备份适合大且需要快速恢复的库，逻辑备份适合较小、需编辑数据或跨机器架构恢复的场景。
- 时间点恢复依赖全量备份之后生成的 binlog；起点应是备份工具记录的 binlog 文件与 position（或可靠等效坐标），不能把在线备份的完成时刻当作起点。
- 事故恢复按“停写/隔离 → 恢复全量备份 → 从备份一致性坐标后的连续 binlog 重放到误操作前的事件位置 → 校验数据和应用连接 → 受控恢复流量”执行。时间筛选只用于定位事件，再按 position 重放；真正的最佳实践是可演练的流程与恢复证据。

## 3 分钟版

这题的主线是基线与增量如何衔接。全量备份提供一个已知状态；MySQL 官方定义的 point-in-time recovery 是先恢复该全量备份，再把从备份时刻到目标时刻的数据变更增量应用回来。实际重放的基线要由备份工具保存的最后恢复 binlog 文件/position（或可靠等效坐标）确定，不能用在线备份完成时刻推断。binlog 是这一增量信息源：要支持时间点恢复，服务器必须启用 binary logging，并且需要知道和保留相关 binlog 文件。

备份方式按恢复对象和约束选。物理备份复制保存数据库内容的目录和文件，官方说明它更适合大而重要、需要快速恢复的数据库；逻辑备份保存 DDL 与数据表示，适合较小的数据量、需要编辑数据/表结构，或迁移到不同机器架构的情形。两者不是互斥的“优劣”，而是恢复速度、可移植性和操作粒度的取舍。

PITR 的操作链是：第一，确认最近一个可用全量备份及备份工具记录的最后恢复 binlog 文件/position；在线备份的完成时刻不是可替代的起点。第二，在隔离恢复实例上恢复这份基线。第三，确认基线坐标之后所需 binlog 文件连续可用；用 `mysqlbinlog` 的时间范围只帮助定位误操作附近的事件，再审阅实际 event position。第四，从基线坐标后的事件开始，按连续文件链重放，并在误操作前已确认的 stop position 停止。第五，核对恢复时间点、关键表行数、约束和应用侧一致性，再决定切换。MySQL 文档说明 `mysqlbinlog` 能把二进制日志事件转成文本并按事件时间或位置选择区间，而应用这些事件会重新执行其代表的数据修改；其 position 示例明确 stop position 之前的事务会被恢复。因此基线坐标错、日志缺段、终点误包含或直接在生产试跑，都会使恢复结果不可信。

工程上把恢复当成闭环：备份任务要有成功性、时长、产物位置和可读性监控；binlog 要有保留期与完整链检查；演练要记录从备份恢复到目标点的实际耗时和校验结果。没有这些真实信息时，不能编造 RPO/RTO 或“已成功恢复”的项目故事。

## 关键细节

- MySQL 8.4 文档将时间点恢复定义为：先恢复全量备份，再从备份时刻向目标时刻增量恢复数据变更。
- 若要执行该恢复，相关 binary log 文件必须可用；MySQL 8.4 默认启用 binary logging，但部署仍应实际核对配置和日志保留，而不是仅依赖默认值。
- `SHOW BINARY LOGS` 可列出 binlog 文件，`SHOW BINARY LOG STATUS` 可查看当前 binlog；操作前应在恢复环境确认文件链与目标边界。
- `mysqlbinlog` 可按事件时间或位置选择日志区间；官方示例建议时间选项只用于寻找实际 event position，而用 `--start-position`、`--stop-position` 应用范围，以降低漏事件风险。
- PITR 的三个前提是：备份一致性坐标可靠、从该坐标到目标点的 binlog 无缺段、终点停在误操作前经确认的 event position；任一项不满足，不能宣称已恢复到目标状态。

## 原理机制

恢复状态流为：`备份一致性坐标 S0 → 恢复实例到 S0 → 从 S0 后的连续 binlog events 重放 → 在误操作前 stop position 停止 → 得到目标状态 St`。全量备份及其可靠坐标决定起点，binlog 决定增量，stop position 决定终点；若坐标、日志链或终点中任一项不可靠，就不能证明 `St` 等于预期目标。物理与逻辑备份的成本主要体现在备份/恢复速度、产物大小、可移植性和操作粒度；PITR 额外依赖日志链、目标边界和重放验证。

## 项目经验版

项目映射提示：填写真实备份方式和频率、备份位置及加密/访问控制、binlog 保留策略、最近演练时间、实测 RPO/RTO、恢复校验项、切换与回滚责任人。没有这些事实时，只描述流程，不要声称“我们已实现分钟级恢复”。

## 常见追问

- 问：为什么全量备份不能单独完成误删后的时间点恢复？答：它只能带实例回到备份时刻；备份之后到目标时刻的变更要靠后续 binlog 重放。
- 问：物理备份和逻辑备份怎么选？答：按恢复速度、数据规模、是否需编辑数据/结构、以及目标机器兼容性选择；物理方式偏快速恢复大库，逻辑方式偏可编辑与迁移。
- 问：binlog 为什么要保留完整链？答：PITR 的增量就是备份一致性坐标之后的 binlog 事件；缺段就无法可靠地把基线推进到目标点。
- 问：时间参数能直接作为恢复范围吗？答：MySQL 8.4 的示例建议它们只用于定位实际 event position；应审阅事件后使用 start/stop position，避免时间范围漏事件或包含误操作。
- 问：能直接把 `mysqlbinlog` 输出打到生产吗？答：不应把它当作默认操作。先在隔离恢复环境确定基线坐标、事件边界和结果，因为重放会执行其代表的数据修改。

## 易错点

- 不要把“备份成功”当作“可恢复”：没有恢复演练和校验，就没有证据说明基线、日志链和目标边界可用。
- 不要把全量备份完成时刻当作重放起点；使用备份工具保存的 binlog 文件/position 或可靠等效坐标，PITR 的增量从该坐标之后开始。
- 不要把物理/逻辑备份说成绝对优劣；恢复速度、可移植性、粒度和规模不同。
- 不要承诺固定 RPO、RTO 或恢复效果；这些是部署、保留策略和演练结果，不是 MySQL 文档给出的通用常数。
