# 如何设计一个在 10 万 QPS/OPS 目标下实现毫秒级调用的 RPC 框架？

## 核心结论

我不会先回答“用 Netty + 某个序列化就能到 10 万”。这里有两个来源口径：一个写 **10 万 QPS**，一个写 **10 万 OPS**；它们只有在“每个请求对应多少网络帧、序列化、下游调用和返回操作”被定义后才能换算。毫秒级也必须先指定 **P50/P99/P999**，不能只看平均值。

框架上我会把热路径拆成：

```text
Client Stub
  -> encode
  -> connection/channel pool + request correlation
  -> Netty IO EventLoop
  -> network
  -> Server IO EventLoop
  -> decode
  -> bounded dispatcher/worker
  -> business handler
  -> encode + response
```

控制面则负责：

```text
registry/name resolver
  -> endpoint health
  -> load-balancing policy
  -> per-method deadline/retry policy
  -> rollout/draining
```

性能核心不是某一个组件，而是四个不变量：**连接复用、IO 线程不阻塞、所有队列有界、端到端时间预算可观测**。容量按目标环境压测出的“单实例安全吞吐”计算，并扣除故障域和容量余量；序列化、native transport、连接数、线程数都只能通过真实 workload profiling 决定。

## 1 分钟版

1. **先定义目标**：区分 10 万 QPS 与 10 万 OPS，明确 unary/streaming 比例、请求/响应大小、P99 延迟目标和业务 handler 成本，再做容量预算。
2. **数据面走短热路径**：长连接/多路复用，Netty EventLoop 只做 IO、轻量编解码和状态推进；阻塞业务、磁盘和下游 RPC 放到独立有界 worker，避免一个慢请求拖住整条 IO loop。
3. **协议和序列化版本化**：帧头至少有 request_id、method、codec/version、deadline 等；序列化选择以真实 payload 的字节数、CPU、分配和兼容性压测为准，不预设某个 codec 永远最快。
4. **治理进入框架**：注册发现、健康状态、负载均衡、deadline、有限重试、幂等边界、限流/过载保护统一配置；不能让业务代码各自重试，形成放大流量。
5. **证明而不是宣称**：看 per-method QPS/OPS、P50/P95/P99/P999、encode/decode、IO-loop lag、worker queue、in-flight、连接 churn、retry amplification、GC 和下游延迟，再用压测、故障注入和滚动升级验证容量与尾延迟。

## 3 分钟版

### 1. 先把“10 万 + 毫秒级”变成可验证契约

先补齐：

```text
traffic_mix        = unary / streaming / oneway 的占比
request_bytes      = P50 / P99
response_bytes     = P50 / P99
target_rate        = 100k QPS 或 100k OPS
latency_slo        = 例如 P99 < X ms（X 必须由题目/业务给出）
handler_cost       = CPU / DB / cache / downstream RPC
connection_count   = 长连接数量级
availability       = 单机/单 AZ/跨 AZ 故障时还要保多少容量
```

如果 10 万 OPS 指的是“网络读写 + 编解码 + 下游调用”等操作总量，它不能直接当 10 万业务请求；反过来也一样。因此我只把来源里的 10 万当目标，不虚构节点数或单机吞吐。

容量计算写成：

```text
safe_qps_per_instance = target-environment load test result at latency/error/CPU/GC gates
required_instances    = ceil(target_qps / safe_qps_per_instance)
provisioned_instances = ceil(required_instances / surviving_capacity_ratio * headroom_factor)
```

`surviving_capacity_ratio` 用来覆盖预期故障域，`headroom_factor` 由容量策略定义。这里不代入虚构数字。

### 2. Client：Stub + Resolver + Channel Manager

业务只看到类似：

```java
UserReply reply = userService.getUser(req, CallOptions.deadline(...));
```

Stub 不直接 `new Socket`，而是：

```text
method metadata
 -> name resolver 得到 endpoint set
 -> health/ready filter
 -> load balancer 选择 subchannel
 -> connection/channel 复用
 -> request_id 注册 in-flight promise
 -> encode/send
 -> response 按 request_id 唤醒 future
```

连接应复用，不能每个请求都 TCP/TLS connect。若协议支持多路复用，一条连接可以承载多个并发 in-flight；但每连接允许多少并发仍要有上限，避免单连接队列无限增长。

### 3. Server：IO EventLoop 与业务执行隔离

Netty 适合把大量连接的 IO 状态推进放到少量 event-loop 线程上。关键规则是：**event loop 上不能做不可控阻塞工作**。

服务端路径：

```text
socket read
 -> frame decode
 -> protocol validation
 -> deadline/admission check
 -> dispatcher
 -> bounded worker / async handler
 -> response encode
 -> socket write
```

如果业务 handler 在 IO loop 上同步查数据库 30 ms，那么即使网络栈很快，同一 loop 负责的其他 channel 也会一起排队，P99 会先恶化。因此要分别观察：

```text
io_loop_utilization
io_loop_task_lag
worker_active
worker_queue_depth
in_flight_requests
```

worker 也不能无界。达到容量门槛时应该快速拒绝/限流/降级，而不是把 50 ms 的排队藏在“毫秒级 RPC”里。

### 4. 协议帧与请求相关性

一个通用二进制帧可抽象为：

```text
magic | protocol_version | flags | request_id
method/service | codec | body_length | metadata | body
```

其中：

- `request_id`：关联异步响应；
- `protocol_version` / `codec`：支持协议与序列化演进；
- `body_length`：做帧边界与最大包保护；
- metadata：承载 deadline、trace、鉴权等受控元数据。

必须限制最大 frame/body、metadata 大小和 in-flight 数，否则攻击流量或误用会把连接内存打满。

### 5. 序列化：看总成本，不做“最快算法”口号

来源明确提到序列化，但没有给 payload 类型。我的选择流程是：

```text
兼容性/跨语言
 -> schema 演进
 -> bytes on wire
 -> encode/decode CPU
 -> allocation/GC
 -> zero-copy/copy count
 -> 调试可观测性
```

对于候选 Protobuf/Kryo/Hessian/自定义 codec，都用真实消息分布压测；即使某个 codec 微基准快，如果产生更多临时对象、包更大或 schema 演进困难，也可能让整体 P99 更差。

codec 必须版本化，灰度期间允许新旧双方协商/兼容，而不是一次升级让所有客户端一起失败。

### 6. 注册发现、健康与负载均衡分开

三件事不能混成一个“服务治理”词：

```text
resolver:       现在有哪些 endpoint
health/ready:   哪些 endpoint 当前应接新流量
load balancer:  在 eligible endpoints 中选哪个
```

负载均衡至少考虑：

- round-robin/weighted 等静态策略；
- active requests / observed latency 等动态信号；
- locality / AZ；
- outlier ejection；
- 慢启动，避免刚上线实例瞬间吃满流量。

不能把“最小延迟”写成固定真理，因为采样延迟本身有滞后并可能造成羊群效应。策略要可配置、可灰度并可观测 endpoint skew。

### 7. Deadline、取消与重试必须共享一个时间预算

每次调用都应该有 deadline：

```text
caller budget = queue + encode + network + server queue + handler + response
```

如果还剩 2 ms，就不应该在下游再开一个 50 ms 默认超时。

重试必须满足：

```text
retryable error
AND remaining deadline > next attempt budget
AND retry budget available
AND method is safe/idempotent or has idempotency key
```

禁止框架默认“失败就重试 3 次”。当服务已过载时，这会把 10 万流量放大成更多 attempt。监控要区分 logical QPS 和 attempt OPS。

### 8. Backpressure 与过载保护

对于 streaming，发送速度超过接收速度时要靠 flow control/backpressure，不能无限 buffer。

对于 unary，也需要类似原则：

```text
max_in_flight_per_connection
max_in_flight_per_client
max_worker_queue
max_global_in_flight
```

超过阈值后：

```text
reject fast
 -> client respects deadline/retry budget
 -> optional fallback/degrade
```

而不是：

```text
accept everything
 -> queue grows
 -> P99 explodes
 -> clients timeout and retry
 -> retry storm
```

### 9. Netty transport 与线程模型

当前 Netty 4.2 的 IO 抽象允许通过 `MultiThreadIoEventLoopGroup` 等结构组织多 event loop；Linux 等平台也可评估 native transport。native transport 可能减少垃圾并改善某些 workload，但它是可测的部署优化，不是“换 epoll/io_uring 就一定 1 ms”。

线程数按 profiling 调整：

- 太少：event-loop utilization/lag 上升；
- 太多：调度、cache miss 和上下文切换增加；
- 真正阻塞工作如果混进 IO loop，再多 IO 线程也只是掩盖问题。

### 10. 故障、滚动升级和连接生命周期

需要覆盖：

- registry 短暂不可用；
- endpoint 失联/健康变差；
- client-server 连接断开；
- server 过载；
- codec/protocol 版本不兼容；
- 下游超时；
- 单 AZ 容量损失；
- 滚动发布造成大量 reconnect。

滚动升级时：

```text
instance marked draining/not-ready
 -> resolver/health 不再给它新流量
 -> existing in-flight bounded drain
 -> deadline 到后 force close
 -> process exit
```

客户端 reconnect 使用 backoff + jitter，避免一批连接同时重建。Keepalive 只证明连接层还在，不等于业务方法健康；业务 health/readiness 要单独治理。

### 11. 可观测和压测

每个 method 至少看：

```text
logical_qps / attempt_ops
success/error/status
P50/P95/P99/P999 latency
client_queue / server_queue
encode/decode latency + allocation
io_loop utilization/lag
worker utilization/queue
active_connections / connection_churn
in_flight
retry_rate / retry_amplification
payload_bytes
GC pause / allocation rate
endpoint load skew
downstream latency/error
```

压测至少做四类：

1. 正常 mixed workload；
2. 大包/小包、热点 method、慢 handler；
3. 单实例/单 AZ 故障与 reconnect；
4. 过载 + timeout + retry 组合。

只有在目标环境里这些测试仍满足 latency/error/resource gate，才能说“证明了 10 万目标”。

## 关键细节

- **QPS ≠ OPS**：必须先定义一个业务请求会触发多少框架/网络操作。
- **平均延迟不够**：毫秒级目标要指定 P99/P999 等尾延迟。
- **连接复用是热路径基础**：每请求建连会把握手与内核资源成本带入每次调用。
- **IO loop 不阻塞**：业务 handler、磁盘、DB、慢下游应隔离到异步/worker 边界。
- **队列必须有界**：无界 queue 只是把过载变成延迟雪崩和 OOM 风险。
- **in-flight 要有上限**：既是内存边界，也是下游保护边界。
- **deadline 是端到端预算**：不是每一跳都重新给一个完整 timeout。
- **重试会制造额外 OPS**：容量模型必须统计 attempt，而不只统计 logical request。
- **幂等是业务语义**：框架不能因为有 request_id 就自动让有副作用的方法可安全重放。
- **resolver、health、LB 是三层**：发现 endpoint、判断可接流量、选择 endpoint 的职责不同。
- **序列化必须版本化**：性能之外还要考虑 schema 演进和灰度兼容。
- **native transport 是优化项**：必须用目标 workload 验证，不是固定性能保证。
- **keepalive 不等于 health**：连接能响应 PING 不代表业务服务能正确处理请求。
- **draining 防止升级抖动**：先摘流量再排空 in-flight，减少发布期间的尾延迟和失败。

## 原理机制

RPC 的低延迟可以看成一个排队系统：

```text
T_total
= T_client_queue
+ T_encode
+ T_client_io_queue
+ T_network_req
+ T_server_io_queue
+ T_decode
+ T_worker_queue
+ T_handler
+ T_encode_resp
+ T_network_resp
```

框架能够直接控制的不是业务 `T_handler`，而是尽量让其他项**有界、可观测、不过载**。

核心状态机是：

```text
request created
 -> deadline/admission check
 -> endpoint selected
 -> in-flight registered(request_id)
 -> frame queued/sent
 -> server accepted
 -> handler executed
 -> response correlated
 -> promise complete
```

异常路径：

```text
connect failure / unhealthy endpoint / timeout / server overload
 -> classify error
 -> cancel work where possible
 -> consult retry + idempotency + remaining budget
 -> retry another eligible endpoint OR fail fast
```

正确性和性能依赖这些不变量：

1. 一个 `request_id` 的 response 只能完成对应 in-flight 调用；迟到响应不能污染新请求。
2. IO event loop 不执行不可控阻塞任务。
3. 每层 pending/in-flight 有明确上限，过载可被拒绝而不是无限排队。
4. deadline 随调用链消耗，不能在每跳重置。
5. retry 受 attempt、时间和幂等预算限制。
6. endpoint 下线时先停止接新流量，再有界排空已有请求。
7. 协议/codec 版本可兼容迁移，不依赖全量同时升级。
8. 所谓“10 万 + 毫秒级”最终由端到端压测证明，而不是由某个组件名称证明。

## 项目经验版

来源没有给真实系统的节点数、CPU、payload、P99、框架实现、线上故障或个人职责，因此这里不能编造“我们线上 8 台机器做到 10 万 QPS”。

真实项目映射时，我会先收集：

```text
method traffic distribution
request/response size distribution
current P50/P99/P999
connection count
encode/decode CPU and allocation
io-loop utilization/lag
worker queue and handler time
downstream latency
retry amplification
GC profile
endpoint skew
```

然后做 flame graph / allocation profile / packet-size / queue-time 分解，先找最大项。常见优化顺序不是“换一个更快 codec”固定答案，而可能是：

```text
去掉每请求建连
 -> 把阻塞任务移出 IO loop
 -> 限制/拆分队列
 -> 优化 handler/downstream
 -> 减少复制和分配
 -> 优化 codec
 -> 评估 native transport
```

每一步都用同一 workload 回归 P99、错误率和资源占用，避免吞吐提升但尾延迟或 GC 变差。

上线采用 canary：

```text
1% client/service traffic
 -> compare latency/error/retry/CPU
 -> 逐步扩大
 -> 保持前一协议/codec version 可回退
 -> 滚动时 graceful drain
```

## 常见追问

- 问：为什么 Netty event loop 不能直接执行业务逻辑？
  答：它通常同时服务多个 channel。一个不可控的阻塞 handler 会让同一 loop 上其他连接一起排队，影响尾延迟；轻量、确定性的状态推进可以留在 IO loop，阻塞/慢任务要隔离。

- 问：10 万 QPS 要多少台机器？
  答：题目没有给 payload、handler 成本和硬件，不能直接报台数。先在目标环境测出满足 P99/error/CPU/GC gate 的 `safe_qps_per_instance`，再按故障域和 headroom 计算实例数。

- 问：为什么不能默认失败就重试三次？
  答：过载时重试会放大 OPS，并进一步恶化延迟。重试必须受 retryable error、剩余 deadline、attempt budget 和幂等语义约束。

- 问：序列化选 Protobuf 还是 Kryo？
  答：先看跨语言/schema 演进，再对真实 payload 测 bytes、encode/decode CPU、allocation 和 P99。没有 workload 就不能把任何一个写成通用性能冠军。

- 问：长连接很多时 Netty 线程是不是越多越好？
  答：不是。线程过少会造成 event-loop lag，过多会增加调度和 cache 成本。应通过 loop utilization/lag、CPU、上下文切换和连接分布压测选择，而不是按连接数一比一配线程。

- 问：服务发现和负载均衡有什么区别？
  答：发现解决“有哪些 endpoint”，health/readiness 解决“哪些现在可接流量”，负载均衡解决“本次从 eligible endpoint 里选谁”。把三者拆开才便于治理和故障处理。

- 问：如何避免滚动发布时大量 RPC 失败？
  答：实例先进入 draining/not-ready，停止接收新调用，让已有 in-flight 在 deadline 内完成，再 force close；客户端 reconnect 要 backoff + jitter，避免连接风暴。

- 问：为什么有 keepalive 还需要 health check？
  答：keepalive 主要看连接是否还活着，业务进程可能连接正常但线程池、依赖或特定服务已不可用。调用路由需要独立 readiness/health 信号。

- 问：怎么证明“毫秒级”？
  答：固定目标 percentile 和 workload，分解 client queue、codec、network、server queue、handler、response 等各段，并在正常、热点、过载、故障和发布场景下验证 P99/P999，而不是只看单机平均值。

## 易错点

- 把 10 万 OPS 和 10 万 QPS 当成同一个指标。
- 只说“Netty + Protobuf/Kryo”就认为性能设计完成。
- 用平均延迟代替 P99/P999。
- 每次 RPC 都建 TCP/TLS 连接。
- 在 event loop 上同步查数据库、磁盘或慢下游。
- worker/in-flight queue 无界，靠“多排队”承接流量峰值。
- 每一跳重新设置完整 timeout，导致端到端 deadline 失效。
- 框架默认无限/固定次数重试，却不检查幂等和 retry budget。
- 把 keepalive 当业务健康检查。
- 把 registry、health 和 load balancing 混成一个黑盒。
- 认为 native transport 一定比 NIO 快且一定能达到固定吞吐。
- 只测 codec 微基准，不测真实 payload 和整体 P99/GC。
- 下线实例直接 kill，不做 graceful drain。
- 压测只做稳态，不做 endpoint 故障、过载和重试放大。
- 用虚构的阿里/字节/银行线上节点数或延迟数据支撑方案。
