# MySQL 的事务隔离级别有哪些？默认是什么？

## 核心结论

InnoDB 支持四个事务隔离级别，按隔离强度从低到高是：

```text
READ UNCOMMITTED
→ READ COMMITTED
→ REPEATABLE READ
→ SERIALIZABLE
```

MySQL/InnoDB 的默认隔离级别是 **REPEATABLE READ（RR）**。

真正需要理解的是 RC 和 RR 的快照差异：在 `READ COMMITTED` 下，每一次一致性非锁定读都会建立新的快照；在 `REPEATABLE READ` 下，同一事务中的一致性非锁定读复用第一次一致性读建立的快照。因此同一事务里重复执行普通 `SELECT`，RC 可能看到其他事务后来提交的结果，而 RR 通常仍看到同一快照。

## 1 分钟版

- `READ UNCOMMITTED`：隔离最低，普通读取可能看到未提交的数据，也就是脏读。
- `READ COMMITTED`：只看已经提交的数据；但每次一致性读都会拿新的快照，所以同一事务两次普通 `SELECT` 可能结果不同。
- `REPEATABLE READ`：InnoDB 默认级别；同一事务的一致性非锁定读使用第一次一致性读建立的快照，重复读取更稳定。
- `SERIALIZABLE`：比 RR 更严格；在 `autocommit=0` 时，InnoDB 会把普通 `SELECT` 隐式转换成 `SELECT ... FOR SHARE`，因此锁和等待更多，并发度更低。
- 不要把“RR 防幻读”背成绝对结论：普通一致性读走 MVCC 快照；`SELECT ... FOR UPDATE/FOR SHARE`、`UPDATE`、`DELETE` 等锁定访问是另一条路径，范围访问还可能使用 gap/next-key locking。

面试一句话：**MySQL/InnoDB 四级隔离，默认 RR；RC 是每次读新快照，RR 是事务内复用首次一致性读快照，Serializable 再进一步增加锁定和串行化。**

## 3 分钟版

### 1. READ UNCOMMITTED

这是隔离最弱的一档。

普通读取可能看到别的事务还没有提交的数据，因此可能发生 dirty read：

```text
T1: UPDATE account SET balance = 0;   -- 未提交
T2: SELECT balance ...                -- RU 下可能读到 0
T1: ROLLBACK;
```

如果 T2 已经基于这个中间状态做了业务判断，就使用了一个后来根本不存在的提交结果。

所以 RU 通常只适合非常特殊、能够接受不一致读取的场景，不能为了“少一点锁”就默认使用。

### 2. READ COMMITTED

RC 的关键是：

```text
每一次 consistent read
→ 创建自己的 fresh snapshot
```

例如：

```text
T1: BEGIN;
T1: SELECT value FROM t WHERE id = 1;  -- 读到 10

T2: UPDATE t SET value = 20 WHERE id = 1;
T2: COMMIT;

T1: SELECT value FROM t WHERE id = 1;  -- RC 下可以读到 20
```

两次 `SELECT` 都只读已提交版本，但第二次可以看见 T2 新提交的版本。

这就是为什么 RC 可以避免脏读，却不保证“同一事务里普通查询重复读取一定相同”。

### 3. REPEATABLE READ

RR 是 InnoDB 默认隔离级别。

对于普通一致性非锁定读：

```text
事务第一次 consistent read
→ 建立 read view / snapshot
→ 后续 consistent read 复用这个 snapshot
```

例如：

```text
T1: BEGIN;
T1: SELECT value FROM t WHERE id = 1;  -- 建立快照，读到 10

T2: UPDATE t SET value = 20 WHERE id = 1;
T2: COMMIT;

T1: SELECT value FROM t WHERE id = 1;  -- RR 普通一致性读仍按原快照看
```

这就是 RR 的“可重复读”核心机制：InnoDB 用多版本数据让普通 `SELECT` 读取事务自己的快照，而不是靠把所有被读行一直锁死。

但这里必须再加一个边界：

```text
普通 SELECT（consistent nonlocking read）
≠
SELECT ... FOR UPDATE / FOR SHARE
≠
UPDATE / DELETE 等锁定读写
```

锁定读要读取并锁住可修改的当前记录。RR 下对于范围条件，InnoDB 可能使用 record lock、gap lock、next-key lock，阻止其他事务在受保护范围插入冲突记录。

所以“RR 如何处理幻读”不能只用一句“MVCC 解决幻读”概括：普通快照读的重复结果来自 snapshot；需要当前数据并加锁的范围读/写则依赖锁定策略。

### 4. SERIALIZABLE

`SERIALIZABLE` 比 RR 更严格。

在 `autocommit` 关闭时，InnoDB 会把普通：

```sql
SELECT ...
```

隐式当成：

```sql
SELECT ... FOR SHARE
```

来处理。

效果是读写之间的互斥/等待更多，更接近串行执行，但代价是并发能力下降。所以它一般不是高并发业务的默认选择。

### 5. 默认值和配置范围

MySQL 的 `transaction_isolation` 支持：

```text
READ-UNCOMMITTED
READ-COMMITTED
REPEATABLE-READ
SERIALIZABLE
```

默认值是：

```text
REPEATABLE-READ
```

但“默认是 RR”不代表线上某个连接当前一定是 RR，因为隔离级别可以在 global、session 或 next transaction 范围设置。排查真实系统时要查当前连接实际配置，而不是只背默认值。

## 关键细节

- **InnoDB 默认 RR**，这是面试最常问的第二问。
- **RC 和 RR 最值得比较的是 read view 创建时机**：RC 每次一致性读新快照；RR 事务内第一次一致性读建立快照，后续复用。
- **consistent read 和 locking read 要分开**。普通 `SELECT` 通常走 MVCC 快照；`FOR UPDATE/FOR SHARE` 是锁定读。
- **RR 的锁定范围访问可能使用 next-key/gap locking**，所以不要把所有 RR 行为都解释成“只靠 MVCC”。
- **Serializable 会牺牲并发换更强隔离**，不要把“隔离越高越好”当成无成本结论。
- **隔离级别不是所有并发正确性的替代品**。例如“查余额→在应用里计算→再更新”的 read-modify-write 是否正确，还取决于锁、条件更新、版本号或业务协议。
- **当前连接的实际隔离级别可能被改过**。默认 RR 只是默认配置，不是运行时事实证明。

## 原理机制

隔离级别本质是在回答：

```text
一个事务什么时候、以什么版本视图看到别的事务的变化？
以及需要修改当前数据时，要锁住多大的冲突范围？
```

InnoDB 的 RC/RR 之所以表现不同，核心在 read view 生命周期：

```text
READ COMMITTED
statement 1 -> snapshot A
statement 2 -> snapshot B
statement 3 -> snapshot C

REPEATABLE READ
first consistent read -> snapshot A
later consistent reads -> snapshot A
```

这解释了“为什么 RC 同一事务两次读取可能不同，而 RR 可以重复读取”。

另一方面，一致性快照读并不能替代写入冲突保护。需要“读取当前值并准备修改”时，InnoDB 提供 locking read；范围锁还要考虑新记录插入到查询区间的问题。因此完整理解应该是：

```text
MVCC / read view
负责版本可见性

record / gap / next-key locking
负责锁定访问的并发冲突范围
```

隔离级别改变的是这些机制怎样组合，而不是简单地“等级越高，多加几个锁”。

## 项目经验版

来源没有提供真实项目经历，不能编造“线上从 RR 改成 RC 后 TPS 提升多少”。

真实系统里如果遇到长事务、锁等待或“为什么同一个事务两次查询结果不一样”，我会先确认：

```sql
SELECT @@transaction_isolation;
```

然后区分当前 SQL 是：

```text
普通一致性 SELECT
还是
FOR UPDATE / FOR SHARE / UPDATE / DELETE
```

再看事务边界、索引命中范围和锁等待。只有确认 workload 后，才能判断是否需要调整隔离级别；不能把“RC 并发高”或“RR 更安全”当成直接改配置的理由。

## 常见追问

- 问：MySQL 默认隔离级别是什么？
  答：InnoDB/MySQL `transaction_isolation` 的默认值是 `REPEATABLE-READ`，但 session 或单个事务可以覆盖，所以真实排查要看当前连接设置。

- 问：RC 和 RR 最大区别是什么？
  答：对普通一致性非锁定读，RC 每次读取创建新快照；RR 在事务第一次一致性读建立快照，后续一致性读复用它。

- 问：RR 是不是完全不会出现幻读？
  答：不能这么绝对说。InnoDB 普通一致性读靠同一快照得到稳定视图；锁定范围读/写则使用 record/gap/next-key locking 保护范围。不同访问路径要分别分析。

- 问：为什么 RR 不需要把普通 SELECT 的所有行都一直锁住？
  答：因为一致性非锁定读可以通过 MVCC/read view 读取旧版本快照；它的重复性来自版本可见性，不是普通 SELECT 持有排他锁。

- 问：Serializable 为什么并发低？
  答：它比 RR 更强地把读取纳入锁定/串行化；在 autocommit 关闭时普通 SELECT 会被当成 `SELECT ... FOR SHARE`，更容易产生等待。

- 问：隔离级别越高越好吗？
  答：不是。更强隔离通常意味着更少并发、更高锁等待风险。要按一致性要求、事务长度、冲突概率和性能目标选择。

- 问：隔离级别能避免所有 lost update 吗？
  答：不能把应用层 read-modify-write 正确性全部交给隔离级别。是否会覆盖更新还要看 SQL 形式、是否锁定读取、条件更新/版本控制等并发协议。

## 易错点

- 漏掉 `READ UNCOMMITTED` 或 `SERIALIZABLE`，只会背 RC/RR。
- 忘记 InnoDB 默认是 `REPEATABLE READ`。
- 把 RC 说成“事务开始时生成一次快照”；InnoDB RC 是每次一致性读建立新快照。
- 把 RR 说成“事务 BEGIN 时一定立刻创建 read view”；更准确的是第一次一致性读建立快照，除非使用显式 consistent snapshot 等特殊开始方式。
- 把普通 `SELECT` 和 `SELECT ... FOR UPDATE` 当成完全一样的读取路径。
- 说“RR 防幻读完全只靠 MVCC”或“完全只靠 next-key lock”，忽略快照读和锁定读是两套不同机制。
- 认为 Serializable 没有并发代价。
- 看见默认 RR 就断定某条线上连接当前也是 RR，而不检查 session/transaction override。
- 认为隔离级别自动保证任何业务 read-modify-write 都不会丢更新。
