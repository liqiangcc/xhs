# LeetCode 115：不同的子序列——计数型字符串 DP

## 核心结论

仓库有两条来源共同归一到这个 Canonical：一条明确保留“LeetCode 115 - DP”，另一条进一步保留“给定字符串 s 和 t，计算 s 的子序列中等于 t 的个数，并分析时间复杂度、提供空间优化方案”。因此题意可以回到官方问题契约核对：给定字符串 `s` 和 `t`，统计 `s` 的多少个不同**下标选择方案**形成的子序列恰好等于 `t`；官方测试保证最终答案落在 32 位有符号整数范围内。这里的“不同”是选择了不同的源下标，不是把得到的字符串值去重。

最直接的状态是 `dp[i][j] = s[0..i) 形成 t[0..j) 的方案数`。如果 `s[i-1] != t[j-1]`，当前字符不能用，只能继承 `dp[i-1][j]`；如果相等，可以不用当前字符，也可以把它作为 `t[j-1]`，所以 `dp[i][j] = dp[i-1][j] + dp[i-1][j-1]`。空间压缩成一维后，`j` 必须从右往左更新，否则同一个 `s[i]` 会在本轮被重复使用。

## 1 分钟版

- 定义 `dp[j]`：扫描到当前 `s` 前缀后，形成 `t` 前 `j` 个字符的方案数。
- `dp[0] = 1`：任何 `s` 前缀形成空串都有一种方法——什么都不选。
- 扫描一个 `s[i]` 时，如果它等于 `t[j-1]`，新增方案就是此前形成 `t[0..j-1)` 的所有方案，因此 `dp[j] += dp[j-1]`。
- `j` 必须**倒序**。正序会先修改 `dp[j-1]`，再拿这个“已经用过当前字符”的新值去更新 `dp[j]`，等价于让同一个源字符被选两次。
- 时间复杂度 O(|s|·|t|)，空间 O(|t|)。如果 `|t| > |s|` 可以直接返回 0。这正面覆盖第二条来源要求的复杂度分析与空间优化。
- 官方只保证最终答案是 32 位整数；为避免未证明的中间计数溢出，下面实现把中间值安全饱和到 `Integer.MAX_VALUE + 1`，最后在官方契约下再转成 `int`。

## 3 分钟版

```java
public final class Solution {
    private static final long LIMIT = (long) Integer.MAX_VALUE + 1;

    public int numDistinct(String s, String t) {
        if (s == null || t == null) {
            throw new IllegalArgumentException("s/t must not be null");
        }
        if (t.length() > s.length()) return 0;

        long[] dp = new long[t.length() + 1];
        dp[0] = 1;

        for (int i = 0; i < s.length(); i++) {
            int upper = Math.min(t.length(), i + 1);
            for (int j = upper; j >= 1; j--) {
                if (s.charAt(i) == t.charAt(j - 1)) {
                    dp[j] = Math.min(LIMIT, dp[j] + dp[j - 1]);
                }
            }
        }

        if (dp[t.length()] > Integer.MAX_VALUE) {
            throw new ArithmeticException("result exceeds official 32-bit contract");
        }
        return (int) dp[t.length()];
    }
}
```

例如 `s="rabbbit"`、`t="rabbit"` 的答案是 3；`s="babgbag"`、`t="bag"` 的答案是 5。每一条计数都对应一组严格递增的 `s` 下标。

## 关键细节

- **状态含义一定要说清楚**：统计的是“下标选择方案”，所以源字符串里值相同的两个字符如果位置不同，选择它们形成的是不同方案。
- **为什么 `dp[0]=1`**：空目标只有“不选任何字符”这一种形成方式。这也是递推中匹配第一个目标字符时 `dp[1] += dp[0]` 的来源。
- **为什么倒序**：二维转移只允许从上一行 `i-1` 读取。倒序更新一维数组时，`dp[j-1]` 尚未被当前 `s[i]` 改写，因此仍等价于上一行；正序会破坏这个不变量。
- **为什么可以饱和而不影响官方合法答案**：所有转移都是非负计数的“保留或相加”，没有减法。某个中间状态一旦真实值超过 `Integer.MAX_VALUE`，以后只会保持或增加。如果这个超大状态后来对最终状态有正贡献，最终答案也必然超过官方承诺；若它永远不贡献，保留其精确巨大值也没有意义。因此把中间值截到 `MAX+1` 能防止 `long` 也被组合数撑爆，同时仍精确得到所有官方合法的最终答案。
- **`t` 比 `s` 长**：不可能通过删除字符让序列变长，直接返回 0。
- **空串**：官方约束要求 `s/t` 长度至少 1；实现仍自然支持空目标返回 1、空源对非空目标返回 0，这是 DP 边界的泛化，不应反过来冒充官方输入约束。
- **复杂度**：二维原始 DP 是 O(|s|·|t|) 时间和 O(|s|·|t|) 空间；只依赖上一行后，一维倒序滚动把额外空间降到 O(|t|)，时间仍为 O(|s|·|t|)。

## 原理机制

对于二维状态 `F(i,j)`，考虑源前缀最后一个字符 `s[i-1]`。任何形成 `t[0..j)` 的合法选择，要么**不选**这个字符，于是方案已经包含在 `F(i-1,j)`；要么**选**它作为目标最后一个字符，这只有在 `s[i-1] == t[j-1]` 时才合法，并且前面必须从 `s[0..i-1)` 形成 `t[0..j-1)`，共有 `F(i-1,j-1)` 种。这两个集合按“是否选择下标 i-1”互斥且覆盖全部方案，因此相加不会重不漏。

一维压缩不是改变递推，而只是复用二维表的一行内存。倒序让右侧状态继续读取“上一行”的左邻居；可以把它理解成保持一个数据依赖拓扑。如果写成正序，`dp[j-1]` 已经包含当前字符带来的新方案，当前字符就会穿过同一行再次参与 `dp[j]`，违反子序列每个源下标最多选择一次的定义。

## 项目经验版

来源没有真实项目背景，不能虚构“线上用过这道 DP”。如果这类计数逻辑进入业务，我会先冻结“不同”的身份语义（按位置、按值还是按对象 ID）、结果上界和溢出策略，再用一个小规模穷举 oracle 对随机/全量小输入交叉验证优化后的 DP；只有状态定义和计数身份一致，性能优化才有意义。

## 常见追问

- 问：为什么匹配时不是只写 `dp[j] = dp[j-1]`？答：因为当前字符可以选，也可以不选；不选的旧 `dp[j]` 方案仍然有效，所以要把两部分相加。
- 问：为什么正序一定错？答：正序时更新 `dp[j]` 读到的 `dp[j-1]` 可能已经使用了当前 `s[i]`，于是同一个源下标会在一次扫描里贡献多次；倒序保证读到的是上一轮状态。
- 问：和最长公共子序列有什么区别？答：LCS 优化的是长度，状态转移取 `max`；本题固定目标 `t`，统计所有形成它的下标方案，转移做计数相加。
- 问：能不能用递归 + 记忆化？答：可以，状态仍是 `(i,j)`，每个状态最多计算一次，渐进复杂度也是 O(|s|·|t|)；迭代 DP 更容易做一维空间压缩且没有深递归栈。
- 问：官方说最终答案不超过 int，为什么还不直接用 int？答：最终状态有上界，不等于所有目标前缀的中间组合数都已经被证明有相同上界。饱和计数只多用 `long`，可以把这个未证明的中间溢出风险显式关掉。
- 问：空间优化为什么必须倒序而不是正序？答：因为二维递推读取的是上一行的 `F(i-1,j-1)`；倒序可在原数组里保留这个旧值直到被使用，正序会提前覆盖它。

## 易错点

- 把“不同子序列”理解成对最终字符串内容去重，而不是不同下标选择。
- 一维 DP 从左往右更新，导致一个源字符在同一轮被重复使用。
- 忘记 `dp[0]=1`，于是第一个目标字符永远无法获得计数。
- 匹配时覆盖旧 `dp[j]`，丢掉“不使用当前字符”的方案。
- 只因为官方最终答案 fits int，就未经证明地宣称所有中间前缀计数也不会溢出。
- 只给二维 DP，不回答第二条来源明确要求的时间复杂度与空间优化方案。
