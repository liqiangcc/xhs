# 结合 Java 代码演练如何避免死锁：锁顺序、超时锁与 TryLock

## 核心结论

这道题要把两类策略分开：**统一锁顺序**是结构性预防——所有线程对同一组资源都按一个稳定、唯一的全序获取锁，就无法形成“你等我、我等你”的锁获取环；**带超时的 `tryLock`**是失败控制——一次拿不齐所需锁就在预算内失败并释放已持有锁，从而避免该次调用无限等待，但反复同节奏重试仍可能饥饿或活锁。下面以 Java 21 `ReentrantLock` 给出两个可编译实现，并把释放、超时和中断边界写进契约。

## 1 分钟版

- **锁顺序**：为资源定义稳定且唯一的 `orderKey`；无论业务请求是 `A→B` 还是 `B→A`，都先锁较小 key，再锁较大 key。所有参与者遵守同一全序时，循环等待被破坏。
- **释放必须在 `finally`**：只释放当前线程确实拿到的锁；第二把锁或临界区抛异常时也不能泄漏第一把锁。
- **超时 `tryLock`**：给“两把锁全部拿到”一个总等待预算。第一把耗掉的时间要从第二把的剩余预算扣除；拿不到就返回失败并回滚本次持锁。
- **边界**：`tryLock(timeout, unit)` 在 Java 21 中可因超时返回 `false`，也可因中断抛 `InterruptedException`。超时不是公平性保证；若上层重试，应限制次数并配合退避/抖动和监控。

## 3 分钟版

这里不虚构具体转账或业务模型，最小输入是两个可加锁资源和一个临界区 `Runnable`。`Resource.orderKey` 必须在参与同一锁域的不同资源之间唯一且稳定；若两个不同资源 key 相同，直接拒绝，因为这时“全序”没有定义完整。

```java
import java.util.Objects;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public final class DeadlockAvoidance {
    public static final class Resource {
        final long orderKey;
        final ReentrantLock lock = new ReentrantLock();

        public Resource(long orderKey) {
            this.orderKey = orderKey;
        }
    }

    public static void withOrderedLocks(Resource a, Resource b, Runnable critical) {
        Objects.requireNonNull(a);
        Objects.requireNonNull(b);
        Objects.requireNonNull(critical);
        if (a == b) {
            a.lock.lock();
            try {
                critical.run();
            } finally {
                a.lock.unlock();
            }
            return;
        }
        if (a.orderKey == b.orderKey) {
            throw new IllegalArgumentException("distinct resources need unique orderKey");
        }
        Resource first = a.orderKey < b.orderKey ? a : b;
        Resource second = first == a ? b : a;
        first.lock.lock();
        try {
            second.lock.lock();
            try {
                critical.run();
            } finally {
                second.lock.unlock();
            }
        } finally {
            first.lock.unlock();
        }
    }

    public static boolean withTimedLocks(
            Resource first,
            Resource second,
            long timeout,
            TimeUnit unit,
            Runnable critical) throws InterruptedException {
        Objects.requireNonNull(first);
        Objects.requireNonNull(second);
        Objects.requireNonNull(unit);
        Objects.requireNonNull(critical);
        if (timeout < 0) throw new IllegalArgumentException("timeout must be >= 0");

        long budget = unit.toNanos(timeout);
        long start = System.nanoTime();
        boolean firstHeld = false;
        boolean secondHeld = false;
        try {
            firstHeld = first.lock.tryLock(budget, TimeUnit.NANOSECONDS);
            if (!firstHeld) return false;
            if (first == second) {
                critical.run();
                return true;
            }

            long elapsed = System.nanoTime() - start;
            long remaining = Math.max(0L, budget - elapsed);
            secondHeld = second.lock.tryLock(remaining, TimeUnit.NANOSECONDS);
            if (!secondHeld) return false;

            critical.run();
            return true;
        } finally {
            if (secondHeld) second.lock.unlock();
            if (firstHeld) first.lock.unlock();
        }
    }
}
```

第一个方法允许阻塞等待，但所有调用者最终都按 `orderKey` 排序，所以相反业务方向不会变成相反加锁方向。第二个方法不要求调用者先排序，而是把每次双锁尝试限制在一个总预算里：任何一步失败都会离开 `try`，`finally` 只释放已经成功获取的锁。它适合“拿不到就返回、重试或降级”的场景，不等价于全局锁顺序。

## 关键细节

- **输入/输出契约**：`withOrderedLocks` 要么在同时持有目标资源锁时执行一次 `critical`，要么在参数非法时抛异常；`withTimedLocks` 成功执行临界区返回 `true`，预算内拿不齐锁返回 `false`，等待时被中断则传播 `InterruptedException`。
- **总预算而不是每把锁各等一次**：第一把锁已经等待了 `elapsed`，第二把只使用 `budget - elapsed`。否则“100 ms 超时”可能演变为接近两次 100 ms 的锁等待。
- **只释放拿到的锁**：`firstHeld/secondHeld` 是释放条件。失败获取第二把锁时，第一把仍会在 `finally` 中释放。
- **相同资源**：两个参数引用同一资源时只获取一次锁，避免把可重入特性混进双资源示例。
- **唯一排序键是前提**：两个不同资源如果排序键相同而没有稳定 tie-break，就不能声称已经建立全序。本实现选择显式拒绝，而不是偷偷依赖对象地址或不稳定哈希。
- **超时不是硬实时 SLA**：超时参数限制的是锁 API 的等待条件；线程调度、临界区本身和调用前后代码仍可能增加墙钟时间。
- **复杂度**：资源排序和 bookkeeping 是 O(1) 时间、O(1) 额外空间；真正的等待时间由竞争和选择的策略决定。
- **版本边界**：本候选按 Java SE 21 `ReentrantLock` 文档和 Java 21 可执行测试核对；不要把未核对的公平性、调度或其他锁实现细节混成通用结论。

## 原理机制

死锁规避的关键是处理“等待关系”，而不是只把 `synchronized` 换成另一个 API。假设所有线程都只能按严格递增的 `orderKey` 持有并继续申请资源：若存在锁等待环，就意味着沿环上的 key 必须一直严格递增，最后又回到起点，逻辑上矛盾，所以这种统一全序排除了该类循环等待。

`tryLock` 路线采用另一种机制：不承诺一直等到成功，而是在拿不齐全部资源时放弃当前尝试并释放已持有资源。这样一次调用不会永久卡在“持有第一把、等待第二把”的状态。不过多个线程如果总是同时拿第一把、同时超时、又同时重试，仍可能长期没有业务进展；因此重试策略还需要退避、抖动、次数上限或上层队列化，并区分“避免永久死锁”和“保证公平/最终成功”。

## 项目经验版

当前来源没有真实项目的锁对象、并发量、超时阈值或线上事故数据，所以不能写“我在线上就是这么解决的”。项目映射时应先列出所有会同时持有的资源，定义跨模块一致的排序键并做代码审查；如果业务允许失败，则给 `tryLock` 设置基于延迟预算的超时，记录获取等待时长、超时次数、重试次数和线程 dump，在压测中用相反资源顺序并发请求验证不会形成永久等待。若锁覆盖 I/O 或跨进程资源，还要重新评估本地 `ReentrantLock` 是否就是正确边界。

## 常见追问

- 问：只要用了 `tryLock` 就不会死锁吗？答：不能这样绝对化。带超时且失败后释放已持有锁，能让这次多锁尝试退出永久等待；但错误的释放逻辑、无超时的等待，或其他未纳入策略的资源仍可形成问题，反复同步重试也可能活锁。
- 问：为什么统一锁顺序比“发现死锁再超时”更强？答：统一全序直接约束了允许形成的等待边，结构上排除该锁域的循环等待；超时是拿不到锁后的退出策略，会引入失败、重试和延迟预算等额外语义。
- 问：为什么第二把锁不能再完整等一次 timeout？答：如果调用契约是“整个双锁尝试最多等待一个预算”，就必须扣掉第一把已经消耗的时间，否则总等待上界会被放大。
- 问：线程在 `tryLock(timeout, unit)` 等待时被 interrupt 怎么办？答：Java 21 API 会抛 `InterruptedException`；本例不吞掉它，依靠 `finally` 释放已经拿到的锁，再把取消语义交给上层处理。
- 问：锁顺序是否保证公平、不会饥饿？答：不保证。它针对循环等待；公平性与线程调度、锁的公平策略、临界区长度及到达模式是另一组问题。

## 易错点

- 两个业务方向分别按“from 再 to”加锁，看起来对称，实际会让 `A→B` 与 `B→A` 形成相反锁顺序。
- 只写 `tryLock` 不写 `finally` 和“是否已经持有”的标记，第二把获取失败时泄漏第一把锁。
- 给每一把锁都使用完整 timeout，却口头声称这是整个操作的统一超时预算。
- 使用不唯一或会变化的排序键，却宣称所有资源已有严格全序。
- 把“超时返回”说成“保证最终成功”或“保证公平”；超时重试本身还可能造成活锁/饥饿。
- 捕获 `InterruptedException` 后直接忽略，使取消信号丢失并继续抢锁。
