# Redis AOF 重写的过程

## 核心结论

AOF 重写的目标是按当前数据集重新生成可恢复的 AOF，而不是压缩旧日志。Redis 7.0 之前可按“fork 快照、子进程写临时 AOF、父进程保留增量、完成后发布”的经典单文件流程理解；Redis 7.0 起 AOF 使用 base/incr 文件和 manifest，文件组织必须按版本说明。

## 1 分钟版

- 先区分 AOF 重写和 fsync：前者重建恢复日志，后者决定已追加数据何时落盘。
- Redis < 7.0 的经典实现中，后台重写以 fork 后的内存视图为起点；主进程继续服务并保存重写期间的新增写入。
- 子进程完成临时文件后，主进程把增量衔接到新结果再发布；因此“后台”不等于零影响，fork、COW 和磁盘 I/O 都要容量与延迟监控。
- Redis >= 7.0 改为 multi-part AOF：base/incr 文件由 manifest 组织，排障时不能把旧版单文件 rename 细节当成通用事实。

## 3 分钟版

先声明版本。对 Redis < 7.0：fork 后子进程从 fork 时可见的数据状态生成最小恢复命令；父进程仍把新写入追加到旧 AOF，并保存用于衔接的新写入。子进程结束后，父进程把该增量追加到新结果，并通过文件切换发布。这样恢复结果包含“快照时的状态 + 快照后的变化”。

对 Redis >= 7.0：官方文档说明 AOF 位于 `appenddirname`，并拆分为多个文件；因此回答文件布局、备份和故障恢复时要以 base/incr/manifest 的实际状态为准。两种版本的共同不变量是：已发布的恢复集合必须完整覆盖重写起点及其后的变化；如果重写失败或没有完成发布，继续使用已发布集合，而不是把半成品当作可恢复日志。

## 关键细节

- AOF 记录写命令，重启时可重放这些命令重建数据；重写只需要生成恢复当前状态所需的命令集合。
- Redis < 7.0 的重写期间，新增写入会带来内存缓冲、双写磁盘路径与 COW 资源压力；大实例应观测 fork 耗时、内存峰值、重写耗时和磁盘余量。
- Redis >= 7.0 的 AOF 是多文件集合；备份或排障要先确认当前是否正在重写，再按官方文档处理 `appenddirname` 中的已发布文件。
- `appendfsync` 决定刷盘策略，不能用它替代对重写发布、恢复完整性和资源代价的解释。

## 原理机制

经典流程的状态转换是：已发布旧 AOF → fork 时的数据视图 → 子进程生成临时重写结果，同时父进程收集视图后的增量 → 把增量衔接到新结果 → 发布新集合。fork 让子进程看到起点状态，写时复制使父进程继续处理写请求；代价是写热点页复制和 I/O 竞争。Redis 7 的具体参与文件变为 base/incr/manifest，但仍须保证发布后的集合可从头恢复到最新状态。

## 项目经验版

项目映射提示：请按真实 Redis 大版本填写 AOF 配置、实例内存、写入峰值、fork 耗时、重写时长、COW 峰值和磁盘余量。若没有生产数据，可说明“这是依据官方文档的方案推演”，不要虚构一次重写或恢复事故。

## 常见追问

- 问：AOF 重写会丢失重写期间的新写入吗？答：不会把它们丢在设计之外；经典流程会把 fork 后的新增写入作为增量衔接到新结果，发布前必须保证该增量已被包含。
- 问：为什么不能把 AOF 重写说成压缩？答：因为它从当前数据状态重新生成恢复命令，旧日志中已被覆盖的历史操作不必保留。
- 问：重写为什么仍可能影响线上延迟？答：fork、COW、写入缓冲和磁盘竞争都会消耗资源；后台执行只避免把完整生成过程放在主命令路径。
- 问：Redis 7 之后排查 AOF 时最大的版本差异是什么？答：AOF 由多个文件和 manifest 组织，应检查已发布集合，而不能只按旧版单个 AOF 文件推断恢复状态。

## 易错点

- 不要把 AOF 重写、AOF 刷盘和 RDB 快照混为一谈。
- 不要把 Redis < 7.0 的单文件发布过程套到 Redis 7 的 multi-part AOF。
- 不要说“后台重写完全无阻塞”；要说明 fork、COW、I/O 与容量边界。
