# 10 个线程模拟赛马：全部就绪后开跑，全部到达后裁判公布结果

## 核心结论

这道题有两个不同方向的一次性同步条件：**10 匹马都就绪后才能统一放行**，以及**10 匹马都结束后裁判才能宣布成绩**。一个直接实现是用三个 `CountDownLatch`：`ready(10)` 收集就绪信号，`start(1)` 作为统一起跑门，`finish(10)` 收集完成信号。每个马线程先 `ready.countDown()` 再等待 `start.await()`；裁判等待 `ready.await()` 后打开起跑门；每个马线程结束时在 `finally` 中 `finish.countDown()`；裁判最后等待 `finish.await()` 再宣布。

原题只要求上述并发语义，并没有规定必须使用 `CountDownLatch`。这里选择它作为答案侧实现；用 `CyclicBarrier`/`Phaser` 也可以表达部分或全部协调语义，但不能把具体工具反写成原题约束。

## 1 分钟版

- `ready = new CountDownLatch(10)`：每匹马完成初始化后减 1，裁判等它归零。
- `start = new CountDownLatch(1)`：所有马都在这个门上等待；裁判确认全部 ready 后一次 `countDown()` 同时放行。
- `finish = new CountDownLatch(10)`：每匹马无论成功还是异常都在 `finally` 里减 1，避免裁判永久等待。
- 成绩容器必须是线程安全的，例如 `ConcurrentLinkedQueue`；队列插入动作就定义为本模拟中的“冲线记分点”。
- 裁判流程严格是 `ready.await()` → `start.countDown()` → `finish.await()` → announce。
- 线程中断或执行失败要显式记录，不能为了“保证结束”静默吞掉；全部线程回收后由裁判汇总失败。

## 3 分钟版

```java
import java.util.List;
import java.util.concurrent.ConcurrentLinkedQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicReference;
import java.util.function.IntConsumer;

public final class HorseRace {
    private static final int HORSES = 10;

    public static List<Integer> race(IntConsumer runHorse) throws InterruptedException {
        CountDownLatch ready = new CountDownLatch(HORSES);
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch finish = new CountDownLatch(HORSES);
        ConcurrentLinkedQueue<Integer> finishOrder = new ConcurrentLinkedQueue<>();
        AtomicReference<Throwable> failure = new AtomicReference<>();

        for (int id = 0; id < HORSES; id++) {
            final int horseId = id;
            Thread horse = new Thread(() -> {
                ready.countDown();
                try {
                    start.await();
                    runHorse.accept(horseId);
                    finishOrder.add(horseId); // 本模拟把这里定义为冲线记分点
                } catch (InterruptedException e) {
                    failure.compareAndSet(null, e);
                    Thread.currentThread().interrupt();
                } catch (Throwable t) {
                    failure.compareAndSet(null, t);
                } finally {
                    finish.countDown();
                }
            }, "horse-" + horseId);
            horse.start();
        }

        ready.await();       // 10 匹马全部就绪
        start.countDown();   // 裁判统一放行
        finish.await();      // 10 匹马全部到达或退出

        Throwable t = failure.get();
        if (t != null) {
            throw new IllegalStateException("horse failed", t);
        }
        return List.copyOf(finishOrder); // 此后裁判才可以宣布
    }
}
```

调用侧可以把 `runHorse` 实现成睡眠、计算或可控测试动作。关键并不是“睡多久”，而是同步关系：任何 `runHorse` 都不应在全部 ready 之前执行；裁判也不能在全部 `finish.countDown()` 之前宣布。

## 关键细节

- **为什么不是一个 latch 就够**：ready、统一起跑、全部完成是三个不同阶段。`ready(10)` 是多方到裁判，`start(1)` 是裁判到所有马，`finish(10)` 又是多方到裁判，方向和生命周期不同。
- **为什么 `ready.countDown()` 在 `start.await()` 前**：如果马先等 start 再报告 ready，裁判又在等 ready 归零，会形成逻辑死锁。
- **为什么 `finish.countDown()` 放在 `finally`**：马线程执行动作抛异常或被中断时，也必须让完成计数有确定去向；否则裁判可能永远阻塞。异常仍需单独上报，不能用 `countDown` 把失败伪装成成功成绩。
- **成绩顺序的定义**：多个线程真实“物理到达”的绝对纳秒顺序并不是 Java 普通容器能无歧义观测的概念。本实现明确把成功执行 `finishOrder.add(id)` 定义为冲线记分点，因此队列顺序就是程序可观察的成绩顺序。
- **线程安全**：多个马线程并发写成绩，不能用未同步的 `ArrayList`。这里使用 `ConcurrentLinkedQueue`，裁判只在 `finish.await()` 返回后读取最终快照。
- **可见性**：`CountDownLatch` 的同步点为阶段之间提供 happens-before 保证；裁判在 `finish.await()` 返回后再读取已完成线程产生的结果，避免靠 `sleep` 猜测时序。
- **一次性语义**：`CountDownLatch` 不能重置。如果要反复跑多轮比赛，应该每轮重新创建 latch，或者评估 `CyclicBarrier` / `Phaser` 等可复用协调器。

## 原理机制

这道题本质是两个 barrier-like 阶段加一个单次广播门。第一阶段，10 个马线程各自报告 ready，裁判作为等待方只有在计数归零后继续；第二步，裁判把 `start` 从 1 减到 0，一次释放所有等待马；第三阶段，10 个马线程各自报告 finish，裁判再次等计数归零。这样同步条件由明确状态驱动，而不是由调度时间或 `Thread.sleep` 的经验值驱动。

`CountDownLatch` 还给出内存可见性边界：某线程在 `countDown()` 前完成的动作，对成功从对应 `await()` 返回的线程可见。因此，裁判在 finish latch 之后读取成绩和失败状态，语义比“等一会儿再读”稳定得多。

## 项目经验版

来源没有提供真实线上项目经历，因此不虚构“生产上就是这样写的”。实际工程里我会进一步明确：线程池还是裸线程、比赛是否有超时、单匹马失败是取消整场还是记录 DNF、裁判线程被中断怎么恢复、结果排序的精确定义，以及多轮比赛是否需要可复用 barrier。这些都属于接口/业务契约，不能由一道只有同步要求的题目擅自补成事实。

## 常见追问

- 问：为什么可以用三个 `CountDownLatch`？答：分别表示“10→裁判的 ready 汇聚”“裁判→10 的起跑广播”“10→裁判的 finish 汇聚”，每个 latch 只承担一个阶段。
- 问：可以用 `CyclicBarrier` 吗？答：可以。比如 ready 阶段可以让 10 匹马加裁判参与 barrier，或让 barrier action 触发起跑；但仍要把“全部结束后宣布”这个阶段表达清楚。工具可以替换，语义不能丢。
- 问：为什么不能 `sleep(1秒)` 后让裁判宣布？答：线程调度和任务耗时没有这种确定上界，`sleep` 只是延迟，不是完成条件。
- 问：如果一匹马抛异常怎么办？答：本实现 `finally` 释放 finish 计数，同时记录首个失败；裁判等全部线程退出后抛出汇总异常，因此既不死锁，也不把失败当正常名次。
- 问：如何做超时？答：可以使用 `await(timeout, unit)`，超时后进入明确的取消/中断/失败策略；不能仅返回一个不完整成绩列表并假装比赛完成。
- 问：多轮比赛怎么办？答：`CountDownLatch` 是一次性的；每轮重新创建协调对象，或者改用适合复用阶段的 `CyclicBarrier`/`Phaser`。

## 易错点

- 马线程先 `start.await()`，后 `ready.countDown()`，裁判又先等 ready，直接形成逻辑死锁。
- 用同一个 latch 混合 ready/start/finish 三种方向不同的信号，状态含义不清晰。
- 只在正常路径 `finish.countDown()`，异常后裁判永远等不到 0。
- 多线程并发写普通 `ArrayList`，结果结构本身发生数据竞争。
- 用固定 `sleep` 代替“所有马已经完成”的同步条件。
- 没定义“冲线顺序”的程序观测点，却声称容器顺序等于绝对物理完成时间。
