# 百亿级短 URL 如何生成无冲突短码？

## 核心结论

如果目标是“短码本身可证明不冲突”，核心不要用随机串碰撞后查重，而是先分配全局唯一整数 ID，再用固定 Base62 字典做单射编码。6 位 Base62 有 `62^6 = 56,800,235,584` 个编码，能覆盖 100 亿条假设。系统还需要把 ID 号段领取、映射唯一约束、业务幂等、缓存失效和跨机房写入互斥分别建模；任何依赖存储不可用时宁可明确失败，也不能为了可用性重新发放可能重复的 ID。

## 1 分钟版

先声明设计假设：5 年累计 100 亿条、创建峰值 10 万 QPS、解析峰值 100 万 QPS、短码只使用字母数字；创建接口目标 P99 小于 100ms，解析目标 P99 小于 30ms，目标值只是容量设计输入，最终必须由压测验证。

创建链路是：校验 URL → 检查 `(tenant_id, idempotency_key)` → 从本地已领取号段取唯一 ID → Base62 编码 → 在事务中写 `short_code` 唯一索引和幂等结果 → 成功后返回。号段由一个提供线性化条件更新的权威源分配，实例只消费自己已确认拥有的区间；实例宕机可以浪费尾号，但不能回收重发。

解析链路是：CDN/边缘 → Redis/本地缓存 → 映射主存储。缓存记录目标 URL、状态和 `mapping_version`；更新或禁用短链时先写权威映射版本，再发送失效事件，读路径若发现缓存版本不是当前权威版本就回源，不把缓存当事实源。

故障时坚持“不重复比强行成功更重要”：号段源暂时不可用但本地段还有余量时可继续发号；低于安全水位且无法续段时创建接口 fail-fast。映射库事务失败就不返回成功，由同一幂等键重试；解析侧缓存故障可回源并限流。

## 3 分钟版

### 需求与容量

本题假设短码需要全局唯一且长期不可复用，字符集限定 `0-9a-zA-Z`。RFC 3986 把字母和数字列为 URI 未保留字符，所以 Base62 token 放在 path 中不需要针对这些字符额外转义。容量上 `62^5≈9.16 亿`，不足百亿；`62^6=56,800,235,584`，约是目标量 5.68 倍。接近容量水位时新数据升级到 7 位，旧码按长度继续解析。

### 唯一 ID 与号段

唯一性真正来自 ID 分配，不来自 Base62。权威号段表可以抽象为 `id_segment(biz, max_id, version)`，领取时通过线性化 compare-and-set 把 `max_id` 向前推进一个固定区间。成功领取 `[start,end]` 后，该区间永久只属于一个租约；实例在内存递增发号。段大小取 100 万时，单实例持续 10 万创建 QPS 大约 10 秒领取一次，实际段大小要根据实例数、故障浪费和中心存储压力压测。

故障语义要在发号前确定：实例领段后宕机，剩余 ID 作废；绝不把尾号重新发给其他实例。号段源不可用时，实例只允许继续消费已确认段；到安全水位仍不能续段就停止新建。跨机房只能保留一个写主，或者使用真正能保证号段领取互斥的共识/线性化存储，不能让两个独立主从同一 `max_id` 开始发号。

### 创建写入与幂等

写模型至少有：

`short_url(id, short_code, tenant_id, normalized_url, status, mapping_version, created_at, ...)`

以及幂等键唯一约束：

`UNIQUE(tenant_id, idempotency_key)`

和短码唯一约束：

`UNIQUE(short_code)`。

创建时先查幂等记录；没有结果才取 ID 并编码，然后在同一事务里写映射和幂等结果。请求超时后客户端携带同一个幂等键重试：若前一次已提交，返回原短码；若未提交，新事务可以继续，但旧 ID 即使已取出也不回收。映射库不可用或事务状态无法确认时接口不声称成功，先用幂等键查询最终状态再决定返回或重试。

### 解析缓存与状态变更

缓存不是权威源。缓存值包含 `normalized_url/status/mapping_version/expire_at`。短链被禁用或目标 URL 更新时，权威存储先推进 `mapping_version`，随后发布失效事件并删除/更新缓存。读路径若收到事件前仍读到旧缓存，必须受短 TTL 和版本校验边界限制；高风险状态变更可选择强制回源窗口。若 Redis 不可用，允许按容量预算回源主存储，但要限流保护主库；主库也不可用则返回明确失败，而不是把未知状态缓存继续当永久事实。

### 灰度、观测与恢复

上线前同时做多实例创建压测和解析压测，注入重复请求、领取号段后宕机、号段源不可用、映射事务超时、缓存失效事件延迟和主库切换。验收不变量包括：`short_code` 无重复、同一幂等键最多一个成功映射、已领未用 ID 不复用、禁用链接最终不再解析到旧目标。指标至少包括创建/解析 P50/P95/P99、号段剩余量和领取延迟、唯一约束冲突、幂等重试、缓存命中/回源率、版本失配、失效延迟和恢复耗时。先 1% 创建流量灰度，重复码或号段互斥异常立即关闭新写并回滚到旧入口。

替代方案是随机短码 + 唯一索引冲突重试：实现简单、不暴露递增 ID，但占用率上升后冲突和重试分布变差，仍不能离开唯一索引；哈希截断同样需要碰撞处理。这里选择唯一 ID + Base62，是用可验证的分配协议换取确定性唯一。

## 关键细节

- Base62 字典必须固定并版本化；改变字典会改变同一 ID 的展示。
- 6 位只是当前容量层级，达到水位后新记录升级 7 位，旧码不重编码、不复用。
- URL 去重和请求幂等是不同语义：相同 URL 不一定代表同一次业务创建。
- ID 空洞是允许的；“连续”不是业务要求，唯一和不可复用才是核心不变量。
- 缓存版本必须来自权威映射状态；失效事件只是加速收敛，不能把消息送达当成正确性的唯一前提。

## 原理机制

系统的状态不变量是：

1. 每个已提交映射有唯一 `id`；
2. `short_code = Base62(id)`，固定字典下为单射；
3. 同一 `(tenant_id,idempotency_key)` 最多有一个成功结果；
4. 已确认领取过的 ID 即使未提交映射也不再发放；
5. 解析结果最终以权威映射的 `mapping_version` 和状态为准。

状态流为：

`接收请求 → 幂等检查 → 获取已租用唯一 ID → Base62 → 事务写映射+幂等结果 → 提交 → 发布缓存失效/填充 → 返回`。

失败分支是显式状态：号段耗尽且无法续段就拒绝创建；事务失败不返回成功；事务结果未知先按幂等键查最终状态；缓存失败回源并限流；跨机房没有互斥写能力时不开放双写。资源成本主要是号段权威写、映射事务与唯一索引、缓存内存和失效链路，换来创建热路径不需要每次都访问中心序列，也不需要随机碰撞重试。

项目映射提示：把示例数字替换成真实累计量、创建/解析 QPS、延迟 SLO、短码长度、号段大小、数据库与缓存拓扑、跨机房策略、缓存 TTL、RPO/RTO 和故障演练结果。没有真实数据时只讲设计假设，不声称“线上绝对零冲突”或具体延迟成果。

## 常见追问

- 问：为什么不用随机 6 位码？答：随机空间有限，不能单靠随机性证明不冲突，仍要唯一索引和冲突处理；唯一 ID 到 Base62 把唯一性放到可验证的分配协议。
- 问：号段源挂了怎么办？答：已领取段仍可继续消费；到安全水位无法续段就 fail-fast，不能自己猜新号段。
- 问：客户端超时重试会不会生成两个短码？答：使用租户级幂等键唯一约束；先查询既有结果，事务结果未知也先按幂等键确认最终状态。
- 问：缓存失效消息丢了怎么办？答：消息只是加速；缓存有 TTL 和 `mapping_version`，高风险状态可强制回源，权威映射仍是最终事实。
- 问：删除短链后可以复用短码吗？答：本设计不复用。历史缓存、日志和外部引用仍可能访问旧码，复用会把旧引用指向新对象。

## 易错点

- 不要把 `62^6` 的空间大小误说成随机生成“天然无冲突”；唯一来自 ID 分配和唯一约束。
- 不要在实例故障后回收未用号段；这会把恢复竞态带进唯一性路径。
- 不要在数据库事务结果未知时直接再创建一条；先通过幂等键确认最终状态。
- 不要把缓存失效通知当唯一正确性机制；必须有权威版本和失效兜底。
- 不要只算存储容量，还要给出创建/解析 QPS、延迟目标、故障降级、压测与灰度门槛。
