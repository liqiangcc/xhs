# 手写 `usePrevious`：记录 State 的上一次值

## 核心结论

面试题的经典实现是：用 `useRef` 保存“最近一次已经提交的 value”，在 `useEffect` 中把当前 `value` 写入 ref，并在本次 render 返回 effect 执行前留下的旧值。这样首次 render 返回 `undefined`；当值从 `A` 变成 `B` 时，渲染 `B` 的这一次会拿到 `A`，commit 后 effect 再把 ref 更新为 `B`。

## 1 分钟版

- `useRef` 的对象会跨 render 保持同一 identity，修改 `ref.current` 本身不会触发重新渲染。
- render 阶段先读到 ref 里保存的旧值；commit 后 `useEffect` 再把当前值写进去，因此形成“当前 render 看到上一次已提交值”的时间差。
- 初始没有历史值，所以默认返回 `undefined`；如果业务需要别的初始语义，可以把初始值做成显式参数。
- `usePrevious` 记录的是 render/commit 序列里的前值，不是“每一次 `setState` 调用”的参数历史；相同值更新可能不会产生新的 render。
- 如果“历史值变化本身”需要驱动 UI 更新，就不能只依赖 ref，因为 ref 更新不会触发 render；那属于另一个状态建模需求。

## 3 分钟版

```javascript
import { useEffect, useRef } from 'react';

export function usePrevious(value) {
  const previousRef = useRef();

  useEffect(() => {
    previousRef.current = value;
  }, [value]);

  return previousRef.current;
}
```

假设组件依次提交 `A -> B -> C`：

1. 第一次 render：`previousRef.current` 还是 `undefined`，所以返回 `undefined`；commit 后 effect 写入 `A`。
2. 第二次 render 的当前值是 `B`，但 ref 仍是 `A`，所以返回 `A`；commit 后写入 `B`。
3. 第三次 render 的当前值是 `C`，所以返回 `B`；commit 后写入 `C`。

因此关键不是“ref 能存东西”这么简单，而是**写入发生在 commit 后的 Effect，而读取发生在下一次 render 使用旧快照时**。如果在 render 一开始就把 `previousRef.current = value`，你会立刻覆盖掉真正的 previous value。

## 关键细节

- **首次返回值**：默认是 `undefined`，因为 `useRef()` 没有传初值。若 API 要求 `usePrevious(value, initialValue)`，可以把 `initialValue` 作为 ref 初值，但要把这个契约说清楚。
- **为什么不用普通局部变量**：函数组件每次 render 都重新执行，普通局部变量不会跨 render 保留；ref 对象会在后续 render 中保持。
- **为什么不用 ref 驱动 UI**：React 官方文档明确说明，修改 `ref.current` 不会触发重新渲染；需要驱动显示的数据应使用 state。
- **依赖数组**：这里只在 `value` 改变后更新保存值，因此写 `[value]`。若每次 commit 都执行 effect，也能保持前值语义，但没有必要增加无变化提交时的写入。
- **对象值**：保存的是引用本身，不会自动深拷贝。如果调用方原地修改同一个对象，所谓“previous object”也会指向被修改后的对象；React state 应按不可变方式更新。
- **Strict Mode**：开发环境可能额外执行 effect 的 setup/cleanup 检查；这里 effect 只是幂等地赋值，不依赖外部副作用次数。
- **当前 React 文档的生产 caveat**：官方 `useRef` 文档建议不要在 render 中读取或写入 `ref.current`（初始化例外）。这个 `usePrevious` 是常见面试实现，用来解释 ref 与 effect 的时序；如果 previous value 直接决定生产 UI，优先考虑 state-based 的可渲染状态设计，而不是把 ref 当成 render 数据源。

## 原理机制

函数组件的每次 render 都读取本次 props/state 快照。`useRef` 提供一个跨 render 保持的可变容器，而 Effect 在 commit 之后执行。`usePrevious` 正是利用这个先后关系：

`render(current) -> read stored previous -> commit -> effect stores current -> next render`

所以 ref 中保存的是“最近一次 effect 已经观察到的 value”。这也解释了为什么它不会主动触发新 render：ref 是 React 用来保存不参与渲染驱动的数据容器，而不是 state。

## 项目经验版

来源只有面试手写题，没有真实项目上下文，不能虚构“线上曾用这个 Hook 解决某业务”。实际项目里我会先问 previous value 的用途：如果只是日志、比较、事件处理等不需要主动刷新 UI 的辅助信息，ref 型存储可以很轻；如果 previous value 本身要稳定参与 JSX 渲染或触发更新，则应把它纳入 state/状态机，而不是依赖 ref 的可变值。

## 常见追问

- 问：为什么第一次是 `undefined`？答：因为还没有任何“上一次提交”，而 `useRef()` 的初始 `current` 就是 `undefined`。
- 问：为什么要在 `useEffect` 里更新？答：要让当前 render 先拿到旧值，commit 后再把当前值保存成下一次的 previous；如果 render 时先覆盖，就丢掉旧值。
- 问：`ref.current` 改了为什么页面没更新？答：ref 的更新不会通知 React 重新 render；需要驱动 UI 的数据用 state。
- 问：如果 value 是对象呢？答：ref 保存对象引用，不会克隆。应保持 state 不可变更新，否则 previous/current 可能指向同一个被原地修改的对象。
- 问：`[value]` 能不能省略？答：省略后 effect 每次 commit 都写入当前值，基本语义仍可成立；这里显式依赖 `value`，只在值变化后更新，更直接表达目的。
- 问：生产代码一定推荐这个写法吗？答：作为面试题它很好地展示 `useRef + useEffect` 的时序；但当前 React 官方文档不建议把 ref 当 render 数据源，所以 previous 值若直接参与 UI 建模，应优先评估 state-based 方案。

## 易错点

- 在 render 期间先执行 `previousRef.current = value`，导致返回的已经是当前值。
- 用普通变量保存 previous，下一次 render 时变量重新初始化。
- 误以为更新 ref 会触发 UI 刷新。
- 对对象做原地 mutation，再期待 ref 保留“旧对象快照”。
- 没定义首次 render 的返回语义，却在调用方把 `undefined` 当成真实业务值。
- 把常见面试模式无条件描述成当前 React 生产最佳实践，忽略官方对 render 阶段读取 ref 的 caveat。
