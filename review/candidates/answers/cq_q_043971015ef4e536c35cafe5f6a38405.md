# 操作系统进程间通信（IPC）有哪些常见方式？

## 核心结论

IPC 不应该只背一串名词，更容易记的是它们分别在解决什么通信模型：

- **管道 / FIFO**：把数据当连续字节流传递，简单，适合生产者—消费者式通信。
- **消息队列**：把数据按“消息”排队，天然保留消息边界，更适合异步解耦。
- **共享内存**：多个进程映射同一块内存，数据不必每次都通过消息通道搬运，但必须自己解决同步和共享状态正确性。
- **信号量**：主要解决进程/线程之间的同步，不是用来传大块业务数据。
- **UNIX Domain Socket**：适合同一台机器上的双向客户端/服务端通信，可用 stream/datagram/seqpacket 模型。
- **信号**：适合轻量异步通知和控制事件，不适合作为普通数据通道。

选择时看四件事：**要传字节流还是消息、数据量和性能要求、是否需要双向/客户端服务端模型、共享状态的同步复杂度**。没有一种 IPC 在所有场景都“最快最好”。

## 1 分钟版

- **Pipe / FIFO**：管道是内核缓冲的单向通信通道。匿名 pipe 常用于有亲缘关系、能继承文件描述符的进程；FIFO 多了一个文件系统名字，权限允许的无关进程也能通过这个名字会合。
- **Message Queue**：按消息发送和接收，消息边界比 pipe 的连续字节流更明确；代价是要接受队列容量、内核资源和生命周期管理。
- **Shared Memory + Semaphore/Lock**：共享内存让多个进程直接访问同一共享区域，适合大数据和高吞吐，但共享内存只解决“数据放哪”，同步原语才解决“谁什么时候能读写”。
- **UNIX Domain Socket**：适合同机 client/server，天然支持双向请求响应；需要网络透明性时再考虑 TCP/UDP socket，而不是把本地共享内存硬扩成跨机器方案。
- **Signal**：适合通知“发生了一件事”，比如退出、重载、唤醒；不适合承载复杂业务 payload。

一句话：**简单流用 pipe，消息解耦用 queue，大块共享数据用 shared memory + sync，本机服务化通信用 Unix socket，只做通知用 signal。**

## 3 分钟版

### 1. 管道 Pipe 和 FIFO

匿名管道可以理解成内核里的一个有界字节通道：

```text
writer process -> kernel pipe buffer -> reader process
```

`pipe()` 返回读端和写端文件描述符。因为文件描述符可以经 `fork()` 继承，所以匿名 pipe 很自然地用于父子/相关进程，例如 shell 的：

```text
producer | consumer
```

可移植语义上把 pipe 当**单向**通道；如果要双向，一般创建两条 pipe，或者直接选择 socket。

FIFO，也叫 named pipe，数据通道语义和 pipe 基本一致，但它在文件系统里有名字。这个名字只是让不同进程找到同一个管道，不代表数据真的写进普通文件。因此它适合“进程无亲缘关系，但只需要简单本地流式通信”的场景。

边界是：pipe/FIFO 有容量，空时读可能阻塞、满时写可能阻塞；所以它也有背压问题。它本身是字节流，不应该依赖“我 write 一次，对端就恰好 read 一条完整业务消息”。

### 2. 消息队列 Message Queue

消息队列的模型是：

```text
sender -> [msg1][msg2][msg3] -> receiver
```

它和 pipe 最大的概念差异是：**消息是显式单位**。POSIX message queue、System V message queue 的 API 不同，但都属于“进程通过内核维护的队列交换消息”的模型。

适合：

- 一条一条命令/事件；
- 发送者和接收者不必同步执行；
- 希望保留消息边界；
- 需要一定排队解耦。

但本机 OS message queue 不是 Kafka/RabbitMQ 那类分布式消息系统。它有系统级容量、消息大小、对象生命周期等限制，也不会自动给你跨机器复制、消费组、持久化日志等分布式能力。

### 3. 共享内存 Shared Memory

共享内存的模型不是“把一份 payload 从 A 拷给 B”，而是：

```text
process A virtual address ----\
                               -> same shared memory object/pages
process B virtual address ----/
```

所以它特别适合大块数据、高频数据结构、环形缓冲区等场景：进程可以在共享区域上协作，避免把每份数据都编码成消息再来回经过独立消息缓冲区。

但它只解决了**共享数据可见性的位置**，没有自动解决：

- 两个进程同时写怎么办；
- 一方读到半写入状态怎么办；
- producer/consumer 如何判断空和满；
- 进程崩溃后共享状态如何恢复。

因此常见设计是：

```text
shared memory
+ semaphore / process-shared mutex / atomics
+ 明确的数据结构协议
```

不要把“共享内存拷贝少”直接背成“共享内存永远最快”。同步竞争、cache coherence、数据布局、缺页、错误恢复和开发复杂度都可能成为成本。

### 4. 信号量 Semaphore

Semaphore 的核心用途是**同步动作**：

```text
count > 0 -> sem_wait 可继续并减一
count == 0 -> sem_wait 阻塞
sem_post -> 加一并可能唤醒等待者
```

它可以表达“资源还有几个”“数据是否可消费”“临界区是否允许进入”等条件。

关键边界：**信号量不是普通 payload 通道**。你通常不会把一段 JSON 或 1 MB 图像“通过 semaphore 传过去”；它更像共享内存等 IPC 的协调协议。

### 5. UNIX Domain Socket

同一台机器上如果希望做清晰的 client/server 通信，UNIX Domain Socket 很自然：

```text
client -> AF_UNIX socket -> server
```

它支持 `SOCK_STREAM`、`SOCK_DGRAM`，Linux/Unix 还可用 `SOCK_SEQPACKET`；可以建立连接、双向收发，并在支持的平台上传递文件描述符或进程凭据。

和 pipe 相比，它更适合长期服务、多客户端、双向请求响应；和 TCP 相比，它只解决本机 IPC，不需要把数据走 IP 网络栈的远端寻址模型。

如果未来必须跨机器，socket API 模型更容易迁移到 TCP/UDP，但不能把“Unix socket 和 TCP 完全一样”当作结论，它们的地址、传输范围和部分能力不同。

### 6. Signal

Signal 是异步通知模型：

```text
event -> signal pending/delivery -> target process/thread reacts
```

它适合表达：

- 终止/中断；
- 配置重载；
- 子进程状态变化；
- 某类轻量控制事件。

Signal 有 mask、pending、handler 等语义，而且 signal handler 能安全做的事情受 async-signal-safe 约束。它不是为大块结构化消息设计的；需要传复杂数据时，通常用 pipe/socket/queue/shared memory，把 signal 只作为通知或唤醒机制。

### 7. 怎么选

可以按这个决策顺序：

```text
只是通知？
  -> signal / semaphore（取决于事件还是同步计数）

要传数据？
  -> 要保留消息边界？
       -> message queue / datagram-or-seqpacket socket
     是连续流？
       -> pipe/FIFO / stream socket

数据很大、很高频，而且都在本机？
  -> shared memory + explicit synchronization

多个无关进程，长期 client/server、双向请求响应？
  -> UNIX domain socket
```

实际还要继续考虑权限、安全、阻塞/非阻塞、超时、容量、生命周期、进程崩溃恢复和可移植性。

## 关键细节

- **Pipe 和 FIFO 的区别主要在建立/发现方式**：匿名 pipe 用文件描述符建立关系；FIFO 用文件系统名字作为 rendezvous。打开之后 I/O 语义基本一致。
- **Pipe 要按字节流理解**：不要把一次 `write` 与一次业务消息强绑定；协议层仍需自己做 framing。
- **Message Queue 有消息边界**：适合命令/事件，但队列数量、消息数、消息大小等都受系统资源限制。
- **共享内存必须配同步协议**：共享一块内存不等于并发访问自动安全。
- **Semaphore 解决协调，不是 bulk data transport**。
- **UNIX Domain Socket 是本机 IPC**：支持双向和不同 socket type，适合 daemon/client 模型。
- **Signal 适合控制，不适合大 payload**：handler 还受可安全调用函数范围限制。
- **“共享内存最快”不能绝对化**：应说它可以减少独立消息搬运，但最终延迟还受同步、缓存一致性、调度和数据布局影响。
- **“Socket 就是网络通信”也不准确**：AF_UNIX socket 就是典型本机 IPC。
- **同步和通信可以组合**：例如 shared memory 传数据、semaphore 通知可读；signal 唤醒后再从 pipe 读取真实 payload。

## 原理机制

IPC 的本质是在**隔离的进程地址空间之间建立一种受内核/共享映射管理的可见关系**。可以分成三类：

```text
1. 数据搬运型
   process A -> kernel-managed channel/queue -> process B
   pipe / FIFO / message queue / socket

2. 共享状态型
   process A -> shared pages <- process B
   shared memory
   + synchronization protocol

3. 控制通知型
   event/synchronization state -> target
   signal / semaphore
```

第一类把所有权转移/复制过程显式放在通道上，隔离清晰，但要承担缓冲、复制、排队和 framing。

第二类把双方放在同一共享数据结构上，数据路径短，但正确性责任更多落到应用协议：内存布局、并发同步、发布顺序、崩溃恢复都要设计。

第三类只表达“现在可以做某件事/发生了某件事”，通常和前两类组合，不负责复杂 payload。

所以 IPC 选型本质是在做取舍：

```text
隔离性与简单性
vs
数据路径效率
vs
消息语义
vs
同步复杂度
vs
拓扑和生命周期
```

## 项目经验版

来源没有给用户真实项目经历，不能虚构“线上从 socket 换成共享内存后 P99 降了多少”。

真实项目映射时，我会先问：

```text
同机还是跨机？
父子进程还是无关 daemon/client？
payload 是几十字节控制消息还是 MB 级数据？
需要消息边界还是连续流？
一对一、一对多还是多对多？
是否需要异步排队？
允许阻塞吗？怎么超时？
进程崩溃后通道和共享状态怎么清理/恢复？
```

例如本机媒体进程把大帧交给编码进程，可能考虑 shared memory/ring buffer + 同步；CLI 调 daemon 更自然的是 Unix socket；父进程把日志流交给子进程处理，pipe 很简单。具体选择仍要用目标 workload 测吞吐、尾延迟、CPU、内存和故障行为，而不是只比较理论名字。

## 常见追问

- 问：为什么共享内存通常还要配信号量？
  答：共享内存只让双方能看到同一片数据，不规定谁先写、谁后读。信号量/锁/原子协议用来表达互斥、可读数量、空闲槽位等同步条件，避免并发破坏共享结构。

- 问：Pipe 和 FIFO 到底差在哪？
  答：核心数据通道语义相近，主要差在“怎么找到它”：匿名 pipe 靠已有/继承的文件描述符，FIFO 在文件系统里有名字，因此无亲缘关系的进程也能按权限打开。

- 问：消息队列和 pipe 有什么本质区别？
  答：pipe 更像连续字节流；message queue 以一条条 message 为传输单位并在内核队列里排队，所以消息边界和异步解耦更自然。

- 问：共享内存一定比 socket 快吗？
  答：不能绝对化。共享内存可以避免每条 payload 都走独立消息搬运，但同步竞争、缓存一致性、内存布局和调度可能成为瓶颈。必须按真实数据大小、并发和协议测量。

- 问：UNIX Domain Socket 和 TCP Socket 怎么选？
  答：只在同机且要 client/server、双向通信时，AF_UNIX 很合适；要跨机器就必须使用网络协议族。API 形态相似不代表传输范围和所有语义都相同。

- 问：为什么 signal 不适合传业务数据？
  答：它是异步事件通知机制，信息承载和 handler 执行环境都受限制。复杂 payload 更适合放在 pipe/socket/queue/shared memory 中，signal 只负责提醒“有事发生”。

- 问：Semaphore 算不算 IPC？
  答：算进程间同步机制，System V/POSIX 都提供进程共享 semaphore；但它的主要职责是协调动作/资源计数，而不是传输大块数据。

## 易错点

- 把 IPC 只背成“七八个 API 名字”，却说不清字节流、消息、共享状态、同步和通知的区别。
- 说 pipe 在所有 Unix 上都是双向；可移植语义应按单向理解。
- 认为 FIFO 的业务数据会像普通文件内容一样落盘；文件系统条目主要用于命名和会合。
- 把一次 pipe `write` 当成永久可靠的业务消息边界。
- 说共享内存“天然线程/进程安全”。
- 把 semaphore 当成传 payload 的消息队列。
- 认为 signal 适合传大块结构化数据。
- 认为 socket 只能跨机器，忽略 AF_UNIX。
- 说共享内存无条件最快，不考虑同步、cache coherence、调度和恢复复杂度。
- 把本机 POSIX/System V message queue 等同于 Kafka/RabbitMQ 等分布式消息系统。
