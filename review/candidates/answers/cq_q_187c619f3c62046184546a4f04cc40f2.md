# Go：100 个 goroutine 严格按顺序打印 1 到 100

## 核心结论

原始面经在 Go 的 GMP、goroutine 调度上下文里给出的题目是“100个协程依次打印1-100”。能从来源确定的是：这里的“协程”指 Go goroutine，最终可观察输出必须严格是 `1..100`；来源没有指定必须使用 channel、锁、条件变量，也没有规定输出格式、超时或取消协议。

一个直接且可证明的做法是让 **100 个 goroutine 各负责一个数字**，用一条由 101 个无缓冲 channel 组成的“令牌链”串起执行权。第 `i` 个 goroutine 先等 `token[i-1]`，打印 `i` 后再把令牌发送到 `token[i]`。主 goroutine 只负责向 `token[0]` 发起第一个令牌，并等待 `token[100]`。因此调度器可以任意调度，创建顺序也可以任意，但没有拿到前驱令牌的 goroutine 不可能提前打印。

## 1 分钟版

我不会靠 goroutine 的创建顺序或 `time.Sleep` 猜执行顺序，而是显式建立 happens-before 链：

1. 创建 101 个无缓冲 `chan struct{}`，再创建 100 个 goroutine。
2. goroutine `i` 只做三件事：等前一个令牌、打印 `i`、把令牌交给下一个。
3. 主 goroutine 向第 0 个 channel 发送令牌启动链路，并从第 100 个 channel 接收最终令牌。
4. Go 内存模型规定，channel 的发送与对应接收形成同步关系；无缓冲 channel 又要求发送方和接收方同时就绪。因此“前一个数字已打印 → 发送令牌 → 后一个 goroutine 收到令牌 → 后一个数字打印”形成严格顺序。
5. 最终令牌只有第 100 个 goroutine 完成写入后才会到达主 goroutine，所以函数返回时这 100 个 goroutine 都已经走完自己的工作，不留下正常路径上的悬挂 goroutine。

下面实现选择“每行一个数字”和 `io.Writer` 作为可测试输出接口；这两点是候选 API 选择，不是原题保存下来的要求。

## 3 分钟版

关键不变量是：**任意时刻只有持有当前令牌的 goroutine 有资格写输出；goroutine `i+1` 获得令牌之前，goroutine `i` 的写入已经发生。**

```go
package orderedprint

import (
	"fmt"
	"io"
)

const GoroutineCount = 100

func PrintOneToHundred(w io.Writer) error {
	tokens := make([]chan struct{}, GoroutineCount+1)
	for i := range tokens {
		tokens[i] = make(chan struct{})
	}

	errs := make(chan error, GoroutineCount)

	for i := 1; i <= GoroutineCount; i++ {
		i := i
		go func() {
			<-tokens[i-1]
			_, err := fmt.Fprintln(w, i)
			errs <- err
			tokens[i] <- struct{}{}
		}()
	}

	tokens[0] <- struct{}{}
	<-tokens[GoroutineCount]

	close(errs)
	for err := range errs {
		if err != nil {
			return err
		}
	}
	return nil
}
```

这里不是“channel 天生有序所以输出有序”这么简单。真正的因果链是：

`print(i)` 在 goroutine `i` 内先于 `send(token[i])`；这次 send 与 goroutine `i+1` 的对应 receive 同步；`receive(token[i])` 又先于 `print(i+1)`。把 99 段关系串起来，就得到 `print(1) → print(2) → ... → print(100)`。

`errs` 是容量 100 的独立结果 channel。每个 worker 在交出下一棒之前先把本次写错误放进去，因此不会因为主 goroutine 尚未收集错误而阻塞令牌链。即使某次 `Write` 返回错误，后续 worker 仍继续交棒，避免“错误导致链条半途断掉而永久阻塞”；最后由主 goroutine 汇总并返回第一个错误。

## 关键细节

- **来源边界**：来源明确是 Go 面试上下文、100 个 goroutine、严格按 `1..100` 输出；没有指定同步原语。把 channel 选为方案，而不是把“必须用 channel”伪装成原题事实。
- **输入输出选择**：题目本身没有运行时输入。候选函数接收 `io.Writer` 便于测试，输出选择每个数字一行；面试现场也可以直接换成 `fmt.Println(i)`。
- **100 个 goroutine**：循环固定创建 `GoroutineCount == 100` 个 worker，每个 worker 只打印自己的一个数字。这是满足题意的一种明确实现选择。
- **为什么不依赖调度顺序**：goroutine 何时开始运行不构成业务顺序。真正的顺序由每一步 channel rendezvous 建立。
- **为什么使用无缓冲 channel**：Go 规范规定容量为 0 的 channel 是无缓冲 channel，只有发送方和接收方都就绪时通信才成功；这使令牌交接和同步点非常直观。
- **生命周期**：主 goroutine 等最终令牌；最终令牌只能由第 100 个 worker 在写完后发送。正常返回时所有 worker 都已完成写入、错误上报和交棒。
- **失败边界**：如果传入的 `io.Writer.Write` 自身永久阻塞，当前 worker 无法交棒，整个函数也会等待；若 `Write` 只是返回 error，本实现仍完成令牌链并最终返回 error。
- **不需要 close 令牌 channel**：每条令牌 channel 恰好一次 send、一次 receive，没有 range 接收者，也不靠 close 广播完成信号；额外 close 只增加误用风险。
- **复杂度**：题目固定 100 时资源是固定上界；推广到 `n` 时，时间工作量 `O(n)`，额外 channel/goroutine 状态 `O(n)`。它用并发结构保证顺序，不是为了并行加速。

## 原理机制

把第 `i` 个 worker 写成状态机：

`waiting_i -> writing_i -> reporting_i -> signaling_i -> done_i`

只有 `receive(token[i-1])` 能把它从 `waiting_i` 推进到 `writing_i`。第 `i-1` 个 worker 只有完成自己的写入和错误上报后，才执行 `send(token[i-1])`。因此对相邻两个 worker：

`write(i-1) -> send(token[i-1]) -> receive(token[i-1]) -> write(i)`

Go Memory Model 对 channel 通信给出同步保证；Go 语言规范对无缓冲 channel 给出发送/接收双方同时就绪的通信语义。这里没有多个 worker 并发写同一个 `io.Writer`：令牌保证写入阶段互斥，所以测试使用普通 `bytes.Buffer` 也不会产生并发写数据竞争。

替代方案可以用 `sync.Mutex` + 条件变量/显式 turn 变量，但需要自己维护“轮到谁”的共享状态与唤醒条件；`sync.WaitGroup` 单独只能等待全部完成，不能建立 `1..100` 的执行次序。单 goroutine `for 1..100` 最简单，却没有让题目要求的 100 个 goroutine 参与。

## 项目经验版

原始材料没有保存真实项目场景，因此不虚构线上经历。落到工程代码时，我会把验证重点放在三个可复现条件：重复运行输出始终严格相同；`go test -race` 无数据竞争；函数有清晰的完成点，正常返回时不遗留 worker。若真实场景还要求取消、超时或 writer 可能长期阻塞，则需要把 `context.Context` 和退出协议加入契约，而不能假装当前面试题已经包含这些要求。

## 常见追问

- 问：为什么直接 `for i := 1; i <= 100; i++ { go fmt.Println(i) }` 不行？答：启动顺序不是执行顺序，调度器可以让后创建的 goroutine 先运行；没有同步关系就不能证明输出顺序。
- 问：`WaitGroup` 能不能解决？答：`WaitGroup` 能证明“全部完成”，但不能规定“谁先打印”。要保持 1 到 100 的严格次序，还需要 channel、条件变量或等价的 turn 同步。
- 问：为什么不用 `time.Sleep` 让第 `i` 个 goroutine 睡 `i` 毫秒？答：sleep 只是时间假设，不是同步协议；机器负载、调度、GC 等都可能破坏这种时序，不能形成正确性证明。
- 问：会不会有 goroutine 泄漏？答：正常 writer 能返回时不会。令牌从 0 一直走到 100，主 goroutine 等到最后一个 worker 交棒才返回；但如果 writer 永久阻塞，当前实现也会被卡住，所以“可阻塞 writer”属于需要额外取消协议的新边界。
- 问：为什么 100 个 goroutine 不能共用一个“开始” channel？答：一个共享信号如果有多个竞争接收者，只能决定“某个 goroutine 被唤醒”，不能自然保证编号 `i` 的 worker 必然在 `i-1` 之后获得执行权。这里每一棒都有独立的前驱/后继关系，证明更直接。
- 问：如果题目改成无限循环 `1..100` 反复打印呢？答：状态机就要变成环而不是一次性链，并且必须额外设计停止条件；当前一次性令牌链不能直接宣称满足无限循环需求。

## 易错点

- 把 goroutine 的创建顺序当成调度顺序。
- 用 `time.Sleep` 代替同步原语。
- 只用 `WaitGroup` 等结束，却没有控制每个数字的打印先后。
- 多个 goroutine 同时写普通 `bytes.Buffer` 或其他非并发安全 writer，再用“最后内容看起来对”掩盖数据竞争。
- 某个 worker 出错后直接 return、不再交棒，导致后继 99 个 goroutine 和主 goroutine永久阻塞。
- 把“每行输出”“必须 channel”“每个 goroutine 恰好打印一次”等候选设计选择说成原题明确约束。
