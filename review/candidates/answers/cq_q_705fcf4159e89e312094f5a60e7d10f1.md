# `useFetch`：当 `params` 变化时自动重新请求

## 核心结论

把“发请求”放在 `useEffect` 里，并让 Effect 的依赖包含 `params`。React 会用 `Object.is` 比较依赖项；当调用方传入了新的 `params` 引用时，旧 Effect 先 cleanup，再用新参数执行新的 Effect，因此可以自动重新请求。原题没有保存 `useFetch` 的既有函数签名、`params` 的深比较规则或请求库，这里声明一个最小答案侧契约：`request(params, { signal }) => Promise<data>` 是稳定函数引用，调用方把参数当不可变值使用，语义变化时传入新对象。

仅写 `[params]` 还不够完整：参数快速变化时，旧请求可能比新请求更晚返回，导致旧结果覆盖新结果。因此 cleanup 同时取消旧请求，并用 `active` 标记阻止已经失效的 Promise 更新状态。

## 1 分钟版

- `useEffect` 负责同步网络请求这个外部系统，依赖写成 `[request, params]`。
- 首次挂载执行一次；只要 `params` 引用发生变化，React 会先执行上一次 cleanup，再重新执行 Effect。
- cleanup 里 `AbortController.abort()`，并把 `active=false`，避免旧请求晚到覆盖新参数的结果。
- `params` 是对象时要明确“变化”的语义：React 依赖比较是 `Object.is`，不是深比较。原地修改同一个对象不会触发；每次 render 都创建全新但等值对象，又会导致重复请求。
- 如果业务需要按“参数值”而不是对象 identity 判断变化，应稳定 `params` 的引用、依赖具体 primitive 字段，或构造有明确规范的 request key；不要把不受约束的 `JSON.stringify(params)` 当成通用深比较。

## 3 分钟版

```javascript
import { useEffect, useState } from 'react';

export function useFetch(request, params) {
  const [state, setState] = useState({
    data: null,
    error: null,
    loading: false,
  });

  useEffect(() => {
    const controller = new AbortController();
    let active = true;

    setState(prev => ({ ...prev, error: null, loading: true }));

    request(params, { signal: controller.signal })
      .then(data => {
        if (!active) return;
        setState({ data, error: null, loading: false });
      })
      .catch(error => {
        if (!active) return;
        if (error?.name === 'AbortError') return;
        setState({ data: null, error, loading: false });
      });

    return () => {
      active = false;
      controller.abort();
    };
  }, [request, params]);

  return state;
}
```

面试中最重要的是把依赖语义说清楚：如果 `params1` 和 `params2` 内容一样但不是同一个对象，`Object.is(params1, params2)` 为 `false`，Effect 会重跑；如果直接修改 `params1.page` 后仍传回同一个 `params1`，依赖比较看不到变化，Effect 不会因为这次原地修改而重跑。

## 关键细节

- **依赖必须覆盖 Effect 内的响应式值**：示例里 Effect 读取了 `request` 和 `params`，所以两者都进入依赖数组。若 `request` 是组件内每次 render 新建的函数，它也会造成重复请求；应把它定义为稳定导入，或由调用方 `useCallback` 稳定。
- **对象 identity 不是深比较**：React 对依赖逐项使用 `Object.is`。因此“params 变化”必须先定义为“新引用”还是“字段值变化”。本答案明确采用不可变更新 + 新引用契约。
- **竞态**：A 参数请求先发，随后 B 参数请求发出；如果 A 最后返回而没有失效保护，就可能把 B 的正确结果覆盖掉。cleanup 的 abort + `active` 双保险让旧 Effect 失去写状态资格。
- **AbortError**：取消旧请求通常不应展示成业务错误；示例直接忽略取消错误。实际请求库若不是原生 fetch，需要按其取消 API 适配。
- **loading 语义**：每次新参数触发请求时设为 `true`，成功或非取消失败后设回 `false`。是否保留旧 data 属于产品体验策略，原题没有规定；示例在请求中保留旧 data，失败时清空。
- **Strict Mode**：开发环境可能额外执行一次 setup → cleanup → setup。正确 cleanup 后不应依赖“Effect 只运行一次”的假设。

## 原理机制

`useEffect` 可以看成一次“以依赖快照为版本”的外部同步过程。某次 render 提交后，React 记录这一轮 `[request, params]`；下一次提交时逐项用 `Object.is` 与旧依赖比较。只要其中一项不同，React 先执行旧版本 cleanup，再启动新版本 setup。

对网络请求而言，cleanup 不只是释放资源，也是在建立版本边界：旧版本对应旧 `params`，一旦新版本开始，旧版本就不能再写当前 UI 状态。`AbortController` 尝试终止底层请求，`active` 则保证即使底层请求无法真正取消、或者 Promise 已经接近完成，旧回调也不会更新状态。

## 常见追问

- 问：为什么 `params` 放进依赖数组就能自动请求？答：Effect 首次运行后，React 会在后续提交中用 `Object.is` 比较依赖；`params` 引用变了就先 cleanup 旧 Effect，再执行新 Effect。
- 问：`params` 每次 render 都是 `{ page: 1 }` 怎么办？答：虽然值相同，但对象引用每次都不同，会重复触发。应在调用方稳定对象、依赖真正影响请求的 primitive 字段，或建立规范化 request key。
- 问：直接修改 `params.page++` 呢？答：如果仍传同一个对象引用，React 的依赖比较可能看不到这次变化；推荐不可变更新，生成新的 params 对象。
- 问：为什么既 abort 又要 `active`？答：abort 负责尽量取消 I/O，但不是所有 request 实现都支持取消；`active` 是状态写入的最终防线，保证旧请求不能覆盖新请求结果。
- 问：只写 `[params]` 可以吗？答：如果 Effect 内还读取了响应式的 `request`，完整依赖应该包含它；否则可能捕获旧函数。若 `request` 是模块级稳定函数，可通过结构证明它不是响应式依赖。
- 问：能不能 `[JSON.stringify(params)]`？答：只适合你明确限定为 JSON-safe、序列化顺序稳定且成本可接受的数据域；作为通用方案会遇到序列化语义、键顺序、特殊值和性能边界，不能默认成立。

## 易错点

- 把 React 依赖比较误说成深比较。
- 原地修改 `params`，却期待 Effect 自动感知内部字段变化。
- 每次 render 创建全新 `params` 或 `request`，造成无意义的重复请求甚至循环。
- 参数快速变化时没有 cleanup / stale-response 保护，让旧响应覆盖新响应。
- 把取消请求当成业务失败展示给用户。
- 为了“深比较”直接无条件 `JSON.stringify(params)`，却没有定义支持的数据域和成本。
