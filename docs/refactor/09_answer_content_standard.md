# 09 分题型答案内容标准

> 本文定义 Answer 的内容质量标准。`answer validate --strict` 是结构底线，本文是人工与 Agent 审查 ready 内容的语义标准。

---

## 1. 通用口述结构

所有答案继续保留八个二级章节：

```text
核心结论
1 分钟版
3 分钟版
关键细节
原理机制
项目经验版
常见追问
易错点
```

通用要求：

- 核心结论在 20–30 秒内说明本质。
- 1 分钟版只保留 3–5 个主干点。
- 3 分钟版补齐原理、取舍、场景和边界，不重复 1 分钟版。
- 关键细节写事实和阈值；原理机制写因果链路。
- 项目经验版只使用真实经历，未获得用户事实时改写成“项目映射提示”。
- 常见追问至少 3 个，每个追问必须带 1–3 句短答。
- 易错点必须能指出“哪里容易说反、说绝对或漏掉边界”。
- 版本敏感内容写明适用版本或核对日期。

---

## 2. Concept：概念与对比题

适用：定义、区别、优缺点、选型类问题。

答案必须包含：

1. 一句话定义比较对象。
2. 统一比较维度，而不是分别背两段定义。
3. 选择条件和不适用边界。
4. 至少一个反例或容易混淆点。
5. 追问短答覆盖底层原理、选型和实际使用。

推荐 1 分钟骨架：

```text
结论 -> 维度一 -> 维度二 -> 选择条件 -> 边界
```

---

## 3. Mechanism：原理与源码题

适用：底层实现、执行流程、源码、协议机制类问题。

答案必须包含：

1. 核心数据结构或参与组件。
2. 从入口到结果的主流程。
3. 关键状态变化和并发/一致性保证。
4. 时间、空间或资源开销。
5. 关键版本差异，避免把旧版本结论当成通用事实。
6. 故障或性能边界。

推荐 3 分钟骨架：

```text
目标 -> 数据结构 -> 主流程 -> 保证机制 -> 开销 -> 版本与边界
```

---

## 4. Scenario：场景与系统设计题

适用：高并发、系统设计、导入、缓存一致性、排障方案类问题。

答案必须包含：

1. 需求假设：用户量、QPS、数据量、一致性和延迟目标。
2. 核心数据流，而不是只罗列组件。
3. 数据模型、幂等和一致性方案。
4. 容量评估与关键瓶颈。
5. 超时、重试、降级、补偿和灾备。
6. 可观测指标、压测和上线策略。
7. 至少一个替代方案及其代价。

推荐 3 分钟骨架：

```text
澄清目标 -> 估算容量 -> 画主链路 -> 保证一致性 -> 处理故障 -> 观测与取舍
```

---

## 5. Coding：算法与手撕题

适用：数据结构、算法、SQL 手写和编码题。

答案必须包含：

1. 输入输出和约束。
2. 解题不变量或状态定义。
3. 可直接复述的步骤。
4. Java 实现；SQL 题提供可运行 SQL。
5. 时间与空间复杂度。
6. 空输入、单元素、重复值、溢出等边界用例。
7. 至少一个变体及处理差异。

禁止只写伪代码后把答案标为 ready。

---

## 6. Project：项目深挖题

适用：项目介绍、技术难点、架构选型、事故排查、性能优化。

答案是表达框架，不是虚构故事。必须引导用户补齐：

```text
真实背景与规模
个人职责
约束与目标
备选方案
个人决策与理由
实施过程
量化结果
风险、失败或复盘
```

如果缺少真实项目事实，答案保持“项目映射提示”，不得使用“我负责”“我优化到”等确定口吻。

---

## 7. Behavior：行为与 HR 题

适用：冲突、挑战、规划、优缺点、公司选择和团队协作。

答案必须：

- 使用真实 STAR 证据。
- 强调个人动作，而不是只说团队做了什么。
- 结果尽量量化。
- 给出反思和下一次改进。
- 与岗位要求相关，但不编造公司偏好或个人经历。

未获得用户事实时，只提供提问清单和组织框架，不生成 ready 的个人故事。

---

## 8. Ready 人工审查清单

### 事实

- [ ] 核心结论正确。
- [ ] 版本和阈值没有过期或绝对化。
- [ ] 没有把常见实践写成唯一方案。
- [ ] 没有虚构个人经历、指标或事故。

### 表达

- [ ] 1 分钟版能实际口述完。
- [ ] 3 分钟版比 1 分钟版增加原理和取舍。
- [ ] 每个列表项都能解释 why。
- [ ] 不使用空泛的“提升性能、保证高可用”而没有机制。

### 追问

- [ ] 至少 3 个追问。
- [ ] 每个追问有短答。
- [ ] 至少一个追问检查边界或失败场景。
- [ ] 追问若已成为独立大问题，改建 Canonical 而不是塞进当前答案。

### 复习

- [ ] 易错点可用于下一次回炉。
- [ ] 原题变体都能由当前答案覆盖。
- [ ] `answer validate --strict --noWrite` 通过。
- [ ] `answer sync` 后 Canonical 状态一致。

---

## 9. Curated-Ready 评分与晋级

`answer validate --strict` 仍只是结构底线。答案只有同时满足以下条件，才能标记为 `status=ready`、`quality_tier=curated`：

| 维度 | 分值 | 最低分 |
|---|---:|---:|
| 事实与证据 | 25 | 23 |
| 直接性与相关性 | 20 | 18 |
| 题型专项完整性 | 20 | 16 |
| 原理与因果链 | 15 | 12 |
| 边界与取舍 | 10 | 8 |
| 追问质量 | 5 | 4 |
| 口述质量 | 5 | 4 |

总分必须不低于 90，并且没有任何硬失败。完整机器规则以 `config/answer_quality.json` 为准。

### 9.1 硬失败

以下问题一票否决，不允许用其他维度高分抵消：

- 题型错误、答非所问、跨主题知识污染或只讲“应该怎么答”而没有实际答案。
- 关键事实没有可接受依据、与依据冲突，或把版本/配置敏感结论写成通用事实。
- 项目与行为题虚构个人职责、生产事故、指标、公司情况或用户经历。
- 追问是全库通用面试建议，没有针对当前题目的底层、选型、边界或失败问题。
- Coding/SQL 使用占位骨架、未定义函数、通用表名，或不能编译、解析和通过边界测试。
- 没有覆盖 Canonical 下任一来源问法，缺少 evidence sidecar，或没有隔离的独立审查结论。

### 9.2 证据规则

- 版本行为、默认配置、数值阈值、协议语义、API 契约和废弃信息必须使用第一手来源：标准/规范、官方文档、上游源码/发布说明或原始论文。
- 稳定算法和可执行机制可用代码测试、最小实验或可复现推导作为证据。
- 搜索摘要、无来源博客、论坛/社交内容和旧长尾答案只能用于发现线索，不能独立支撑关键结论。
- 每份答案使用 `review/evidence/{canonical_id}.json` 记录 claim 到来源的映射和 `checked_at`；无法核验时保持 `needs_update`。

### 9.3 独立审查与批次规则

- 编写者和审查者必须处于隔离轮次。审查者只读取 Canonical、来源问法、候选答案、证据和本标准，不读取编写者自评分或预期结论。
- 每份候选最多修改两轮；仍有硬失败或低于门槛时保持 `needs_update`。
- 每批最多 10 题。首个六类型 60 题试点进行 100% 人工抽查；稳定后每批至少抽查 20%。发现任一硬失败，整批回退并执行 100% 复核。
